# Agents overwrite Markdown state files but leave JSON alone — use JSON for machine-maintained progress state

From Anthropic's work on harnesses for long-running agents: when a scaffold file holds a feature list or progress state that the agent must update incrementally across sessions, use JSON rather than Markdown. Their stated reason is that the model is less likely to inappropriately change or overwrite a JSON file than a Markdown one.

The plausible mechanism is that Markdown reads to the model as prose it is licensed to rewrite, while JSON reads as a data structure to be edited surgically — but the useful part is the observed behaviour, not the explanation. The failure it prevents is the one where an agent asked to tick off one completed feature rewrites the whole plan and quietly drops the remaining items, which is only discovered sessions later.

This does NOT mean human-facing instruction files should become JSON. CLAUDE.md-style guidance the agent reads but should not rewrite is fine as Markdown. The rule applies specifically to files the agent is expected to WRITE BACK to across sessions.

NOR DOES IT CONFLICT WITH THE SEPARATE FINDING THAT JSON IS AN EXPENSIVE FORMAT FOR A MODEL TO EMIT. Those two claims look opposed and are not, because they concern different things:
  - JSON as a container for STRUCTURED STATE the agent edits field-wise — a feature list, a progress log, a status map. Cheap, and the structure is exactly what discourages wholesale rewriting. That is this fact.
  - JSON as a wrapper around FREE-FORM TEXT OR CODE the agent must generate — which forces escaping of newlines and quotes throughout and spends attention on bookkeeping instead of the task. Expensive, and to be avoided.
The discriminator is whether the model is filling in fields or serialising a body of text. Small scalar fields inside JSON are fine; a code blob inside a JSON string is not. So a progress file with `{"feature": "auth", "status": "done"}` is the good case, and a tool that takes `{"file": "...", "contents": "<200 lines of escaped source>"}` is the bad one, even though both are JSON.

The surrounding pattern this belongs to: an initializer session that creates the environment setup script, the progress log, and an initial commit; then subsequent sessions each work on exactly one feature and leave the environment clean. The failure being engineered against is the agent trying to one-shot the whole app, which produces both premature 'done' claims and running out of context mid-implementation, leaving the next session to start from a half-built feature it must reverse-engineer.
