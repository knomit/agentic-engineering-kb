# Six pieces of standard coding-agent advice that the vendor's own best-practices page now retires, each with the model-generation change that made it obsolete — and the retirements are scoped to interactive sessions on large-window models, not to architecture

Claude Code's best-practices page carries a "What you can stop doing" section that names previously-standard practices together with the reason each stopped paying. Six of them, with the stated reason for each:

- "The context window is your main constraint, manage it aggressively" — because "Most current models have a 1M-token window and compaction happens on its own, so running out is rare."
- "Add IMPORTANT or ALL CAPS to instructions Claude keeps missing" — because "Current ones follow a plainly worded line, and piling on emphasis mostly makes Claude over-apply the rule." Note the direction: the failure mode of emphasis is now OVER-application, which is the opposite of the under-compliance the practice was defending against.
- "Use subagents to protect your context window" — because "Running out of context is rarely the problem anymore."
- "Delegate to a subagent for a better answer" — because "Handing the same task to a subagent doesn't make the answer any better."
- "`think hard`, `think harder`, `be thorough` in the prompt" — because "Those phrases are ordinary prompt text that nudges Claude within its effort setting rather than keywords that raise it." They are not a dial that raises a budget; the effort setting is.
- "Tell Claude to keep going, loop until done, don't be lazy" — because "Current models usually carry on through an agreed task without being told" and "lines like that are more likely to cause over-work than fix a stall."

THE SCOPE IS THE PART A SUMMARY DROPS, AND IT IS WHAT MAKES THE LIST SAFE TO ACT ON. Every reason is a claim about current models in an INTERACTIVE CODING SESSION with a very large window and automatic compaction. None of them asserts that context budgeting, context isolation or prompting discipline has stopped mattering in general. A fixed-window API integration, a fan-out whose workers each pay for their own prefix, or a pipeline that must keep tool intermediates out of a window has none of those three properties, so the reason does not reach it. Read each row as "the workaround outlived the defect it was written for", and check that your deployment actually has the properties the reason depends on before dropping the practice.

ONE ROW NEEDS A FURTHER BOUNDARY. "Running out of context is rarely the problem anymore" removes one motive for subagent isolation and leaves the others standing: a separate reading of the same vendor's workflow documentation names self-preferential bias, goal drift and agentic laziness as distinct motives for putting work in a fresh context, only one of which is about size. An independent verifier that never saw the conversation is therefore still justified on grounds the window has nothing to do with, and this list does not retire it.

The page carries a seventh row, "Describe your architecture and file layout in `CLAUDE.md`", whose stated reason was not read and is not recorded here.
