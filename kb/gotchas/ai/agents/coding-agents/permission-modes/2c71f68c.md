# Auto mode's repeated-block circuit breaker exists only in the interactive session: it pauses after three blocks in a row OR twenty in total, and a scripted run in the same permission mode does not pause that way

In an interactive terminal session, "After three blocks in a row (or twenty in total), auto mode pauses and goes back to asking you." Both thresholds live in that one sentence and both count: three CONSECUTIVE blocks, or twenty blocks in TOTAL, whichever is reached first. Below either threshold a block is not silent — "When it does block something, you get a notification and the action shows up under **Recently denied** in `/permissions`, where you can retry it with a manual approval." What the threshold produces is a pause and a return to asking, not a terminated run.

THE SAME PERMISSION MODE IN A SCRIPTED RUN DOES NOT BEHAVE THIS WAY. For `-p` runs started with `--permission-mode auto`, "repeated blocks don't pause the run the way they do in a terminal", and the page defers the actual behaviour to a separate document, telling you to read "how the thresholds apply there" "before you rely on it."

The operational consequence is that the pause is the mechanism that converts a prompt-injection attempt, a mis-scoped task or a drifting agent into a human decision — and the unattended path is both where no human is present and where that mechanism is absent. So do not reason about a scheduled, CI-driven or headless run's blast radius from the interactive thresholds, and do not treat "it will stop and ask after a few denials" as a property of auto mode itself. An unattended run needs its bound elsewhere: in what the credential can do, in deny rules, or in the sandbox, rather than in an expectation that accumulated refusals will halt it.

What this does NOT mean: the numbers are not a security boundary even interactively. Three-in-a-row counts consecutive blocks, so an allowed action interleaved between blocks resets that counter, and only the twenty-in-total figure is monotonic.
