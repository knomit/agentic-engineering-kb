# A reviewer agent asked to find gaps will find them, sound work or not

Reviewing in a fresh context is genuinely valuable: a subagent that sees only the diff and the criteria, not the reasoning that produced the change, evaluates the result on its own terms and is not biased toward code it just wrote. Use it before treating unattended work as done.

The failure mode to guard against is what the review then does to the code. A reviewer prompted to find gaps will usually report some even when the work is sound, because that is the task it was given. Chasing every finding produces over-engineering: extra abstraction layers, defensive code, and tests for cases that cannot occur. The output looks like diligence and is actually damage.

The fix is in the reviewer's prompt: instruct it to flag only gaps affecting correctness or the stated requirements, name what the work is being checked AGAINST (the plan, the spec, the listed edge cases), and treat everything else as optional. "Report gaps, not style preferences" is the operative constraint.

The general lesson beyond code review: any evaluator agent whose instruction is to produce findings has a non-zero base rate of findings on perfect input. Calibrate by running it against known-good work and seeing what it invents — that is your false-positive floor, and it is not zero.

Two additions about running this in practice. Claude Code ships a bundled `/code-review` skill that reviews the current diff for bugs in a fresh subagent and returns the findings into the implementing session, so the session fixes and re-reviews without anyone copying findings between windows — which removes the handoff cost and also removes the human who used to filter what reached the code.

And the calibration step above has a published production form. The Claude Code team runs its PR reviewer on PRs known to be clean and counts how often it suggests a HARMFUL change. That is a stricter instrument than a false-positive rate, because it catches the specific failure a precision number misses: a reviewer that invents a plausible problem and proposes a fix that breaks working code. The same team classifies every posted comment by how the author disposed of it — fixed, wrong, intentional, or didn't matter — which separates a false positive ("wrong") from a correctly-identified irrelevance ("didn't matter"); a single false-positive rate conflates the two and points at the wrong remedy.
