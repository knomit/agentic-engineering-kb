# A protected-file denylist compared by string equality BEFORE the OS normalizes the name is not a denylist — `.mcp.json.` passed Visual Studio Copilot's check and the write landed on `.mcp.json` (CVE-2026-103572)

Visual Studio Copilot guards its own configuration by comparing the requested filename against protected names such as `.mcp.json` and `settings.json`. The check "is implemented in `EditsFunctionHandler.GetEditConfirmationTypeAsync`". A name with a trailing dot — `.mcp.json.` — is a different string, so it passes the comparison, and then "the Win32 layer just ignores the dot at the end", so the write lands on the protected file. Writing `.mcp.json` is arbitrary command execution: the published proof of concept added a malicious MCP server and launched calc.exe; changing the `ripgrep` path in Visual Studio settings is a second route to the same end. Microsoft rated it Important remote code execution, "(CVSS Score 8.8.)". Because the flaw was in the shared `Microsoft.VisualStudio.Copilot.Core.dll`, it reached both Visual Studio Copilot and SQL Server Management Studio, older versions including Visual Studio 2022 among them. The trigger is a misaligned or hijacked agent, and a third party can reach it through indirect prompt injection — for example content returned by an MCP server. On the fix the author reports "it seems a call to `GetFullPath` was added, which removes the dot and normalizes the filename"; that is his reading of the patch, not a Microsoft statement.

THE RULE: RESOLVE THE PATH TO ITS CANONICAL OS FORM FIRST, THEN COMPARE. A guard that compares the string the caller supplied is guarding a NAME, and every normalization the platform performs after the comparison is a bypass: trailing dots and spaces, 8.3 short names, case folding, `..` segments, alternate data streams, Unicode equivalence. The ordering is the defect; the specific trailing dot is one instance of it.

What this does NOT mean: a longer denylist does not fix it. Adding `.mcp.json.` to the protected list leaves `.mcp.json..`, and so on for every other normalization the platform applies — the list is not the broken part. A protected-name list is still needed; it has to be evaluated against the resolved path.

One further asymmetry in the same component: a path-traversal variant let the agent READ the user's settings file "without the expected confirmation", and one SSMS chain needed the local installation ID, which can be read from `SSMS.isolation.ini` by a traversal variant. So a corrected write guard does not imply a corrected read guard, and the confirmation prompt and the path check are two controls that have to be checked separately.
