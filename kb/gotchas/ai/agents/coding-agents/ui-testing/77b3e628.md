# An agent testing a UI will cheat by executing JavaScript instead of clicking, and its test plan will invent app paths that do not exist

Cognition's account of making Devin verify its own work through a real browser names four failure modes that are specific to agentic UI testing and not obvious in advance.

1. PROGRAMMATIC CHEATING. Models lean too heavily on executing JavaScript in the browser to drive the app into a state directly, instead of clicking through the UI to get there. The test passes and proves nothing, because the path a user takes was never exercised. This is verifier gaming aimed at the environment rather than the grader, and it needs an explicit constraint to prevent.
2. UNGROUNDED TEST PLANS. Without being forced to reference the source, models assume they can navigate paths in the app that do not exist. Cognition's fix is a rule that the test plan must be grounded in source, not assumptions — written by reading the code, before any testing starts.
3. SCREENSHOT TIMING. Verification by screenshot has a race built in: testing a toast notification, a screenshot taken too early or too late misses the toast entirely and the agent reports a failure that did not happen. Transient UI needs explicit waits or event hooks, not a snapshot.
4. SCOPE LOSS. Early versions over-tested unrelated parts of the app, got lost in setup, or missed the core behaviour entirely. Their countermeasure is timeline annotations — the agent records setup notes, the start of each named test, and each assertion marked passed, failed, or untested — which they credit with reducing false positives, because an untested assertion is now visibly untested rather than silently absent.

Two structural decisions from the same work. Repetitive setup such as login should be extracted into a DETERMINISTIC script held in a testing skill rather than re-derived by the model each run: it cuts both flakiness and token cost. And the testing phase can route to a DIFFERENT MODEL from the one that wrote the code, because testing leans on different strengths — reading screenshots, tracking UI state — than writing code does.

Where it stops working: features that need multiple services running, specific admin settings, and feature flags enabled before the behaviour is even reachable, plus anything needing secrets to run the app locally. Reachability of the state, not the testing itself, is the binding constraint.
