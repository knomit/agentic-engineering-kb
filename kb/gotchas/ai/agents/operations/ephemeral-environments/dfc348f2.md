# A reclaimed agent VM comes back with the conversation and the cached files but not the processes — start services per session, because the gap presents as a connection error with nothing in the history to explain it

On a hosted agent environment, resumption is partial in a specific way. Idle VMs get reclaimed; reopening the session gives a fresh VM with the conversation restored, and the environment cache restores files — but processes that were running do not survive it. So a database or other service the agent started earlier in the session is simply absent, while the transcript still shows it being started and used.

That asymmetry is what makes it expensive. The agent reads its own history as evidence that the service is up, so the symptom reaching it is a connection error with no preceding change to explain it, and it will often start debugging the application rather than the environment. Two things prevent it: start services at the beginning of each session, or in a SessionStart hook, rather than once at setup time; and commit work as you go, since files are the part at risk when the VM is reclaimed.

Two related caches behave the same way and are worth knowing when timing a change: the environment cache rebuilds when the setup script or the allowed hosts change, and about every seven days; and network-access changes reach already-running sessions within about a minute.

What this does NOT mean: restored conversation state is not corrupted or untrustworthy in general. It is accurate about what happened; it is simply not evidence about what is currently running, and an agent has no other signal to distinguish the two.
