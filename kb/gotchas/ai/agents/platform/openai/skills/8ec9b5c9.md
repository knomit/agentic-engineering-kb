# Attaching a skill is three incompatible mechanisms on three OpenAI surfaces, and a just-uploaded version can 404 — retrieve the version before you attach it

OpenAI's skills guide gives three attachment mechanisms, and the format does not carry across them:

- **Hosted shell:** `tools[].environment.skills`, using `skill_reference` entries with `skill_id` and an optional `version`.
- **Local shell:** skills work, but `skill_reference` is not supported — supply the files from local paths with `name`, `description` and `path`.
- **Agents API:** `skill_reference` is not used at all. Skill directories go in the sandbox, and their parent directories are registered in `environment.capability_directories` at session creation.

Capability directories carry constraints that must all hold together: paths must be absolute, inside the sandbox, unique, free of `.` and `..` segments, and already existing, and "A session can register up to 32 capability directories." They are registered at session creation, so a directory created later in the session is not a skill source for that session.

THE ORDERING CONSTRAINT, which is what bites in CI: a newly uploaded version can return `404` briefly. The guide's instruction is to retrieve it with `GET /v1/skills/{skill_id}/versions/{version}` before attaching it to a container or Live session, retrying with backoff and a timeout, and then to use the returned version string in the skill reference. A pipeline that uploads a version and attaches it on the next call is racing a read-after-write window and will present as a flaky 404.

Stated limits: "Maximum zip upload size is 50 MB.", "Maximum file count per skill version is 500.", "Maximum uncompressed file size is 25 MB." A zip upload must contain exactly one top-level folder; a directory upload uses multipart `files[]` parts with every path inside a single top-level folder; and only one `SKILL.md` is allowed per bundle, matched case-insensitively.

Version management has one asymmetry to know before writing cleanup code: `default_version` applies when no version is given and `latest_version` tracks the newest upload, but "You can't delete the default version." Deleting the last version deletes the skill, and deleting a skill removes all of its versions.

Operational consequence: the bundle is portable across these surfaces but the attachment code is not, so the surface is a deployment-time decision rather than a configuration flag. Build the retrieve-before-attach step into the upload path instead of discovering it as an intermittent failure.
