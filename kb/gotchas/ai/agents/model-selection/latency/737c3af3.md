# The speed ranking between a vendor's small and large models inverts between serving modes — the fastest model at standard speed ran less quickly than the larger ones in Fast Mode

Anthropic's Claude Haiku 5.5 launch page (2026-10-07) presents the model as its fastest at standard speed and then states "although it runs less quickly than our Opus models in Fast Mode". Two consequences for anyone picking a model against a latency budget.

First, "which model is fastest" has no answer independent of the serving mode. A small-model-for-latency decision taken from a standard-speed benchmark can be wrong for a deployment that uses a fast serving tier, and the inversion is between SIZE CLASSES — the large model wins — so it is not the direction a size-based prior predicts. Measure latency in the mode you will actually run, on your own trajectory, and re-measure if the serving mode changes.

Second, the throughput knob and the capability knob are now separate on this class of model: "Haiku 5.5 is our first Haiku-class model to come with an adjustable effort setting", so cost-versus-capability can be traded per call rather than per model choice. That makes a routing design that assumes one fixed operating point per model stale: the same model identifier spans a range, and an effort setting chosen for cost moves latency too.

Scope: this is one vendor's statement about one pair of model families at one date, taken from a launch page with no methodology, so it is evidence that the ranking CAN invert across serving modes, not a measurement of by how much or a claim that it holds for other vendors or later versions. Customer latency claims on the same page likewise carry no stated methodology.
