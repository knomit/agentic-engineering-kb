# A three-clause trigger meant to fire selectively — edited files, ran commands, or made 8+ tool calls — fired on 99 of 111 turns, and each firing re-read the conversation at roughly 5–6k input-equivalent tokens

A harness extension that reacts to turn-level events needs a trigger, and a disjunction of ordinary agent behaviours is not a filter. One published account of Claude Code's built-in Next Steps Supervisor mod states its trigger as "This mod only runs after a turn that edited files, ran commands or made 8 or more tool calls." Measured against the author's own usage: "99 of my 111 turns in Claude Code met that bar".

THE COST IS PER FIRING, NOT PER SESSION. The supervisor forks and re-reads the conversation on each check; the ModSmith README "estimates about 5–6k input-equivalent tokens per check on a 50k-token session". That figure scales with the conversation, so the cheap-looking check gets more expensive exactly as the session gets long — and it rises again when the prompt cache expires.

TWO CONSEQUENCES FOR DESIGN. First, price a turn-event trigger by multiplying its per-check cost by the fraction of turns that actually match, measured on a real transcript, not by the fraction you intended. Second, an always-firing advisory surface stops being read: the author notes that because it fires on nearly every turn, users may start ignoring it, which is the failure mode where the extension still costs tokens and no longer changes behaviour.

WHAT THIS DOES NOT MEAN. The defect is not the three conditions individually — each one describes a turn where a reviewer plausibly adds value. It is that they are OR-ed, and in agentic coding work almost every turn satisfies at least one. A compound trigger reads as narrow and behaves as wide; the only way to know which is to count matches on a transcript you already have.

Pack analysis: this generalises past advisory mods to any supervisor, judge or reflection stage attached to a turn boundary, which is the same economics as an LLM-judge per action.
