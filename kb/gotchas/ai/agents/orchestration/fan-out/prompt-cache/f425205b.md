# Sibling agents in one fan-out share a prompt cache only when six attributes match, so the runtime deliberately holds all but the first for up to 5 seconds — and their cache expires in five minutes, not an hour

Agents in one Claude Code dynamic-workflow run can read each other's prompt cache, and the matching condition is a six-part conjunction: two agents share a prefix when their model, effort level, agent type, tools, output schema AND working directory are the same, because that is what builds the same tools-and-system-prompt prefix. An agent that starts after a matching sibling's response has begun reads that sibling's cache on its first request.

The runtime makes that happen by DELAYING agents on purpose. When a fan-out starts several matching agents at once, Claude Code holds all but the first until the first agent's response begins, then releases the held agents together so their first requests read the shared prefix instead of each processing it uncached. The hold is capped at `CLAUDE_CODE_WORKFLOW_PREFIX_STAGGER_MS`, 5000 milliseconds by default, and setting it to `0` disables the hold. So a fan-out's time to first result includes up to five seconds of deliberate stall; on a wide fan-out that buys N-1 uncached prefix reads, and on a two- or three-item fan-out it can cost more than it saves — which is what the knob is for.

The lifetime is the part most likely to surprise someone reasoning from the main conversation's behaviour: "A workflow agent's requests fall outside the main conversation's cache TTL bucket, so its cache holds for five minutes by default, including on a Claude subscription." Setting `subagentPromptCacheTtl` to `1h` extends it, and the API bills 1-hour cache writes at a higher rate. Five minutes is therefore the window inside which the sharing has to happen.

That window interacts with the concurrency cap, and the two together decide whether a long fan-out shares anything at all. The runtime runs up to 16 concurrent agents by default — fewer when Claude Code has fewer CPUs available, including inside a CPU-limited container — and the limit is settable from 1 to 256 with `CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS` (requires Claude Code v2.1.269 or later). A 500-item pipeline therefore runs in waves, and a wave that begins more than five minutes after the first agent's response finds the shared prefix expired and pays a fresh cache write, unless the TTL was raised.

Pack analysis, following from the six-attribute list rather than stated in the source: passing a `schema` to some agents of a fan-out and not others splits them into two prefixes, as does giving one stage a different tool set or a different effort level. If a fan-out is meant to share a prefix, those four script-level choices — model, effort, tools, schema — have to be uniform across its agents, and "they are all the same agent type" is not sufficient.
