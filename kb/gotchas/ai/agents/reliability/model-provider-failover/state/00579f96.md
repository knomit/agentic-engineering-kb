# Switching model providers carries no session state — an agent mid-task does not resume, and any tool action it may already have taken has to be reconciled before a restart

A second approved provider gives you capacity, not continuity: "Switching providers does not by itself resume its conversation and saved work or reconcile prior actions." OpenAI puts recovery for an in-flight Agents API session explicitly outside the scope of its failover guidance and calls it substantially harder.

What follows for where you may place a failover boundary. Only a self-contained, read-only inference step is safely replayable — for example a timed-out assessment whose result was never used and whose deadline has not passed. Accept one result per logical request and ignore a late response from an earlier attempt. If an action MAY already have completed, confirm its outcome and block duplicate writes before restarting, and restart only through a tested path.

The same rule governs a partial response: do not blindly replay it, and do not assume it can be continued on the other route. Once output has reached another system, recovery is a restart with reconciliation, not a resume.

The practical consequence for agent design: put the failover boundary at the single inference call, not around a multi-step agent loop, unless you have built durable state and reconciliation of your own. A retry policy that treats a long agentic turn as one retryable unit will re-execute its side effects.

What this does NOT mean: it is not a claim that provider failover is unusable for agents. It bounds where the switch can sit — a read-only step inside a loop can fail over even when the loop as a whole cannot.
