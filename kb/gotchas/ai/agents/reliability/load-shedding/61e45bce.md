# Fast error responses make least-outstanding-requests load balancers send MORE traffic to the sick server

The standard advice for load shedding is to reject as cheaply and as fast as possible, so the server spends nothing on work it is dropping. Amazon follows this — except in one configuration where it deliberately does the opposite.

When the service sits behind a load balancer using a least-outstanding-requests algorithm, the balancer routes to whichever server has the fewest requests in flight. A server that is shedding load returns errors almost instantly, so its in-flight count drops, so the balancer concludes it is the healthiest server in the fleet and steers even more traffic at it. The overloaded server gets hammered precisely because it is failing efficiently.

Amazon's fix is to slow the shed responses down to match the latency of successful responses, so the balancer's in-flight signal stays honest.

DOCUMENTED INSTANCE — this took down www.amazon.com site-wide. A single server in the remote catalog service filled its disk. It mishandled that error and began returning EMPTY responses to every request, very fast, because returning nothing is quicker than returning something. The load balancer did not notice the responses were zero-length; it noticed only that this server was far faster than its peers, and steered a large share of all website traffic to it. The entire site went down because one server could not display product information. The fix was to find and remove the bad server.

That incident widens the fact in an important way. The trigger need not be a deliberate load-shed or even an error status: ANY degraded-but-fast response path has the same effect, including a success-coded empty result. The balancer's health signal was latency, and latency was inversely correlated with correctness. So the general lesson is that the load balancer's health signal and the server's failure behaviour are one coupled system, and optimising the server in isolation can invert the routing. Check what your balancer actually measures — round-robin and connection-count balancers do not have this problem; least-outstanding-requests and latency-aware ones do.

This applies to any agent-serving fleet behind such a balancer, and equally to a custom router distributing agent sessions or model calls across workers or provider endpoints: if the router prefers the least-loaded or fastest worker and overloaded workers fail fast, the router is a positive feedback loop pointed at the sickest node. The agent-specific version of the empty-response case is a worker that returns a truncated, refused, or zero-token completion quickly — it will look like the best endpoint to a latency-aware router, and nothing in the routing layer inspects whether the completion was useful.
