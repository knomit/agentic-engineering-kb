# Sticky routing converts a small per-request defect into a large per-user one — 16% of requests became ~30% of users affected

During Anthropic's August-September 2025 context-window routing incident, misrouted traffic peaked at 16% of Sonnet 4 requests on August 31, yet "approximately 30% of Claude Code users who made requests during this period had at least one message routed to the wrong server type." Anthropic names sticky routing as the amplifier: once a session landed on the wrong server type, subsequent requests in that session tended to follow it.

Two consequences worth designing around. First, the arithmetic: for any session-affinity scheme, the fraction of USERS who see a defect is strictly larger than the fraction of REQUESTS that carry it, and the multiplier grows with session length. An agent, which issues many model calls per user task, sits at the bad end of that curve — a per-request error rate that looks like an acceptable background level in a dashboard is a much higher per-task failure rate in practice.

Second, the direction of the monitoring fix: a request-level error-rate metric systematically understates user-visible impact under stickiness, so report the defect rate per session or per task as well, not only per request. This is the same shape as correlated failure — stickiness removes the independence that makes a low per-request rate feel safe — but the correlating mechanism here is a routing decision that is deliberately cached, not a shared dependency.
