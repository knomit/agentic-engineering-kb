# An inference-performance optimisation is a correctness change to sampling — mixed bf16/fp32 in approximate top-k picked wrong tokens, and an earlier workaround had masked the bug for months

Two of the three bugs in Anthropic's September 2025 postmortem were performance work that silently changed which token got emitted. An August 25 deployment carried a runtime performance optimisation that "incorrectly assigned high probability to inappropriate tokens" on TPU servers; the observable symptom was foreign-script characters appearing mid-sentence in English responses (Thai and Chinese are named) and syntax errors injected into code. The same deployment exposed a latent miscompilation of XLA:TPU's approximate top-k operation, where mixed-precision arithmetic — bf16 against fp32 — produced precision mismatches when sorting token probabilities.

The part worth carrying: a December 2024 workaround for a related symptom had masked the deeper approximate top-k bug, so the defect sat latent for roughly eight months and only surfaced when an unrelated change altered the conditions. Anthropic's resolution was to stop approximating — switching from approximate to exact top-k with operations standardised on fp32 — and to add detection tests specifically for unexpected characters in output.

For anyone operating an inference stack: treat sampling-path optimisations (approximate top-k, reduced precision, fused kernels) as changes that require correctness evidence, not just latency and throughput evidence, because their failure mode is a plausible-looking wrong token rather than a crash or a slowdown. And treat a symptom-level workaround as an open defect, not a fix — it removes the signal that would have led you to the cause.
