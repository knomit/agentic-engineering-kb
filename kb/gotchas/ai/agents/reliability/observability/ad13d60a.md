# Shed and fast-failed requests drag your latency metrics down, so an overloaded agent service looks fastest at its worst moment

Rejecting a request is far cheaper than serving one, so every shed request enters your latency histogram as a very fast sample. Amazon's rule: if a service is shedding 60% of its traffic, its median latency can look excellent while the latency of the requests it actually served is terrible — the successful-request latency is being diluted by the fast failures.

A second Builders' Library article states the same trap independently and generalises the cause: errors are OFTEN fast — access-denied, throttling, and validation-error responses all return quickly — so any spike in rejections makes latency look deceptively good. They name it 'metric pollution' and give the fix directly: log a SEPARATE timer for successful responses, and put that metric on dashboards and alarms instead of a generic Time metric covering all outcomes.

This is sharp for agent systems because the cheap-rejection path is everywhere: a tool server returning a 429, an orchestrator refusing to spawn a subagent past a concurrency cap, a router rejecting a request before it reaches the model, a guardrail refusing a prompt. All of them complete in milliseconds against multi-second real work, so the more overloaded or more heavily filtered the system gets, the better its aggregate latency graph looks.

What to do: emit shed/rejected requests on a separate metric stream and compute latency percentiles over accepted, successful requests only. Keep the rejection count and rejection rate as first-class metrics rather than letting rejections hide inside a p50.

The same source extends the technique to a second axis worth adopting for agents: where an operation's latency depends heavily on input or response SIZE, emit bucketed metrics (their examples are SmallRequestLatency and LargeRequestLatency) rather than one blended timer. Agent turns vary by orders of magnitude in context length and tool-result size, so a single blended latency metric mixes distributions that have nothing to do with each other. They pair this with bounding request and response sizes in the first place, to avoid complex brownout modes.

This does NOT mean stop measuring rejected requests — it means stop mixing them into the same distribution as served requests. Amazon also alarms on the rejection RATE specifically, and treats a persistently non-zero false-positive rate (rejecting while capacity was actually available) as evidence the service is either tuned too sensitively or suffering a load-balancing imbalance, not as normal operation.
