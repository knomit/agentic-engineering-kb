# Deleting a bad package from the repository does not stop the pipelines that already contain it — revocation has to act where the artifact is, by package version or source reference

Amazon's account of its move to continuous delivery records a revocation failure worth copying the fix for: removing a bad package from the repository does NOT stop pipelines that already contain it. The control that works is a block at the pipeline layer, placed on a known-bad package version or source-control reference, which halts every pipeline carrying that artifact wherever it has already reached.

The general shape, which is why this transfers: a pipeline copies an artifact out of its source early, so revoking at the source changes only what future builds pick up. Anything already in flight holds its own copy and keeps going. The question to ask of any revocation mechanism is therefore not "can I delete the bad thing" but "does the thing that is currently executing re-read the place I deleted it from" — and in a pipeline the answer is no.

For agent systems the same asymmetry applies to every artifact an agent loads rather than resolves per call: a prompt version, a pinned model, a tool manifest, a skill or plugin bundle, a container image. Unpublishing it stops the next load; stopping a run that already holds it needs a kill at the executing layer.

Two mechanisms the same account pairs with the block, because a halt is itself disruptive: the deployment engine maintains a minimum healthy host count so stopping mid-deployment does not drop serving capacity, and a deployment the engine detects as failed rolls back automatically rather than waiting for the halt. Teams can also override a pipeline halt deliberately, which is how a fix ships while a blocker is in place.

Scope: this is Amazon's description of its own internal pipeline practice, with no measurement attached to the artifact-block mechanism specifically. See [[bbcd36c7]] for the bake criteria that decide whether a change should have progressed at all.
