# Fallback capacity must be sized for everyone failing over at once, because correlated failover is what triggers it

A failure mode named in Amazon's Builders' Library that agent systems reproduce almost exactly. The author's home ISP went down; he tethered to a different provider's cellular network; the cellular network then slowed too — because every neighbour working from home had the same fallback and executed it simultaneously. A completely independent backup system was taken down by the correlated behaviour of the clients failing over to it.

The agent version: a fallback model provider, a secondary API key, or a cheaper backup model configured as the failover target for a primary. The failover is triggered by a primary-side outage or rate limit, which is a fleet-wide event by nature — so the fallback receives not a trickle but the entire load of the primary, instantly, from every client at once. A fallback provisioned for 'some traffic sometimes' fails at exactly the moment it is needed, and now both paths are down.

Two consequences worth designing for. First, size and rate-limit-negotiate the fallback for full primary load, not for average spillover, or accept explicitly that the fallback is best-effort and will shed. Second, stagger the failover itself — the same jitter argument that applies to retries applies to failover decisions, because a threshold every client evaluates against the same signal fires on every client at the same instant.

Note the asymmetry with the usual redundancy story: this failure needs no shared infrastructure between primary and fallback. The two providers can share nothing at all and the correlation still exists, because it lives in the clients' behaviour rather than in the systems.
