# Jitter retries randomly, but jitter SCHEDULED work deterministically per host — random scheduling destroys debuggability

Two different uses of jitter that need opposite implementations, from Amazon's Builders' Library.

For RETRIES, jitter must be random. Backoff alone does not fix overload because all the failed callers back off by the same amount and re-collide on the retry; randomness spreads them in time.

For SCHEDULED work — periodic jobs, timers, cron, delayed work — Amazon deliberately does NOT pick the offset randomly per host. They use a consistent method that yields the same number every time for the same host. The reason is diagnostic, not performance: if a resource is being overwhelmed or a race condition fires, deterministic offsets make it happen the same way each time, producing a pattern humans can recognise and root-cause. Random per-run offsets mean the overload happens at random, which makes troubleshooting much harder. So the rule is: randomize the retry, but make the schedule offset a stable function of host identity.

The underlying observation is that clients on a regular interval (once a minute, or a daily job) line up across their own fleet and fire in the first seconds of the minute or the first seconds after midnight. These spikes are short enough to be invisible in aggregated metrics — you have to look at per-second load to see them. On Amazon EBS and AWS Lambda, working with clients to jitter their periodic workloads did the same amount of work on less server capacity.

For agent systems this applies directly to scheduled/cron-triggered agents, polling loops, and background evaluation runs, all of which default to firing on the minute boundary across every replica.
