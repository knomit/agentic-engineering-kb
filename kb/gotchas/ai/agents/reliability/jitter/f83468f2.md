# Jitter retries randomly, but jitter SCHEDULED work deterministically per host — random scheduling destroys debuggability

Two different uses of jitter that need opposite implementations, from Amazon's Builders' Library. Two separate articles state this consistently.

For RETRIES, jitter must be random. Backoff alone does not fix overload because all the failed callers back off by the same amount and re-collide on the retry; randomness spreads them in time.

For SCHEDULED work — periodic jobs, timers, cron, delayed work — Amazon deliberately does NOT pick the offset randomly per host. They use a consistent method that yields the same number every time for the same host; the correlated-failures article names the concrete technique as seeding the random function with a well-known per-server parameter such as the server's name or IP address, so each server's jitter is stable over time yet differs from every other server's.

The reason is diagnostic, not performance: if a resource is being overwhelmed or a race condition fires, deterministic offsets make it happen the same way each time, producing a pattern humans can recognise and root-cause. Random per-run offsets mean the overload happens at random, which makes troubleshooting much harder. The correlated-failures article states the downside plainly — jitter makes application behaviour vary across servers and time, so bugs and failures become harder to reproduce — and stable per-host seeding is the stated way to keep the spread without paying that cost. So the rule is: randomize the retry, but make the schedule offset a stable function of host identity.

The underlying observation is that clients on a regular interval (once a minute, or a daily job) line up across their own fleet and fire in the first seconds of the minute or the first seconds after midnight. These spikes are short enough to be invisible in aggregated metrics — you have to look at per-second load to see them. On Amazon EBS and AWS Lambda, working with clients to jitter their periodic workloads did the same amount of work on less server capacity.

WHAT TO JITTER — Amazon's enumerated list, which is broader than most teams apply:
  - the frequency at which each server runs housekeeping jobs
  - the delay before a failed call is retried
  - the thresholds at which mode shifts occur (e.g. refreshing state from a remote store)
  - expiration times of short-term credentials and secrets
  - cache TTLs across servers
  - resource limits themselves, such as JVM heap and connection pool sizes

That last one is the surprising entry: varying the LIMITS across the fleet, not just the timings. Identical limits are a correlated-failure source in their own right, because evenly-distributed load crosses them on every replica at once.

For agent systems this applies directly to scheduled/cron-triggered agents, polling loops, and background evaluation runs, all of which default to firing on the minute boundary across every replica — and, via the limits entry, to context-window thresholds, summarisation/compaction trigger points, token budgets, and cache TTLs, which agent fleets typically set to one identical constant everywhere.
