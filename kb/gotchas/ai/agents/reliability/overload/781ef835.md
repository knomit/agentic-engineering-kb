# Under load an agent worker fails its health check by being too busy to answer it, and the fleet shrinks itself to death

The downward spiral, from Amazon's Builders' Library. The problem in an overload is NOT that servers return errors. It is that a browned-out server does not answer the load balancer's health-check ping within the ping's timeout — because of CPU contention, long garbage-collection pauses, or simply having no free worker threads. Failing that ping asks the balancer to remove the server for a non-trivial period. During a traffic surge, shrinking the fleet is the worst possible response: the remaining servers absorb even more load, brown out, fail their own pings, and the fleet spirals down.

A second Builders' Library article states the resulting priority rule outright: the single most important request a server receives is the load balancer's ping, because failing it means the server is removed and sits idle — and in a brownout the last thing you want is a smaller fleet. So the ping is not merely exempt from load shedding, it sits at the TOP of the shedding priority order, above every piece of real work.

The concrete configuration mistake and its fix, which is a real number worth having: when a service sits behind a proxy or load balancer that supports a max-connections setting, it looks natural to size the HTTP server's worker thread pool to EQUAL the proxy's max connections. That is exactly the misconfiguration — health-check requests need connections too, and there are none left. Amazon sizes the worker pool LARGER, 'anywhere from a handful of extra workers to double the configured proxy max connections'. Idle workers are cheap. The load shedding article gives the same constraint from the other direction: set the proxy/load-balancer max-connections HIGH and let the server do the accurate shedding with local information, but never let max connections exceed the server's listener threads, listener processes, or file descriptors, or the server loses the resources it needs to answer health checks at all.

Two other stated techniques:
- Enforce max concurrent requests inside the server, with health-check requests always admitted and normal requests rejected past a threshold. Implementations at Amazon range from a plain semaphore in Java to CPU-utilisation trend analysis.
- Run the dependency health-check logic on a background thread that updates an isHealthy flag, and have the ping handler just read the flag. This keeps ping responses fast and puts a predictable, constant load on the dependency instead of one request per ping. CAVEAT the article is explicit about: you must detect the background thread dying, because if it exits the server stops noticing failures AND stops noticing recoveries — it freezes at whatever the flag last said.

For agent workers the pool-sizing version is the one to check first: agent request handling is long-lived (a single agent turn can occupy a worker for minutes across many model round-trips), so worker pools are small and saturation is the normal state under load, not an exceptional one. A health endpoint that has to contend with in-flight agent turns for a slot will time out long before the model does. Reserve capacity for it, and keep the readiness path off any code path that calls the model.
