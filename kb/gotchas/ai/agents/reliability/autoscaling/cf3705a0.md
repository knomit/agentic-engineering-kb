# Load shedding and reactive autoscaling tuned to the same signal deadlock — the shedder holds the metric below the scaling trigger forever

If an agent service scales reactively on a utilisation signal (CPU, in-flight concurrency, queue depth) and also sheds load at a similar target on that same signal, the shedder wins. It rejects enough work to hold the metric under the threshold, so the autoscaler never sees — or sees only a delayed — signal to add capacity. The system stabilises in a permanently degraded state where it is rejecting traffic and refusing to grow.

The second-order version is worse and is the reason to care even when the two thresholds differ: teams size fleets for the loss of a whole availability zone by reading system metrics as a proxy for headroom. With shedding in play, those metrics understate how close the fleet is to its rejection point, so the fleet can look like it has redundancy it does not have. Amazon's stated consequence is that with load shedding you must load-test to breakage to know real capacity — inferring headroom from CPU stops working.

For agent products the equivalent pairing is an admission controller or concurrency cap sitting in front of a worker pool that scales on the same utilisation number. Separate the signals: shed on a metric the scaler does not read (e.g. shed on request age or queue latency, scale on offered throughput including rejected requests), or set the shed threshold strictly above the scale-out threshold so scaling always fires first.
