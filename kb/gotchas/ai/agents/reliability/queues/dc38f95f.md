# When agent processing time crosses the queue's visibility timeout, the queue fork-bombs the overloaded system with duplicate copies of the same task

The failure Amazon names explicitly as a fork bomb. A queue hands a consumer a message with a lease (SQS calls it VisibilityTimeout) — finish within it, or the queue assumes you crashed and gives the message to another consumer. If the first consumer is still running past the deadline, the SAME message is now being processed twice in parallel. The second consumer also runs long, so a third picks it up, and so on.

Why this is a positive feedback loop rather than a bounded annoyance: processing latency RISES during overload — slower database queries, servers taking on more work than they can handle. So the condition that triggers duplication is the same condition duplication makes worse. The system multiplies its own load precisely when it has none to spare.

Agent workloads sit squarely in the danger zone. An agent turn's duration is highly variable and depends on how many tool calls and model round-trips the model decides to make, so any fixed visibility timeout will be exceeded by the tail of the distribution — and a slow model endpoint shifts the whole distribution at once, which is the correlated version of the same bug.

The two stated fixes: (1) HEARTBEAT the message — periodically extend the lease while genuinely still working, which is the same mechanism as a leader-election lease; or (2) have the processor STOP work when the message expires, so a doomed run does not race its own replacement.

Second-order consequence to check at the same time: duplicate parallel delivery means your task handler must be idempotent, and the in-flight message count inflates. Queue services cap in-flight messages (distinct from queue depth, which is effectively unbounded), and a handler that fails to delete a message — the classic version is an uncaught exception on the processing path — keeps it in flight for the whole visibility timeout. Under load that cap becomes the real throughput limit. Amazon's preference is to move excess messages to a different queue rather than letting them sit visible.
