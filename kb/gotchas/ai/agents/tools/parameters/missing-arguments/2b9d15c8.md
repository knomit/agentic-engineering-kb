# A model missing a required tool parameter may invent a plausible value rather than ask — and strict tool use will not catch it, because an invented value is schema-valid

When a user's request does not contain enough information to fill a tool's required parameters, the model has two options and picks between them inconsistently: ask the user for the missing value, or emit the call anyway with a value it made up. Anthropic's tool-use documentation illustrates the second case with a `get_weather` call carrying `"unit": "fahrenheit"` that the user never supplied, and qualifies the reliability of asking in one sentence: "This behavior is not guaranteed, especially for more ambiguous prompts and for less capable models."

That qualifier is the whole of what the vendor commits to. It is graded by capability and prompt ambiguity, and it names no models, so it supports no claim about any particular model or tier. Treat asking-rather-than-inventing as a tendency that weakens with weaker models and vaguer prompts, not as a property you can attribute to a named model.

**The trap is that the obvious guardrail does not address this.** Adding `strict: true` to a custom tool definition makes Claude's tool calls match your schema exactly — but a fabricated parameter is type-correct and often enum-valid, so it conforms. Strict tool use guarantees the SHAPE of the arguments, never that a value was grounded in anything the user said. A tool call can be 100% schema-conformant and still be acting on an invented premise.

The operational consequences:

- **Never let a required parameter's presence stand as evidence the user supplied it.** For any parameter whose wrong value is costly or irreversible — an account id, an amount, a recipient, a date, a unit of measure — validate it against something outside the model's output, or echo it back for confirmation before acting.
- **Prefer making such a parameter optional with an explicit unknown, over required.** A required field forces a value into existence; an optional one lets the absence be represented, which is the information you actually want.
- **Put the disambiguation instruction in the tool description**, where it is read at selection time, rather than relying on the model to volunteer a question.

Ambiguity here is a property of the request, not only of the model: the same tool on the same model will fabricate more often as prompts get vaguer, so a clean evaluation on well-specified inputs says nothing about production traffic.
