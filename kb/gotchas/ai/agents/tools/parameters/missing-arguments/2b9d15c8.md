# A model missing a required tool parameter may invent one rather than ask — and this varies by model tier

When the user's request does not contain enough information to fill a tool's required parameters, the model has two options and picks between them inconsistently. Anthropic documents the split by tier: Claude Opus is much more likely to notice the gap and ask the user for the missing value, while Claude Sonnet might ask — especially if prompted to think before emitting the tool call — but might instead infer a plausible value. Behaviour degrades further with more ambiguous prompts and less capable models, and is explicitly not guaranteed for any of them.

The documented example is worse than a simple guess: asked "What's the weather?" with no location, the model emitted `get_weather` with `location: "New York, NY"` AND `unit: "fahrenheit"` — inventing not only the missing required argument but an optional one the user never mentioned. A confidently fabricated argument is indistinguishable, downstream, from a correct one.

Why the obvious fix does not work: strict tool use (`strict: true`) guarantees the emitted call conforms to your JSON schema. Schema conformance says nothing about whether the *values* were grounded in the user's request — a hallucinated location is perfectly schema-valid. If a wrong value is costly, the defence has to be elsewhere: validate arguments against something real before executing, require confirmation for consequential calls, or design the tool so an unspecified parameter is representable (an explicit null or an "ask the user" branch) rather than silently defaultable.
