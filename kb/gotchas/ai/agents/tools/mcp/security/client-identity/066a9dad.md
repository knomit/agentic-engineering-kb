# A URL-based client ID proves who owns a domain, not which process is listening on localhost — so any local program can wear a legitimate MCP client's name during consent

MCP `2026-07-28` replaced Dynamic Client Registration with **Client ID Metadata Documents** — the `client_id` is an HTTPS URL the authorization server fetches to learn who the client is (`00fd386c` covers what that buys). The same revision's security page adds three attack sections that did not exist in `2025-06-18` — nor in `2025-11-25`, checked directly on the 18th run — and two of them are about the limits of that identity model.

**1. CIMD PROVES A DOMAIN, NOT A PROCESS — "Localhost Redirect URI Impersonation".** Native and local MCP clients normally use `localhost` redirect URIs. The spec states the gap flatly: "the metadata document proves control of a domain, but it cannot prove which local process is listening on a `localhost` redirect URI." The attack is three steps and needs no vulnerability:

> 1. Providing the legitimate client's metadata URL as their `client_id`
> 2. Binding to any `localhost` port, and providing that address as the redirect_uri
> 3. Receiving the authorization code via the redirect when the user approves

And the reason it survives review: "The server will see the legitimate client's metadata document and the user will see the legitimate client's name, making attack detection difficult." Every signal a human or a server would check reads correct. Any local process — another MCP client, a piece of malware, a second copy of your own app — can present itself as your client during consent.

**THE AUTHORIZATION-SERVER COUNTERMEASURES IN FULL, WITH THEIR MODAL STRENGTHS** (added 18th run from `basic/authorization/security-considerations`, the page this fact previously recorded as unread). Under "Localhost Redirect URI Risks", authorization servers:

- **SHOULD** display additional warnings for `localhost`-only redirect URIs
- **MAY** require additional attestation mechanisms for enhanced security
- **MUST** clearly display the redirect URI hostname during authorization

That is the complete set, and the modal split matters: the only **MUST** is *displaying a hostname to a human*. The measure that would actually attest which process is listening is a **MAY**, and the spec names no mechanism for it. So the specification's answer to localhost impersonation is a consent-screen affordance, not a technical control — which is why a client author cannot fix this in their client and can only prefer authorization servers that implement the warnings.

**2. PKCE DOES NOT PREVENT A MIX-UP ATTACK, AND THE SPEC SAYS WHY.** "An MCP client typically interacts with many authorization servers over its lifetime", and an attacker controlling one may induce the client to send it a code or token issued by an honest one (RFC 9207 §1). The mitigation is Authorization Response Validation — binding the response to the authorization server the client recorded before redirecting. The sentence to remember, because PKCE is widely treated as covering this whole family: "**PKCE alone does not prevent this attack because the client transmits the `code_verifier` to the attacker's token endpoint.**" PKCE binds the code to *the client*; it says nothing about *which server* the client is talking to, and in a mix-up the client hands the attacker both halves. "Resource indicators do not help when the attacker's authorization server is intercepting requests before they hit the honest authorization server."

   The mitigation has a stated dependency that is itself a deployment condition: "This mitigation depends on honest authorization servers emitting `iss`; it provides no protection against an honest server that does not." A client cannot make an authorization server emit `iss`, so the control only exists if every server you talk to cooperates — which for a general-purpose MCP client is not something you control either. **`bdb36fce` now carries the mechanism** — the normative `iss` validation table, its fail-open bottom row, and the MUST NOT-normalize comparison rule.

**3. WHOM THE SERVER LETS IN IS POLICY, NOT PROTOCOL — "CIMD Trust Policies".** Because any HTTPS URL can be a `client_id`, authorization servers accepting CIMD choose their own admission rule, and the spec lists the range without picking one: allowlists of trusted domains for protected servers; accept any HTTPS `client_id` for open servers; reputation checks for unknown domains; restrictions based on domain age or certificate validation; and prominently displaying the CIMD and associated client hostnames to prevent phishing. "Servers maintain full control over their access policies."

**THE THROUGH-LINE.** Both weaknesses land in the same place: CIMD moved client identity from *a credential the server issued* to *a document the client points at*, and the residual risk moved with it — out of the protocol and into the consent screen. Two of the three defences above are things a human is expected to read. That framing is this pack's; the spec presents the three sections separately.
