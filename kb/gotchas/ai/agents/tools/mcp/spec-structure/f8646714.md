# MCP 2026-07-28 split authorization into four pages and moved the attack descriptions out of the specification into a non-normative tutorial — the rules and the reasons for them now live in different documents

Through `2025-11-25`, MCP authorization was **one file** — `docs/specification/<rev>/basic/authorization.mdx`, 708 lines at `2025-11-25` — carrying the normative requirements and the attack descriptions together. `2026-07-28` splits it into a directory of four pages (`index`, `security-considerations`, `client-registration`, `authorization-server-discovery`).

**WHAT THE SPLIT DID TO THE SECURITY CONTENT.** Diffing the `2025-11-25` `## Security Considerations` section against the standalone `2026-07-28` page: the normative **MUST** / **SHOULD** / **MAY** bullets survive essentially verbatim, and four blocks of *explanatory* prose were deleted outright.

1. **The localhost impersonation recipe.** `2025-11-25` gave the three-step attack (present the legitimate client's metadata URL as your `client_id`, bind any `localhost` port and offer it as the `redirect_uri`, collect the code on redirect) plus why it survives review: "The server will see the legitimate client's metadata document and the user will see the legitimate client's name, making attack detection difficult." `2026-07-28`'s page keeps only the conclusion — "Client ID Metadata Documents cannot prevent `localhost` URL impersonation by themselves." — and the three countermeasure bullets.
2. **The authorization-server SSRF mechanism.** `2025-11-25`: "The authorization server takes a URL as input from an unknown client and fetches that URL. A malicious client could use this to trigger the authorization server to make requests to arbitrary URLs, such as requests to private administration endpoints the authorization server has access to." `2026-07-28` keeps a **SHOULD**-consider pointer to the CIMD draft and drops the mechanism. (Related: `59a75c06` on who the SSRF victim is.)
3. **The two dimensions of Access Token Privilege Restriction** — audience-validation failure as a defect complete on its own, versus token passthrough as forwarding — enumerated in `2025-11-25`, deleted here. (`ba5db3ec` holds this distinction, sourced from the tutorial page where it still appears.)
4. **The concrete CIMD trust-policy options** (domain allowlists, accept-any-HTTPS, reputation checks, domain-age or certificate restrictions, displaying client hostnames prominently), replaced by a cross-reference to CIMD spec §6.4 and §6.8. The enclosing "Authorization servers **MAY** implement domain-based trust policies" survives; only the menu of options went.

**WHERE THE DELETED MATERIAL WENT — MOSTLY MOVED, NOT LOST.** The mechanics reappear in `docs/docs/2026-07-28/tutorials/security/security_best_practices.mdx` under new `### Mix-Up Attacks`, `### Localhost Redirect URI Impersonation` and `### CIMD Trust Policies` headings, each structured as "Attack Description" / "Mitigation", and the two documents cross-link. Those three sections are new to *that* page in `2026-07-28` — verified absent from it at both `2025-06-18` and `2025-11-25`.

**THE CONSEQUENCE, WHICH IS THE POINT.** The requirement and the threat model it answers are now in different documents, and only one of them is the specification. Read `specification/basic/authorization/security-considerations` alone and you get obligations with no attacker; read the tutorial alone and you get attacks whose countermeasures are only by reference. Neither is sufficient for an implementer, and nothing on either page says so. **Practical rule:** when a `2026-07-28` authorization requirement looks arbitrary, the missing rationale is in `docs/2026-07-28/tutorials/security/security_best_practices` or in the single-file `2025-11-25` `basic/authorization.mdx` — both still published.

**A SECOND HAZARD FROM THE SAME SPLIT: ONE RULE, TWO PAGES, TWO MODAL STRENGTHS.** Splitting a document duplicates the rules that straddle the seam, and the copies need not match in force. Worked example — including the `scope` parameter in a `WWW-Authenticate` challenge:

- `basic/authorization/index.mdx` states it normatively: "MCP servers **SHOULD** include a `scope` parameter in the `WWW-Authenticate` header".
- `basic/authorization/authorization-server-discovery.mdx` states the same thing as plain prose: "Servers **can** also include a `scope` parameter in the `WWW-Authenticate` challenge", then cross-references the Scope Selection Strategy section for the semantics.

**This is not a downgrade, and it was checked rather than assumed** — the SHOULD survives intact on `index.mdx`, so the weaker sentence is a non-normative pointer to it, not a replacement for it. But a reader arriving at the discovery page with a discovery question (which is the page's whole purpose) meets "can" and has no cue that the binding statement lives elsewhere. **The generalisable move when reading any split specification: before recording that a requirement weakened between revisions, grep every page of the new revision for the rule — a rule that appears twice will be found at its weakest phrasing first if the weakest copy is on the topic page you went to.** The mirror of the *moved-not-deleted* trap above, and the same root cause.

**GENERALISE CAUTIOUSLY.** The observation that a spec reorganisation can relocate rationale into non-normative material while leaving the normative text intact is this pack's reading of one document set. Only the MCP instance is evidenced here.

**SOURCING, AND A RE-CHECK OF THE DIFF ITSELF.** Read from the specification repository on branch `main` and established by diffing revision directories, not by re-reading. `main` is the live editing branch rather than a release tag.

The first diff bounded the `2025-11-25` region on end-of-file rather than on the following heading, so it also swept in the sibling `## MCP Authorization Extensions` section and showed it as deleted. **It was not deleted — it moved to the split's `index.mdx` (line 415), intact.** Re-running the diff bounded correctly on the next `##` heading confirms the four-block enumeration above is complete and that nothing normative was lost: the only other differences are link-path rewrites and line reflows where the same requirement survives on both sides. An over-wide range adds phantom findings rather than hiding real ones, so the conclusion was never at risk — but the phantom was one heading away from being written down as a fifth deletion.

Note also that the fourth page of the split, `authorization-server-discovery`, carries at least one rule with **no** ancestor in `2025-11-25` at all — see `36d792c3`. A split is therefore not safe to treat as a pure reorganisation: check each page for genuinely new normative content as well as for relocated content.
