# The MCP revision date does not increment for backwards-compatible changes, so it cannot tell you which features exist

MCP revisions are strings of the form YYYY-MM-DD, and the date means "the last date backwards incompatible changes were made" — not the last date the spec changed. The spec states explicitly that the version will not be incremented as long as changes maintain backwards compatibility. Two consequences that bite:

- Negotiating revision X with a peer tells you the compatibility floor, not the feature set. A server and client can both report the same revision while the spec text underneath has gained features since either was written. Feature detection has to come from declared capabilities, never from comparing revision dates.
- A revision marked **Current** may continue to receive backwards-compatible changes. Only revisions marked **Final** are frozen. Pinning your reading to a dated URL and treating it as immutable is therefore wrong for the current revision — re-read it.

Revisions are marked Draft (not ready), Current (ready, still mutable), or Final (past, frozen).

**The current revision is `2026-07-28`, superseding `2025-11-25`, and has been continuously since 2026-07-30 (last verified against the live versioning page 2026-09-24).** Do not cite `2025-11-25` or `2025-06-18` as current. The move was backwards-incompatible and large — see the stateless redesign facts in this pack.

**The negotiation MECHANISM itself changed in 2026-07-28, and this is the part that invalidates older integration code.** Under `2025-11-25` and earlier, version and capabilities were agreed once per connection during an `initialize` handshake, both sides settled on exactly one revision for the session, and failed negotiation terminated the connection. That handshake no longer exists. Now:

- Every request declares its own version via the `io.modelcontextprotocol/protocolVersion` key in `_meta` (and, on Streamable HTTP, the `MCP-Protocol-Version` header). **The server accepts or rejects each request independently** — negotiation is per-request, not per-connection. Clients and servers MAY support multiple protocol versions simultaneously.
- A version the server does not support returns `UnsupportedProtocolVersionError` listing the versions it does support. The client may retry the same request at a mutually supported version, or surface an error to the user if none exists. This is a recoverable, per-request error, not a connection teardown.
- Clients wanting to choose a version up front call `server/discover`, a **mandatory** RPC (servers MUST implement it) returning supported protocol versions, capabilities, and identity in one request. Calling it is optional for the client — sending any request directly and handling a version error is equally valid.
- Client capabilities likewise ride on every request (`io.modelcontextprotocol/clientCapabilities`), so capability detection is per-request too.

So the old advice "detect features via capability negotiation at `initialize`" is now wrong on its face: there is no `initialize`. Read capabilities from `server/discover` or from the per-request `_meta` exchange. Interoperability with the handshake-based revisions (`2025-11-25` and earlier) is handled by a separate backward-compatibility section rather than by the negotiation above.

Deprecation has a defined clock worth planning against: a feature marked Deprecated stays in the spec for at least twelve months — or at least ninety days under the expedited-removal exception — before it becomes eligible for removal, and a deprecated feature must document a migration path or state that none is required. So a deprecation notice is not an emergency, but the ninety-day path means it is not a guaranteed year either. `2026-07-28` formalised this as a named feature-lifecycle policy (Active / Deprecated / Removed) with a published registry of currently-deprecated features.
