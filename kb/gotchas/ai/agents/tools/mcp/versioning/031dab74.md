# The MCP revision date does not increment for backwards-compatible changes, so it cannot tell you which features exist

MCP revisions are strings of the form YYYY-MM-DD, and the date means "the last date backwards-INCOMPATIBLE changes were made" — not the last date the spec changed. The spec states explicitly that the version will not be incremented as long as changes maintain backwards compatibility. Two consequences that bite:

- Negotiating revision X with a peer tells you the compatibility floor, not the feature set. A server and client can both report the same revision while the spec text underneath has gained features since either was written. Feature detection has to come from capability negotiation at `initialize`, never from comparing revision dates.
- A revision marked **Current** may continue to receive backwards-compatible changes. Only revisions marked **Final** are frozen. Pinning your reading to a dated URL and treating it as immutable is therefore wrong for the current revision — re-read it.

Revisions are marked Draft (not ready), Current (ready, still mutable), or Final (past, frozen). As of 2026-07-26 the current revision is **2025-11-25**, superseding 2025-06-18. Clients and servers MAY support several revisions at once but MUST agree on exactly one for a session; failed negotiation is expected to terminate the connection gracefully rather than fall back silently.

Deprecation has a defined clock worth planning against: a feature marked Deprecated stays in the spec for at least twelve months — or at least ninety days under the expedited-removal exception — before it becomes eligible for removal. So a deprecation notice is not an emergency, but the ninety-day path means it is not a guaranteed year either.
