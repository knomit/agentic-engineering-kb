# Enabling tools on the Claude Messages API costs system-prompt tokens on every request, the count is per model version and moves non-monotonically, and the forced-tool-use surcharge is not published for either current flagship

Enabling tools on the Claude Messages API silently injects a tool-use system prompt that is billed as input tokens on every request, on top of the tool definitions themselves (names, descriptions, schemas) and the `tool_use` / `tool_result` blocks in the transcript. The published count is per MODEL VERSION and per `tool_choice` MODE, and three things about it are easy to miss.

THE MODE MATTERS, WHERE IT IS DOCUMENTED. `auto` and `none` use the cheaper prompt; `any` and `tool` use a larger one. Claude Haiku 4.5 is 496 tokens versus 588; Claude Opus 5 is 286 versus 406; Claude Sonnet 5 is 354 versus 474. Where both figures exist, reaching for forced tool use as a reliability fix imposes a standing surcharge of roughly 90-120 tokens on every request.

THE SURCHARGE IS NOT PUBLISHED FOR EITHER CURRENT FLAGSHIP, AND THAT IS THE TRAP. For Claude Opus 5.5 and Claude Sonnet 5.5 the docs list ONLY the `auto`, `none` figure — 286 tokens each — with no `any`, `tool` row at all. So on the two models a reader is most likely to be using, the cost of forced tool use is unstated. Do NOT carry the Opus 5 delta (+120) across to Opus 5.5 on the strength of the matching 286: the base figures being equal is not evidence the forced-mode figures are, and the older pair's own bases differ from each other (286 vs 354) while their deltas match (+120). If the surcharge matters to a budget, measure it from the `usage` metrics on a real request rather than inferring it.

THE COUNT MOVES NON-MONOTONICALLY ACROSS VERSIONS, so a cost estimate does not survive a model upgrade in either direction. The Opus line, `auto`/`none`: 4 and 4.1 at 313, 4.5 at 496, 4.6 at 497, 4.7 at 675, 4.8 at 290, 5 at 286, 5.5 at 286. Opus 4.7 is nearly 2.4x its own successor. A team that sized its context budget on 4.7 and upgraded would have over-provisioned; a team that sized on 4.1 and moved to 4.5 would have under-provisioned by 183 tokens per request.

The one way to pay nothing: pass no `tools` at all with `tool_choice` `none`, which costs 0 additional system-prompt tokens. The table assumes at least one tool is provided, so passing tools and setting `none` does not get you back to zero — it gets you the cheaper of the two rows.

WHAT THIS DOES NOT MEAN: these figures are not the total tool-use cost. They exclude the tool definitions and every `tool_use` / `tool_result` block, which in an agentic loop dominate them by orders of magnitude; optimising the system-prompt row while passing forty verbose tool schemas is the wrong end of the problem. The figures also live in a vendor doc that is revised in place as models ship, and the model rows are reordered as older models are demoted under an "Additional models" divider, so read the live table rather than a cached value — including for a model whose number you believe you already know.
