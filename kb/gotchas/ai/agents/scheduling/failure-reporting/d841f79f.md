# A source that failed to load is indistinguishable from a quiet day, because the run starts without that source's tools and the agent reports nothing new

If an MCP server is down or its token has expired, the run still starts — just without that server's tools. Nothing in the agent's context distinguishes "this source returned no new items" from "this source was never readable", so the honest-looking output is a report saying nothing new happened.

The stated rule is "Report a failed read as unreadable, never as a quiet day", and it has three parts, all of which matter:
1. leave that source's bookmark where it is, because advancing it over an unread window loses that window permanently;
2. write the report from the sources that did load;
3. end the report with a line naming what was unreadable ("pull requests unavailable this run").

Operational consequence: a scheduled agent needs an explicit per-source read outcome, carried into its own output. A silent tool absence is the failure mode; an error message the agent never sees cannot be reported.

This does NOT mean a failed source should abort the run. Partial output plus a named gap is the prescribed behaviour; the gap is what makes the quiet day checkable.
