# A scheduled agent that reads "the last 24 hours" loses items when the run is late and repeats them when it is early — keep a per-source bookmark instead

A fixed lookback window is wrong in both directions, and naming only one of them is how the bug survives review: "A late run leaves a gap and an early run repeats items." The window is anchored to when the run happens, and nothing about a schedule guarantees that.

The replacement is a per-source timestamp of the newest item that source has actually yielded, persisted in a store the run can write (the reference implementation keeps `bookmarks.json` in a `state` store, with entries like `"slack": "2026-09-14T13:02:11Z"`). Each run reads from its bookmark forward. This is not optional bookkeeping for a scheduled agent: every run starts in a fresh sandbox, so a bookmark the run does not persist does not exist.

Operational consequence: the unit of progress is one bookmark per source, not one per run. Sources fail independently, so a single global cursor advanced at the end of a run silently skips whatever one broken source would have returned.
