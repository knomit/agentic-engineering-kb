# Six named events force a fresh cache write mid-session, and at 120K context one write costs as much as 25 reads — but a change of effort only forces one on Amazon Bedrock, Google Cloud's Agent Platform or a gateway

Anthropic's own cost guide for Claude Opus 5.5 names six events after which to expect a cache write: pausing longer than the cache lifetime; changing effort on Amazon Bedrock, Google Cloud's Agent Platform or a gateway, where the level is part of what the cache matches; turning on fast mode for the first time in a conversation, which changes part of what the cache matches; connecting or disconnecting an MCP server, which can change what loads at the start of each request; switching models, since the new model starts from an empty cache; and compaction, which rewrites the history the cache matched.

The price of that write is the point. At 120K tokens of context a five-minute cache write on Opus 5.5 costs about $0.60 and a read about $0.02, so one write costs as much as 25 reads. A one-hour write at the same context is about $0.96. Cache writes bill at 1.25x input for a five-minute cache and 2x input for a one-hour cache. The cache lifetime itself differs by how the session is paid for: in Claude Code it is one hour on a subscription, and five minutes on an API key, on a cloud provider, or once a subscription draws on usage credits.

Consequence: treat each of those six as a purchase, not a setting. Connect or disconnect MCP servers, pick the model, and turn on fast mode before the session accumulates context rather than during it, and batch such changes together so one write covers them all. A session showing a low cache share in usage reporting has usually hit one of the six rather than grown too large.

What this does NOT mean: it is not true in general that changing effort invalidates the prompt cache. On Opus 5.5 with an API key or a Claude subscription, changing effort keeps the cache; the effort level is part of the cache match key only on Amazon Bedrock, Google Cloud's Agent Platform, or behind a gateway. Dropping the deployment-target half of that condition turns a true statement into advice that would wrongly discourage using the effort dial at all.

A second post from the same team makes the MODEL-SWITCH event's consequence concrete, and it runs against the very reason people switch. Caches are per model, so the cheaper model starts from an empty prefix and pays a full cache write over the whole accumulated history: at "100k tokens into a conversation with Opus," dropping to Haiku for one easy question "would actually be more expensive" than asking Opus. The per-token saving is real and the write swamps it — so a mid-session downgrade made to save money costs money, and the deeper the conversation the worse the trade.

The remedy is not to avoid cheap models but to avoid changing the model INSIDE one cached prefix. Hand the cheap work to a subagent running that model, with a hand-off message prepared by the expensive one, so the parent conversation keeps its prefix intact and the subagent starts a small prefix of its own; Claude Code's Haiku-based Explore agent is the team's stated example. Stated as a rule by that team: "Don't change models mid-session."
