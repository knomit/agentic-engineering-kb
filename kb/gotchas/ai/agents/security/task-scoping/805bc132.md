# Task breadth is a security parameter — a broad instruction widens what injected content can steer toward without ever tripping the confirmation gate

OpenAI reports that giving an agent a very broad instruction — their example is "review my emails and take whatever action is needed" — **can** make it easier for hidden malicious content to mislead the model, and states this holds "even though it is designed to check with you before taking sensitive actions." Published 2025-11-07.

That qualifier is the part worth keeping. The intuitive model is that an approval gate makes task scope a quality concern rather than a security one: however wide the brief, anything dangerous still stops for a human. The source says otherwise, and it gives its own mechanism.

**THE MECHANISM, AND IT IS THE SOURCE'S, NOT AN INFERENCE — TASK SCOPE AND DATA SCOPE ARE THE SAME DIAL.** The post's worked example runs: you ask an agent to "generally respond to your emails from overnight because you are busy this morning"; an attacker sends an email carrying misinformation; and then — the load-bearing parenthetical — "the agent may look for anything like bank statements in your email (which you gave access to for the task) and will share them with the attacker." The breadth of the brief is what set the breadth of the DATA GRANT. A confirmation gate never enters into it: the search of your mailbox is squarely inside what you authorised, and by the time anything reaches a gate the attacker's objective is already served. So the reason breadth is a security parameter is not that it sneaks past the approval step — it is that it enlarges the set of data the agent is entitled to touch in the first place.
The post pairs this with the corresponding control: "Where possible, limit an agent's access to only the sensitive data or credentials it needs to complete the task", illustrated with ChatGPT Atlas's logged-out mode for tasks that need no authenticated access.

The consequence for design: treat the breadth of the task specification as a control you tune, alongside tool permissions and approval gates, rather than as a UX preference. The source's own advice is "It's safer to ask your agent to do specific things, and not to give it wide latitude to potentially follow harmful instructions from elsewhere like emails", and it is explicit that "this doesn't guarantee there won't be attacks, it makes it harder for attackers to be successful."
*THIS PACK'S OPERATIONALISATION, marked as such because the source does not say it:* name the accounts, folders and action verbs in the brief, and prefer several narrow invocations to one open-ended one — each invocation then carries only the access its own task needs, which is the coupling the source's example turns on.

*ALSO THIS PACK'S, AND FLAGGED BECAUSE AN EARLIER VERSION OF THIS FACT STATED IT AS THOUGH CITED:* a plausible secondary effect is that a wide brief also makes an attacker-suggested action look in-scope at the moment the user is asked to approve it, since the user authorised an open-ended goal and no specific step visibly contradicts it. The post does not make this argument and offers no evidence for it. It is retained as a hypothesis only.
