# A prompt injection carried inside an encrypted reasoning block arrives as the model's own prior thought, and leaves no plaintext for a monitor to read

The replayability of provider-encrypted reasoning blocks has a second consequence, and for anyone building agents it is worse than the confidentiality one. An attacker who gets a model to internalise a malicious instruction can capture the resulting encrypted reasoning block and place it where another agent will pick it up — a shared session, a published trajectory. When that block is replayed, the receiving model does not treat it as untrusted input. It treats it as ITS OWN PRIOR REASONING, because that is structurally what the field is.

THE SENTENCE THAT MAKES THIS AN ARCHITECTURAL PROBLEM RATHER THAN A BUG: "The malicious thought can therefore transfer across model scales and across tasks while leaving no plaintext artifacts for monitors to catch." Every content-inspecting defence this pack has recorded — input sanitisation, output scanning, an LLM judge reading the transcript, chain-of-thought monitoring — operates on text. The payload is not in the text. It is in an opaque field that the monitor cannot read and that the model can. So this is not a monitor that performs badly; it is a channel the monitor is not connected to.

WHY THIS IS NOT HYPOTHETICAL: THE MATERIAL IS ALREADY PUBLIC AT SCALE. The paper makes two separate statements about its corpus — "We collected 6,708 publicly available agent trajectories from GitHub and Hugging Face", and, of its extraction results, "By decoding 315,320 reasoning blocks scraped from public repositories". THE PAPER DOES NOT SAY the 315,320 blocks were drawn from exactly those 6,708 trajectories, so no ratio between them is asserted here and none should be derived. What both statements independently establish is the point that matters: encrypted reasoning blocks sit in public repositories in large numbers, which is the same population an agent-training or agent-benchmarking pipeline ingests. The paper's framing is poisoning of public agentic rollouts — so the exposure is not only to an attacker targeting you directly, but to anyone consuming shared trajectories.

WHAT TO DO. Treat a provider-encrypted reasoning field arriving from ANY source you did not generate as untrusted input that your defences cannot inspect, and therefore as something to STRIP rather than something to scan. Concretely: do not replay reasoning blocks from shared session files, published trajectories or bug-report attachments into a live agent; and if you ingest public agent trajectories for training or evaluation, drop the encrypted reasoning fields rather than carrying them through. This is one of the rare cases where the only available control is at the boundary, because inspection is not on the menu.

HOW THIS PAIRS WITH THE MONITORING FACTS. [[42e1218f]] concluded that where a monitor sits beats how good it is; this is the limiting case of the same point, where no placement of a text-reading monitor helps at all and only the routing decision does. Note also the direction of travel against [[1d01a338]]: that fact is about secrets leaking OUT of a reasoning blob; this one is about instructions travelling IN. Same architectural cause, opposite flow.

NOT ESTABLISHED, AND STATED SO THE GAP IS NOT LATER FILLED BY GUESSWORK: a specific end-to-end demonstration of this vector appears in the paper's narrative, but the sentences describing it did not come back on a verbatim-demanding re-read, so no worked example, victim model or payload is reproduced here. What is attested is the mechanism, the public-corpus statements, and the monitor-invisibility claim quoted above. The provider mitigations noted in [[1d01a338]] and in [[33aed84c]] are scoped to the paper's Figure 1 attacks and are not a statement that this vector is closed.
