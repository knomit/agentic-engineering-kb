# Log the request before you validate it, but sanitise it first — an unsanitised caller string is a log-injection and disk-fill vector

Amazon's ordering rule is counter-intuitive and correct: record details about the request BEFORE running validation, authentication, or throttling. Otherwise the requests you most need to explain — the rejected ones — are the ones with no log entry, and you cannot answer why a caller was turned away.

But logging attacker-controlled input has two failure modes they name explicitly, and both must be handled at the same time:

- **Disk fill and cost.** If a caller passes a 1 MB string, that string lands in the log entry. Truncate before logging — Amazon cites this as a real risk of filling disks and blowing out log storage spend.
- **Log injection.** Filter out ASCII control characters and any escape sequences meaningful to your log format. Their stated concern is that a caller can pass a string that is itself a well-formed service-log entry and get it injected into your logs (they link xkcd 327, the Bobby Tables comic). A forged log entry corrupts the audit trail and any metric computed from it.

So the rule is: encode, escape, and truncate untrusted input at the log boundary, and do it before validation runs, not after.

Agent systems have more untrusted-content surface than a typical API, and the content is longer and more adversarial: user prompts, tool results fetched from the web, file contents, subagent outputs, and model-generated arguments all end up in traces. Anything that reaches an agent's trace has already passed through a channel a prompt-injection attacker may control, so a forged trace entry is a plausible attack, not a hypothetical — and traces are increasingly read back BY models during debugging, which makes an injected entry an instruction-delivery channel as well as an audit-integrity problem.

Pair it with Amazon's stated policy on sensitive fields: decide what may be logged on an OPT-IN basis rather than opt-out, precisely so that a sensitive parameter added later is not logged by default. They log enough to know who a request came from, but leave out request parameters that do not affect routing or processing — e.g. when parsing a customer message fails, the payload is deliberately not logged, however much harder that makes troubleshooting. Logs also get encryption, restricted operator access, and regular access baselining.
