# The agentic supply chain's payload is in the metadata, not the code — your reviewers read source, your agent reads descriptions

The organising insight, from the AI Agent Traps framework (Franklin et al., 2026), quoted verbatim: "The attacker's target is not the agent but the information environment the agent consumes: tool descriptions, retrieval corpora, persistent memory stores, skill registries, and web content. The agent's own capabilities become the attack mechanism."

Named techniques, all now observed rather than theorised:

- **Tool Poisoning Attacks** — malicious instructions hidden in tool *description* fields, invisible to human reviewers but processed by the model as trusted context. "The payload is not in the code but in the metadata, exploiting the gap between what humans audit and what agents consume."
- **MCP Rug Pulls** — tool descriptions change *after* approval. Approval is a point-in-time decision taken against mutable metadata.
- **Cross-origin escalation** — a malicious server shadows the tools of a trusted one.
- **postmark-mcp**, the first documented malicious MCP server in the wild: it "spent fifteen versions building legitimacy before silently adding a single line of exfiltration code". Package age and release history are not evidence of intent.
- **CVE-2025-6514** (CVSS 9.6), "a critical RCE vulnerability ... discovered in core MCP infrastructure used by hundreds of thousands of developers, demonstrating that even the protocol's transport layer carried exploitable trust assumptions." So this is not only a metadata problem.

The consequence for practice: **code review does not cover your agent's attack surface.** A review process that diffs source but not tool metadata is structurally blind to this entire class. Pin and diff tool descriptions across versions the way you pin dependencies, and re-verify on change rather than only at first approval — the rug-pull technique exists precisely because most integrations verify once.

This is the same lesson as the MCP spec rule already in the pack that tool *annotations* are untrusted and must not gate auto-approval. Descriptions are equally attacker-controlled and, unlike annotations, are fed directly to the model as guidance.

=== TWO PARTS OF THE FRAMEWORK THIS FACT HAD MISSED, ADDED 2026-08-20 ===
Both are in the same section as the framing sentence above, and both change what a defender does rather than merely naming another technique.

1. **APPROVAL FATIGUE IS CLASSIFIED AS AN ATTACK, NOT AS FRICTION.** The framework covers the approval-fatigue problem, "which the framework treats as a deliberate attack on the human reviewer rather than incidental operational friction." That reclassification is the useful part: if wearing down the reviewer is a technique, then the RATE of approval prompts is a security parameter, an integration that raises it is degrading a control, and "users click through everything anyway" stops being an excuse for removing the prompt and becomes the attacker's objective. It also means the count of prompts your agent generates per hour belongs on a dashboard.

2. **MULTI-AGENT SYSTEMIC TRAPS, INCLUDING ONE NO PER-AGENT CONTROL CATCHES.** The framework "identifies multi-agent systemic traps, including cascading failures triggered by correlated agent behaviour and fragmented payloads that reconstitute only when aggregated across agents, that will become operationally relevant as multi-agent deployments reach production scale." The fragmented-payload case is the sharp one: every fragment is individually benign, so every per-agent scanner passes it, and the payload exists only in the aggregate that no single agent sees. Any content inspection sited at the individual agent is structurally unable to detect it — detection has to sit wherever the fragments are recombined. Note the modality: OWASP states this as anticipatory ("will become operationally relevant"), not as an observed incident, and this fact does not upgrade it.

A SOURCE LEAD, recorded rather than acted on: the same document points at the MCP Security White Paper as providing "the most granular threat taxonomy for tool invocation protocols, identifying 12 distinct categories including tool poisoning, rug pulls, and cross-origin escalation" — i.e. a twelve-category superset of the three named here, in a document this pack has not read.
