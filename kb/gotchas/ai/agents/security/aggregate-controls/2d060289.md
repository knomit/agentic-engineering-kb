# The broadest security requirement in a control framework is usually an aggregate of five separate controls — and satisfying one reads as satisfying all

In OWASP's AIUC-1 crosswalk, the two most broadly mapped requirements are **"prevent unauthorized AI agent actions"** (8 of 10 threats) and **"restrict unsafe tool calls"** (8 of 10) — reflecting how central scope enforcement and least-agency controls are across the agentic threat model.

The crosswalk then attaches a warning to the broadest one that generalises well beyond this standard:

> B006 aggregates multiple distinct control functions (scope enforcement, tool-use restriction, privilege control, inter-agent constraints, and runtime containment). Implementations should address each control function independently rather than treating B006 as a single checkbox. **Coverage of one function does not imply coverage of others.**

**This is a structural failure mode of control frameworks, not a quirk of this one.** The requirement that maps to the most threats is broad *because* it is vague, and breadth of mapping is exactly what makes it look like the highest-value box to tick. A team implements scope enforcement, marks the requirement satisfied, and inherits a claimed mitigation against eight threat classes while runtime containment and inter-agent constraints were never built. The audit passes. The control coverage is fictional for six of the eight.

Practical rule: when a single requirement maps to most of your threat model, treat that as a **decomposition signal, not a coverage win.** Split it into its constituent control functions and track each separately, because the aggregate will otherwise be reported green on the strength of whichever sub-control was easiest.

**A specific TOCTOU trap named for tool-call authorization**, worth checking directly:

> Implementations should address whether tool-call authorization is verified **only at request time or re-validated at execution time**, particularly in **distributed or asynchronous workflows where conditions may change between approval and execution**.

That gap is where a human-approved action executes under conditions that no longer hold — the approval was for a state of the world that has since changed. It is invisible in synchronous testing, because request time and execution time coincide there; it only appears once the tool call is queued, deferred, retried, or handed to another agent. Any architecture with durable tasks, queued tool execution, or long-running approval gates has this exposure by construction.
