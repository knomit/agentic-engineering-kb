# Memory- and skill-file poisoning is time-delayed by design, so session-scoped monitoring cannot see it — and it presents as a reliability bug

Snyk's **ToxicSkills** analysis found published skills that poison an agent's *persistent memory files* — `SOUL.md` and `MEMORY.md` are the named examples — producing time-delayed behavioural modification that persists across sessions. The **ClawHavoc** operation embedded social engineering in fake skill *documentation* to deliver obfuscated payloads; Koi Security's audit of that campaign additionally found reverse-shell backdoors that trigger **during normal use rather than at installation**, and skills that silently exfiltrate bot credentials out of configuration files.

HOW COMMON, which is the figure that decides whether this is a curiosity or a default assumption: OWASP records the ClawHavoc campaign as "~12% of 2,857 ClawHub skills found malicious in Feb 2026 audit". Roughly one in eight published skills in a single registry, in one audit. Note the frame before reusing it — that is a proportion of the skills AUDITED in one registry at one date, not a base rate for skill ecosystems generally, and the audit was targeted at a campaign already suspected. Even read conservatively it makes "scan the registry once at install" an untenable posture. The same disclosure line also names Claude Desktop extension RCE, so the campaign spanned skills and extensions rather than skills alone.

The attack shape, in OWASP's words: "An attacker poisons an agent's persistent memory through a single crafted interaction. Days later, when a user asks an unrelated question, the embedded instructions activate and achieve unauthorized actions long after the initial compromise. The agent treats its own memory as trusted context, yet an adversary can write to it through ordinary interaction channels."

Two consequences that change what you build:

- **Install-time scanning is insufficient when the trigger is normal use, and session-scoped anomaly detection is insufficient when the dwell time exceeds a session.** OWASP states it flatly: "Monitoring scoped to individual sessions will never detect it. The compromise persists silently across every future interaction." What is needed is diffing the agent's *persistent state* — memory files, installed skills, config — across sessions, treated as a monitored artifact rather than as agent-owned scratch space.
- **Triage will point you the wrong way.** A memory-poisoned agent behaving anomalously looks exactly like a reliability malfunction to the team watching in real time; only forensic analysis reveals the compromise. A team that treats it as a safety issue — restart the agent, check for drift, review the training data — "might miss the persistence mechanism entirely and get compromised again." The security response (hunt the initial access vector, analyse memory state, look for indicators of ongoing control) is the one that contains it.

Note the interaction with skill portability: skills are now published as a cross-platform open standard, so a poisoned bundle runs across harnesses with different sandboxing rather than being contained to one vendor.
