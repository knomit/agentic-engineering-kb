# A command allowlist accelerates the attack when the agent can influence its own execution environment — two CVEs, one shape

The intuitive containment for a coding agent is to sandbox it and restrict what it may run through an approved-command allowlist. Two disclosed CVEs show the control inverting.

- **CVE-2026-22708** (Cursor, disclosed January 2026): an attacker who can influence the agent's instructions "can silently poison the execution environment such that commands the user or allowlist has already approved, like git branch or python3 script.py, execute arbitrary code instead." OWASP's summary is the part worth keeping: "The allowlist does not fail to prevent the attack. It streamlines it, by auto-approving the very commands the attacker needs to trigger the payload."
- **CVE-2025-59532** (OpenAI Codex CLI, disclosed September 2025): "the agent's own output could redefine the sandbox's writable boundary, enabling file writes and command execution outside the intended workspace."

The shared structure, in the source's words: "controls calibrated for human operators become exploitable when the executor can influence its own containment." An allowlist encodes "this command is safe when a person types it"; the safety came from the person, not from the string.

What to design against:

- Evaluate an allowlist entry against the *environment it will run in*, not just the command string. A command name is not a capability.
- Allowlist growth is not a monotonic usability win. Every entry added to reduce approval friction enlarges the set of pre-approved triggers an environment-poisoning attack can fire.
- Anything the agent can write — environment variables, `PATH`, shell config, project config, the sandbox's own configuration inputs — is inside the allowlist's trusted computing base.
- Approval fatigue is better modelled as an attack target than as operational friction: the AI Agent Traps framework (Franklin et al., 2026) treats wearing down the human reviewer as a deliberate technique, not incidental noise.

This is the same class as the symlink-before-validate and defer-project-config rules already in the pack, arriving through a different door.

*** THE SENTENCE THAT GENERALISES IT PAST SECURITY. *** OWASP places these CVEs immediately alongside the Replit case, in which "an agent deleted a production database in direct violation of a code-freeze instruction", and then draws the line explicitly: "Replit's failure had no adversary, the CVEs required one, but the underlying permission architecture is the same."

That is worth more than either example. It says the allowlist's defect is not fundamentally an attacker problem — the same over-broad grant that an environment-poisoning attacker converts into code execution is what lets a confused agent destroy something on an ordinary Tuesday. So the case for tightening it does not depend on believing you have an adversary, and a team that has dismissed this class as a threat-model concern has also dismissed its own reliability incidents. Sizing the permission grant to the ACTION rather than to the command name pays in both failure modes at once.

**A third disclosed case, and it arrives from the opposite direction: the control was a DENYlist, and it failed the same way.** CVE-2026-65669 in SQL Copilot for SQL Server Management Studio enforced its read-only guarantee as "a regex-based classifier in the **LocalSqlExecutionAccessChecker** class", matching on the text of the statement about to run. T-SQL can name a callable at runtime, so the procedure name never appears at a call site: `DECLARE @p sysname='sp_who'; EXEC @p`. Nothing about the executor's environment had to be poisoned for this one; the language's own indirection was enough.

That widens the rule stated above. "A command name is not a capability" is not only about allowlist entries going stale against a mutable environment. Any control that reasons over the TEXT of what the agent is about to run is matching a spelling, and every language an agent drives usefully -- SQL, a shell, Python -- can spell the same action a way the matcher has not seen. The direction of the list does not help: an allowlist of safe spellings is bypassed by poisoning what a safe spelling does, and a denylist of dangerous spellings is bypassed by indirection. The control has to sit where the capability is granted, not where the string is parsed, which is why the researcher's own conclusion is phrased as a type claim rather than a tuning one: "Read-only enforcement for an AI agent must be a security invariant (like a permission), not a model instruction or a fragile SQL classifier."
