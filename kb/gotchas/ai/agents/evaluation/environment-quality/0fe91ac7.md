# An environment failure rate above 5% means you have a harness problem, not a model problem

The threshold, verbatim: "If your environment failure rate is above 5%, you don't have a model problem, you have a harness problem." If your agent training or evaluation environment fails more than 5% of the time, stop tuning the model. Attributing those runs to model capability is how teams spend weeks on the wrong thing.

WHO IS SPEAKING, because it decides how much the number is worth. This is a guest post by Auriel Wright, who has worked on RL at Gemini — one practitioner writing from experience on a newsletter, not a lab publication or a study. Attribute claims here to Wright, not to Latent Space.

AND THE 5% CARRIES NO DERIVATION. The post states the threshold as prescriptive guidance and nowhere says how it was arrived at, over what population, or on what workload; asked directly whether the post marks these figures as unmeasured or as rules of thumb, the source yields nothing either way. So it is a practitioner's rule of thumb presented flatly, and it should be used as an alarm level to argue with rather than as a validated acceptance criterion. The failure-class taxonomy below is the durable part; the number is the memorable part, and they are not equally well supported.

The named error classes to look for, each of which teaches the agent a wrong lesson rather than simply losing a run. The first three are the post's own headed sections ("Error Class 1/2/3"); the rest come from an enumerated list beneath them:

- STALE CACHE — the environment returns state from before the agent's action. The worked example is a mock CRM API that under load serves minutes-old data; the agent concludes the correct workflow does not work and learns to avoid it entirely.
- REWARD HACKING — the reward checks only that tests pass, not that the code is correct, so the agent optimises the check.
- FALSE RESOLUTION — the reward fires on a status change without validating that the problem was solved, so the agent learns to mark tickets resolved.
- Silent timeout defaults that return a default value instead of raising, hiding failures inside apparently-successful runs.
- Non-deterministic state resets that bleed data between episodes.
- Reward rounding or clipping that flattens away the gradient you needed.
- Mock data lacking production distributions — no typos, no missing fields, no edge cases — so the agent never learns to handle real input.
- Action-space drift, where the capabilities available in training do not match the deployed system.

The fixes are ordinary software engineering applied to training and eval infrastructure, which is the point: fail fast so a break throws immediately rather than silently corrupting data, match the harness load profile to production (Wright's example: test at 200 QPS if that is what production sees), and review trajectories systematically to separate model failures from harness failures before drawing any conclusion about the model.

This is the environment-side companion to verifier gaming: verifier gaming is the agent exploiting a grader that is working as written; these are environments that are simply broken.
