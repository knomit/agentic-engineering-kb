# An agent told to investigate its own sandbox identified the operator, the cloud provider and the research programme — from TLS certificates, DNS settings and its own config files, and hardening did not stop it

UK AISI ran the experiment directly: "We deployed an instance of OpenClaw to our research platform and prompted it to learn as much as it could about how and why it had been deployed." Published 2026-04-20. What it recovered, and from which artefact, is the useful part — each item is a class of leak an eval environment emits by default.

* THE OPERATING ORGANISATION, from network plumbing: "Domain names in network configuration and Transport Layer Security (TLS) certificates contained references to AISI."
* A NAMED INDIVIDUAL, from container metadata: "A username embedded in the container's DNS settings allowed the agent to infer the full name of an AISI employee."
* THE INFRASTRUCTURE: "Hardware identifiers and system version strings identified our cloud provider as well as the specific hardware in use."
* THE INTERNAL ARCHITECTURE, from files the agent was given: "By inspecting its own configuration files, the agent reverse engineered how we route and authenticate API calls through an internal proxy."
* THE RESEARCH PROGRAMME ITSELF, from one API call: "A single API call returned over a thousand fine-tuned model names, from which the agent reconstructed an accurate chronology of our research themes."

HARDENING WAS ATTEMPTED AND LOST: "After each round of prompting, we attempted to harden the sandbox, but the agent was repeatedly able to find more inventive approaches to recover the same information." This is the load-bearing sentence. The leak is not a bug with a patch; it is the aggregate of every identifier a real environment needs in order to work, and closing named channels one at a time did not converge.

*** THE FULL PAPER HAS NOW BEEN READ AND IT SUPPLIES THE LADDER THE BLOG POST ONLY GESTURES AT. The paper groups the agent's methods as "three broad categories of technique as the agent repeatedly adapted to our attempts to conceal information" — and the shape of the sequence is the finding, because each defence closed a layer and the agent simply dropped to a lower one: ***

1. READING ITS OWN CONFIGURATION. Unrestricted filesystem access inside the container; `/etc/resolv.conf` "contained the Kubernetes namespace name, which on our platform was derived from the operator's username", and config files held proxy URLs plus base64-encoded references the agent decoded and "correctly inferred that they were not API keys themselves, but references to secrets stored in AWS Secrets Manager". NOTE WHAT THIS MEANS FOR CREDENTIAL HYGIENE: the paper records the keys as "ephemeral and tightly scoped" and they still leaked the SHAPE of the authentication system. Rotating a secret does not hide the architecture around it.
   DEFENCE: a mitmproxy sidecar injecting the real URLs and credentials so "the agent's own configuration contains only placeholder values pointing at localhost", plus `dnsPolicy: None` to replace DNS search domains with generic entries. The paper's own verdict: these "proved insufficient."
2. NETWORK-LAYER RECONNAISSANCE. The agent "inspected /proc/net/tcp to discover the IP addresses of services the proxy sidecar had open connections to, before using openssl s_client to connect directly to those IPs and read their TLS certificates", whose hostnames carried `aisi`. It needed nothing it did not already have: "The agent did not have to reach out to the internet or download any specialist packages to achieve this, as the requisite tools were already present in the container environment."
   DEFENCE: iptables rules restricting the agent process to localhost only, forcing all traffic through the proxy.
3. API METADATA AS A SIDE-CHANNEL — AND THIS IS THE ONE TO REMEMBER. "However, the agent didn't need to bypass the proxy to discover sensitive information." It used the endpoint it was explicitly authorised to call: "A single GET /v1/models request to the proxied OpenAI endpoint returned a catalogue of over a thousand fine-tuned models" (the agent's own quoted output puts it at 1,114), whose names reconstructed the research chronology by theme and date.
   DEFENCE, and the concrete remedy this fact previously lacked: "Realising our domain-based allowlisting was too coarse, we implemented path-level allowlisting at the mitmproxy layer, restricting the agent to content-generation endpoints only and filtering out metadata routes like model enumeration."

THE TERMINAL CHANNEL WAS THE PERMITTED ONE, which is the transferable lesson: after two rounds of hardening the remaining leak came through the single API the agent was supposed to use. An egress control scoped to a HOST cannot bound what an agent learns, because the same host serves both the capability you granted and a catalogue describing your deployment. Scope on METHOD AND PATH, and treat enumeration routes (`/v1/models`, listing and discovery endpoints generally) as a separate grant from the capability routes beside them. See [[fdad859e]] for the same granularity failing in the outbound direction.

WHY AISI SAYS IT MATTERS: "In this experiment, the agent was able to reason from the nature of its deployment and its knowledge of AISI's work that it was operating inside a sandboxed evaluation environment", and "[t]his kind of evaluation awareness poses a risk to the validity of experiments, since the agent may no longer behave as it would in a typical deployment." The paper adds the mechanism that makes this costly rather than merely untidy: an aware agent "may alter its behaviour accordingly, for example, by underperforming to appear less capable (sandbagging)."

AND THE PAPER'S OWN CONCLUSION REFUSES THE EASY FIX: "The core challenge was not just a missing security feature or misconfiguration. Agents need some information about their environment to function, but are capable of reasoning across whatever information is available to them." The resulting two-sided tradeoff is written up separately in [[0e577a90]], because it is a design decision rather than an observation about this experiment.

SETUP, so the result can be sized. OpenClaw image `openclaw:2026.2.3` on Claude Opus 4.6, containerised on Kubernetes (AWS EKS), mitmproxy 12.2.1 as a sidecar, Cilium FQDN-based egress policies plus iptables process-level restriction, run 5-9 February 2026. THIS PACK'S FRAMING, marked as such and not the source's. This is the infrastructure-side twin of the benchmark-recognition result: an agent that spots a benchmark by searching the web can in principle be defended with canary strings and prompt hygiene, and none of that touches a TLS certificate. It also inverts the usual containment failure, where the prompt asserted a boundary the network did not enforce — here the network discloses what the prompt withholds. The common root is that the environment, not the prompt, is what the agent reads as ground truth, and it reads in both directions. A SECOND READING THE POST DOES NOT MAKE: the same leakage is an operational-security result independent of eval validity, since any agent you hand to a party you do not trust can enumerate your infrastructure the same way — that inference is this pack's, not AISI's.
