# Every remote call multiplies your test matrix by 5, and you cannot assume call N+1 works because call N did

A concrete multiplier from Amazon's Builders' Library, worth knowing before estimating agent test coverage. Single-machine Pac-Man: 10 test scenarios. The same logic distributed, with four calls to a remote board service each having five outcomes (POST_FAILED, RETRYABLE, FATAL, UNKNOWN, SUCCESS), needs 200. The multiplier is per call site, not per program.

The load-bearing part is the second clause. In single-process code, if a call to a collaborator succeeded, it is reasonable to assume the next call to the same collaborator will also work — they share fate. Across a network they do not: the remote side can fail independently between two calls in the same logical operation. So the failure cases must be tested at every call site, not once per dependency.

For agents this maps onto a real and under-tested gap. Agent evals overwhelmingly test the happy path plus a handful of hand-written error strings, then assert on the final answer. What goes untested is the state the agent is left in when a tool succeeds, then the NEXT tool call to the same service returns UNKNOWN or FATAL mid-task. That is where agents produce confidently wrong output: they have partial state, no signal that it is partial, and a strong prior toward continuing. Fault injection at each tool call site — not just at the first one — is what covers this, and it pairs with trajectory assertions rather than output-only scoring.

The article also notes why this is easy to defer: distributed bugs are latent. They can sit in production for months before the combination of conditions that triggers them occurs, so absence of incidents is not evidence of coverage.
