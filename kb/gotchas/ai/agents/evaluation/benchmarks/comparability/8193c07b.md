# The same model scores differently on the same benchmark across eval harnesses

A published benchmark number is a property of the model AND the harness that produced it, not of the model alone. The documented case: the same model gets significantly different MMLU scores under the HELM implementation, the EleutherAI implementation, and the original paper's implementation — differences arising from prompt formatting, answer extraction, and scoring choices rather than from anything about the model.

The practical rules that follow: never compare a number you measured to a number someone else published unless you ran the identical harness; when citing a competitor's or a vendor's benchmark claim, cite the implementation too; and when you build an internal eval, freeze the harness before you start tuning, because a harness change and a model change produce the same-looking delta on your dashboard.

This generalises past MMLU to agent benchmarks, where the surface area for harness divergence is larger still — scaffold, tool set, retry policy, and step limit all move the score, which is why agentic leaderboards separate native function-calling from prompt-based workarounds rather than pooling them.

**THE STEP LIMIT DOES NOT JUST MOVE SCORES — IT REORDERS RANKINGS. A measured case (OpenAI, 2026-08-10).** On ExploitBench, which tests developing a V8 vulnerability into a full exploit, the standard setting caps agents at 300 turns. At that cap GPT-5.6 Sol 'solves tasks more token-efficiently and performs best', beating the cyber-specialised GPT-5.6-Cyber. Raise the cap to 600 turns and 'the performance gap between the two models narrows'. Same models, same benchmark, same harness — one hyperparameter decides which model looks better and by how much.

Why this happens, and why it will keep happening: a turn cap does not measure capability, it measures capability per unit of budget. A model that reasons more verbosely or explores more branches is penalised by a tight cap and rewarded by a loose one, independent of whether it eventually solves more tasks. OpenAI's own footnote makes the confound explicit — the specialised model 'tends to be more extensive and comprehensive... in its reasoning budget, leading to higher token usage', so its comparisons are run at each model's highest reasoning level rather than at matched token cost.

What to do about it: treat the turn/step cap as a reported parameter of any agentic result, the way you would report temperature or context length — a score without its cap is not interpretable. When choosing between models, set the cap to your production budget rather than the benchmark default, because the benchmark default encodes someone else's cost tolerance. And when a vendor reports a win, check whether the cap was the vendor's own; a result stated at exactly one budget is a result you cannot extrapolate in either direction.
