# A harness-level model router governs the main thread only — subagents pick their own model, so the routed share of your traffic is not the share that costs the most

Reported by the team that built the router, as a known gap in their own deployment rather than as a measured loss: "Right now subagents pick their model independently of the router."

Routing implemented as harness middleware intercepts the model choice for the thread it wraps. A subagent spawned during that thread is a separate invocation and chooses its own model, so it is outside the router's scope by construction — nothing is misconfigured. In an architecture that delegates heavily, that unrouted path can carry more tokens than the thread that was routed, which makes the gap a cost problem rather than a tidiness one.

The operational consequence is a measurement discipline, and it applies to any control placed at the harness layer, not only routing: report the controlled and uncontrolled traffic separately. A saving measured on the routed thread and then stated as a saving on the run attributes to the whole system a change that only reached part of it — and the error grows precisely as delegation grows, so the figure looks best in the architecture where it is least true.

What this does NOT mean: the subagents are not unrouted because routing them is a bad idea. It is an unclosed gap in one implementation, and the generalisable point is that scope, not correctness, is what to check first when a harness-level control reports a smaller effect than expected.
