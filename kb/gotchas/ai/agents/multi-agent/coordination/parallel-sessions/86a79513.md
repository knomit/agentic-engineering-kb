# Parallel agent sessions on one repository do not know about each other, and the symptom is one session's test failing on a bug another session is mid-fix on — nothing notifies either of a stale base either

When a repository is worked by several isolated agent sessions at once, each with its own VM and branch, the sessions do not know about each other. The failure is not a merge conflict at the end; it shows up inside a session as a test failure whose cause is a defect another session is concurrently fixing, which the first session will then try to diagnose and work around. Separately, the agent is not notified about merge conflicts with the base branch, so a session whose base has moved keeps building on a stale tree until a human asks it to rebase.

Three practices follow, and they are about the division of work rather than about the agents. Split parallel tasks along file boundaries, so two sessions do not reason about the same code. Merge the branches in a deliberate order rather than all at once, and send the next session a follow-up after a merge lands so it starts from the new base. And ask for a rebase explicitly when the base has moved, because nothing in the loop will raise it.

What this does NOT mean: this is not an argument against running sessions in parallel, and it is not solved by giving the sessions a shared channel. The cost being avoided is a session spending turns on a symptom it cannot explain, and file-boundary partitioning avoids it at the planning stage, before any coordination mechanism would have to exist.
