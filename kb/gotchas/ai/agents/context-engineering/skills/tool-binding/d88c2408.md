# A tool bound to a skill does not exist until the skill is read — Deep Agents gates tool availability on read order, and the prompt-cache escape works only on models that accept new tools mid-conversation

A vendor post describing its own implementation; no evaluation is reported. A skill is a directory with a SKILL.md whose YAML frontmatter carries a name and description, plus optional scripts/, references/ and assets/ folders, disclosed in three stages: only names and descriptions in the system prompt, the full SKILL.md read when a task matches, and scripts or references loaded only when the instructions call for them.

THE BINDING, AND ITS ORDERING TRAP. Tools are no longer disclosed separately from skills: "List the tools in the skill's frontmatter under `metadata.include_tools`", and they enter context only after the agent has read that skill. The consequence is an availability rule, not a configuration one — "a call to it before then fails as an unknown tool." So the symptom of a mis-sequenced run is an unknown-tool error on a tool that is correctly configured and genuinely present. Labels may map to tool groups, and a resolver function can gate tools on runtime permissions such as user role, which means the same skill can expose different tools to different callers.

WHAT TO DO ABOUT THE FIRST MODEL CALL. Without intervention the model sees only descriptions and must spend a round trip reading a skill, with no guarantee it picks the right one. The application can detect an explicit user request — a slash command, say — and pass the skill in `pinned_skills`, so its instructions are in context before the first model call. The division of labour is the part to design around: Deep Agents does not parse messages, so the application defines the syntax and does the detection. Pinning is therefore only as reliable as the application's own request detection, and where there is none the model is back to choosing from descriptions alone.

LONG THREADS GO STALE BY DEFAULT. Skills were previously fixed for a thread's duration. "Setting skills_metadata to None makes the next run rescan the skill library", so a long-running thread picks up skills that were added, edited or deleted after it started. Without that, a thread outlives the library it was built from.

THE CACHE CONDITION, WHICH MUST BE STATED WITH ITS QUALIFIER. Adding tools mid-conversation normally invalidates the prompt cache. The escape is narrow: "on models that accept new tools mid-conversation, adding them keeps the prompt cache intact" — bound tools arrive through a new system message, and pinned skills as tagged messages, so the cached prefix does not change. On models WITHOUT that support, the tools are appended to the request, the prefix changes, and the cache is lost. Treat mid-conversation tool binding as a model-dependent optimisation, never as a property of the skills mechanism.

Two further costs that are easy to forget: a rescan that finds new skills changes the system prompt and so invalidates the cache as well (small for idle threads, since provider caches typically expire after inactivity anyway), and the whole discovery stage rests on each skill's name and description being distinguishable enough for the model to match a task to it.
