# Adding a skill can make routing WORSE before it makes it better — one deployment measured about a 20% drop in triggering, recovered only by writing negative examples and edge cases into the description

Making a skill available is not a monotonic improvement. In the one deployment with published numbers, "Glean saw this directly: skill-based routing initially dropped triggering by about 20% in targeted evals". It "recovered after they added negative examples and edge case coverage in descriptions" — not by rewriting the skill's procedure, and not by renaming it.

The mechanism this implies: a description that says only what the skill does competes with its siblings on similarity to the request, so a new description can capture requests that belonged to a neighbour and lose requests of its own to one. What the description has to carry is the decision boundary — when to use the skill, when NOT to, and the expected outputs and success criteria — which the source renders as an explicit "Use when vs. don't use when" block.

The operational consequences. First, measure triggering before and after you add a skill to a library, on prompts that belong to the NEIGHBOURING skills as well as to the new one; a before/after on the new skill's own prompts cannot see this regression. Second, when a workflow has a fixed contract and you do not want fuzzy routing at all, name the skill in the prompt ("Use the `<skill name>` skill.") and make the call explicit rather than tuning the description further.

The same deployment reports the upside once the description was fixed: "A Salesforce-oriented skill increased eval accuracy from 73% -> 85% and reduced time-to-first-token by 18.1%".

Scope and what this does NOT establish: both figures are one customer's results on their own evals, reported by their platform vendor, not a benchmark. The 73%-to-85% accuracy gain is attributed to having the skill, and the ~20% drop to skill-based routing before the description carried negative examples; the post does not report both measurements on the same eval at the same time, so do not state them as a single before/after curve.
