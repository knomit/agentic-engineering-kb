# An agent's persistent context has four stages with four different format rules — and every one of them fails silently

Six facts in this pack are about the SAME artifact — the context an agent carries across a session and across sessions — at four different points in its lifecycle. Read separately they give conflicting-sounding advice (be terse; be structured; never evict that; pin this). Read together they resolve into one rule per stage, and one property shared by all four that is the actually useful part.

STAGE 1 — WHAT ENTERS AT STARTUP. Only the selection surface should be resident. For Agent Skills that is literally enforced: level 1 loads ONLY the SKILL.md frontmatter name and description; the body loads when the agent judges it relevant, and bundled files load only when it decides it needs them. The rule that follows is that the DESCRIPTION is the entire selection surface — a skill with excellent content and a vague description costs resident tokens and never fires. Descriptions compete with their siblings, so lead with the distinguishing trigger condition rather than restating the name.

STAGE 2 — WHAT STAYS RESIDENT EVERY SESSION. Persistent instruction files load into every session, so length is a direct tax on attention. The counterintuitive failure: adding a rule to fix a behaviour can make the agent follow FEWER of your rules, because important ones are lost in the noise. Diagnostic: a rule being ignored means the file is too long, and the fix is deletion, not a stronger restatement; a question the file already answers means the phrasing is ambiguous. Per-line test: would removing this cause mistakes?

STAGE 3 — WHAT SURVIVES COMPACTION. Here the rule inverts from 'cut' to 'protect'. A tool_use message and its tool_result must NEVER be separated — most provider APIs reject the resulting message list outright, and any naive drop-oldest-N or keep-last-N-tokens scheme breaks this on the first eviction landing mid-pair. Prefer truncating oversized TOOL RESULTS over dropping messages, since that is where the tokens are while conversation structure is preserved. And pin the objective: pin metadata is written during the first reduction and persists through every later one, which is the simplest mechanism for keeping a system prompt or initial task statement alive across a long run. An unpinned objective is one summarization away from being paraphrased into uselessness.

STAGE 4 — WHAT THE AGENT WRITES BACK. Use JSON, not Markdown, for machine-maintained progress state: the model is less likely to inappropriately rewrite a JSON file. Note the scope precisely, because it looks like it contradicts the separate finding that JSON is an expensive format to emit, and does not. JSON as a container for STRUCTURED STATE the agent edits field-wise is cheap and the structure is what discourages wholesale rewriting. JSON as a wrapper around FREE-FORM TEXT OR CODE forces escaping throughout and is expensive. The discriminator is whether the model is filling in fields or serialising a body of text.

THE PROPERTY ALL FOUR SHARE, and the reason to hold them together: EVERY ONE OF THESE FAILS SILENTLY. A skill that never fires raises nothing. A rule lost in a long instruction file raises nothing — the agent simply does the thing you forbade. An objective paraphrased away by summarization raises nothing; the agent keeps working, on a subtly different task. A progress file rewritten wholesale raises nothing, and is discovered sessions later when the dropped items are noticed missing. None of these is an error condition, so none appears in error-rate monitoring or in output-correctness evals. They are found only by auditing the artifact itself.

WHAT TO DO WITH THIS — a per-stage audit, since no runtime signal will prompt you: (1) for each skill and tool, does the description state a distinguishing trigger condition, and does it actually fire on the tasks you expect; (2) for the resident instruction file, is every line load-bearing by the removal test; (3) does your compaction preserve tool pairs and pin the objective — test with a conversation long enough to actually trigger eviction, because short ones never do; (4) is machine-written state in a field-structured format, and does it still contain the items it contained last session.

HOW TO DECIDE WHAT GOES IN, AND WHEN TO TAKE IT OUT. To populate stage 2, mine your own transcripts for correction phrases ('can you also…', 'did you check…', 'still wrong') — each marks a point where the agent should have acted unprompted, giving a frequency-ordered backlog rather than a wishlist weighted toward yesterday's annoyance. This requires making corrections INSIDE the session so the transcript captures them. To prune it, treat every 'always', 'never', emphatic phrase, few-shot example and wrapper agent as stamped with the model it was written against: on upgrade the first experiment is DELETION, not addition, because scaffolding a model no longer needs does not merely become redundant, it consumes attention and constrains the output distribution.

WHAT THIS DOES NOT MEAN. Not an argument that less context is always better — instruction files still need what a model cannot derive from the code (bash commands it cannot guess, style rules that DIFFER from defaults, environment quirks, project-specific architectural decisions), and 'delete first' is a starting experiment rather than a guarantee. The countervailing direction from the same period is real: models now over-delegate to subagents without being prompted, so on some axes the tuning problem on a new model is damping behaviour rather than removing scaffolding. Nor is verification obsolete — an EXECUTABLE check the agent runs itself (test suite, linter, hook) remains the right mechanism and is unaffected; what has stopped paying is the PROMPTED request that the model re-read its own output. Stage-4 advice does not apply to human-facing files the agent reads but should not rewrite; those are fine as Markdown. Source-strength caveats carry: the ~80% prompt-reduction figure is a conference-talk summary of team practice, not published documentation, and its named exemplars (Fable, Opus 4.8) have been succeeded by Opus 5; the transcript-mining hit rate is one practitioner's unquantified self-report; the Strands defaults are one SDK's choices rather than universal constants; and Anthropic publishes no token budget or size cap for skills, so if you need a limit you must measure it.
