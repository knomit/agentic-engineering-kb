# Three shipped answers to context accumulation, and the deciding question is what each one DESTROYS — summarise, discard whole documents, or decouple the retrieval key from the value

Everyone agrees accumulated context has to be managed down. The three shipped approaches are usually compared on their headline numbers, which are all vendor-reported and not comparable. The useful axis is different and rarely stated: **each one destroys something different, and which loss you can tolerate is the actual decision.**

**WHY MANAGING IT DOWN IS NOT OPTIONAL.** Chroma's context-rot work found performance varies significantly with input length even on trivial tasks, across all 18 models tested — the assumption that the 10,000th token is processed as reliably as the 100th does not hold for any of them. Two specifics decide the design. First, a SINGLE topically-related distractor drops performance below the needle-only baseline, and four compound it; distractors are not uniformly harmful and the spread between them widens as context grows, so per-distractor behaviour cannot be averaged away. Second, degradation scales INVERSELY with query-answer semantic similarity, so real queries — which share little vocabulary with the answer — degrade much faster than needle benchmarks suggest. The consequence: **retrieval precision buys more than recall does. Passing everything and trusting a large window is a measured regression, not a neutral default.**

**THE THREE APPROACHES, BY WHAT THEY DESTROY.**

*Summarisation destroys the specifics.* Coarse-abstraction systems strip away the constraints, edge cases and numeric details that made the memory useful — the summary reads fine and has deleted the part you needed. This is the failure mode at one pole of Microsoft Research's abstraction/specificity framing.

*Document-level pruning destroys whole items and keeps the rest verbatim.* Chroma's Context-1 trains the search agent to DISCARD irrelevant results mid-search rather than compress everything. Their stated design position: unlike ReSum-style lossy summarisation it never rewrites evidence, and unlike MemGPT-style external paging it needs no memory tier — kept documents stay verbatim, discarded ones are simply gone. **If evidence fidelity matters — legal, finance, anything you must cite — prefer discarding whole documents over compressing all of them.**

*Key/value decoupling destroys nothing but adds an indirection.* Memora stops embedding the thing you want to retrieve: a 6–8 word primary abstraction is what gets embedded and searched, the full rich memory value is stored but NEVER retrieved through its own embedding, and cue anchors give alternative retrieval paths. Retrieval is policy-guided and iterative, expanding through cue anchors to surface **related-but-not-similar** memories — which pure embedding similarity cannot do, since it only ever returns things that look like the query. Note this directly targets the context-rot finding above: it is a response to retrieval degrading when query-to-target similarity is low.

The opposite pole is worth naming too, because it is the default people fall into: content-fragmentation systems (plain RAG over history, Mem0) preserve detail but produce brittle, isolated entries that lose narrative coherence — you retrieve the fact and still do not know the story it belonged to. Graph-based systems avoid both but require rigid ontologies that do not generalise across domains, so the maintenance burden lands on you, per domain.

**TWO IMPLEMENTATION DETAILS THAT MAKE THE PRUNING APPROACH WORK, and are easy to omit.** The agent works to a bounded budget (32,768 tokens in Context-1) under GRADUATED pressure rather than a single limit: usage is displayed after every turn, at ~24,000 tokens the system suggests pruning or concluding, and past that only pruning and concluding are permitted — the agent is told the budget continuously rather than discovering it by hitting a wall. And the training trick: pruning removes chunks from the model's view but PRESERVES the full unpruned trajectory for reward computation, crediting the agent for encountering relevant documents regardless of whether they survive. Without that separation the agent is punished for discarding a document that turned out to matter, and learns to hoard.

**WHAT THIS DOES NOT MEAN — carried from the sources, because each blocks a real misreading.**

- **The numbers are not comparable and mostly should not be planned against.** Memora is a single vendor research post that **states no limitations at all** — its only forward-looking items are future work, not conditions where the method underperforms — and a memory-system evaluation with no reported failure conditions and self-selected baselines is not a measurement to plan capacity against. Chroma sells retrieval infrastructure and Context-1 is their own model evaluated by them; treat the ensemble-beats-Opus claim as vendor-reported. In both cases the ARCHITECTURE is the transferable part.
- **Context-1 is not evidence that a small model suffices.** The UNTRAINED base gpt-oss-20b reaches 0.58 Final Answer Found at Difficulty 2+ against 0.95–0.99 for frontier models; the trained model reaches 0.88 and 0.97 as a 4x ensemble. The result is about task-specific RL training for context management, not parameter count — swapping in an off-the-shelf 20B model gets you 0.58.
- **Shortening context does not tell you which failure you avoided.** Long-context failures are model-specific and QUALITATIVELY different, not merely less accurate: copyright refusal, instruction non-compliance (summarising instead of answering), degenerate repetition, and plain wrong answers. An accuracy-only score conflates "refused", "summarised instead" and "answered wrongly", which have completely different fixes — classify failures by type before tuning chunk counts. The failure MODE also differs by family: Claude models abstain more and hallucinate less, GPT models produce confident incorrect answers, so the same distractor rate costs a visible non-answer in one and a silent wrong answer in the other.
- **There is no portable right number of chunks.** Retrieval recall itself saturates at very different points by CORPUS — 8k on Natural Questions but 128k on HotPotQA and FinanceBench — so the corpus, not just the model, sets where it saturates.
- **Every threshold cited here is model-vintage-bound.** The Databricks saturation points (~4k for Mixtral-8x7b-Instruct up to ~125k for GPT-4o and Claude 3.5 Sonnet) are mid-2024 models, several generations old; the context-rot roster tops out at Claude Opus 4 / Gemini 2.5 / o3. The mechanisms are about attention behaviour under length and are not version-bound; the numbers are. Re-measure before setting a context budget, and test one doubling beyond your intended maximum — both quantified failure curves roughly TRIPLE per doubling and pass 50% within two doublings of onset, so a mode sitting at 4–5% in your longest tested configuration is the visible start of a steep curve rather than a tolerable background rate.
- **These are combinable, not exclusive.** Nothing prevents decoupled keys over a corpus that a pruning agent then searches. The claim is only that each carries a distinct loss, and that choosing without naming the loss is how teams discover months later that their citations no longer resolve.
