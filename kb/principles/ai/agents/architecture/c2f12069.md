# Your durability substrate decides your multi-agent topology — an event log doubles as the shareable trace, a VM snapshot does not

Three of this pack's architecture facts prescribe durability, and two prescribe how much context a peer agent needs. Read together they entail something none of them states: YOUR CHOICE OF DURABILITY SUBSTRATE SILENTLY DECIDES WHETHER YOU CAN SHARE TRACES, AND THEREFORE WHAT MULTI-AGENT TOPOLOGIES ARE AVAILABLE TO YOU.

The chain:

1. An externalised, append-only EVENT LOG is one prescribed durability substrate — the session held separately from the brain and the hands, so a crashed harness reboots from the log via wake(sessionId) rather than losing the run. The stateless-reducer position arrives at the same artifact from the other direction: model the agent as (state, event) -> state with no hidden internal state, and pause/resume/human-escalation all fall out of the externalised state rather than each needing its own mechanism.
2. Agents that ACT need full agent traces, not individual messages, because every action carries implicit decisions and conflicting decisions produce work products that cannot be reconciled at integration time.
3. An append-only event log of everything the agent did IS a full agent trace. These are not two artifacts that resemble each other; they are the same object viewed by the recovery system and by a peer agent respectively.

THE CONSEQUENCE THAT FOLLOWS: if you build the event-log session for durability, you have already built the trace-sharing substrate that collaborating writer agents require. Multi-agent collaboration on writes becomes an access-control decision over an artifact you already have, not a new mechanism to design.

AND THE CONVERSE, WHICH IS THE PART THAT WILL SURPRISE PEOPLE: hypervisor-level SNAPSHOT-AND-RESUME does not give you this. Snapshotting captures memory, process trees, and filesystem so a session can shut down entirely across async gaps lasting minutes, hours, or days — and it is a genuinely different and in some ways stronger durability guarantee, since it survives arbitrary in-process state that no event log models. But a VM memory image is not readable by another agent. It restores ONE agent to ITS prior state; it conveys nothing to a peer. So a team that chooses microVM snapshots for durability has solved recovery and has NOT thereby acquired a shareable trace, and must emit the log separately if it later wants collaborating agents. Choosing snapshots is choosing a substrate whose recovery artifact is private by construction.

THE SECOND CONSEQUENCE, at the organisational edge: A2A's opacity principle has agents interact WITHOUT sharing internal memory, tools, or proprietary logic — a deliberate trade for cross-organisational trust and IP protection. Since the shareable artifact is the session log, the log's shareability boundary IS the trust boundary. Inside one trust domain, withholding the log is a self-inflicted wound and A2A's isolation buys nothing. Across trust domains the log cannot cross at any price, so the coordination risk that trace-sharing would have mitigated must instead be absorbed by narrow, verifiable task contracts and validation of returned Artifacts. Note the layering this sits in: MCP standardises agent-to-tool communication, A2A standardises agent-to-agent, and a system can and often should speak both — A2A outward to peer agents, MCP downward to its own tools.

WHAT TO DO WITH THIS: decide durability substrate and collaboration topology TOGETHER rather than in sequence. The common failure is to pick a runtime for isolation and async-gap survival, ship it, and then discover that adding a second writing agent requires an artifact the runtime never produced.

WHAT THIS DOES NOT MEAN. Not a claim that snapshots are the wrong choice — they answer a requirement event logs do not, namely surviving multi-day async gaps without burning compute to stay alive, and the security argument for hypervisor isolation over shared-kernel containers stands separately because agents execute untrusted model-authored code. The two are combinable; the claim is only that snapshot durability does not IMPLY trace availability. Nor does it mean every multi-agent design needs the full log: the sharing requirement applies to agents that WRITE. An advisor or reviewer agent should get the artifact and a clean context precisely because inherited trace length degrades its attention, so for read-only peers the log is the wrong thing to hand over. And the event-log design assumes the agent will need durable state, computation, and room to scale to multiple brains and hands — a short-lived single-sandbox agent gets very little from it for real added complexity.
