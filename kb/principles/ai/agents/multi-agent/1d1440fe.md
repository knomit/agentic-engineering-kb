# A reviewer agent errs in both directions, and its purpose decides WHICH — security reviewers are deliberately tuned to miss, quality reviewers structurally invent

Three shipped reviewer agents appear in this pack and they are architecturally the same thing: a second model inspects an artifact or a proposed action and returns a verdict. The useful finding is that **their error rates point in OPPOSITE directions, and the direction is set by what the reviewer is for — not by implementation quality.** A team that measures one direction and assumes the other is symmetric will misjudge the control.

**SECURITY REVIEWERS ARE DELIBERATELY TUNED TOWARD FALSE NEGATIVES.** The stated reason is that a noisy guard gets disabled and then protects nothing, so permissiveness is chosen on purpose:

- Goose's adversary mode instructs its reviewer to err on the side of ALLOW and block only clearly dangerous things. It also ships **fail-open** — a reviewer error allows the call through — and covers only two tools by default (`shell` and `computercontroller__automation_script`), leaving everything else unreviewed unless configured, which matters most for the MCP-server tools a user added later and never thought about.
- Claude Code's auto-mode classifier publishes both numbers: stage 1 is a single-token filter with no reasoning, deliberately tuned to over-block at an **8.5% false-positive rate**; stage 2 runs chain-of-thought only on what stage 1 flagged, cutting false positives to **0.4%** but at **17% false negatives** on genuinely overeager actions. A shipped, well-engineered classifier still misses roughly **one in six**.

The dominant miss is worth knowing because it is not a capability failure: Anthropic characterises it as the classifier correctly identifying the danger but misjudging CONSENT — "A similar action was approved earlier, but one approval isn't a pattern." **Do not build consent inference on top of single approvals.**

**QUALITY REVIEWERS ARE STRUCTURALLY BIASED TOWARD FALSE POSITIVES.** A reviewer prompted to find gaps will usually report some even when the work is sound, because that is the task it was given. The damage is not the report but what the loop does with it: chasing every finding produces extra abstraction layers, defensive code, and tests for cases that cannot occur — output that looks like diligence and is actually damage. **Any evaluator agent whose instruction is to produce findings has a non-zero base rate of findings on perfect input.**

**WHY THE ASYMMETRY IS NOT AN ACCIDENT.** The cost of each error type is reversed between the two uses. A security reviewer that fires too often gets switched off by its users, so its designers trade misses for quiet. A quality reviewer that fires too rarely contributes nothing, so its designers trade noise for coverage. Same architecture, opposite tuning, driven by which failure the operator will actually tolerate.

**WHAT TO DO WITH IT.**

1. **Calibrate in the direction your reviewer is NOT tuned for.** For a quality reviewer, run it against KNOWN-GOOD work and count what it invents — that is your false-positive floor, and it is not zero. For a security reviewer, the equivalent is adversarial testing for misses, because its published false-positive rate tells you nothing about its miss rate.
2. **Do not reuse a reviewer across the two purposes.** A security-tuned reviewer pointed at code quality will pass sound-looking bad work; a quality-tuned reviewer pointed at tool calls will block constantly and be disabled.
3. **Filter the return path.** The generator must filter evaluator feedback against the ORIGINAL USER INTENT before acting on it — without that filter the loop degrades into looping, scope creep, and the generator following the evaluator into work the user never asked for. An unfiltered evaluator-to-generator channel is where the pattern fails, not the review itself.

**THE CONTEXT RULE THAT MAKES QUALITY REVIEW WORK, and it inverts the usual instinct:** the evaluator must start from COMPLETELY CLEAN context — no shared briefing, no handoff of the generator's trace. The stated reason is context rot: the generator's context is long by the time the artifact exists, and inherited length degrades the reviewer's attention. This is the specific case where context isolation beats context sharing, and **it works BECAUSE review is read-only** — the evaluator contributes intelligence, never writes. Give it real tools rather than only the artifact (Anthropic's evaluator drove the running application through Playwright MCP and caught defects a diff read would not surface); an evaluator restricted to reading the diff can only find what is visible in the diff.

**WHAT THIS DOES NOT MEAN — carried from the sources, because each blocks a specific misreading.**

- **Not an argument to remove reviewers.** Every source keeps them. Cognition reports a coding agent plus review agent catching "an average of 2 bugs per PR, of which roughly 58% are severe", and Anthropic reports a single agent reliably overpraising its own work on subjective and objective judgments alike, producing "bland" output with stubbed features absent external evaluation pressure.
- **A security reviewer is a friction reducer, not a boundary.** Treat it as raising the cost of an attack and catching careless behaviour, not as the thing that makes an untrusted-content path safe. If the deployment has private data, untrusted content and an exfiltration channel at once, this control does not break the trifecta — it is another model that can be talked around, guarding a subset of calls, that defaults to yes when it breaks.
- **The quality reviewer's ROI is model-version-dependent and decays.** Anthropic measured the evaluator becoming "unnecessary overhead" at Opus 4.6 for tasks inside the model's native capability, cost-justified only at the BOUNDARY of it — against roughly a 20x price multiplier ($9 solo versus $200 for the three-agent harness on a 20-minute task). Re-benchmark on each model upgrade rather than treating the harness as permanent.
- **Tiering removes most of the question.** Claude Code's design keeps the classifier off the majority of actions entirely by tiering on reversibility: state-free tools are allowlisted, in-project file edits bypass the classifier because version control already makes them reviewable, and only shell, web fetches, external tools, subagent spawns and out-of-project writes reach it. If an action is cheaply reversible by an existing mechanism, that mechanism IS the control and re-checking it is pure latency. Note also what entering auto mode REMOVES: blanket shell access, wildcarded script interpreters and package-manager run commands are stripped from any pre-existing allowlist, so more autonomy means a NARROWER standing allowlist, not a wider one.
