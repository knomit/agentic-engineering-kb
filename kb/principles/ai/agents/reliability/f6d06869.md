# Granularity is the design variable for every agent resource control — a control at the wrong granularity turns a partial failure into a total one

Six of this pack's reliability facts come from different Amazon Builders' Library articles about ostensibly different mechanisms — bulkheads, circuit breakers, quotas, sharding, admission control. Read together they are all the same design decision made in different places, and all six failure modes are the SAME failure: the control was correct in kind and wrong in granularity, which made it worse than having none.

The pattern, stated once:

- CONCURRENCY LIMIT, global vs per-dependency. One service-wide limit prevents overload but not partial function — a slow dependency consumes the whole shared allowance and the service rejects work that never needed it. Per-dependency bulkheads confine the damage to the codepaths that use it.
- CIRCUIT BREAKER, service-level vs failure-domain-level. One breaker over a partitioned store lets a single hot partition trip everything: with 10 partitions you turn a 90%-available situation into a 0% one. Align the breaker with the dependency's real independent-failure boundary (for DynamoDB, the table, not the endpoint).
- LOAD SHEDDING, global vs per-tenant. Tenant workloads are uncorrelated, so an aggregate spike is almost always ONE tenant. Global shedding makes every well-behaved tenant pay for it.
- SHARDING, fixed vs combinatorial. Plain shards cut blast radius linearly (1/4 with 4 shards); shuffle shards cut it combinatorially (1/28 for the same 8 workers in shards of 2). Route 53's 2048 virtual name servers in shards of 4 give ~730 billion combinations, enough for a unique shard per customer domain.
- QUOTA ENFORCEMENT, fleet-wide vs per-server. Enforcing quota/N assumes uniform request distribution; connection-balancing load balancers and DNS-cached multi-balancer fleets break that assumption, and the client is throttled below its nominal quota exactly as it approaches the limit.
- INSTRUMENTATION, remote-call vs whole-codepath. Guarding only time spent inside the remote call misses retry sleeps and loop counts, so a limit reads healthy while the harness runs out of workers.

The generative question this gives you, to ask once per control: WHAT IS THE SMALLEST UNIT THAT FAILS INDEPENDENTLY HERE, and is my control placed at that unit or above it? Placed above it, the control samples a partial failure and reports a total one.

For agent platforms the units are concrete and usually available: per tool (or tool group) for concurrency, since an agent with N tools has N independent failure modes; per tenant or workspace for quotas, with units of agent runs, tool calls or tokens rather than HTTP requests; per sandbox/worker pool for placement, since a tenant workload that reliably wedges its executor is exactly the poison-pill case shuffle sharding was built for; and per whole codepath for instrumentation, because agent loops are inherently modal — a turn may take 1 tool call or 40.

A framework-level instance of the same error, from outside the AWS material: Goose subagents inherit the parent's full context and extensions BY DEFAULT, with tool restriction opt-in. The isolation boundary sits above the unit that should be isolated, so the safe-by-default assumption does not hold.

WHAT THIS DOES NOT MEAN: an imprecise control is still usually better than none. Amazon is explicit that a breaker misaligned with a partitioned dependency remains worth having, because with no breaker the overloaded partition exhausts the caller's concurrency and takes down requests that never touched that dependency at all — the prescription is to align granularity, not to remove the control while you work out where it belongs. Two further conditions carry from the sources and must not be dropped: shuffle sharding's guarantee is that an unaffected tenant retains SOME healthy workers, not all of them, so it requires fault-tolerant retrying callers and interchangeable workers; and quota/N is genuinely fine in practice when quotas are high enough that clients stay far from the ceiling. Finally, granularity trades against testability — Amazon's own rule is to use the simplest allocation that holds and add complexity only after testing or an incident proves it necessary, because more elaborate schemes are harder to instrument and their failure modes surface in production rather than review.
