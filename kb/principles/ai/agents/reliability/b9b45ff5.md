# When an agent underperforms, the prior should favour the harness over the model — five independent measurements say the infrastructure moves the score more

Separate sources, separate methods, same conclusion: the largest measured swings in agent performance come from the harness and its infrastructure, not from the model. The transferable rule is diagnostic ordering — when an agent underperforms, exhaust harness causes before concluding the model is the limit or reaching for an upgrade.

The measurements, each from a different source:

- RETRIEVAL LAYER. A Kubernetes task took 6,000+ seconds with local file access and 89 seconds with indexed code search. Same model, same task, different context infrastructure. Agents degrade systematically past roughly 400K LOC, and adding code-intelligence tools was worth +0.259 reward in the 400K-2M LOC band.
- RESOURCE ALLOCATION. Terminal-Bench 2.0 scores moved ~6 points across six resource configurations with model, harness and task set held constant. Below 3x headroom the movement is reliability noise; above it, resource limits were silently blocking the agent from invoking heavyweight tools at all.
- TRIAL ISOLATION. Shared state between eval trials produces correlated failures that read as a model regression.
- TASK SPECIFICATION. A task at 0% pass@100 is most often an ambiguous specification rather than a capability ceiling.
- ENVIRONMENT QUALITY. Above a 5% environment failure rate, the harness is the bug and tuning the model is the wrong work.
- CONTEXT MANAGEMENT. Chroma's Context-1 took a 20B base model to trajectory recall 0.640 to 0.739 and output recall 0.361 to 0.641 by training it to prune retrieved documents mid-search, and reports a 4x ensemble matching frontier models on retrieval.

The practical ordering this implies before upgrading a model or rewriting a prompt: (1) is the retrieval layer structural or lexical, and is the codebase past the scale where that matters; (2) does the agent have resource headroom, specified as a guaranteed allocation and a kill threshold that are two SEPARATE numbers; (3) is each trial or session environment genuinely fresh; (4) is the task specification unambiguous enough that a competent human could satisfy it; (5) what is the environment's own failure rate.

The same lesson holds outside evals in classical form: retry amplification (3 retries at each of 5 layers is 243x load on the bottom dependency) is a harness-topology property that no model change affects.

WHAT THIS DOES NOT MEAN: not a claim that model choice is unimportant — Anthropic's multi-agent work found the opposite on its axis, that upgrading the model beat doubling the token budget on the older model, and token volume explained ~80% of performance variance on BrowseComp. Both hold: model choice dominates where the bottleneck is reasoning capacity, harness dominates where the bottleneck is what the agent can see, reach, or be scored on. The claim here is about which to CHECK FIRST when diagnosing underperformance, because harness causes are cheaper to test and are the ones that masquerade as model incapability.

SOURCE CAVEAT, load-bearing: Sourcegraph sells code search and Chroma sells retrieval infrastructure, and both benchmarks are their own. The order-of-magnitude latency gap and the relative orderings are hard to explain away; treat the exact reward deltas and the 400K figure as vendor-reported and as an inflection point from one benchmark rather than a validated constant. The Terminal-Bench, trial-isolation and pass@100 findings are Anthropic's and are not vendor-interested in the same way.
