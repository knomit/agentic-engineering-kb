# When a model misuses a tool, the leverage is in the tool's interface, not in the prompt — and prompting harder is measurably negative-value

Four facts here point at one decision that gets made wrongly by default. When an agent uses a tool badly, the instinct is to strengthen the instruction. The evidence says to change the tool instead — and, separately, that strengthening the instruction now carries a measured cost rather than being merely ineffective.

**THE POSITIVE CASE — THREE INSTANCES OF MAKING THE MISTAKE UNREPRESENTABLE.**

- Anthropic's SWE-bench agent kept mishandling relative filepaths. Changing the tool to REQUIRE absolute paths fixed it outright, after which the model used the method flawlessly. The named principle is poka-yoke: rather than instructing the model harder, change the argument so the mistake cannot be expressed.
- A model missing a required parameter may invent a plausible value rather than ask. The stated defence is not a better prompt — it is to design the tool so an unspecified parameter is REPRESENTABLE (an explicit null, or an ask-the-user branch) rather than silently defaultable, plus validating arguments against something real before executing and requiring confirmation for consequential calls.
- Some formats are structurally hard to emit regardless of capability — diffs (which need line counts before the new code exists) and code embedded in JSON (which forces escaping throughout). The rule is to keep tool formats close to text the model has seen naturally occurring, not to instruct it to be careful.

Anthropic's own allocation is the strongest single data point: building that agent, they **spent more time optimising tools than optimising the overall prompt**.

**THE NEGATIVE CASE — WHY THE PROMPT LEVER HAS GOT WORSE, NOT JUST STAYED FLAT.** Emphatic instructions written to stop a weaker model under-using tools now push current models the other way: "CRITICAL: You MUST use this tool when…" overtriggers where plain "Use this tool when…" is correct, as do "If in doubt, use [tool]" and "Default to using [tool]". Appended self-verification instructions should be REMOVED on migration rather than reworded, because current models already verify their own work. And the Claude Code team cut their frontier-model system prompt by roughly 80%, specifically removing few-shot examples (the model "was just more creative than the examples we gave it"), "do not do X" directives (which leave the model arbitrating between your prohibition and the user's request), and instructions only 90% true (which teach the model that your rules have unstated exceptions).

**WHY THE WRONG CHOICE PERSISTS: THE TWO LEVERS HAVE OPPOSITE FAILURE SIGNATURES.** An under-triggering model gives a visibly lazy or wrong answer, so you notice and reach for a stronger instruction. An over-triggering one gives the RIGHT answer after four unnecessary tool calls and a long thinking block — it degrades as cost and p95 latency, not as an error. Nobody files a bug, so the prompt is never revisited and the interface fix is never considered.

**THE OPERATIONAL RULE.** When an agent misuses a tool, ask first whether the schema, the argument types, or the output format can make the mistake unrepresentable. Reach for the prompt only when it cannot. On a model upgrade, treat every emphatic phrase, few-shot example, "always" and "never" as a dated workaround stamped with the model it was written against, and try DELETING before adding.

**WHAT THIS DOES NOT MEAN — carried from the sources, because each blocks a specific misreading.**

- **Schema constraints are not a substitute for grounding.** Strict tool use guarantees the emitted call conforms to your JSON Schema and says nothing about whether the VALUES were grounded in the user's request — a hallucinated location is perfectly schema-valid. Interface design closes the *representability* gap, not the *truthfulness* gap.
- **The ask-vs-invent behaviour is tier-dependent and not guaranteed for any model.** Claude Opus is much more likely to notice a missing parameter and ask; Claude Sonnet might ask, especially if prompted to think first, or might infer. Behaviour degrades further with more ambiguous prompts and less capable models. So do not design an interface that depends on the model choosing to ask.
- **This is not an argument against verification generally.** An EXECUTABLE check the agent runs itself — a test suite, a linter, a hook — remains the right mechanism and is unaffected. What has stopped paying is the PROMPTED request that the model re-read and second-guess its own output.
- **"Delete first" is a starting experiment, not a guarantee that less configuration is always better.** The countervailing direction from the same period is real: current models over-delegate to subagents without being prompted, so on some axes the new-model tuning problem is damping behaviour rather than removing scaffolding.
- **Source strength varies across the inputs.** The ~80% prompt-reduction figure and the tool-optimisation-over-prompt-optimisation claim come from a conference-talk summary of team practice rather than published documentation, and its named exemplars (Fable, Opus 4.8) have since been succeeded by Opus 5 — do not quote that figure as current. The poka-yoke and missing-parameter findings are from Anthropic's published engineering and tool-use documentation respectively.

Note this is a different axis from the separate finding that a tool's cost is paid in SELECTION rather than capability, which is about how many tools to expose. This one is about the shape of the tools you have already decided to expose.
