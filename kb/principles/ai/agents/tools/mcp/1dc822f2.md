# Almost every MCP authorization control is contingent on a counterparty you do not operate — and the spec's failure defaults are inconsistent across them, so "we implemented it correctly" does not tell you what protection you have

Seven separately-sourced readings of MCP's authorization surface each name a limit on their own control. Counted together they show a property none of them states alone: **a conformant MCP client's actual security posture is set mostly by properties of authorization servers and MCP servers it does not operate — and the specification's default when the counterparty does not cooperate is NOT consistent across the controls.** Two fail closed, one fails open, and three are delegated to policy or to a human reading a screen. A team that has "implemented MCP authorization" therefore still does not know which protections it has; that is a per-counterparty enumeration, not a conformance property.

**THE LEDGER, with each control's own stated failure default. These are the sources' claims, not a generalisation over them.**

*FAIL CLOSED (2):*
- **PKCE support discovery.** Clients **MUST** implement PKCE *and* **MUST** verify support before proceeding, against authorization-server metadata, because OAuth 2.1 and PKCE define no discovery mechanism. If `code_challenge_methods_supported` is absent the client **MUST** refuse to proceed — absence is a definitive negative, not unknown. Note the unusual second half: MCP requires the field from OpenID Connect Discovery 1.0 providers **even though OIDC does not define it**, and makes its absence a hard stop, so a spec-conformant OIDC provider that omits it is unusable by a conformant MCP client. Dates from `2025-11-25`, not `2026-07-28`.
- **Authorization-server metadata issuer validation.** After retrieving the metadata document the client **MUST** check that the `issuer` inside it is identical to the issuer identifier used to build the well-known URL, and **MUST NOT** use the metadata on a mismatch. New in `2026-07-28`; the *probing* half that makes the check necessary shipped one revision earlier, in `2025-11-25`.

*FAILS OPEN (1):*
- **RFC 9207 mix-up defence.** Where the authorization server neither advertises `authorization_response_iss_parameter_supported` nor sends `iss`, the specified client action is **proceed** — unprotected. A general-purpose MCP client, which by design talks to many authorization servers it does not operate, cannot unilaterally obtain this control. It is also stacked on the previous one: the recorded issuer must come from a validated metadata document, and "it provides no protection if the expected issuer was obtained from an unvalidated source." A future revision is expected to upgrade server inclusion of `iss` from **SHOULD** to **MUST**; until then client rejection stays keyed on the metadata flag.

*DELEGATED TO POLICY OR TO A HUMAN (3):*
- **Localhost redirect-URI impersonation.** CIMD "proves control of a domain, but it cannot prove which local process is listening on a `localhost` redirect URI", so any local process can wear a legitimate client's name during consent, and "the server will see the legitimate client's metadata document and the user will see the legitimate client's name, making attack detection difficult." The authorization-server countermeasures are exactly three, and the modal split is the finding: **SHOULD** warn on localhost-only redirect URIs, **MAY** require additional attestation, **MUST** clearly display the redirect URI hostname. The only MUST is a display obligation; the measure that would actually attest the process is a MAY with no mechanism named. A client author cannot fix this in their client.
- **CIMD admission.** Because any HTTPS URL can be a `client_id`, the spec lists the range of trust policies — domain allowlists, accept-any-HTTPS, reputation checks, domain-age or certificate restrictions, prominent display of CIMD and client hostnames — and picks none. "Servers maintain full control over their access policies."
- **Choosing among multiple authorization servers.** One Protected Resource Metadata document can list several, each an independent OAuth 2.0 authorization server; clients **MUST** keep separate registration state per server and **MUST NOT** assume credentials port between them. But MCP states **no criteria for which to pick** — "beyond the scope of this specification", delegated to RFC 9728 §7.6. A security-relevant choice (it decides who issues your tokens) that every client will answer differently. Treat "we take the first entry" as the undocumented default it is.

**THE ONE CONTROL THAT IS FULLY YOURS, and it is worth noticing as the exception.** The client-side dereference bans are unconditional and depend on nobody: implementations **MUST NOT** automatically dereference `$ref` values resolving to a network URI, opt-in fetching **MUST** be disabled by default, and a schema failing to validate because of an unresolved external `$ref` **SHOULD** be rejected rather than silently treated as permissive. Same for `icons` — HTTPS or `data:` only, no credentials, magic-byte content sniffing, bounded size. These you can simply implement.

**WHAT TO DO WITH THE LEDGER.** Enumerate, per authorization server and per MCP server you connect to, which of the contingent controls that counterparty actually supplies — does it advertise and emit `iss`, does it publish `code_challenge_methods_supported`, does it warn on localhost redirect URIs, what is its CIMD admission policy. That list, not your conformance test, is your posture. Where a control is unavailable, the choice is to accept the exposure explicitly or to narrow which servers you will talk to.

**WHAT THIS DOES NOT MEAN — carried from the sources, because each blocks a specific misreading.**
- **Do not conflate the two mix-up defences.** Issuer validation of the *discovery document* fails closed (a mismatch is a MUST NOT); `iss` validation of the *authorization response* fails open. Two protocol layers, opposite failure modes, and a client can implement either without the other.
- **PKCE is not the general mix-up control.** "PKCE alone does not prevent this attack because the client transmits the `code_verifier` to the attacker's token endpoint." PKCE binds the code to the client, not to which server the client is talking to. Resource indicators also do not help when the attacker's authorization server intercepts before the honest one.
- **CIMD does not remove the confused-deputy precondition.** A static client ID shared across users remains one of that attack's four required conditions; CIMD makes the ID self-published rather than server-issued, not per-user.
- **The SSRF direction is now mutual, not merely inverted.** The client-side direction (client dereferences server-supplied discovery URLs) is the one people miss and still leads; but as of `2026-07-28` the spec states "SSRF risks are not limited to MCP clients" — an authorization server supporting CIMD fetches a URL supplied by an unknown client. The durable rule is that whichever party dereferences a URL supplied by the other is the target.
- **Version attribution is not uniform across these controls and matters for what you must support.** PKCE discovery and the endpoint-probing order date from `2025-11-25`; issuer validation, the RFC 9207 defence and the `$ref` ban are new in `2026-07-28`; `icons` dates from `2025-11-25`. Each source fact carries its own verification method and scope; this synthesis does not restate them.
- **The counting and the fail-open/fail-closed grouping above are this pack's.** The specification presents these controls in separate sections and never tallies their failure defaults against each other.
