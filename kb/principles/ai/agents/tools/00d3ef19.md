# A tool's cost is paid in SELECTION, not capability — which is why adding a better tool measurably makes agents worse below a scale threshold

Four measurements, three of them from the same benchmark family and one from a different team's practice, converge on a claim that inverts the default instinct to equip an agent generously: ADDING A CAPABLE TOOL HAS NEGATIVE EXPECTED VALUE UNTIL THE PROBLEM IS BIG ENOUGH, and the reason is that a tool's cost lands on SELECTION rather than on capability.

THE EVIDENCE THAT THE COST IS REAL AND MEASURED:

- A SIGNED THRESHOLD, not a diminishing return. Adding code-intelligence tools is worth −0.080 reward under 400K LOC and +0.259 in the 400K–2M LOC band. Below the threshold the tools do not merely fail to help; they make the agent worse. Scope this precisely: 400K is a reported inflection point from one benchmark, not a validated constant, and the exact deltas are vendor-reported — use it as the scale at which to start investing, not as a cliff.
- THE VENDOR SAYS IT AGAINST ITS OWN INTEREST. 'More tools sometimes made performance worse due to poor strategic usage', reported by the company selling the structured-search product being measured.
- AVAILABILITY IS NOT SELECTION. Across 1,281 scored runs, agents made 7,993 keyword-search calls against 2,449 semantic-search calls — roughly 3:1 toward grep even when better retrieval was available. Exposing a superior tool does not mean the agent uses it; the default lexical habit is strong.
- THE FAILURE HAS A NAME AND A SIGNATURE. Tool thrashing: one baseline run made 96 tool calls over 84 minutes with 6 distinct approach reversals (score 0.32); the same task with a structured search interface took 5 targeted calls in 4.4 minutes (score 0.68), 30% cheaper ($0.51 vs $0.73) and 38% faster on average. THE REVERSALS ARE THE TELL — an agent that keeps abandoning and restarting its strategy is signalling that its tools do not answer the question it has, and more turns will not fix it. Watch reversal count, not just call count.

WHY SELECTION IS THE BINDING CONSTRAINT. Every tool competes with its siblings for a selection decision the model makes under uncertainty, and every description is text the model must disambiguate against. So the marginal tool spends context and selection budget whether or not it is ever called. This is why the Claude Code team's rule is DISTINCTNESS rather than count — 'every tool we add has a distinct function from every other tool' — and why they removed grep and other dedicated search tools in favour of native bash: when the model can compose a shell command, a specific tool a general one already subsumes is not a convenience, it is another sibling.

THE TWO WAYS TO ADD CAPABILITY WITHOUT PAYING THE SELECTION COST:

1. LET A GENERAL TOOL ABSORB IT. Justify a new tool when no existing tool can do the job, not when an existing one could do it more awkwardly.
2. MOVE IT BEHIND A SUBAGENT BOUNDARY WITH ITS OWN CONTEXT. A purpose-built search service beat both alternatives on both axes — taking it as 1.00x, an agent with MCP tools ran 1.14x time / 1.63x cost and an agent with local search 2.19x time / 1.32x cost, at comparable result quality. The stated cause is division of labour: a component doing exactly one task issues more direct queries and returns DENSER output, while a general-purpose agent burns context on the mechanics. Note what this shows — the win comes from REMOVING the selection problem from the main loop, not from adding a tool to it.

IF YOU ADD ANYWAY, DIFFERENTIATE EXPLICITLY. Adding a retrieval tool without removing or clearly differentiating what it supersedes just gives the agent more ways to thrash. Make the superseded tool's description say when NOT to use it.

THE LEGITIMATE EXCEPTION, worth naming because it is the only one in these sources: a redundant tool can earn its place by making the agent's actions LEGIBLE to a human. Claude Code's dedicated file-edit tool survived not because bash could not perform the edit but so the client can render a dedicated UI for edits. If you keep a redundant tool, know which reason you are invoking — capability or legibility.

WHAT THIS DOES NOT MEAN. Not an argument for minimal tooling in general: above the threshold the same infrastructure is worth +0.259, and the multi-repo retrieval delta (+0.209 F1 versus +0.085 single-repo) says the benefit scales with how scattered the relevant code is. Not an argument that MCP is expensive — the MCP configuration was the FASTER of the two general-purpose options; what it paid for was generality. Not a claim that a specialist always wins: the result generalises to a narrow, HIGH-TRAFFIC capability that dominates the agent's trajectory, which is unusual enough to be worth measuring on your own hot path rather than assumed. Calibration caveats carry from the sources: the bash-absorbs-grep finding assumes a strong model in a SHELL-EQUIPPED harness, and an agent without shell access or on a weaker model does not get bash for free; the cardinality guidance is a conference-talk summary of team practice rather than published documentation; and Sourcegraph sells both the code search and the search product measured in three of these four inputs, so treat directions as credible and magnitudes as indicative.
