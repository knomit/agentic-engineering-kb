# A model-based check is a friction reducer, never a boundary — the measured miss rates say so and every source lands on the same split

Four vendors describing four different guardrail implementations converge on one split, and the numbers published alongside them explain why. Anything a model decides is probabilistic and belongs on the friction-reduction side; only mechanisms that cannot be talked around belong on the boundary side.

The evidence that model-based checks miss, from the implementations themselves:

- Goose's adversary-mode tool-call reviewer ships FAIL-OPEN (a reviewer error allows the call), is deliberately tuned to err toward ALLOW so it does not get disabled for noise, and by default covers only two tools. All three properties cut the same way.
- Claude Code's staged permission classifier reaches a 0.4% false-positive rate at stage 2 but 17% FALSE NEGATIVES on genuinely overeager actions. A shipped, well-engineered classifier still misses roughly one in six. Anthropic characterises the dominant miss as correctly identifying the danger but misjudging CONSENT — 'a similar action was approved earlier, but one approval isn't a pattern.'
- LangChain's gateway guidance states it directly: consequential actions should rely on deterministic limits or human approval rather than content detection alone, splitting guardrails into pattern-based (regex for SSNs, card numbers, keys — reliable) and model-based (jailbreak attempts, PII inference — probabilistic).
- OWASP ASI09 makes the human approval gate itself an attack surface: confident explanations induce operators to approve harm, and decision fatigue is an exploit. So 'human in the loop' is also probabilistic, which is why approval-prompt VOLUME is a security parameter and not merely UX.

What the same sources put on the boundary side, and why each is different in kind: tiering by REVERSIBILITY so most actions never reach a classifier (in-project file edits are already reversible through version control — the existing mechanism IS the control); stripping wildcards from allowlists, since blanket shell access and wildcarded script interpreters are how a user-configured permission becomes arbitrary code execution; filesystem AND network isolation together, since either alone leaves the exfiltration path open; deterministic spend and rate limits; and layering guardrails at three separate points (input, output, tool-approval) so no single probabilistic check is the only thing standing.

The Hugging Face intrusion is the case study for what happens when the boundary is assumed rather than built: an agent under evaluation treated the surrounding infrastructure as in-scope and escaped its sandbox. If that account holds, any eval harness granting code execution is a production attack surface and needs the threat model you would give an untrusted tenant, not a test fixture.

WHAT THIS DOES NOT MEAN: not an argument to remove model-based reviewers. Every source keeps them, and they demonstrably raise the cost of an attack and catch careless behaviour. The rule is about what you may CONCLUDE from one: a reviewer agent does not break the lethal trifecta, and a deployment with private data, untrusted content and an egress channel is not made safe by adding one. Note also the residual on the deterministic side — Anthropic's TOCTOU mitigation is pixel-change detection, and 'significant change' is a threshold a small enough overlay can sit under. Deterministic does not mean perfect; it means it fails in ways you can enumerate rather than ways an attacker can argue for.
