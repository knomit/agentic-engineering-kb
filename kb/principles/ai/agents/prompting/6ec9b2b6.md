# Prompt and harness scaffolding is model-version-stamped: on upgrade, try deleting before adding

Four independently sourced facts in this pack point the same way: scaffolding added to compensate for a weaker model does not merely become redundant when the model improves — it becomes actively harmful. The corrective is directional and worth making a standing rule: on a model upgrade, the first experiment is DELETION, not addition.

The converging evidence:

- SYSTEM PROMPT LENGTH. The Claude Code team maintains different system prompts per model, cutting roughly 80% for frontier models while keeping fuller instructions for older ones. They specifically removed few-shot examples (the model 'was just more creative than the examples we gave it'), 'do not do X' directives (which force the model to arbitrate between your prohibition and the user's request), and instructions only 90% true (which teach the model that your rules have unstated exceptions).
- EMPHATIC PHRASING. 'CRITICAL: You MUST use this tool when…' now overtriggers where plain 'Use this tool when…' is correct. Appended self-verification instructions should be REMOVED on migration rather than reworded, because current models already verify their own work.
- EVALUATOR HARNESSES. Anthropic measured a generator-plus-evaluator loop becoming 'unnecessary overhead' at Opus 4.6 for tasks inside the model's native capability, remaining cost-justified only at the boundary of it — against a roughly 20x price multiplier ($9 solo vs $200 for the three-agent harness on a 20-minute task).
- INSTRUCTION FILE LENGTH. A bloated persistent instruction file causes the agent to follow FEWER rules, because important ones are lost in the noise. The diagnostic is that a rule being ignored means the file is too long, and the fix is deletion rather than a stronger restatement.

The unifying mechanism is that scaffolding consumes attention and constrains the output distribution. When the model needed the constraint, that trade was worth it. When it no longer does, you are paying attention budget to make the model worse.

The operational rule: treat every 'always', 'never', emphatic phrase, few-shot example, and wrapper agent as carrying an implicit stamp naming the model it was written against. On upgrade, re-benchmark each one rather than migrating the configuration wholesale.

WHAT THIS DOES NOT MEAN: this is not an argument that prompts should be minimal in general, nor that verification is obsolete. The sources are explicit on both limits — an EXECUTABLE check the agent runs itself (a test suite, a linter, a hook) remains the right mechanism and is unaffected; what has stopped paying is the PROMPTED request that the model re-read and second-guess its own output. Likewise the evaluator loop still earns its cost at the boundary of a model's capability, and instruction files still need the content a model cannot derive from the code. Note also the countervailing direction from the same period: models now over-delegate to subagents without being prompted, so on some axes the tuning problem on a new model is damping behaviour rather than removing scaffolding — 'delete first' is a starting experiment, not a guarantee that less configuration is always better. Source-strength caveat: the ~80% figure and the tool-cardinality reasoning come from a conference-talk summary of team practice rather than published documentation, and the named exemplar models (Fable, Opus 4.8) have since been succeeded by Opus 5, so do not quote that figure as current.
