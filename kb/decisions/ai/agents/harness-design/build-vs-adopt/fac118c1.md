# Adopting an existing agent harness splits ownership at a stated line — the harness owns the loop, sandbox and approval policy; the host app owns interface, context and records — and the open-source part is the harness and integration surface only

The build-or-adopt question for an agent runtime is usually argued on effort. OpenAI's own framing argues it on ownership: "If you are building software that needs an agent, you can start with Codex instead of inventing a new runtime." What you give up and keep is drawn explicitly — the harness enforces sandbox and approval policy, while the host application keeps its interface, its context, and its records; hosts still decide where agents run, which files and tools they can reach, which actions need approval, and how results return to records.

THE INTEGRATION SURFACE HAS THREE SHAPES, and picking the wrong one is the usual mistake: `codex exec` for bounded non-interactive jobs such as scripts and CI; the SDK for programmatic workflows; and the app-server for anything with a persistent conversation. "With Codex app-server, we expose those capabilities through a documented client protocol:" — "applications can create threads, start turns, receive events, and handle approval requests." That last clause is the one that matters for a product with a human in the loop: approval requests arrive as protocol events the host renders, so the approval UX is the host's and the approval POLICY is the harness's.

THE BOUNDARY OF THE OPENNESS IS STATED, AND IT IS NARROWER THAN "OPEN SOURCE" SUGGESTS: "The open-source layer is the harness and integration surface; model access and managed services remain separate." So adopting the harness removes the runtime from your build list and does not remove the vendor from your dependency list — you can self-host the loop and still require the vendor for inference.

WHAT THIS DOES NOT MEAN. Published open source does not tell you the licence, the authentication model or the rate limits, none of which the source states. And a worked example in the same post gates consequential writes behind a human — one integration "requires human approval before a shipment is rebooked" — which is an illustration of the host exercising the harness's approval mechanism, not evidence the harness blocks such writes by default.
