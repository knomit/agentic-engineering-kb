# Fan-out is the architecture where prompt caching helps least — each new context window starts a cold prefix, so multi-agent costs more than its token multiplier implies

Two established facts in this pack, combined, produce a cost consequence neither states. Flagging up front that the combination is a DERIVATION from the mechanisms both sources describe, not a measured result — no one has published the measurement.

THE TWO INPUTS. First, for a single-threaded agent the dominant cost term is cache reads on a growing prefix, not fresh input or output tokens — which is why IBM Research measured Claude Sonnet at $79 total over 417 AppWorld tasks against GPT-4.1's $155, nearly double, despite GPT-4.1 having the lower per-token list price. Second, the orchestrator-worker architecture wins by buying a way to spend MORE tokens in parallel ACROSS SEPARATE CONTEXT WINDOWS, not by reasoning better — multi-agent research systems run ~15x the tokens of a chat interaction, and on BrowseComp token volume explained ~80% of performance variance.

THE DERIVATION. Separate context windows means separate prefixes, and a fresh prefix is a COLD cache. So the tokens a fan-out architecture adds are disproportionately billed at full input rates rather than at discounted cache-read rates, while the tokens a single long-running agent adds are disproportionately cache reads. Two consequences follow:

1. A token multiplier understates the cost multiplier for fan-out. If you budget a 15x architecture by multiplying your current spend by 15, you will underestimate, because your current spend is cache-weighted and the new spend is not.

2. A model's cache-read advantage does not transfer to fan-out. The specific reason Sonnet beat GPT-4.1 on total cost — cheaper cache reads on a replayed prefix — is weakest in exactly the architecture that keeps starting new prefixes. So a model-selection decision made by measuring a single-threaded agent should not be assumed to hold once you fan out; re-measure per architecture.

This gives an independent cost argument for an ordering the sources already recommend on capability grounds: max out model choice before reaching for multi-agent. Anthropic separately found that upgrading the model beat doubling the token budget on the older model.

WHAT THIS DOES NOT MEAN, carried from both sources because each blocks a real misreading. It is NOT an argument against multi-agent — the deciding variable remains whether the second agent WRITES: agents that act need maximal shared context and serialized writes, agents that only advise do better with isolated context and a filter on the return path. It does not license routing decisions made from a pricing page in either direction; the portable finding is that you must measure end-to-end cost per COMPLETED task on your own workload, not price-per-token and not estimated task difficulty. The IBM router's headline 21% cost and 9% latency reductions for a 4% accuracy drop are vendor-reported by the authors of the router being evaluated, so lean on the $79-vs-$155 comparison instead. The small-capability-gap constraint on model pairing is separate and still binds — Cognition's SWE-1.5 primary with a Sonnet 4.5 consultant FAILED because 'the quality ceiling was set by the primary, and the primary wasn't strong enough', so a large gap defeats the pattern rather than justifying it on cost. And the +90.2% multi-agent figure is anchored to superseded model generations and should be read as a point-in-time result. Finally, note this reasoning assumes provider pricing that discounts cache reads relative to fresh input; a provider without that discount, or a workload whose prefix churns every turn anyway, does not have the asymmetry this fact is about.
