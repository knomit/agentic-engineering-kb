# Put the model router in the harness and decide once per thread — prompt-cache lifetime, not model quality, is what decides whether mid-thread re-routing is worth it

One team's account of routing on its own open-source coding agent; the authors call the result a foundation rather than a finished optimum, and the findings are scoped to their traffic.

PLACEMENT. "We believe that routing decision belongs in the agent harness, not a generic gateway." The reason is informational rather than architectural fashion: the criteria that decide a tier depend on the agent's own prompts, tools and task mix, and a generic gateway does not hold any of that. The router is implemented as middleware that swaps the model without changing the rest of the agent, and the tier interface is kept model-agnostic so that replacing a tier as better models appear is a small change.

THE PROCEDURE THEY USED, in order: classify historical threads by task type, using cost and turn count as rough complexity proxies; pick a few models along the cost-versus-intelligence frontier spanning fast, balanced and performance tiers, from different providers; have a classifier read the thread's first human message and choose a tier, with a base prompt telling it to pick the least expensive model likely to complete the task and a short plain-language description of the work each tier should handle; then A/B against a single-model baseline on live traffic. The first classifier was an LLM with structured output and was later moved to a faster dedicated decision model.

ONE DECISION PER THREAD, AND THE CONDITION THAT DECIDES IT. The model is chosen at the start and kept. What rules out mid-thread re-routing is not quality but warm state: "switching models throws it away, so the new model re-reads the thread at full price." The authors note this cost is often small for async agents, whose cache lifetimes are short anyway. So the tradeoff turns on how long your prompt cache actually lives, not on how much better the other model is — and for an interactive agent with a long-lived warm cache the same arithmetic points the other way. The accepted cost of deciding once is that a thread which changes topic or complexity keeps its original tier.

MEASUREMENT, WHICH IS WHERE THE INTERESTING CHOICE IS. Offline evals were judged hard to grade for a coding agent, where PR quality and reviewability are what matter, so the router was judged on live traffic instead: "Merged PRs per thread became our main success metric." Live A/B exposes some users to a possibly weaker router, which is the price. Sparse user feedback nonetheless surfaced routing mistakes the aggregate did not — engineers flagged low quality in a fast-tier-only control quickly enough that the test was ended early (under-routing), and separately objected to simple requests going to the strongest model (over-routing).

WHAT THIS DOES NOT MEAN. It is not a claim that gateway-level routing is wrong in general. The part that does not transfer is the CRITERIA: they were written from this agent's own task analysis plus provider guidance, they are tied to its task set, and the full criteria text is not published. General benchmark scores are a starting point only, because they do not reflect a specific agent's task mix — and because new models move the cost-quality curve, the tiers need periodic review rather than one-time tuning.
