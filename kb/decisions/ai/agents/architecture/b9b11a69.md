# There are exactly two answers to 'the execution environment can die' — move the loop out, or make the environment resumable — and each forfeits something the other keeps

Every agent that executes code faces the same fact: the environment running that code can be rescheduled, time out, lose its network, be suspended, or crash. Four sources answer it, and they split cleanly into TWO strategies that are not variations on each other. This is a decision to make deliberately, because each forfeits something the other keeps, and the forfeit shows up late.

STRATEGY A — MOVE THE LOOP OUT OF THE THING THAT CAN DIE. Three independent sources reach this from three different motivations, which is what makes it worth naming:
- Anthropic's Managed Agents separates BRAIN (model plus harness), HANDS (sandboxes, tools) and SESSION (append-only event log). A failed harness reboots from the log via wake(sessionId); a failed container is simply replaced. The stated prior problem is that engineers could not distinguish a harness bug from a network fault from a container crash. Reported side benefits: time-to-first-token p50 down ~60% and p95 down over 90% (stateless brains stop blocking on container provisioning), and credentials move out of the container that executes untrusted model-generated code.
- Anthropic's sealed-VM tier reaches the SAME placement from the opposite direction: the agent loop goes OUTSIDE the VM and code execution stays inside, explicitly for reliability, because a VM that can be suspended, lose its network, or be rebooted is a bad host for the orchestration loop that has to survive those events.
- The 12-factor stateless-reducer position gets there from testability: model the agent as (state, event) -> state with no hidden internal state, and pause, resume and human escalation all fall out of the externalised state rather than each needing its own mechanism. Human escalation becomes just another tool call, inheriting the same logging, retry semantics and resumability.

STRATEGY B — MAKE THE ENVIRONMENT ITSELF RESUMABLE. Cognition's answer is hypervisor-level snapshots capturing memory, process trees and filesystem, so a session shuts down entirely while idle and resumes exactly where it left off. Their motivation is the one Strategy A does not address well: real engineering work has ASYNC GAPS — waiting on a CI run, a code review, a human decision — lasting 'minutes, hours, sometimes days', and without snapshotting an agent survives those only by burning compute to stay alive.

WHAT EACH FORFEITS:
- Strategy A forfeits arbitrary in-process state. An event log models what you chose to emit; a memory image survives everything, including state no log captures.
- Strategy B forfeits a peer-readable artifact. A VM memory image restores ONE agent to ITS prior state and conveys nothing to another agent — so snapshot durability solves recovery WITHOUT producing a shareable trace, and a log must be emitted separately if collaborating writer agents are wanted later. (Developed at length in the separate fact on durability substrate and topology.)
- Strategy B also carries a build cost stated plainly by its own advocate: the snapshot layer was the single most time-intensive piece of infrastructure they built, on top of a year of hypervisor engineering, with orchestration alone consuming over three quarters of engineering time to run thousands of concurrent VMs — and one company abandoned the effort when the combined surface area became untenable. Read that as a build-versus-buy signal.

THE COST THAT ARRIVES WITH STRATEGY A AND SURPRISES PEOPLE: once the loop is outside and execution is sealed inside a VM, HOST ENDPOINT DETECTION GOES BLIND. The isolation protecting the host also removes your monitoring of what the agent did inside it. The current mitigation is pull-based OTLP exports for AFTER-THE-FACT log retrieval — note 'after-the-fact': you have traded live detection for forensics. Budget for replacing that visibility rather than assuming the VM subsumes it.

THE PRACTICAL RULE: decide loop placement from whether your workload has async gaps and whether you will ever want a second writing agent — not from isolation requirements alone. The common failure is picking a runtime for isolation, shipping it, and then discovering it never produced the artifact the next requirement needed.

WHAT THIS DOES NOT MEAN. The two strategies are COMBINABLE, not exclusive as implementations — the claim is that each alone leaves a specific gap. Neither is a security argument on its own: hypervisor isolation over shared-kernel containers stands separately and for its own reason, that containers sharing a kernel mean one compromised session can reach every other container's filesystems, credentials and network connections, which matters precisely because agents execute untrusted model-authored code. And the decoupled event-log design explicitly assumes the agent will need durable state, computation, and room to scale to multiple brains and hands — a SHORT-LIVED SINGLE-SANDBOX agent gets very little from either strategy for real added complexity, and should do neither. Vendor caveat: the Cognition customer figures (Itaú, 17,000 engineers, 11 months: migrations 5–6x faster, 70% of static-analysis vulnerabilities auto-remediated, test coverage 2x) are vendor-reported and uncontrolled, as are the Managed Agents latency numbers.
