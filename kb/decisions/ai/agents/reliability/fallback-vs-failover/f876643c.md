# Amazon almost never uses fallback — which puts it against the standard 'fall back to a cheaper model' agent pattern, and the deciding condition is whether the path is exercised continuously

Amazon's Builders' Library distinguishes four strategies for critical failures, and the distinction is the whole argument:
- RETRY — do the same activity again, immediately or after a delay.
- PROACTIVE RETRY (hedging) — do it several times in parallel, take the first to finish.
- FAILOVER — do the same activity against a DIFFERENT COPY of the endpoint.
- FALLBACK — use a DIFFERENT MECHANISM to achieve the same result.

Amazon states it almost never uses fallback. Their five reasons: it is hard to test (the failure modes that trigger it, like overload, are hard to replicate, and the combinatorics explode); the fallback can itself fail, so it improves the odds rather than guaranteeing anything; it frequently makes the outage WORSE, increasing both scope of impact and recovery time; it is often not worth the risk, because the fallback must be making some tradeoff or you would use it all the time; and its bugs are latent, surfacing months or years after launch when nobody remembers the code.

The argument that generalises best is the self-contradiction one, stated about their own cache/database outage: if querying the database directly were more reliable than going through the cache, why have the cache at all? A fallback path is by construction the path you decided was worse. Invoking it at the moment things are already breaking means entering an untested mode during the most chaotic moment.

WHY THIS IS A LIVE DISAGREEMENT FOR AGENTS. 'Fall back to a cheaper or different model when the primary is rate-limited or down' is close to universal advice in agent engineering, and it is textbook distributed fallback — a different mechanism, not a different copy. Under Amazon's reasoning it carries every listed hazard, and one more they do not face: the fallback model is not merely slower, it behaves DIFFERENTLY. Different tool-calling accuracy, different instruction-following, different sensitivity to a prompt tuned on the primary. So the untested mode you enter mid-incident is untested in behaviour, not just in plumbing, and the failure will be silent — wrong tool calls and degraded answers, not errors.

WHAT DECIDES IT. Amazon's own resolution is not 'never have a second path', it is CONVERT FALLBACK INTO FAILOVER by exercising it continuously in production: run both paths all the time and treat both as equally valid sources of data — their suggestion is randomly choosing between the two responses when both return. Once the secondary path carries real traffic continuously it is no longer a fallback and no longer carries the latent-bug risk.

So the condition is exercise, not architecture:
- Secondary model serving a steady share of production traffic, with its quality measured on the same evals — legitimate failover, keep it.
- Secondary model that only activates on primary failure and has never served real traffic — fallback, and the pattern Amazon would remove. Either promote it to continuous traffic or delete it and spend the effort on primary reliability.

Their listed alternatives to fallback, in preference order: improve the reliability of the primary path (they cite moving to a higher-availability datastore rather than writing failover logic between two); let the CALLER handle the error by retrying, which is why AWS SDKs ship default retry policies; and push data proactively so there is no remote call to fail — IAM roles for EC2 push signed credentials to every instance valid for many hours, so a disruption of the push mechanism does not break requests. The agent analogue of the last one is preloading context, tool definitions and policy into the worker rather than fetching them at inference time.

This composes with the correlated-failover hazard recorded separately: a fallback is not only untested, it also receives the entire primary load at once, since whatever knocked out the primary knocked it out for every client simultaneously.
