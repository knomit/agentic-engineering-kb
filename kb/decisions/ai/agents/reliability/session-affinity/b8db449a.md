# Three credible sources disagree on session affinity — and MCP's answer (delete the state) is the one that names the real condition

Three credible sources take three different positions on binding a client to a backend, and the disagreement is live rather than resolvable by picking the newest.

- **Azure (pin, and fail loudly):** for stateful model APIs the gateway MUST route a conversation back to the backend holding its history, and when that backend is unavailable it should return HTTP 429 rather than silently reroute to an instance with no history. Rerouting hides the failure instead of handling it.
- **Anthropic (pinning concentrates harm):** in the Sept 2025 postmortem, sticky routing turned a defect present on ~16% of requests into roughly **30% of users affected**, because an unlucky client stayed stuck to a bad backend for its whole session. Affinity converts a per-request defect rate into a much higher per-user one.
- **MCP `2026-07-28` (remove the state):** the protocol deleted sessions outright (SEP-2567). Servers needing cross-call state mint explicit handles passed as ordinary tool arguments; list endpoints no longer vary per connection; deployments load-balance without affinity at all.

**These are not actually in conflict — they are answers to different questions, and the condition that separates them is whether the state can be made explicit and addressable from outside the connection.**

- If state is *implicit* in a backend's memory (a thread the vendor's API holds for you, a warm in-process cache you cannot name or move), you have no choice: pin, and follow Azure — the state is only reachable through that one instance. Then accept Anthropic's consequence and instrument for it.
- If state can be made *explicit* — a server-minted handle, a conversation ID, an event log the next instance can load — MCP's move is available and strictly better: delete the affinity requirement rather than engineering around it.

**The operational corollary holds under every one of the three.** Wherever you do pin, the pin is also your blast-radius boundary, so per-request defect rates stop being the honest denominator: measure defect rates **per session or per user**, because affinity is precisely the mechanism that decouples the two. A dashboard reading 16% while a third of users are affected is not a monitoring bug — it is the expected reading of the wrong denominator.

Do NOT read this as "stateless is always right." Making state explicit has its own cost, priced in the same MCP revision: handles in tool arguments are model-visible and injection-reachable, and losing transport resumability moves at-least-once delivery onto the application.
