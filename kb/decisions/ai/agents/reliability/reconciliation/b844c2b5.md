# Level-triggered reconciliation is self-healing by construction; an edge-triggered workflow has to have self-healing built into it

The structural difference, stated plainly by Amazon. A constant-work system re-applies the FULL desired state every cycle, so it starts from a clean slate each pass and is permanently in 'repair everything' mode. A configuration file truncated by a network glitch is fixed on the next pass. A node that missed an update entirely just gets the next one, with no backlog. Nobody wrote repair logic; the repair is the normal operation.

An EDGE-TRIGGERED workflow system — a change becomes an event, the event drives actions — has none of that for free. The change must first be DETECTED, the actions often have to occur in a correct sequence, and every case where an action fails or leaves transient corruption needs its own explicit handling. It also accumulates backlogs, because the events are conserved. The article's summary is the line to remember: workflows are not naturally self-healing, you have to make them self-healing.

The decision for agent systems, where both shapes are common:

- Choose LEVEL-TRIGGERED (re-read and re-apply the whole state each loop) for anything whose correct state is a function of current inputs and is cheap to recompute: which tools/skills are registered, which model a route points at, which tenants are enabled, whether a set of resources matches a spec. You get idempotency, crash tolerance, and drift correction without designing for them.
- Choose EDGE-TRIGGERED (queue, workflow, event) when the work is genuinely a discrete side-effecting action that must happen exactly once and cannot be re-derived from state — send the email, charge the card, post the PR comment. Then accept that you own detection, ordering, retry, and backlog management, and see the queue-backlog recovery arithmetic before committing.

The cost note the author adds against the intuition that constant work is wasteful: because a constant-work design needs no separate retry machinery and no state machines, it can consume LESS energy than the workflow it replaces, and fetching one S3 object in a loop from hundreds of machines costs far less than the engineering time to build something cleverer. The waste argument applies to physical goods (brewed coffee poured away), not to propagating a configuration — the difference between propagating 1 and 10,000 health-check results is negligible.
