# Hard vs soft concurrency allocation: hard wastes capacity, soft lets one slow dependency hog it, and the source declines to pick — it categorises work as droppable instead

Once you bulkhead per dependency you must divide a fixed concurrency budget between the bulkheads, and Amazon reports all three obvious strategies having a specific failure:

- HARD allocation. Service load-tested at 50 concurrent requests, two APIs, 25 each. Fails when the traffic mix is not what you guessed: you return errors on the busy API while overall server utilisation is low. Clients change access patterns unpredictably, so no up-front split is right for long.
- SOFT allocation. 35 each against a 50 global cap, so either API can dip into the slack. Fails in the other direction: when one API's dependency slows, it takes 35 of the 50, leaving 15 for the other API, which can then still run out.
- BURST-THEN-RATCHET. Allow the overage briefly, then ratchet back. Absorbs bursts and survives a long slow dependency, but reintroduces the hard-allocation problem for sustained traffic, and Amazon's own assessment is that it is complex and hard to prove correct across every production workload.

What Amazon actually reaches for instead is classifying work as 'droppable' vs 'non-droppable' and shedding by class: above roughly 90% of maximum concurrency, reject droppable work only. This extends to more than two classes, each with its own threshold.

Deciding condition: use the simplest allocation that holds, and add complexity only after testing or an operational incident proves you need it — Amazon's stated reason is that the more elaborate schemes are harder to test, instrument, and monitor, so their failure modes surface in production rather than in review.

For an agent platform, the droppable/non-droppable split is usually the natural one: speculative or background work (prefetch, summarisation, subagent fan-out, retries) is droppable; the user-facing turn in progress is not.

WHAT THE SOURCE ACTUALLY RECOMMENDS, stated precisely because the mechanism is easy to misname. The article's section is "Hard vs. soft allocation of concurrency limits", and it does **not** endorse either model outright, nor does it mention priority classes anywhere in that discussion. Hard allocation's drawback is that "hard allocation makes full resource utilization tricky" — a heavily-called API gets rejections while the server has spare capacity. Soft allocation's drawback is crowding out: if one API's dependency slows, "now that API can hog 35 threads, leaving only 15 for the other API."

The hybrid it describes lets an API "dip into the shared buffer for a short duration, but over time limiting it to a smaller value" — and it calls that complex and hard to prove, with the standing guidance that "we strive to use the simplest approach possible", adding complexity only once testing or operational experience shows it is needed.

The mechanism it does name in this section is a work classification, not a priority ordering: categorise work as "droppable" or "non-droppable", and once concurrency reaches a high threshold — its example is 90% of maximum — reject the droppable work and accept only the non-droppable. It notes this extends to more categories, each with its own threshold. Load shedding and bulkheads appear elsewhere in the article but are not part of the hard-versus-soft argument.

For an agent system the operational reading is: decide in advance which calls you are willing to drop under load — a speculative pre-fetch, an optional enrichment, a background summarisation — and which you are not, because that classification is what the threshold acts on. A scheme with no droppable class has nothing to shed and will shed whatever arrives last.
