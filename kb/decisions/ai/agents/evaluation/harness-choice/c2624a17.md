# Harness choice moves COST, not success rate, when the turn budget is held fixed — and moves SCORE when the budget or the grader is what differs. Two measurements, one condition separating them

Two credible measurements point in opposite directions about how much the harness matters, and the thing that reconciles them is WHICH harness parameter was allowed to vary. Read them together before quoting either.

**MEASUREMENT A — HARNESS MOVES COST, BARELY MOVES SCORE (Arena, HarnessTax, 2026-09-16).** 21 model–harness pairs, seven models, three harnesses (Claude Code, Codex CLI, and Pi, a minimal open-source harness), on SWE-bench Lite and Terminal-Bench 2.0. Method: 30 randomly sampled tasks per benchmark, each pair run three times per task, each harness started from its native configuration at its high effort setting, EVERY ATTEMPT CAPPED AT 100 AGENT TURNS, costs computed from a fixed direct-API price list dated 2026-09-01 applied identically across harnesses, 95% confidence intervals from 10,000 bootstrap resamples.
Result: "the average harness effect on success rate stays within ±2% on SWE-bench Lite and within about ±5% on Terminal-Bench 2.0", while "Across shared models, Claude Code costs about 2.0× as much as Pi and 1.6× as much as Codex on SWE-bench Lite, and 1.5× as much as Pi on Terminal-Bench 2.0, using geometric means of cost ratios." The worked case: Claude Fable 5 "solves 97.8% of attempts in Claude Code, 96.7% in Codex and 96.7% in Pi, yet Claude Code costs about twice as much as Pi ($1.33 vs $0.67)."
THE MECHANISM IS NOT MORE TURNS. "For Fable 5 on SWE-bench Lite, Pi and Claude Code average 15.4 and 15.3 turns per attempt, yet Claude Code costs about twice as much for a 1.1% increase in the success rate." The cost is per turn, and it starts before the first one: "Across all seven models, Claude Code's mean initial context is over 10× Pi's, with longer instructions and larger tool schemas." Pi provides four tools — read, write, edit, and bash. The authors note turn definitions vary across harnesses.
A THIRD RESULT, INDEPENDENT OF COST: a model is often not best in its own provider's harness. "Across the six Anthropic and OpenAI models and both benchmarks, an alternative harness achieves the highest observed success rate in nine of twelve comparisons." Named instances: Sonnet 4.6 at 68.9% in Codex versus 66.7% in Claude Code on SWE-bench Lite at similar cost; GPT-5.6 Sol at 83.3% in Pi versus 78.9% in Codex on Terminal-Bench 2.0 "at about half the cost ($0.42 versus $0.76)".

**MEASUREMENT B — HARNESS MOVES SCORE, AND CAN REORDER RANKINGS.** [[8193c07b]] records the same model scoring differently on MMLU across the HELM, EleutherAI and original implementations from prompt formatting, answer extraction and scoring choices; and OpenAI's ExploitBench case where raising the turn cap from 300 to 600 narrows a gap that had one model beating another at the tighter cap. [[d18637a2]] adds that agentic coding scores move about 6 points on CPU and RAM allocation alone.

**THE CONDITION THAT SEPARATES THEM, AND IT IS THE DECIDABLE PART.** In A the budget was pinned — one price list, one 100-turn cap, native configs — and the harnesses differed in scaffolding, prompt length and tool surface. Under that setup the model's capability carried across scaffolds, and the scaffolds differed in what they charged to express it. In B the varying parameter WAS the budget or the measuring apparatus: turn caps, scoring and extraction rules, machine size. So: **a harness difference that changes how much the model is allowed to spend, or how the answer is graded, moves the score; a harness difference in scaffolding and tooling at a fixed budget mostly moves the bill.** Neither result licenses the other's headline.

**HOW THIS SITS AGAINST THE PACK'S STANDING POSITION, WHICH IT NARROWS RATHER THAN OVERTURNS.** [[a829cfd4]], [[b9b45ff5]], [[8a7dc152]] and [[1feacc9e]] all hold that the apparatus moves an agent result more than the model does, and that a score without its configuration is uninterpretable or outright suspect. A is consistent with that second half and is a counterexample to a careless reading of the first: with the apparatus's budget parameters pinned, the residual harness effect on SUCCESS was within ±2% / ±5% while the effect on COST ran to about 2×. The correct reading is that "the apparatus dominates" is a claim about the BUDGET AND GRADING parameters specifically, not about every difference between two harnesses — and that cost is an axis those facts do not measure at all. Do not cite A as evidence that harness choice does not matter; it is evidence that it matters on a different axis than the one leaderboards report. Note also that A's ±2% band does not contradict [[1feacc9e]]'s "a score that moves in either direction is an eval defect until proven otherwise": A is reporting a band it could not distinguish from noise at 30 tasks × 3 runs, not a movement it explained away.

**WHAT TO DO.** Report the turn cap, the effort setting and the price basis as parameters of any agentic result — A's numbers are only interpretable because it states all three. When choosing a harness for production, run your own model against at least one minimal alternative and compare cost at matched success, because the default harness is where the tax is paid silently. When comparing published numbers, first ask whether the budget and the grader were held fixed; if they were not, you are reading B, not A.

**WHAT A DOES NOT ESTABLISH, in the authors' own words:** "These findings can be limited to the two open-source benchmarks we test, which the models may have encountered during training. Results may differ on other benchmarks and workloads." Two further scope facts a reader would otherwise miss: for SWE-bench Lite the study "block[s] external network access from all task containers, disable[s] the default web tools in Claude Code and Codex, and reject[s] hosted tool declarations at the API request level" — so features of the richer harnesses were switched off for the comparison — and the 100-turn cap was chosen "to control the cost of long runs", which bounds the result to tasks that finish inside it. The authors also state the general case is unsettled: "Richer harness features may still benefit other models, workloads, or interaction settings. Harness complexity should therefore be treated as an empirical trade-off."
