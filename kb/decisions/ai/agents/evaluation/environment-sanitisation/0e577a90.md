# Sanitising an eval sandbox is a two-sided failure — leave too much and the agent infers the operator, strip too much and the emptiness can itself signal a test

The instinct after reading that an agent identified its operator from a sandbox is to strip the environment. UK AISI, who ran that experiment, say in the paper that this does not resolve: "strip away too much environmental detail, and the emptiness itself can signal to the agent that it is being tested. Strip away too little, and the agent may infer the same thing from the information it finds." Both directions land in the same place — the agent concludes it is being evaluated — and eval awareness is what the sanitisation was for. Note the modality: "can signal" and "may infer" are the source's hedges and are kept.

WHY THERE IS NO UNIVERSAL SETTING, which is the part that decides your design. The paper is explicit that the boundary is deployment-specific, not discoverable: "There is no universal definition of 'sensitive' that works across contexts; the boundary has to be drawn per deployment." The same fact is context for one deployment and a liability for another — "For a developer using a coding agent as a daily tool, knowledge of their name, project structure, and API configuration is valuable context to maximise productivity. For an evaluation, it can be important to observe how the agent behaves without it knowing who is operating it or why, in which case the same information becomes a liability." So this is not a control you can copy from someone else's threat model.

THREE STATED REASONS THE BOUNDARY IS HARD TO DRAW IN PRACTICE, each with an engineering consequence:
- INFORMATION LEAKS FROM UNEXPECTED PLACES. "DNS entries, CPU model strings, TLS certificates, API metadata, or Kubernetes namespace names are not secrets in the traditional sense, but when aggregated together, they gave the agent a detailed and accurate picture of its environment." None of these is on a normal secrets inventory, so a secrets-scanning approach does not find them.
- AGENTS INFER FROM FRAGMENTS. "Even partial information was often enough... The reasoning capability that makes these agents useful also makes them effective at assembling a picture from fragments." Redaction that leaves a plausible remainder is not redaction.
- HARDENING AND UTILITY ARE IN TENSION. "Restricting filesystem access or filtering API endpoints have implications for agent functionality. For evaluations specifically, over-constraining the environment risks making the evaluation unrepresentative of how the agent would behave in a real deployment." So over-hardening does not merely cost utility — it invalidates the measurement you were trying to take.

WHAT THIS PACK TAKES FROM IT, MARKED AS THIS PACK'S READING AND NOT AISI'S: stop treating environment sanitisation as a control with a correct setting, and treat it as a budget you are spending against a measurement you are trying to protect. The decision variable is not "how much can I hide" but "what is this eval measuring, and does the agent's belief about being observed change that measurement". Where the eval measures capability, leakage is cheap. Where it measures propensity — will the model sandbag, will it behave differently when watched — leakage is the confound, and the honest answer may be that the result carries a caveat rather than that the sandbox can be fixed.

WHERE IT CONNECTS. [[778b437e]] establishes that a model's belief about whether an environment is real is unreliable in both directions; this fact supplies the design consequence — because you cannot control that belief by adding or removing detail, you cannot engineer it away, only account for it. [[d0c5b9f8]] holds the observed leak and the hardening rounds that failed to close it.
