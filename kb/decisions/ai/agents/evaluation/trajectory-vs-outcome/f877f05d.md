# Assert on the trajectory, but not on the exact tool-call sequence — the line is invariants versus paths

There is a real tension in agent eval advice that is easy to resolve wrongly in either direction.

One side: output-only scoring is insufficient for tool-calling agents, because an agent can reach the correct final answer through a destructive or unsafe tool call, and grading only the answer passes it. This is why tool-call verification and transcript analysis appear in Anthropic's list of code-based grader techniques alongside outcome verification.

The other side: Anthropic explicitly names over-specifying paths as a failure mode. Requiring a specific sequence of tool calls in a particular order is 'too rigid and results in overly brittle tests' — the eval then fails agents that solved the task by a different valid route, and it locks the suite to today's model behaviour so any harness or model improvement reads as a regression.

The resolving condition: assert trajectory INVARIANTS, not trajectory PATHS. Invariants are properties that must hold on every valid route — no write outside the workspace, no call to the delete endpoint, the payment tool called at most once, credentials never passed to an unapproved sink. Paths are 'search, then read, then edit, in that order'. Invariants survive a better agent; paths do not.

A useful test when writing an assertion: if a strictly smarter agent that solved the task in fewer steps would fail this check, the check is a path and should be rewritten as an invariant.
