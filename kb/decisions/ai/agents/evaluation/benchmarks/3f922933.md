# The line between an eval and a benchmark is whether success is visible in a reply at all — LangChain's three criteria are more steps per task, an environment per task, and scoring on what the agent did

LangChain defines a benchmark as a type of OFFLINE eval made of tasks, each carrying instructions, a containerized environment and a test script. The three stated differences from a simpler eval, verbatim: "Tasks involve more steps." "Each task comes with an environment." "Scoring checks what the agent did."

The decision this frames: whether the behaviour you want to score can be judged from a request-and-response pair at all. Once it cannot — because the work spans many steps, or because the evidence of success sits in an environment rather than in a message — you are paying for per-task environment provisioning whether or not you call the result a benchmark. The three criteria therefore read as one condition with three symptoms, and the cost that follows (an isolated environment per task, plus a test script per task) is the real content of the decision.

The build path given: collect tasks from traces, define what good looks like with judges or code checks, then hill-climb on the score. Tooling datapoint: Harbor runs benchmarks and logs each run as a LangSmith experiment, and it powers Terminal-Bench.

PACK ANALYSIS, not in the source: the post offers "hill-climb on the score" without the counterweight, and a hand-built benchmark that a team optimises against is the textbook setting for the score and the capability parting company. Nothing here is a reason to skip that caution.

Scope: a tooling vendor's taxonomy, not a standard, and no measurement attaches to it. Its value is as a cost trigger — a name for the point at which eval infrastructure stops being a dataset.
