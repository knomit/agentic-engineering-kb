# Symphony's non-goals say where the work moves rather than disappears — it mandates no sandboxing or approval policy, and ticket and PR writes are the agent's job, not the orchestrator's

Symphony states its non-goals explicitly, and each one names something an adopter still has to build. It is not a general-purpose workflow engine or a distributed job scheduler. It ships no rich web UI, multi-tenant control plane or prescribed dashboard. It has no built-in logic for editing tickets, PRs or comments — "Symphony is a scheduler/runner and tracker reader", so those writes live in the workflow prompt and the agent's own tooling, and the orchestrator has no first-class tracker write API. And OpenAI describes it as a reference implementation rather than a maintained standalone product.

Two of the non-goals are security-relevant and should not be read past. Symphony mandates no strong sandboxing beyond what the agent and the host OS already provide, and it mandates no single approval, sandbox or operator-confirmation policy. Combined with the harness's own scope — a Codex sandbox covers only its shell tool, not MCP-provided tools ([[94e415d3]]) — the containment of a fleet of continuously running agents is entirely the adopter's to design, and an unattended run cannot approve anything, so pre-authorisation is forced and belongs in a narrowed credential rather than a prompt rule ([[05066247]]).

What the spec does enforce on the isolation side is filesystem shape, not privilege: run the coding agent only in the per-issue workspace path (`cwd == workspace_path`); the workspace path must stay inside the workspace root; workspace keys are sanitised to `[A-Za-z0-9._-]` with every other character becoming `_`; and workspaces persist across runs, with successful runs NOT auto-deleted. That last one is a disk-growth commitment, not a convenience.

A cluster of smaller rules in the spec all resolve the same tension — an unattended run must not hang — and are worth copying as a set: approval and user-input requests must not stall a run indefinitely; an unsupported dynamic tool call gets a failure response so the session continues rather than dying; stderr is never parsed as protocol; and, pointing the other way, unknown template variables and filters must FAIL rendering. So the rule is fail-open at the tool and transport boundary, where the agent can recover and carry on, and fail-closed at the configuration boundary, where a silently empty substitution would send a confidently wrong prompt to an agent nobody is watching.

One optional extension shows the shape of credential handling they chose: a client-side `linear_graphql` tool runs a single GraphQL operation using the orchestrator's configured Linear auth, so the agent never holds raw tokens, and multi-operation documents are rejected — a narrow, single-statement interface rather than a token handed over.
