# An agent orchestration substrate must express cycles and runtime-determined fan-out, which rules out DAG-only workflow engines

The instinct when picking a substrate for agent orchestration is to reach for an existing DAG workflow engine — the team already runs one, and an agent looks like a pipeline. LangChain's retrospective after three years of LangGraph names the five things production agents do that a DAG cannot express, verbatim: "retrying failed tool calls, asking users for missing information, revising answers after validation, calling tools repeatedly until they have enough context, and pausing for human input before resuming." Every one of those is a cycle. If your substrate is acyclic, those five behaviours have to be smuggled in as external retry wrappers and re-invocations, which is where the state handling gets lost.

The second requirement is fan-out whose WIDTH is not known until runtime — map-reduce over however many items a previous step produced. LangGraph added a dedicated `Send` construct for this, letting a node "route work to one or more downstream nodes dynamically, without statically defining every transition." A substrate that requires the full edge set at definition time forces you to either cap the fan-out or generate the graph per run.

The third shift is about granularity, and it is the one that dates older designs: a node was originally "deterministic code or a single LLM call," and now a node can contain "a full agent run." Orchestration is over agents, not over model calls. A substrate whose unit of work is one LLM call makes nested agents awkward for no gain.

The useful inversion in their account is that a plain agent loop is not a simpler alternative to a graph — "a loop is just a directed, cyclic graph," a line the post attributes to David Khourshid rather than claiming as its own, and the reason they ended up building the simpler library on top of the graph one rather than beside it. Treat "we only need a loop" as a statement about your current requirements, not about the substrate you need.

This is a framework vendor describing its own product's evolution, so read the requirements as sound and the conclusion that you need THIS framework as unestablished — the same requirements are satisfiable with a durable-execution engine or hand-written control flow.

ONE PRECISION THE "LOOP IS A GRAPH" LINE INVITES: it does not say a loop is a one-node graph. A realistic agent loop has distinct model-call and tool-execution steps, so the claim is about cyclicity, not about node count — and nothing in it licenses treating your loop as a single unit of orchestration.
