# Azure's orchestration patterns: pick by coordination shape, and the avoid-conditions are the useful half

Microsoft's guidance starts with a complexity ladder — direct model call, then single agent with tools, then multiagent orchestration — and says use the lowest level that reliably meets requirements. They name single-agent-with-tools as "often the right default for enterprise use cases", justifying multiagent only when a single agent genuinely cannot cope due to prompt complexity, tool overload, or the need for distinct security boundaries per agent. Note that third one: separate trust boundaries are a legitimate reason to split agents even when capability alone would not require it.

The five patterns, each with its disqualifying condition (the more decision-relevant part):
- Sequential (pipeline) — avoid when stages are embarrassingly parallel, when an early stage can emit low-quality output that later stages will happily consume, when agents need to collaborate rather than hand off, or when the work needs backtracking or dynamic routing.
- Concurrent (fan-out/fan-in) — avoid when agents need cumulative context in order, when you need deterministic reproducible ordering, when agents cannot reliably coordinate writes to shared state, or when you have no conflict-resolution strategy for contradictory results. Aggregation strategy should match the task: voting for classification, weighted merge for scored recommendations, model-synthesized summary for narrative.
- Group chat (shared thread, chat manager) — agents are typically read-only here, no tool-driven mutation. Avoid when the chat manager has no objective way to determine completion. Concrete cap: limit to three or fewer agents to keep control maintainable. The maker-checker loop is a sub-case needing explicit acceptance criteria, an iteration cap, and defined fallback when the cap is hit.
- Handoff — full control transfers between agents. Avoid when the right agent is identifiable from the initial input (use deterministic routing instead), when routing is rule-based, or when you cannot bound handoff bouncing.
- Magentic — a manager agent builds and refines a task ledger for open-ended problems, with worker agents that mutate external systems. Its distinguishing value is that the plan is documented and reviewable by a human BEFORE execution. Avoid when the path is deterministic, when the work is time-sensitive (it optimises for deliberation, not speed), or when you expect stalls with no resolution path.

Cross-cutting: every dynamic pattern here needs an explicit iteration limit. Infinite loops — tool-call loops, refinement loops, handoff bouncing — are named as the recurring failure across all of them.
