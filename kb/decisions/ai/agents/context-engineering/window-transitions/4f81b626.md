# Fresh context window vs compaction: decide on whether the run's state is durable outside the context

Two pieces of Anthropic guidance prescribe different things at the same moment — the context window is nearly full and the task is not done. The context-engineering post presents compaction (summarise the history, reinitialise, carry forward the most recently touched files) as the technique for long runs. The prompting docs say the opposite, in one sentence: "When a context window is cleared, consider starting with a brand new context window rather than using compaction." Their reason is a capability claim — "Claude’s latest models are extremely effective at discovering state from the local filesystem."

The condition that separates them is whether the run's state exists anywhere except the message history.

If it does — a coding agent in a repo, where git history, a structured `tests.json`, and freeform progress notes hold the state — prefer the fresh window. Compaction's documented risk is that over-aggressive summarisation silently drops subtle context and you discover the loss much later; a restart that re-reads real artifacts cannot lose what the artifacts still say. If it does not — a research or conversational task whose only state is the transcript — there is nothing to rediscover and compaction is the only move available.

A later Anthropic harness-design writeup supplies a second, independent reason to reset: CONTEXT ANXIETY. Some models "begin wrapping up work prematurely as they approach what they believe is their context limit" — degrading output quality before the window is actually exhausted. The observation is reported on SONNET 4.5: "we found Claude Sonnet 4.5 exhibited context anxiety strongly enough that compaction alone wasn't sufficient." Compaction does not fix it, because the model still sees a long and filling context; the post's complaint about compaction is exactly that "it doesn’t give the agent a clean slate." So the argument for resets is not only lossless-ness, it is that a model behaves worse near a boundary it can see.

SCOPE OF THAT SECOND SOURCE, because it is easy to over-read: the harness-design post does NOT state a preference for fresh windows over compaction. What it contributes is the context-anxiety observation and the handoff requirement below. The reset preference itself rests on the prompting docs alone.

The actionable corollary is that this is a choice you make EARLY, not at the limit: spend the first context window building the durable state rather than starting the feature, because that is what converts an expensive lossy compaction into a cheap restart. PACK ANALYSIS for the concrete form of that state — writing the tests first, and a single script that starts the servers and runs the suite and linters; the harness-design post contains no such prescription and no `init.sh`, so do not cite it for one.

Then be prescriptive in the restart prompt. The prompting docs say so directly — "Be prescriptive about how it should start:" — and their first bullet is "Call pwd; you can only read and write files in this directory." A fresh window knows nothing about what it inherited, so "continue where you left off" is not an instruction it can act on. The harness-design post states the requirement in general terms, as "a structured handoff that carries the previous agent's state and the next steps," and treats it as the part that makes resets work at all.

Do not read this as "compaction is obsolete". It is that filesystem-backed agents have an option conversational ones do not.
