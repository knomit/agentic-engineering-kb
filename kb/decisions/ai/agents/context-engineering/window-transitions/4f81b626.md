# Fresh context window vs compaction: decide on whether the run's state is durable outside the context

Two pieces of Anthropic guidance prescribe different things at the same moment — the context window is nearly full and the task is not done. The context-engineering post presents compaction (summarise the history, reinitialise, carry forward the most recently touched files) as the technique for long runs. The current prompting docs say that for tasks spanning multiple context windows you should consider starting a BRAND NEW window instead, because current models are extremely effective at discovering state from the local filesystem.

The condition that separates them is whether the run's state exists anywhere except the message history.

If it does — a coding agent in a repo, where git history, a structured `tests.json`, and freeform progress notes hold the state — prefer the fresh window. Compaction's documented risk is that over-aggressive summarisation silently drops subtle context and you discover the loss much later; a restart that re-reads real artifacts cannot lose what the artifacts still say. If it does not — a research or conversational task whose only state is the transcript — there is nothing to rediscover and compaction is the only move available.

A later Anthropic harness-design writeup reports the same preference from build experience and adds a second, independent reason to reset: CONTEXT ANXIETY. Opus 4.5 was observed wrapping up work prematurely as it approached what it perceived as its context limit — degrading output quality before the window was actually exhausted. Compaction does not fix this, because the model still sees a long and filling context; a full reset does, because the fresh agent has no sense of an impending limit. So the argument for resets is not only lossless-ness, it is that a model behaves worse near a boundary it can see.

The actionable corollary is that this is a choice you make EARLY, not at the limit: spend the first context window building the durable state (write the tests, write an `init.sh` that starts servers and runs the suite and linters) rather than starting the feature, because that is what converts an expensive lossy compaction into a cheap restart. Then be prescriptive in the restart prompt — call pwd and state the writable directory, review the progress notes, `tests.json` and the git log, run a fundamental integration test before touching new features. A fresh window knows nothing about what it inherited, so "continue where you left off" is not an instruction it can act on. The harness-design post calls this the structured handoff, and treats it as the part that makes resets work at all.

Do not read this as "compaction is obsolete". It is that filesystem-backed agents have an option conversational ones do not.
