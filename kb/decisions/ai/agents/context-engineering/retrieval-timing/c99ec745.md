# Pre-fetch vs just-in-time retrieval: decide on P(needed) times size, because a wrong pre-fetch costs twice

Two credible sources prescribe opposite defaults for the same decision: when the agent will need some data, do you fetch it before the model runs, or expose a tool and let the model ask?

12-factor-agents (appendix factor 13) says pre-fetch. If you already know which tool you want called, call it deterministically and put the result in context, letting the model do the hard part of using the output rather than the easy part of deciding to ask for it. What that buys is concrete: one fewer model round-trip, so lower latency and fewer tokens spent on a tool_use / tool_result exchange that was a foregone conclusion. Their pattern is to inject the fetched data as an event in the conversation thread rather than as a prompt-template parameter, which keeps the template clean.

Anthropic's context-engineering guidance says the opposite by default: keep lightweight identifiers — file paths, queries, links — and let the agent load what it needs at runtime, the way Claude Code pipes through head and tail rather than reading whole files. Context is a finite attention budget, and material the agent never uses still spends it.

The two are reconcilable, and the deciding quantity is P(the data is needed) multiplied by its size.

Pre-fetch when the probability is near certain AND the payload is small and bounded — the current git tags, the user's account tier, today's date, the repo's config. Here the tool call is ceremony and skipping it is free.

Go just-in-time when either term is bad. Low probability: one of fifty files might matter and you cannot tell which, so pre-fetching all fifty spends fifty times the budget for one hit. Unbounded size: a query that might return ten rows or a million cannot be safely inlined at all.

The asymmetry that should bias you toward JIT under uncertainty is that a wrong pre-fetch costs twice. You pay the tokens, and you pay again in degraded decisions — Context Rot's measurement is that confusable, unused material is not inert padding but an active distractor that lowers accuracy, and that a coherent-looking irrelevant passage is worse than an obviously random one. A skipped JIT fetch costs one round-trip; a wrong pre-fetch costs tokens plus attention plus a worse answer, and unlike the round-trip it does not show up in your latency graph.

Note what 12-factor's version does NOT claim: it assumes you have reasonable confidence the tool is needed and that its output is not prohibitively large. Those assumptions are the whole condition — stated as an unconditional "pre-fetch everything you might need", the factor is wrong, and "might" is doing the load-bearing work.

WHICH REF CARRIES WHICH HALF OF THE RULE — pack analysis, and worth stating because the product form appears in none of the sources. The 12-factor appendix supplies the LIKELIHOOD term only, as a rule of thumb with no number: "If there's a high chance that your model will call tool X", and its governing instruction is "If you already know what tools you'll want the model to call, just call them DETERMINISTICALLY." Its stated cost is round trips — "don't waste token round trips" — and it uses no paying-twice framing. It names no size, token-budget or context-window condition at all, and it gives no guidance on when NOT to pre-fetch: nothing on uncertain likelihood, large or costly results, staleness, or fetches that go unused.

The SIZE term, and with it the reason a wrong pre-fetch is paid for twice, comes from the other two refs rather than from the appendix — the cost of occupying context with material the model did not need. So the multiplicative form here is this pack's composition of the three, and a reader checking it against the 12-factor appendix alone will not find it there.
