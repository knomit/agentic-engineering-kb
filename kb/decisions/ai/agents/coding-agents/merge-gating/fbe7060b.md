# Above roughly 30,000 merges a day a global merge-queue lock was not replicable, so correctness moved AFTER the merge — into post-merge and pre-deploy automated testing

A merge queue that serialises every change is a global lock, and at Anthropic's merge rate it could not be carried over into the replacement for git: the team reports it could not replicate a global merge-queue lock, and in its place "we’ve invested in post-merge and pre-deploy automated testing". The accepted consequence is that concurrent changes can conflict semantically and land, and the testing after the merge is what catches them.

The same commit path is designed around the absence of global state: "Commits must be cheap, incremental, and lock-free." and "The development lifecycle in Scion discourages refs" beyond main and release branches, because a ref is shared mutable state that every writer contends on.

The tradeoff stated plainly: pre-merge serialisation buys a repository whose main line is always consistent, and it costs throughput proportional to the merge rate. Post-merge verification buys throughput and costs you a window in which main is broken. As agent fleets raise the merge rate, that first cost grows and the second does not, which is why the gate moves.

Operational consequence: before adding a merge queue to a repository that coding agents write to, work out the serialised merge rate it implies and compare it with your projected merge rate. If the queue cannot keep up, the design question is not a faster queue — it is which breakages you can detect and revert after the fact, and how fast.

What this does NOT mean: this is not "skip pre-merge CI". Pre-merge checks on the individual change are unaffected; what was given up is the guarantee that two changes were tested TOGETHER before either landed. And it is conditional on having post-merge and pre-deploy test coverage good enough to find a semantic conflict — without that, dropping the queue just moves the breakage to production.
