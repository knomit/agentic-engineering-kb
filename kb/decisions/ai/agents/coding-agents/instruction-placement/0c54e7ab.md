# Who executes an instruction decides where it goes: an instruction file is advice the model may set aside, so a rule that must hold every time belongs in a hook, a deny rule or a managed setting — and the enforced set has to stay small

Claude Code's best-practices documentation splits agent instructions by WHO executes them. "Non-deterministic: you write the instruction, and Claude (the model) reads it." "Deterministic: you configure the instruction, and Claude Code (the harness) *has* to execute this." Of the deterministic kind it says "Claude Code applies this every time, no matter what the model decided to do"; of a line in an instruction file, "whether Claude follows that line on a given turn is still Claude's call."

The consequence is a placement rule rather than a style preference. "`CLAUDE.md` is for guidelines, and Claude is allowed to decide a guideline doesn't apply", so "If something has to happen every time, make it a hook, a deny rule, or a managed setting", and "your \"never\" rules belong in deny rules or hooks." The page is explicit about what the instruction-file version buys: a line like "Always typecheck before you finish" "works most of the time" — which is the same sentence as saying it fails some of the time, and most-of-the-time is not what a "never" was written for.

THE RULE CARRIES ITS OWN COUNTERWEIGHT, AND DROPPING IT INVERTS THE ADVICE. "Whatever the scope, keep the enforced set small. Every hook and deny rule will occasionally fire when it shouldn't, and someone has to maintain each one." And: "If you ever find yourself at forty of them, most are probably preferences that Claude could have weighed on its own." So the test for promoting a rule into the deterministic layer is whether an exception would be a DEFECT, not whether you would prefer compliance. Forty is given as a review trigger, not a cap; the page states no limit on hooks or deny rules.

What this does NOT mean: not that the deterministic layer is unconditionally stronger than an instruction. A hook-enforced gate has a ceiling of its own — a separately documented block cap on the Stop hook lets the harness end a turn over the hook's objection after an unbroken run of blocks, so "the harness has to execute this" describes each dispatch, not the outcome of an arbitrarily long standoff.
