# Minimal blocking merge gates are a throughput-conditional choice — the same policy the Codex team calls correct at 3.5 PRs per engineer per day they call irresponsible at low throughput

In a repository where agents write the code, the OpenAI team describes deliberately minimising blocking merge gates: short-lived PRs, flaky tests handled by rerunning rather than by blocking, agents responding to review feedback inline and often squash-merging their own PRs, with human review optional and most review agent-to-agent.

The reason given is an economic one with both halves stated. When agent throughput far exceeds human review attention, a correction after merge is cheap and waiting before merge is expensive. The source names the boundary itself: the same policy "would be irresponsible in a low-throughput environment."

So the decision variable is the ratio between the rate of change arriving and the rate of attention available to inspect it — not a general view about CI strictness. Read the other way round, a team whose humans can still read every diff gets nothing from this trade and loses the gate.

What this does NOT mean: it is not a case for weakening non-blocking enforcement. In the same repository the invariants that are not negotiated at review time — layering, structured logging, naming, file size — are enforced mechanically by custom linters and structural tests on every change, and a separate background process continuously removes the drift that cheap merges let in. The low gate count is survivable only alongside that machinery, not instead of it.
