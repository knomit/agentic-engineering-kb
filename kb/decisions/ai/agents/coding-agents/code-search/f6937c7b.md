# A specialised search subagent beat both MCP tools and local search on speed and cost — measured, with the tradeoff named

Sourcegraph benchmarked three ways for a coding agent to find code across repositories of varying size, and published relative numbers with comparable result quality across all three. Taking their Code Finder as the 1.00x baseline:

  TIME   Code Finder 1.00x | agent with MCP tools 1.14x | agent with local search 2.19x
  COST   Code Finder 1.00x | agent with local search 1.32x | agent with MCP tools 1.63x

So a purpose-built search service was fastest and cheapest on both axes, more than twice as fast as an agent driving local search tools. The ordering flips between the two metrics for the other two options: MCP tools were nearly as fast as the specialist but the most expensive, while local search was the slowest yet cheaper than MCP.

THE STATED CAUSE is division of labour, and it is the part that generalises: a component that does exactly one task can issue more direct queries and return DENSER output, whereas a general-purpose agent burns context window on the mechanics of searching. The cost is not the search itself, it is the intermediate tool results the main agent has to read to steer it.

WHAT THIS DOES AND DOES NOT SAY. It is evidence for extracting a narrow, high-traffic capability into a specialised component with its own context — not a general argument that MCP is expensive. The MCP configuration was the fastest of the two general-purpose options; what it paid for was generality. Read the result as: if one tool call pattern dominates your agent's trajectory, the specialist version of it is likely to win on both axes at once, which is unusual enough to be worth measuring for your own hot path.

SOURCING CAVEAT: this is a vendor benchmarking its own product against alternatives, with relative rather than absolute figures and no published task set. Treat the direction as credible and the magnitudes as indicative.
