# Per-token price does not predict agent cost — the cheaper-listed model cost nearly double over 417 tasks because cache-read pricing dominated

IBM Research measured a CodeAct agent on the AppWorld Test Challenge (417 tasks) and found Claude Sonnet 4.6 cost $79 total ($0.19/task) against GPT-4.1's $155 ($0.37/task) — nearly double — despite GPT-4.1 having the lower per-token list price "on both input and output". The inversion is sharper than the totals alone show: Sonnet 4.6 also took "roughly three times as many reasoning steps to finish the same tasks", so it was half the cost while running a far longer trajectory. Their attribution: cache-read pricing. Sonnet 4.6's lower cache-read pricing meant it "benefited disproportionately" from the high cache-hit rates agent workloads produce, enough to overcome both its higher base pricing and its longer trajectories.

THE MODEL PAIR IS SPECIFIC AND THE VERSION IS PART OF THE CLAIM. This is a measurement of Claude Sonnet 4.6 against GPT-4.1 on one workload, not a general property of Sonnet-class or GPT-class models. Cache-read pricing is a per-version, per-vendor term that changes with each release, so the finding to carry forward is the mechanism and the method, not the direction of this particular pair.

This is the specific reason a routing or model-selection decision made from a pricing page is unreliable for agents. An agent replays a growing prefix on every turn, so the dominant cost term is cache reads on that prefix, not fresh input or output tokens. Two models with the same headline input price and different cache-read discounts have materially different agent costs, and trajectory length — how many turns the model takes to finish — multiplies the difference in whichever direction the model is worse.

The corollary for routing design: IBM argue routing is a systems optimisation problem, not a task-difficulty classification problem, because the router must weigh cost, quality, latency, compliance and reliability at once, and because end-to-end latency is dominated by infrastructure state — which hardware the model runs on, whether the cache is warm, how busy the endpoint is — rather than by the model's theoretical speed. They report a router optimising jointly rather than by difficulty reaching 84% accuracy at $93 and 83 seconds, which they describe as a 21% cost reduction and 9% latency reduction against running Opus alone for a 4% accuracy drop, at a router overhead of roughly 6 ms and 2 kB of memory per task. Those figures are one point on a frontier — the source's "Configuration 1 (latency-optimized)", with a second configuration that "pushes cost even lower" — so they describe a chosen operating point, not the router's performance.

What decides it: route on measured end-to-end cost per completed task on your own workload, not on price-per-token and not on estimated task difficulty. The 6 ms overhead figure means the router itself is never the reason not to route; the reason not to route is that a difficulty-based router explores the wrong tradeoff curve and can cost more than the single strong model it was meant to replace. Note the accuracy figures come from the authors of the router being evaluated — treat the 21%/9% as vendor-reported, while the $79-vs-$155 comparison is the more portable finding.

Two further mechanisms break the same inference, and neither is visible in a per-token rate comparison. The first is the TOKENIZER. Anthropic's Claude Haiku 5.5 launch page (2026-10-07) says the model ships an updated tokenizer "which means it uses slightly more tokens per task" — so a lower price per token is multiplied by a larger token count for identical work, and the two moves can cancel. A tokenizer change is not announced on a pricing page and does not appear in any rate, so it is invisible to exactly the comparison teams make when swapping models. The second is PROMPT-LENGTH TIERING: the same page prices by prompt size rather than one flat rate, stating "Haiku 5.5 is especially good value when used for tasks with prompts up to 100,000 tokens", so an agent whose context grows across a long trajectory can cross into a worse tier part-way through a run that was priced from its first turn. That page also names the dominant term independently: "Because cache reads make up a large share of models' token consumption".

So three distinct mechanisms now support the same operational rule: cache-read pricing, tokenizer-driven token count, and prompt-length tiers. The only comparable figure is measured cost per completed task on your own workload, re-measured after any model swap — including a swap within one vendor's family, where a tokenizer or tiering change can arrive with the new version.
