# MCP was tried first as the IDE integration surface for Codex and abandoned — exposing an agent as a tool and hosting an agent's session are different problems

For the VS Code extension, the Codex team first exposed the harness as an MCP server. They report that "maintaining MCP semantics in a way that made sense for VS Code proved difficult", and replaced it with a JSON-RPC protocol mirroring the TUI loop, later stabilised as the App Server and now named their first-class integration path.

The post frames three options and what each costs. An MCP server (`codex mcp-server`) is easy to call as a tool but is limited to what MCP exposes, and richer session semantics such as diff updates may not map cleanly onto it. A cross-provider harness protocol is portable across providers but tends to converge on a common subset, which makes rich interactions harder to represent. The harness's own protocol exposes the full surface — thread lifecycle, auth including "Sign in with ChatGPT", model discovery, config — at the cost of writing and maintaining a client-side binding per language. Two further shapes are listed for narrower uses: non-interactive CLI mode for one-off tasks and CI, and a TypeScript library for server-side use, which predates the App Server and covers a smaller surface.

The condition that separates them is what the integrator is doing. Calling an agent as one capability inside someone else's loop is the case MCP fits. Hosting the agent's interactive session — turns, streaming item updates, mid-turn approvals, resumable threads — is the case it strained under here. The decision is about which side of that line the integration sits on, and demand from JetBrains, Xcode and a desktop app orchestrating many agents in parallel is what pushed this team across it.

What this does NOT mean: nothing here says MCP is the wrong protocol for exposing tools to an agent, which is the direction it was designed for. The claim is scoped to using it as the surface that hosts an agent's own session.
