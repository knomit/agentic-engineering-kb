# Before building the idempotency contract, check whether the operation can be level-triggered instead — that is the only way to make UNKNOWN not matter

Five facts here form one chain, and the chain has an exit most teams walk past. Stating it as a decision rather than five separate rules is the point.

THE PROBLEM. A tool call over a network has five outcomes — POST_FAILED, RETRYABLE, FATAL, UNKNOWN, SUCCESS — and agent harnesses almost universally collapse them to success/failure. UNKNOWN (the timeout) is the one that corrupts state: the caller knows NOTHING, so the request may have succeeded, failed, or been processed with the reply lost. POST_FAILED is categorically different — the caller knows deterministically the request never arrived, so retry is always safe. These must not share a code path. UNKNOWN is irreducible: the client and server do not share fate, so it is a permanent feature of any tool crossing a network, which is nearly all of them.

WHY AGENTS SUFFER MORE THAN SERVICES. A human operator has an instinct that says 'check whether it went through before retrying'. An agent does not. It sees 'failed', retries, and double-executes the payment, the send, the ticket creation — then builds subsequent reasoning on state it has misread, which the compounding-error property of agent loops amplifies.

THE EXIT, AND IT IS THE PART TO CHECK FIRST. If the operation's correct end state is a FUNCTION OF CURRENT INPUTS and is cheap to recompute, make it LEVEL-TRIGGERED — re-read and re-apply the whole desired state each cycle — and UNKNOWN stops mattering entirely. A level-triggered system is permanently in repair-everything mode: a truncated write is fixed on the next pass, a missed update just gets the next one, with no backlog and no repair logic anyone wrote. You get idempotency, crash tolerance and drift correction without designing for them, and you need none of the contract below. Candidates in an agent platform: which tools and skills are registered, which model a route points at, which tenants are enabled, whether a set of resources matches a spec.

EDGE-TRIGGERED IS FOR WHAT CANNOT BE RE-DERIVED — send the email, charge the card, post the PR comment. Choose it deliberately, because you then own detection, ordering, retry and backlog management, and 'workflows are not naturally self-healing, you have to make them self-healing'. Only here do you owe the full contract:

1. TOKEN AND MUTATION IN ONE ACID OPERATION. If they diverge you get token-recorded-but-nothing-created (every retry returns success for a thing that does not exist) or created-but-token-lost (the next retry creates a second one — the exact failure idempotency was for). Writing the dedupe key to one store and the effect to another without a transaction spanning both is not idempotency, it is a race.
2. STORE THE ORIGINAL PARAMETERS AND VALIDATE ON REPLAY. A known token arriving with different parameters gets a validation error naming the mismatch, NOT the cached response — different parameters probably mean a different intended outcome. This catches a real agent-specific bug: a harness reusing one key across a model's revised retry, where the model CORRECTED an argument between attempts. Silently returning the first result would discard the correction and report success.
3. BOUND THE RETENTION, DELIBERATELY. Forever is impractical and harmful — a future request identifier can collide with an old one and produce a bogus cache hit. The stated rule of thumb is the resource's lifetime plus an interval after which a late-arriving request would either have arrived already or no longer be valid. This varies per service and resource type; choose it rather than inherit it.

AND THE RESPONSE SHAPE, which decides whether any of this actually helps. Returning `AlreadyExists` to a retry technically satisfies idempotency — no server-side side effect — but the RESPONSE changed, and a changed response changes the caller's execution flow, so the side effect merely landed on the client. Return a SEMANTICALLY EQUIVALENT response instead: not byte-identical (a state field legitimately progressing pending -> running is fine) but the same KIND, so the caller processes it identically and never learns a retry occurred. For an agent this is the difference between an invisible retry and a derailed trajectory — given `AlreadyExists` a model concludes it erred or that another actor intervened, and goes off to investigate, apologise, or attempt cleanup. A tool result is a prompt, and `AlreadyExists` reads as 'something is wrong' because outside a retry it usually is. Apply least astonishment even to the awkward case: a retry arriving after someone else deleted the resource still gets the equivalent response (e.g. the instance in `terminated` state) rather than an error.

WHERE THAT IS ALL IMPOSSIBLE, surface UNKNOWN honestly to the model: say in the tool result that the operation MAY have completed and that the next step is to QUERY FOR ITS EFFECT, not to repeat it. 'Timed out, state unknown, verify before retrying' is a different prompt than 'error'.

ONE SECOND-ORDER COST TO INSTRUMENT WHILE YOU DO THIS: retries with backoff multiply the CALLER's concurrency even when every dependency is fast, because backoff means deliberately sleeping while holding a slot. Bulkhead and measure the whole codepath that calls a dependency, not the time inside the remote call — only the former captures retry sleeps and loop counts. Agent loops are inherently modal (a turn may take 1 tool call or 40), so an agent-concurrency limit measured on model-call time alone reads healthy while the harness runs out of workers.

WHAT THIS DOES NOT MEAN. The idempotency contract is not free and is not universally right — it pushes real complexity into the service and is explicitly not right for every solution. Reserve it for side effects genuinely needing an at-most-once guarantee (payments, provisioning, sending, irreversible writes); read-only and naturally idempotent tools need none of it. Nor is level-triggering universally cheaper in principle — the cost argument is that constant work needs no retry machinery or state machines, and propagating a configuration is not like pouring away brewed coffee, so the waste intuition misleads for configuration but would not for physically consumed goods. Before committing to edge-triggered, see the queue-backlog recovery arithmetic separately recorded in this pack.
