# Three stated conditions that veto an LLM gateway, and the reminder that Global deployments already are one

Microsoft's gateway guidance is unusual for prescriptive vendor architecture content in that it spends most of its length on reasons NOT to add the component, and states three explicit vetoes. Don't implement a gateway if it jeopardises your ability to meet agreed service-level objectives; if it leaves the workload unable to protect the confidentiality, integrity or availability of itself or its users' data; or if it makes negotiated performance targets impossible.

The concrete costs behind those vetoes, which are the part worth carrying: a gateway is a new single point of failure, from platform outage, from config or code deployment, or from a misconfigured route. It expands the attack surface with its own IAM, hardening and maintenance. It sits where it can see raw prompts and raw completions, so regulatory and data-compliance scope now covers it too. It adds per-request latency and can become a throughput bottleneck. And it can break capabilities that depend on connection or session semantics — streaming needs long-lived connections without premature timeouts or buffering, and stateful APIs need session affinity.

THE STRONGEST SINGLE POINT: the managed routing you would build may already exist. Microsoft notes that Global and Data Zone deployments route each request to a datacentre with available capacity and "are themselves a gateway implementation," so most workloads should solve throttling that way rather than by building custom infrastructure — and separately, "don't implement a unified gateway solely to increase quota." They also warn that some gateway functionality simply overlaps what the AI service already does.

WHAT DECIDES IT, stated as conditions rather than a verdict. A gateway earns its place when you do NOT control the client code, or when changing gateway configuration is genuinely safer than rolling out client configuration; when you need per-model-deployment access segmentation that the platform's identity model cannot express; when you need per-client usage attribution for chargeback that the backend's access logs cannot distinguish; or when you need server-side traffic shifting for blue-green model rollouts. It does NOT earn its place when you own the clients, they are few, and they are easy to update — in that case the same logic goes in the client. Nor does it earn its place for chargeback when clients can simply be given dedicated instances, which gives you identity, network and billing separation without routing logic.

One topology is called out as an outright anti-pattern: a single-region gateway fronting model instances in several regions. "Any service outage on your gateway instances renders all regions inaccessible" — it converts a set of independent regional endpoints into one correlated failure domain, and Microsoft says not to use it for business-critical workloads. If you go multi-region, note that even a multi-region gateway deployment leaves the control plane in a single region, and that when one region is taken out of rotation the survivors must absorb 100% of its traffic, which has to be provisioned for in advance.
