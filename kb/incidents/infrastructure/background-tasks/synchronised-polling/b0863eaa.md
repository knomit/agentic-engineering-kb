# Every pod stalled for a moment every minute: an unjittered 60-second flag refresh, a config carrying every rule for every service, and up to 8 worker processes per pod multiplied into a tail-latency floor

At Habitat's initial service launch, requests at p99 and above were stalling even though downstream storage answered quickly — the coroutine that would parse the response was waiting to be rescheduled. Live-service CPU profiling found the cause: "periodic JSON parsing of our feature flag configurations via Statsig".

Three independently reasonable decisions multiplied. Statsig "was configured to poll for refreshed configs every minute with no jitter". "the config included every production rule across every service". And "an architectural decision was made to run up to 8 Python processes per pod to push higher CPU usage and provide lower latencies". Combined: "every minute each pod would have some moment where all of its workers stalled processing in-flight requests and instead would spend their CPU cycles parsing a giant configuration file."

The fix touched all three dimensions rather than one: "deploy a smaller targeted config, lengthen the refresh interval, and add some jitter to background tasks like these."

The detection practice is the reusable part, because this class is invisible to ordinary utilisation metrics. OpenAI treats event-loop scheduling delay as a first-class saturation signal alongside CPU, memory, network and disk, measured "By periodically scheduling background tasks and recording the delta between expected and actual execution time". At high utilisation with CPU-heavy work in the loop, even modest per-process concurrency produced "significant scheduling jitter, up to hundreds of milliseconds and in some edge cases several seconds", and the standing response is to keep each process serving only a small number of concurrent requests and scale out the process count instead. The CPU in question is real work the service owns — routing, compression, encryption, checksumming, health checking, shadowing and hedging — not an accident, so concurrency in an async runtime is not CPU parallelism and the loop is the thing to watch.

The shape, stated for transfer: a shared periodic task, fired on a synchronised timer, whose payload grew for reasons unrelated to this service, multiplied by a process count chosen for reasons unrelated to either. No single one of the three decisions is visible from the others, which is why it survived to production and why the symptom appeared as a tail-latency floor rather than as an error. Any agent runtime that refreshes prompts, tool schemas, skill manifests or policy on a timer carries the same exposure: scope the payload to the consumer, jitter the timer, and measure the scheduler and not only the CPU.
