# LIFO connection reuse concentrated traffic on the slowest processes and kept them degraded after the burst was gone — OpenAI broke the metastable loop by switching the pool to FIFO

OpenAI's online storage platform Habitat hit this in production while running as a Python service.

The symptom was a failure that outlived its trigger. After the client overloading part of the service was stopped, "a subset of processes remained degraded well past the bursty traffic" and got worse rather than better: "we noticed those processes experienced runaway degradation, receiving increasingly more requests until we restarted them." Steady-state load was already skewed before the fix — "some tail processes serving 5-10x the number of concurrent requests as the average." The team names the class: metastable failure.

The cause was the pool's reuse ORDER. "Python's aiohttp TCPConnector defaults to LIFO connection reuse: the most recently returned connection is selected for the next request." During a burst, the slow or overloaded servers are the ones that return their connections to the pool LAST — so LIFO picks those same connections first for the next requests, steadily concentrating traffic on the processes already struggling. A client process doing many concurrent requests may hold only a handful of server connections in the first place, so its whole load lands on a handful of processes.

The fix: "Patching the connection pool to use FIFO reuse broke this feedback loop and even reduced our steady state request variance as well." Before the real cause was known, capping maximum connection reuse duration limited the degradation, which is what confirmed the pool was implicated. Habitat now relies on Istio and Envoy for pooling and load-aware balancing instead of tuning the Python pool.

What this does NOT mean. LIFO is not a bug: reusing the most recent connection lets the extra connections created for a burst idle out, which is why it is the default. The transferable claim is that connection-reuse order IS a load-balancing policy, and LIFO's bias points at whichever peer answered slowest. Any client-side pool in front of a fleet of same-role processes inherits that bias, whatever the language.

A neighbouring mechanism to keep separate: fast error responses make least-outstanding-requests balancers send MORE traffic to a sick server [[61e45bce]]. Both are feedback loops toward the failing peer, but one runs through reuse order and the other through response speed, so fixing either leaves the other in place.
