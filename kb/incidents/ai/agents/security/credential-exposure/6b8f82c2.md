# A researcher's vibe-coded agent dashboard leaked an API key for three weeks — the attacker found it via certificate transparency and simply asked the agent for the key

March 2026, disclosed by METR on 2026-08-31. A researcher with no access to sensitive data or credentials ran agents on a personal EC2 instance "intentionally made publicly accessible behind Google authentication." The instance held an API key for METR's general-access (public models) account. "The vibe-coded app included a fail-open vulnerability that silently disabled authentication, which led to the system being exposed to the public internet for several days."

THREE PARTS, EACH TRANSFERABLE.

1. DISCOVERY. METR's assessment of how the instance was found: the attacker was "looking through recently-registered websites (e.g. in certificate transparency lists) to find vibe-coded sites with high-signal keywords relating to LLMs or agents, for purposes of harvesting potentially exposed model provider API keys." Standing up an agent app on a fresh TLS certificate publishes its own existence, and "this looks like an LLM app" is a workable selector over that stream. METR states this as what it suspects from its analysis, not as confirmed attacker tradecraft.

2. EXTRACTION. "the attacker prompted an agent directly to reveal its model provider API key, added an SSH key for persistent access, and over the course of three weeks used the stolen credentials to consume a significant amount of API credits on publicly-available models." The agent itself was the exfiltration primitive — no file read, no container escape, no exploit. Any credential an agent can use, an unauthenticated caller of that agent can ask it for.

3. NON-DETECTION FOR THREE WEEKS. The consumed credits "would have been worth approximately $600,000, although the model developer had granted them to METR for free." METR names three reasons it went unnoticed and each is a detection-design lesson. The legitimate workload's own noise was the cover: an organisation running large-scale evaluations with pre-deployment models is "very acclimated to getting lots of weird rate limit and API errors, many of which are spurious and don't actually reflect high usage." The observable existed but was not surfaced: the internal usage dashboard "didn't show data on rate-limited requests to all users, even if they were occurring." And the economic detector was switched off: "Because we were not paying for these tokens, there was no natural token spend ceiling, and as of the incident there was no way to put a spending limit on keys like this one."

THE GENERALISATION. Billing is a security control. A comped, granted or unmetered key has that control disabled, and a high-token-volume workload has no anomaly baseline to begin with — so the two mechanisms that normally catch API-key theft are both absent precisely where agent evaluation and research work happens. If you cannot put a spend ceiling on a key, you need a rate or volume ceiling that does not depend on someone paying attention to a bill.

RESPONSE. Access revoked for the researcher, the instance stopped and imaged, all present credentials rotated, the laptop imaged and wiped, the relevant partner AI company alerted and kept updated; an external security consultant validated the findings and ran its own compromise assessment, alongside manual and agent-assisted forensics confirming no compromise beyond the single stolen key. Durable changes: policy tightened on placing METR credentials or data on non-METR infrastructure or devices, a formal security review for any researcher publicly deploying an application, wider monitoring with "noise" alerts eliminated, and spend alerts added to keys where possible.
