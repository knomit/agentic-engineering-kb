# CVE-2026-65669: AGENTS.md stored as database metadata let a db_owner escalate to sysadmin, because the agent executed with the privileges of whoever read the object

Johann Rehberger's BlueHat Asia write-up covers "[CVE-2026-65669](https://msrc.microsoft.com/update-guide/vulnerability/CVE-2026-65669), a SQL Server Elevation of Privilege Vulnerability rated critical by Microsoft." Two independent design decisions in SQL Copilot for SQL Server Management Studio combined into a privilege-escalation chain; either one alone is survivable.

**Decision one: the agent's persistent instruction documents live in the database's own metadata.** Copilot reads "**CONSTITUTION.md** which applies database-wide" and "**AGENTS.md** which can apply to individual objects, such as tables or columns", and "These are implemented as extended properties and added via the `sp_addextendedproperty` stored procedure." Writing an extended property on an object you own is an ordinary, low-privilege schema operation. It is now also a write into other users' agent context.

**Decision two: the agent runs as the reader, not as the writer.** "The important realization was that Copilot executes with the privileges of the connected user." So a principal with `db_owner` on their own database plants instructions, a sysadmin later asks Copilot about that object, and the instructions execute with sysadmin rights. No permission check fires anywhere, because every action is inside the rights of the account that happened to open the object — the same structure as [[agent-configuration]], where writing another agent's config file is a code-execution grant rather than a compromise.

**The read-only guarantee was a string matcher, and T-SQL has dynamic dispatch.** "After reversing the relevant code for `ReadFromDatabase` with my AI research crew and `ILSpy`, it turned out that the read-only enforcement is a regex-based classifier in the **LocalSqlExecutionAccessChecker** class." A procedure name held in a variable never appears at a call site: `DECLARE @p sysname='sp_who'; EXEC @p`. Any language that can name a callable at runtime defeats a pattern-matching denylist over its source text, and SQL, shells and every scripting language all can.

**Published mitigation.** Not a patch to the trust model as reported: "Microsoft [has administrative controls](https://learn.microsoft.com/en-us/ssms/github-copilot/admin-controls) for SQL Copilot, including controls to disable Copilot, configure group policies, and set an execution context." Treat an execution context setting as the control that actually addresses decision two; disabling Copilot addresses decision one by removing the feature.

**What to do, in the author's own terms:** "Read-only enforcement for an AI agent must be a security invariant (like a permission), not a model instruction or a fragile SQL classifier." Operate a database agent on a least-privileged connection rather than an administrative one, and when you add persistent instruction documents to any store, re-derive who can write them — "Persistent instructions such as AGENTS.md and CONSTITUTION.md introduce new trust relationships into the database permission model."

**What this does NOT mean.** It is not an argument against instruction files, and it is not specific to SQL Server. The transferable condition is the conjunction: an agent loads persistent instructions from a store that lower-privileged principals can write, AND the agent executes with the privileges of the principal who reads rather than the one who wrote. Check both before concluding you are unaffected — an instruction store that only administrators can write is fine, and a reader-privileged agent whose instructions come from a trusted path is fine. The general defect is that attaching an instruction channel to an existing store silently extends that store's grants to cover code execution, and the grants were sized for data.
