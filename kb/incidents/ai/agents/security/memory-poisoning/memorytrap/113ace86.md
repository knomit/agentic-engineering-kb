# MemoryTrap: one approved dependency install wrote into Claude Code's memory, its GLOBAL HOOKS CONFIG and its system prompt at once — and the v2.1.50 fix closed only the system-prompt path

Cisco's MemoryTrap finding against Claude Code, published 13 May 2026 by Idan Habler (ASI06 entry lead for OWASP's Top 10 for Agentic Applications), is an instance of ASI06 Memory & Context Poisoning that carries one detail the memory-file framing of that entry misses.

The workflow was ordinary: clone a repository, let the agent help with it, approve a dependency install the agent suggested. The payload reached THREE persistent surfaces — the agent's persistent memory, its GLOBAL HOOKS CONFIGURATION, and its system prompt — so a single approval shaped behaviour across later sessions, OTHER PROJECTS, and reboots. In the author's words: "Once those surfaces are poisoned, the system may continue treating attacker-controlled content as legitimate guidance."

Two points are not already covered by memory-file poisoning in general:

- **Hooks configuration and local agent config are part of the trusted operating environment, not convenience features.** A hook fires on the agent's own tool-call lifecycle, so poisoning it is persistence with execution attached. Persistence hunting and cross-session state diffing that cover memory files but not hooks and config will miss it entirely.
- **The entry point was the agent being helpful.** Suggesting an npm install is the agent's normal behaviour and a human approving it is the control working as designed, so there is no anomalous step for a detector to fire on.

The vendor fix and its scope. Claude Code v2.1.50 removed user memories from the system prompt, which closed the specific high-trust override path Cisco identified. The author calls this "the right fix for the path we found" and is explicit that it addresses only that path — the memory and hooks surfaces remain writable and the general shape is unaddressed. Do not read the version number as remediation of ASI06.

No CVE and no quantitative data are given. The author's recommendation is a principle rather than a control set — "memory should be treated as part of the attack surface," with scrutiny comparable to execution paths and credentials — and he raises the need for validation, separation and visibility over persistent context without prescribing a mechanism.
