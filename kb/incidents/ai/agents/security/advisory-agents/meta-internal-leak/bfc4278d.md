# An agent with no permissions caused a data exposure: it posted flawed engineering advice on an internal forum, an employee implemented it, and every control that gates agent ACTIONS was irrelevant

March 2026, reported 20 March, recorded in OWASP's Q1 2026 exploit roundup. An AI agent gave flawed engineering advice on an internal Meta forum. An employee implemented it, and the change made a large amount of sensitive user and company data available to engineers. Exposure lasted about two hours. Meta stated no user data was mishandled. No CVE. The roundup's own classification of the incident is "Unsafe agent guidance, internal data exposure, agentic misbehavior".

The structural point is what to take from it. The agent had NO permissions on the access-control system. It wrote a forum post. Every control that gates what an agent may DO — tool allowlists, approval prompts, scoped tokens, sandboxing, egress rules — was intact and irrelevant, because the human was the actuator. An advisory agent's blast radius is the set of changes its READERS are able to make, which is usually far larger than anything you would grant the agent directly.

OWASP's stated mitigations follow from that: validate recommended configuration changes with policy checks — applied to the CHANGE wherever it originated, not to the agent — restrict agent influence over access settings, require approval for visibility changes, and separate advisory AI from systems that control access.

What this does NOT mean: not that advisory agents are more dangerous than acting ones, and not that the employee was the failure. The lesson is a scoping error. An advisory deployment is commonly ruled out of agent risk review precisely BECAUSE it holds no permissions, and that is the reasoning this incident falsifies.

Scope: "a large amount" is the roundup's own quantifier — no figure is published — and the account is secondary reporting rather than Meta's own post-mortem, so the two-hour window and the no-mishandling claim are the company's statements as relayed.
