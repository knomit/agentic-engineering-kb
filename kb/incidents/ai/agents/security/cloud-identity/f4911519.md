# A scripted cloud-destruction run stayed inside the identity's existing role assignments — what blocked deletions was resource-side locks, and what gave the automation away was two tokens live in the same 70 seconds

Microsoft's account of Storm-3168 describes two compromised service principals in one Azure tenant with the work divided between them: one handled reconnaissance, the other discovery, destruction and credential collection. The authorization story is the part worth carrying. "The operations followed the identity's existing Azure role assignments." There was no escalation step to catch, because every destructive call was one the identity was entitled to make — through a group-granted Storage Account Contributor role plus direct Contributor and SQL DB Contributor roles.

WHAT HELD: "Azure resource locks and storage account-level deletion protection blocked deletion attempts." Those controls attach to the resource and do not consult what the caller is permitted to do, which is why they still functioned when the permission check had nothing to object to. The operational consequence for anyone handing an agent real cloud credentials: permission scoping bounds what the agent may ATTEMPT and bounds nothing once the grant is broad and the caller is legitimate. The layer that survives a legitimate over-permissioned identity is a resource-side protection — locks, deletion protection, immutability, separate control over backup and recovery resources — that the identity's own roles cannot lift. Recovery resources are a first-class target rather than collateral here: the run also attempted to remove Site Recovery and Azure Backup protection locks, and bulk key-listing returned keys including for Site Recovery-related accounts.

WHAT GAVE IT AWAY: the signal named is temporal and structural, not per-call. "Two of the tokens used for deletion were active during the same 70 second period", alongside the timing and the division of labour across the two principals, is what "strongly indicates automated or scripted execution". A detection keyed on the content of individual API calls sees nothing unusual, because each call is ordinary and authorized; concurrency and rate across one identity's tokens is where the shape appears.

TWO SCOPE LIMITS. The source says "automated or scripted execution" and shows no agent internals, so this is evidence about what authorized automation does to a tenant, not a measurement of model-driven agent behaviour. And it is one tenant: Microsoft could not confirm that a client ID, client secret and tenant ID exposed in a public GitHub issue was the initial access vector, and "we did not observe a ransom note or confirm successful data exfiltration". Parallel SQL deletions all failed, and Microsoft attributes that to an unsupported API version rather than to any control.

ONE SEPARABLE CREDENTIAL-HYGIENE POINT, stated by the same account: the secret had been removed from the GitHub issue, and "the secret remained accessible through the issue's public edit history". Editing or deleting the post that leaked a credential does not un-leak it, so rotation is the only remediation.
