# Sentry agentjacking: fabricated error events posted through a project's PUBLIC DSN carried the commands, and coding agents asked to investigate ran them at 85% across 100+ executions

Tenet's "agentjacking" validation, disclosed June 2026 and updated 17 June, recorded in OWASP's Q2 2026 GenAI and Agentic AI Exploit Roundup. The attacker submits FABRICATED error events to a project through its public Sentry DSN, with remediation instructions written into the event body. No compromise is needed to do this: a DSN is a write credential meant to be embedded in shipped clients, so the ingest path is open to anyone holding one.

The trigger is a developer asking their coding agent to investigate the error. The Sentry MCP integration returns the attacker's text as a tool result, and the agent executes the attacker-chosen commands with the permissions it already holds — the developer's own machine, credentials and network position. Nothing is escalated; the attacker inherits whatever the agent was already trusted with.

The figure, researcher-reported: an 85% success rate across more than 100 agent executions, in testing against Claude Code, Cursor and Codex. Read the frame before reusing it. This is controlled validation by the firm that found it, not observed exploitation in the wild, and those three harnesses are the ones Tenet tested rather than an exhaustive list of affected products.

The shape is what generalises: an observability pipeline has an unauthenticated WRITE side and a highly trusted READ side, and connecting an agent to the read side turns the write side into an instruction channel. Anything with open ingest has this property — telemetry, webhook receivers, support-ticket intake, contact forms, public issue trackers.

OWASP's stated mitigations: treat event bodies as untrusted, require approval for new commands and for package execution, and restrict shell access, available secrets and outbound destinations. Note what is NOT a mitigation. Authenticating the MCP connection, pinning the server, or trusting the Sentry vendor change nothing here: the data is attacker-authored before it ever reaches Sentry, and it arrives over a correctly authenticated channel from a legitimate service.
