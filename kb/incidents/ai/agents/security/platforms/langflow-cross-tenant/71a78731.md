# Langflow cross-tenant flow execution (CVE-2026-55255, fixed in 1.9.1): executing another tenant's flow is not reading their data, it is acting as them — so every path that RESOLVES a flow id needs the ownership check, not just the listing

Observed exploitation on 22–25 June 2026, published by Sysdig on 26 June and recorded in OWASP's Q2 2026 exploit roundup. Against Langflow deployments — particularly those sharing flows across tenants — an operator enumerated flow IDs from an exposed listing, then used a cross-tenant execution flaw (missing ownership checks) to RUN other users' flows, and sent a credential-leak request. Separately it attempted remote code execution through the public flow-build endpoint. CVE-2026-55255 covers the cross-tenant execution and CVE-2026-33017 the separate RCE path; Sysdig identifies Langflow 1.9.1 as the fix for the ownership-check flaw.

Report the outcome with the hedges the source gives. Sysdig stated the second-stage payload did not arrive, and no confirmed credential theft was established. This is observed exploitation ATTEMPTS with an unproven result, not a confirmed breach — the CVEs and the patch level are the solid parts.

Why it matters beyond one product: in an agent-building platform a FLOW is both program and credential holder, so executing someone else's flow is not reading their data, it is acting as them, with their connected integrations and their API keys. Authorization therefore has to sit on every code path that RESOLVES a flow id — execute, build, export, schedule, webhook — and not only on the listing endpoint that reveals ids. The enumeration step was a convenience for the attacker, not the vulnerability: hiding the listing and leaving the execution path unchecked fixes nothing, because an id can also be guessed, leaked or shared.

OWASP's stated mitigations: patch, enforce ownership checks on every flow-resolution path, restrict enumeration, remove public exposure, and isolate tenants.
