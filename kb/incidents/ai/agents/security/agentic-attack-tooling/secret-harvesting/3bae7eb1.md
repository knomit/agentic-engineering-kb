# An agentic framework went from searching public GitHub for secrets to exfiltrating Azure Key Vault in five minutes — and when its cloud API call was rejected for an unsupported version it retried with a supported one and got HTTP 200 about a minute later

Microsoft Threat Intelligence (published 2026-11-05) reports a campaign in which "Microsoft Threat Intelligence has observed threat actors using an agentic AI offensive framework" to search public GitHub for exposed credentials — application secrets, cloud keys and AI inference API keys — using queries built from a target organisation's name plus secret, cloud-service and AI-provider keywords, and then to use what it found. Reporting starts "Starting in August 2026, Microsoft observed threat actors", with "As early as October 28, 2026, Microsoft began observing successful service principal sign-ins".

**THE TIMELINE IS THE FINDING.** The agents could "advance from scanning GitHub for secrets to exfiltrating data from Azure Key Vault in just five minutes." Five minutes is shorter than a secret-scanning alert's triage queue, shorter than a change-approval window, and shorter than most rotation runbooks. Two consequences follow and neither is optional. First, **removing a committed secret is not remediation** — by the time the commit is reverted the credential has already been used; treat any credential that has ever been public as compromised and rotate it, rather than deleting the exposure and closing the ticket. [[f4911519]] is an independent instance of the same point from a different campaign, where the leaked secret "remained accessible through the issue's public edit history". Second, a detection pipeline whose value is "we would have caught this within the hour" has no value against this adversary; the leverage moves to prevention (managed identities instead of stored secrets, least privilege, restricted app registration) and to blast-radius limits, not to response speed.

**THE AGENT RECOVERS FROM REJECTION, AND THAT IS THE SECOND FINDING.** An Azure Resource Manager call failed because the agent used an unsupported API version; it retried "using the ARM API version 2023-07-01 and returned HTTP 200." The post times three such recoveries: "Approximately 28 seconds after the first failed response", "Approximately 60 seconds after that request", and "Approximately 80 seconds after the failed request". The design consequence: **an error response is an input to the attacker's next attempt, not a deterrent.** Any control whose protection is that a caller will get the parameters wrong — an obscure API version, an undocumented shape, a confusing rejection — expires within about a minute here.

That pairs directly against [[f4911519]], where parallel SQL deletions in an earlier campaign "all failed" and Microsoft attributed the failure "to an unsupported API version rather than to any control". The same accidental obstacle, two months apart: once it stopped the run, and once the agent stepped over it in roughly a minute. An API-version mismatch is not a control, and a campaign that it happens to stop is not evidence that it will.

Conversely the failures are the detection opportunity, because they precede the success by seconds: the post names "Sign-in errors AADSTS7000215 (invalid secret) or AADSTS7000222 (expired secret)" as the observable, and an alert that fires only on *successful* anomalous sign-ins arrives after the exfiltration.

**WHAT THE CREDENTIALS BOUGHT.** Service principal sign-ins across multiple tenants, including a multitenant application credential compromised at a vendor-owned source; then enumeration of subscriptions, roles, AI model deployments and configuration, extraction of credential-bearing settings (storage keys, App Service settings, connection strings, publishing credentials, AKS credentials), Microsoft Graph searches across SharePoint and OneDrive, tokens for single-tenant OAuth apps, Key Vault secret reads, Azure DevOps searches and Run Command on VMs.

**THE DETECTION GUIDANCE WORTH CARRYING ACROSS CLOUDS** is behavioural rather than signature-based: one source IP appearing across three or more service principals, and token requests spanning ARM, Key Vault, Storage and Graph from a single identity. Pack analysis, not the source's claim: tool-fingerprint and IP detection are the brittle half, because the post's own wording is "ARTEX by default uses Nmap, curl, wget, Python HTTP clients, Norma SDK WebFetch" — *by default* is a configuration — and of the published addresses the post says "The latter IP address is a Tor exit node". Also stated in the post: "workload identity policies require Workload ID Premium licensing", so the recommended Conditional Access control is not available on every tenant.

**TWO READING TRAPS.** (1) **This post names no threat actor in its prose.** The string STORM-0940 appears only inside a hyperlink slug pointing at an earlier (Oct 21, 2026) post about the same framework, which is the source behind [[f2df901b]]. Do not carry that attribution onto this campaign; the only attribution stated here is to the framework. (2) The corroborating vendor credit — "A similar campaign involving the same IPs addressed was also reported by [Todyl]" — says *similar campaign, same IPs*, not the same campaign, so it does not make this a two-source account of these events.
