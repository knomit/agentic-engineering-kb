# The 2001 amazon.com outage: a cache-miss fallback to the database took down the website and every fulfillment center worldwide

The documented incident behind Amazon's position against fallback, worth knowing in detail because the shape recurs in agent systems.

SETUP. A new feature displayed up-to-date shipping speeds for every product. The two-tier website architecture meant web servers queried the supply chain database directly, and the database could not keep up — high traffic, and pages showing 25 or more products each with an inline shipping speed. The fix was a caching layer running as a separate process on each web server.

THE FALLBACK. The team also handled the case where the cache process failed: if the cache is unhealthy, query the database directly. Roughly `if (cache_healthy) get_speed_via_cache(sku) else get_speed_from_database(sku)`.

WHAT HAPPENED. It worked for months. Then the caches all failed at around the same time — a correlated failure, since every web server ran the same cache process. Every web server fell back to querying the database directly and simultaneously. The load locked up the database completely. Every web server process was blocked on it, so the entire website went down. The supply chain database was also critical for fulfillment, so the outage propagated backwards: all fulfillment centers worldwide ground to a halt.

WHY IT IS INSTRUCTIVE.
1. The fallback AMPLIFIED the failure. Without it, losing the caches would have degraded one feature — shipping speeds not displayed. With it, the failure became a total site outage plus a global fulfillment outage. The fallback was worse than having none.
2. The reasoning was self-refuting from the start. The cache existed because the database could not take the load. The fallback sent the full load to the database. It could only ever work while it was rarely used.
3. Testing would not have caught it. Amazon notes that even simulating a cache failure would have missed this, because the bug required simultaneous failures across MULTIPLE machines to trigger.
4. It was latent for months. The code shipped, worked, and the triggering coincidence arrived long after everyone had moved on.

AGENT-SYSTEM ANALOGUES, which are the same structure with the labels changed: a semantic-cache or prompt-cache layer in front of an expensive model, falling through to the live model on cache failure; a retrieval cache falling through to full-corpus search; an embedding cache falling through to live embedding calls; a local/small model falling through to a frontier API. In every case the cache exists precisely BECAUSE the backing service cannot absorb the uncached load, the cache is uniform across workers so it fails everywhere at once, and the fallback then delivers exactly the load the backing service was never sized for. The safe design is to shed or degrade — serve the request without the cached enrichment — rather than to pass the full uncached load through.
