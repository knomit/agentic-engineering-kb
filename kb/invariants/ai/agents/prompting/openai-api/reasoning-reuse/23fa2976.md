# Reusable reasoning is keyed to the history in front of it: edit, shorten or insert anything in that prefix and the API drops the affected reasoning even when you return the item unchanged, and the request still succeeds

A reasoning item carried forward in the OpenAI Responses API is not self-contained. "This history is the item's prefix", and "If you edit, shorten, or insert a message in that prefix, the API drops the affected reasoning." Returning the item byte-for-byte does not save it: in the documentation's own worked example "the API drops reasoning that depended on the original rows, even if you send the reasoning item back unchanged".

WHAT MUST HOLD, stated in full: keep "the previous input and the response's output items in their original order", "keep the history that produced it intact", and "append new messages and tool results at the end". New instructions go "at the point where they take effect" rather than by rewriting an earlier message. Which items are eligible at all depends on configuration as well as history: "The selected model and reasoning.context setting determine which available reasoning items the model can use", and "For newer frontier models, the API checks the conversation history before each reasoning item you send back."

WHY THIS IS SHARP. There is no error, no status and no documented signal. "The request can continue with the conversation you provide, and the model can generate new reasoning" — so an application that trims, redacts, deduplicates or reorders history to save tokens keeps working, pays for fresh reasoning on every turn, and loses whatever the preserved reasoning was buying, with nothing in the response to attribute the regression to. The documentation's diagnostic is to "Find the first place your app changes an item it already sent."

THE PARTIAL-INVALIDATION DETAIL. Dropping is per-item and positional, not all-or-nothing: in the ledger example the reasoning BEFORE the edited tool result stays reusable and only the reasoning that came after it is dropped. So the cost of an edit scales with how early in the history it is, and an edit near the top of a long conversation is the expensive one.

A RELATED TRAP IN THE SAME MECHANISM. Histories that contain `configuration_update` items are not supported by "Automatic compaction, automatic truncation, and standalone /responses/compact"; such a history needs an explicit `compaction_trigger`, and afterwards a fresh update that restates "every setting you changed". Replacing a prefix with a summary is itself a prefix edit: "Replacing the prefix can invalidate reasoning you replay after the summary."

NOT STATED by the source: which models count as "newer frontier models", what other `reasoning.context` values exist, how the prefix boundary is computed, and whether dropped reasoning is billed.
