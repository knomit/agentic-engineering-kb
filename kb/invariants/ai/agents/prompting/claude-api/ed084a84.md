# Assistant prefill and budget_tokens are now 400 errors, not degraded behaviour — and thinking defaults differ per model

Two long-standing prompt-engineering techniques became hard failures rather than quietly-worse behaviour, which matters because a 400 takes down a production path on the day you switch models.

1. Prefilled assistant responses — supplying a partial assistant message on the LAST turn for the model to continue from — are unsupported starting with Claude 4.6 models and Claude Mythos Preview; such requests return 400. Assistant messages elsewhere in the conversation are unaffected, so it is specifically the trailing prefill that breaks. Replacements, by original use case: structured outputs (or a tool with an enum field) for forcing JSON/classification shape; a plain system instruction for preamble suppression, with post-processing to strip the occasional leak; and for continuations, move the interrupted text into a USER message ("your previous response was interrupted and ended with […] — continue from where you left off").

2. `thinking: {type: "enabled", budget_tokens: N}` is deprecated on Opus 4.6 and Sonnet 4.6 and returns 400 on Claude 4.7 and later. The replacement is `thinking: {type: "adaptive"}` with `output_config.effort`, using `max_tokens` as the hard ceiling. There is no direct token-budget equivalent — you steer depth with effort, not with a number. The rejection message names the replacement: "'thinking.type.enabled' is not supported for this model. Use 'thinking.type.adaptive' and 'output_config.effort' to control thinking behavior."

THE VERSION RULE IS NOT MONOTONIC, so check the model rather than the generation. Claude Mythos Preview supports both extended and adaptive thinking. In the other direction, Claude 4.5 and earlier models that support thinking accept extended thinking ONLY and reject `adaptive` with a 400 — so moving a request backwards across that boundary fails just as a forwards move does.

THE DEFAULT VARIES BY MODEL, AND SO DOES WHETHER YOU MAY TURN THINKING OFF AT ALL. These are two separate properties and the second is the one that removes a configuration you were relying on. Three regimes, not two:

- OFF by default, `disabled` accepted: Opus 4.6, Opus 4.7, Opus 4.8, Sonnet 4.6.
- ON by default, `disabled` accepted conditionally: Opus 5 and Sonnet 5. Opus 5 accepts `disabled` "at effort high or below; combining it with effort xhigh or max returns a 400 error", and the restriction "is enforced on each request".
- ALWAYS ON, `disabled` rejected at every effort: Fable 5, Mythos 5, Fable 5.1, Mythos 5.1 and Opus 5.5. "Models marked Always on cannot turn thinking off."

Note the direction of travel inside one model line: Opus 5 can be run with thinking disabled at effort high or below, and Opus 5.5 cannot be run with thinking disabled at any effort. A prompt and cost model built for Opus 5 with thinking off has no equivalent configuration on Opus 5.5 — the fallback is `display: "omitted"`, which hides thinking text but does not stop the thinking or its token cost.

Sonnet 5.5 is a special case carrying a THIRD thinking type. It rejects `disabled` at every effort level and takes `thinking: {type: "between_tools"}` in its place, accepted only at effort high or below and accepted on no other model. `between_tools` turns off UP-FRONT thinking, not all thinking, so it is not a rename of `disabled`.

Never assume that omitting the parameter, or passing `disabled`, means the same thing across a model migration. The authoritative per-model table — supported types, default, and which values return 400 — is the thinking-troubleshooting page, and any value it does not list as rejected is accepted.
