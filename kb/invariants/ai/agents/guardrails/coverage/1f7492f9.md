# Agent-level guardrails attach to two positions in a chain, not to the chain: input guardrails run only for the first agent and output guardrails only for the agent producing the final output, so every tool call in between is uncovered unless a tool guardrail is attached to it

OpenAI's Agents SDK offers four distinct controls, and their scopes are not interchangeable. "Input guardrails run only for the first agent in the chain." "Output guardrails run only for the agent that produces the final output." "Tool guardrails run on the function tools they're attached to." Human approval is a per-tool flag (`needsApproval: true` in JavaScript, `needs_approval=True` on the Python decorator) that pauses the run before the tool executes.

THE GAP. In a manager-style workflow — an orchestrator that calls sub-agents and tools — the first and last positions are guarded and the interior is not. The guide says this plainly: agent-level guardrails do not cover every tool call in such a workflow, and tool guardrails are what covers them. Its placement rule follows from the same thing: put validation next to the tool that creates the side effect, because that is the only position whose coverage does not depend on where in the chain the agent happens to sit.

THE MISREADING THIS EXISTS TO BLOCK. Attaching an input and an output guardrail to the orchestrator looks like guarding the run, and reads as guarding the run on an architecture diagram, but guards only the request going in and the answer coming out. Every irreversible action the run takes happens between them. Count a chain's covered surface by counting guarded tools, not guarded agents.

APPROVALS ARE RESUMABLE, AND THE STATE IS THE UNIT. On a tool that requires approval "The run records an approval interruption instead of executing the tool", "The result returns `interruptions` plus a resumable `state`", the application approves or rejects the pending items, and "You resume the same run from `state` instead of starting a new user turn." For review that is not immediate, serialize the state (`result.to_state()` in Python, `result.state` in JavaScript), store it, and resume later. Under streaming, let the run settle, inspect `interruptions`, resolve them, then resume from the same state. Interruptions also arise after handoffs and inside nested `agent.asTool()` calls, so a nested call is not a way around the gate.

BLOCKING VERSUS PARALLEL INPUT GUARDRAILS. The guide names the deciding condition rather than a default: run the input guardrail blocking when the cost or risk of starting the main agent is too high, and in parallel when lower latency matters more than avoiding speculative work. It states no default, so do not assume one — read it off your SDK version.

TWO FURTHER RULES IT STATES. Fail closed if human review times out or becomes unavailable. And Responses API and Agents SDK applications do not automatically inherit Codex Auto-review — review and enforcement have to be built into your own harness, so a control you have seen in the vendor's coding product is not present in an app you assemble from these primitives.

WHAT THE PAGE DOES NOT GIVE. No numeric limits, timeouts or default values for guardrails or approvals, and no documented behaviour for a tripped output or tool guardrail; only the input case is shown, raising a tripwire exception the application catches.

SCOPE. One vendor's SDK contract, read as documentation rather than measured. The coverage rule is specific to how that SDK binds guardrails to agents; the counting discipline it implies is not.
