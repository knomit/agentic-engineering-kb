# MCP has two error channels and picking the wrong one hides the failure from the model

The MCP spec defines two distinct, non-interchangeable error mechanisms, and the distinction is load-bearing:

- Protocol errors — standard JSON-RPC error responses. Use for unknown tool names and server-level faults. These are transport-layer problems: the call never legitimately ran.
- Tool execution errors — returned as a normal successful JSON-RPC result whose body carries `isError: true` plus the error text in `content`. Use for API failures, business-logic errors, AND input validation errors.

THE BOUNDARY MOVED IN REVISION 2025-11-25. The earlier 2025-06-18 framing put "invalid arguments" on the protocol-error side. SEP-1303, landed in 2025-11-25, clarifies that input validation errors should be returned as Tool Execution Errors rather than Protocol Errors — explicitly so the model can self-correct. If you implemented against the older reading, a tool called with a bad argument value currently fails in a way the model cannot see or fix, and moving it to `isError: true` is a behavioural improvement, not just a compliance detail. Unknown tool name remains a protocol error; a known tool called with arguments that fail validation does not.

Getting this wrong breaks the agent loop in a specific way. A rate-limit, not-found, or bad-argument condition raised as a JSON-RPC protocol error surfaces to the client as a transport failure, and the model may never see it as a tool result it can reason about and retry differently. Returned as `isError: true`, it lands in the conversation as readable text the model can act on.

Which makes the error string a prompt: "Failed to fetch weather data: API rate limit exceeded" tells the model to back off or try another source. An opaque code or a raw stack trace tells it nothing and it will re-issue the same call. For a validation error, name the offending field and the accepted form.

Rule of thumb: if the tool exists, that is `isError: true` — whether the domain said no or the arguments were wrong. Reserve protocol errors for "there is no such tool" and genuine server faults. This two-channel split survived the 2026-07-28 rewrite unchanged, and is one of the more stable parts of MCP.

THE NUMBERS UNDERNEATH CHANGED IN 2026-07-28, so hard-coded error codes need auditing:

- **Resource-not-found moved from `-32002` to `-32602`** (Invalid Params), to align with JSON-RPC. A client matching on `-32002` silently stops recognising the condition.
- A new **error-code allocation policy** partitions the JSON-RPC server-error range: `-32000` to `-32019` stays implementation-defined (existing SDK usage grandfathered), while **`-32020` to `-32099` is reserved for the MCP specification**. If you minted your own codes above `-32020`, you are now colliding with reserved space.
- Codes introduced during that draft were renumbered accordingly: `HeaderMismatch` `-32001` → `-32020`, `MissingRequiredClientCapability` `-32003` → `-32021`, `UnsupportedProtocolVersion` `-32004` → `-32022`. `HeaderMismatchError` was also added to the schema, having previously existed only in transport prose.

Separately, the same revision pushed transport-level faults onto real HTTP status codes rather than burying them in JSON-RPC envelopes — an unknown method returns HTTP 404, and an unsupported protocol version returns HTTP 400 carrying `-32022`. That means a gateway or proxy can now see and route on MCP failures without parsing the body, but it also means a client that only inspects the JSON-RPC payload will miss errors that never produced one.
