# MCP has two error channels and picking the wrong one hides the failure from the model

The MCP spec defines two distinct, non-interchangeable error mechanisms, and the distinction is load-bearing:

- Protocol errors — standard JSON-RPC error responses. Use for unknown tool names, invalid arguments, and server-level faults. These are transport-layer problems: the call never legitimately ran.
- Tool execution errors — returned as a normal successful JSON-RPC result whose body carries `isError: true` plus the error text in `content`. Use for API failures, invalid input data, and business-logic errors.

Getting this wrong breaks the agent loop in a specific way. A rate-limit or not-found condition raised as a JSON-RPC protocol error surfaces to the client as a transport failure, and the model may never see it as a tool result it can reason about and retry differently. Returned as `isError: true`, it lands in the conversation as readable text the model can act on.

Which makes the error string a prompt: "Failed to fetch weather data: API rate limit exceeded" tells the model to back off or try another source. An opaque code or a raw stack trace tells it nothing and it will re-issue the same call.

Rule of thumb: if the tool ran and the domain said no, that is `isError: true`. If the request itself was malformed or the tool does not exist, that is a protocol error.
