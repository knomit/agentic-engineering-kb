# MCP 2026-07-28 has no version handshake, and only a dual-era implementation crosses the boundary — a modern client against a legacy server can be silently served under the wrong semantics

MCP 2026-07-28 replaced session-scoped version negotiation with a per-request declaration, and the specification gained a page — docs/specification/2026-07-28/basic/versioning.mdx — that has no counterpart in any earlier revision. The interop rules below are the ones to implement against.

WHAT CHANGED, verified by comparing revisions rather than assumed. At 2025-11-25 negotiation happened at initialization and the parties "**MUST** agree on a single version to use for the session", with the server free to answer a version the client did not ask for and the client obliged to disconnect if it cannot support it. At 2026-07-28 there is no negotiation handshake: every request declares its version in `_meta` under the key `io.modelcontextprotocol/protocolVersion` (also carried in the `MCP-Protocol-Version` header on Streamable HTTP), and the server accepts or rejects each request independently. On an unsupported version the server **MUST** answer `UnsupportedProtocolVersionError` (code -32022) LISTING the versions it does support, and the client **SHOULD** pick a mutually supported one and retry. The failure mode inverted: the legacy client disconnects, the modern client retries against a disclosed list — and the modern server is obliged to disclose that list, which the legacy server never was.

VERSION ATTRIBUTION CHECKED ACROSS THE WHOLE PREDECESSOR REVISION, not the page: all 41 files of revision 2025-11-25 (docs/docs, docs/specification and schema/2025-11-25) were fetched and grepped unanchored. `UnsupportedProtocolVersionError`, `-32022`, `server/discover` and `dual-era` return ZERO hits. The token `protocolVersion` DOES appear at 2025-11-25 — 15 times across 5 files — but only as the `initialize` handshake field on `InitializeRequestParams` and `InitializeResult`, never as a per-request `_meta` key. A grep for the identifier alone would wrongly conclude nothing changed; the field moved and its meaning changed with it.

THE COMPATIBILITY MATRIX IS SEVEN ROWS, AND TWO OF THEM FAIL — DIFFERENTLY. The spec's own terms: "modern" is 2026-07-28 and later, "legacy" is 2025-11-25 and earlier, "dual-era" supports both.
- MODERN CLIENT -> LEGACY SERVER: fails, and this is the dangerous cell. The server "may reject the request with an implementation-defined error, stay silent, or even process an era-ambiguous method under legacy semantics." A request can therefore be accepted and executed under the wrong protocol's rules with no error anywhere. The stdio transport page names the concrete case: "some legacy servers do not validate that a request arrives after `initialize` and would process an era-ambiguous method (such as `tools/call`) under legacy semantics."
- LEGACY CLIENT -> MODERN SERVER: fails, and cannot recover: "Legacy clients have no fall-forward mechanism." Because of that, a modern-only server **SHOULD** name its supported protocol versions in any error it returns to an `initialize` request on any transport, since that string may be the only diagnostic the old client can show a user.
- THE OTHER FIVE ROWS WORK, AND EVERY ROW THAT CROSSES THE ERA BOUNDARY SUCCESSFULLY HAS A DUAL-ERA IMPLEMENTATION ON ONE SIDE — three such rows: dual-era client against a modern server, dual-era client against a legacy server, and legacy client against a dual-era server. (Modern/Modern and Legacy/Legacy do not cross the boundary at all; the spec puts Legacy/Legacy out of scope.) So dual-era is the only way across, and it is a property of exactly one participant, not a negotiation between them. A dual-era server selects behaviour from how the client opens (modern `_meta` -> stateless modern handling; `initialize` -> legacy semantics scoped to the process or session) and **MAY** serve both eras on the same endpoint concurrently.

ERA IS A PROPERTY OF THE SERVER, NOT OF A REQUEST. Clients **SHOULD** cache the determination for the lifetime of the server process (stdio) or origin (HTTP) and **MAY** persist it across restarts of the same server configuration, re-probing if the cached assumption later fails.

DETECTION IS SPECIFIED PER TRANSPORT, AND THE OBLIGATION IS NOT THE SAME ON BOTH — read the binding page, not the summary on the versioning page:
- **stdio**: a dual-era client **SHOULD** probe with `server/discover` before any other request, setting its preferred modern version in `_meta`. Three outcomes: a `DiscoverResult` means modern, select from `supportedVersions`; a recognised modern JSON-RPC error means modern-but-wrong-version, use its advertised `supported` list and "Do **not** fall back to `initialize`"; any other error or no response within a reasonable timeout means legacy, fall back. A MUST NOT that is easy to violate: "The fallback **MUST NOT** be keyed to one specific error code" — legacy servers answer unknown pre-`initialize` requests with implementation-defined errors, commonly -32601 or -32602, or not at all. A MODERN-ONLY client "does not need to probe, but probing is still **RECOMMENDED**", precisely to turn the silent-wrong-semantics case above into a deterministic failure.
- **Streamable HTTP**: detection is weaker by design. A dual-era client **MAY** detect the era by attempting a modern request first, and on `400 Bad Request` **SHOULD** inspect the response body before falling back. A 400 is NOT evidence of a legacy server: modern servers also return 400 for `UnsupportedProtocolVersionError`, `MissingRequiredClientCapabilityError` and header-validation failures. Recognised modern error in the body -> retry or correct the request; empty body or unrecognised -> fall back to `initialize`.

ALSO ON THE HTTP PAGE, and it is the concrete shape of what statelessness removed: 2025-03-26 through 2025-11-25 used Streamable HTTP differently — servers could assign a session via `Mcp-Session-Id` (terminated with HTTP DELETE), clients could open a standalone SSE stream with GET, servers could send JSON-RPC requests on SSE streams, and streams were resumable via `Last-Event-ID`. "None of these mechanisms are part of this revision." A modern-only server receiving such traffic **SHOULD** answer `405 Method Not Allowed` to GET or DELETE, ignore any `Mcp-Session-Id` without minting or echoing one, and ignore `Last-Event-ID`.

EXTENSION NEGOTIATION, on the versioning page: extensions are advertised in an `extensions` map inside capabilities, identifier to per-extension settings object, and identifiers **MUST** follow the `_meta` key naming rules with a mandatory prefix (e.g. `io.modelcontextprotocol/ui`, `io.modelcontextprotocol/tasks`); an empty settings object means support with no settings. If one party supports an extension and the other does not, the supporting party **MUST** either revert to core protocol behaviour or reject the request, and extensions **SHOULD** document their fallback. This capabilities-map mechanism is absent from 2025-11-25, which mentions extensions only as prose ("Additional capabilities can be negotiated through extensions to the protocol") and as a separate authorization-extensions repository.
