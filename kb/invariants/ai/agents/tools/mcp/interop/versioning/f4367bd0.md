# MCP 2026-07-28 has no version handshake, and only a dual-era implementation crosses the boundary — a modern client against a legacy server can be silently served under the wrong semantics

MCP 2026-07-28 replaced session-scoped version negotiation with a per-request declaration, and the specification gained a page — docs/specification/2026-07-28/basic/versioning.mdx — that has no counterpart in any earlier revision. The interop rules on it are the ones to implement against.

WHAT CHANGED, verified by comparing revisions rather than assumed. At 2025-11-25 negotiation happened at initialization and the parties "**MUST** agree on a single version to use for the session", with the server free to answer a version the client did not ask for and the client obliged to disconnect if it cannot support it. At 2026-07-28 there is no negotiation handshake: every request declares its version in `_meta` under the key `io.modelcontextprotocol/protocolVersion` (also carried in the `MCP-Protocol-Version` header on Streamable HTTP), and the server accepts or rejects each request independently. On an unsupported version the server **MUST** answer `UnsupportedProtocolVersionError` (code -32022) LISTING the versions it does support, and the client **SHOULD** pick a mutually supported one and retry. The failure mode inverted: the legacy client disconnects, the modern client retries against a disclosed list — and the modern server is obliged to disclose that list, which the legacy server never was.

VERSION ATTRIBUTION CHECKED ACROSS THE WHOLE PREDECESSOR REVISION, not the page: all 41 files of revision 2025-11-25 (docs/docs, docs/specification and schema/2025-11-25) were fetched and grepped unanchored. `UnsupportedProtocolVersionError`, `-32022`, `server/discover` and `dual-era` return ZERO hits. The token `protocolVersion` DOES appear at 2025-11-25 — 15 times across 5 files — but only as the `initialize` handshake field on `InitializeRequestParams` and `InitializeResult`, never as a per-request `_meta` key. A grep for the identifier alone would wrongly conclude nothing changed; the field moved and its meaning changed with it.

THE COMPATIBILITY MATRIX HAS TWO FAILING CELLS AND THEY FAIL DIFFERENTLY. The spec's own terms: "modern" is 2026-07-28 and later, "legacy" is 2025-11-25 and earlier, "dual-era" supports both.
- MODERN CLIENT -> LEGACY SERVER: fails, and this is the dangerous cell. The server "may reject the request with an implementation-defined error, stay silent, or even process an era-ambiguous method under legacy semantics." A request can therefore be accepted and executed under the wrong protocol's rules with no error anywhere. The spec's mitigation on stdio is that clients **SHOULD** send `server/discover` first so the failure is deterministic — which is the reason to make that call even though calling it is otherwise optional.
- LEGACY CLIENT -> MODERN SERVER: fails, and cannot recover: "Legacy clients have no fall-forward mechanism." Because of that, a modern-only server **SHOULD** name its supported protocol versions in any error it returns to an `initialize` request on any transport, since that string may be the only diagnostic the old client can show a user.
- Both DUAL-ERA rows work, and dual-era is the only way to bridge. A dual-era server selects behaviour from how the client opens (modern `_meta` -> stateless modern handling; `initialize` -> legacy semantics scoped to the process or session) and **MAY** serve both eras on the same endpoint concurrently.

ERA IS A PROPERTY OF THE SERVER, NOT OF A REQUEST. Clients **SHOULD** cache the determination for the lifetime of the server process (stdio) or origin (HTTP) and **MAY** persist it across restarts of the same server configuration, re-probing if the cached assumption later fails. Detection differs by transport: on stdio, probe with `server/discover` and fall back on any error that is not a recognised modern error; on Streamable HTTP, attempt a modern request and INSPECT THE BODY of a `400 Bad Request` before falling back. In both cases a recognised modern JSON-RPC error identifies a modern server and the client retries rather than downgrading.

EXTENSION NEGOTIATION, on the same page: extensions are advertised in an `extensions` map inside capabilities, identifier to per-extension settings object, and identifiers **MUST** follow the `_meta` key naming rules with a mandatory prefix (e.g. `io.modelcontextprotocol/ui`, `io.modelcontextprotocol/tasks`); an empty settings object means support with no settings. If one party supports an extension and the other does not, the supporting party **MUST** either revert to core protocol behaviour or reject the request, and extensions **SHOULD** document their fallback. This capabilities-map mechanism is absent from 2025-11-25, which mentions extensions only as prose ("Additional capabilities can be negotiated through extensions to the protocol") and as a separate authorization-extensions repository.
