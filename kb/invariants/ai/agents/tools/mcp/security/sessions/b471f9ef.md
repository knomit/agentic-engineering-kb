# MCP sessions are not authentication — and in 2026-07-28 protocol sessions were removed entirely, relocating the same attack into tool arguments

**Scope first, because the spec moved.** Everything below about session IDs is normative for MCP revisions `2025-11-25` and earlier. Revision `2026-07-28` **removed protocol-level sessions and the `Mcp-Session-Id` header from the Streamable HTTP transport altogether** (SEP-2567). If you are implementing against the current revision there is no protocol session to secure. If you are maintaining a deployment on an older revision — or a gateway bridging both — the rules still bind.

Two normative rules for revisions that still have sessions, easy to violate when carrying over habits from ordinary web session handling:

- MCP servers that implement authorization MUST verify all inbound requests, and MUST NOT use sessions for authentication. A valid session ID is not evidence of who the caller is.
- MCP servers MUST use secure, non-deterministic session IDs (secure RNG, e.g. UUIDs); sequential or otherwise guessable identifiers are disallowed. Rotation and expiry further reduce exposure.
- Servers SHOULD bind the session ID to user-specific information when storing or transmitting session data — the spec suggests a composite key of the form `<user_id>:<session_id>`, where the user ID is derived from the verified token rather than supplied by the client. This is what makes a guessed session ID useless.

The attack this closes is specific to multi-server stateful HTTP deployments with a shared event queue. An attacker who knows a session ID sends a malicious event to Server B carrying that session ID; Server B enqueues it keyed by session; Server A, polling the queue for that session, retrieves the payload and delivers it to the legitimate client as an asynchronous or resumed response. The client then acts on attacker-authored content that arrived over its own trusted channel. Resumable/redeliverable streams widen this: deliberately terminating a request before the response can cause the original client to resume it via its GET for server-sent events, and a `notifications/tools/list_changed` triggered this way can leave a client holding tools it never knowingly enabled.

**Do not read the removal as the vulnerability class being fixed — it was relocated.** `2026-07-28` tells servers that need cross-call state to use **explicit, server-minted handles passed as ordinary tool arguments**. That handle is now an unauthenticated bearer of server-side state sitting in the tool-argument namespace, where it is: visible to the model, writable by anything that can influence the model's arguments (including prompt injection), and no longer covered by any transport-layer rule about entropy, rotation, or user binding. So the three rules above do not go away at `2026-07-28` — they stop being the transport's job and become yours, applied to your own handles. Mint them from a secure RNG, bind them to the verified user identity, and re-authorize on every use, because the protocol has stopped doing any of that for you.

Related hardening in the same revision, which does genuinely close gaps rather than move them: clients MUST validate a present `iss` parameter (RFC 9207) against the recorded issuer before redeeming an authorization code; client credentials MUST be keyed by issuer identifier, MUST NOT be reused across authorization servers, and MUST be re-registered when the authorization server changes.
