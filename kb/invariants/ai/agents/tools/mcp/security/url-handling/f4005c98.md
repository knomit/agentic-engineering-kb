# Validate the scheme of MCP-supplied OAuth URLs and never open them via a shell

An MCP server supplies the authorization URL that the client opens during OAuth. If the client passes that string straight to `window.open()` or to a shell, a malicious server gets code execution.

Two normative requirements: clients MUST allow only `http://` and `https://` schemes for authorization URLs (http:// solely for loopback — localhost, 127.0.0.1, ::1 — during local development; production authorization servers MUST use https://), and MUST reject `javascript:`, `data:`, `file:`, `vbscript:` and similar. Allowlist validation is preferred over blocklisting. Separately, clients MUST NOT use shell commands (cmd.exe, sh, PowerShell) to open URLs, and SHOULD use a platform-specific non-shell opener — a URL containing shell metacharacters otherwise becomes command injection.

Why this is worse than a normal XSS: in proxy architectures where a local proxy spawns MCP servers as child processes over stdio, JavaScript execution in the client context lets the attacker read the proxy's authentication token, make authenticated requests to the local proxy, and have it spawn arbitrary commands — a browser-scoped bug escalating to RCE with user privileges. The stdio transport is not itself the flaw; it is the escalation path that turns a client-side vulnerability into system compromise, and only in proxy-based deployments, not in direct stdio use.
