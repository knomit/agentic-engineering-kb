# A multi-tenant MCP server's isolation lives in the storage shape, not in the auth check — and cleanup needs three triggers, not one

OWASP's secure MCP server development guide states the multi-tenant isolation requirement at implementation level rather than policy level, which is exactly where it tends to be mis-satisfied. For multi-tenant systems it requires isolating execution contexts, memory and temporary storage per user or agent, and it explicitly prohibits global variables, class-level attributes and shared singletons for user data. The prescribed shape is per-session objects or a session-keyed state store, its named example being Redis with `session_id` namespaces.

THE CLEANUP RULE NAMES THREE TRIGGERS AND FOUR ARTIFACT CLASSES, and dropping either half is how this gets done wrong: on session end, disconnect, **or** timeout, the server must deterministically flush file handles, temporary storage, in-memory context, and cached tokens. A teardown path wired only to a graceful session end leaves cached tokens and in-memory context live behind both an abandoned connection and an expired one.

The guide pairs this with resource limits in the same breath — per-session or per-user quotas on memory, CPU, filesystem use, and API rate — on the grounds that a shared server is a shared exhaustion target.

Operational consequence: "we validate the token on every call" does not establish tenant isolation and is not an answer to this requirement. A server can authorize every request perfectly and still hand back the previous caller's data from a module-level cache, a class attribute, or a client object initialised once at import. The check that matters is whether any user-derived value is reachable from a name that outlives the session.

What this does NOT mean: this is about the server's own process state, not the protocol's session semantics. [[b471f9ef]] covers the separate rule that an MCP session or state handle is not authentication — a server can satisfy that one and still leak across tenants through its own memory, and vice versa.
