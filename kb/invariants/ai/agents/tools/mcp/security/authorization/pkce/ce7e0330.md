# MCP makes PKCE support a discovery check that fails closed — an absent `code_challenge_methods_supported` means refuse to proceed, and MCP requires the field from OpenID providers even though OIDC does not define it

"Implement PKCE" is table stakes and not worth recording. What MCP adds is a **negotiation requirement with a fail-closed default**, and it is the part implementations skip.

MCP clients **MUST** implement PKCE *and* **MUST** "verify PKCE support before proceeding with authorization". The spec explains why this needs its own rule: "Since OAuth 2.1 and PKCE specifications do not define a mechanism for clients to discover PKCE support, MCP clients **MUST** rely on authorization server metadata to verify this capability." The check therefore has to happen out of band, against metadata, before the redirect.

*(Pack analysis, not the source's: the reason an out-of-band check is needed at all is that PKCE has no in-band negotiation — an authorization server that does not support it simply ignores the `code_challenge` parameter and the flow completes, so a client sending PKCE blindly cannot tell from the response whether it got any protection. The spec states the absence of a discovery mechanism; it does not spell out this consequence.)*

**THE TWO METADATA CASES, BOTH FAIL-CLOSED.**

- **OAuth 2.0 Authorization Server Metadata** — "If `code_challenge_methods_supported` is absent, the authorization server does not support PKCE and MCP clients **MUST** refuse to proceed." Absence is treated as a definitive negative, not as unknown.
- **OpenID Connect Discovery 1.0** — and this is the unusual one. The spec notes that OpenID Provider Metadata "does not define `code_challenge_methods_supported`", while observing the field "is commonly included by OpenID providers". It nonetheless requires clients to check for it and, if absent, to **refuse to proceed** — and then places an obligation on the provider: "Authorization servers providing OpenID Connect Discovery 1.0 **MUST** include `code_challenge_methods_supported` in their metadata to ensure MCP compatibility."

So MCP requires a metadata field that the underlying discovery specification does not define, and makes its absence a hard stop. **The deployment consequence:** a spec-conformant OIDC provider that omits the field is unusable by a conformant MCP client. *(Pack analysis again: because the client refuses before initiating authorization, the provider has no request to log — so this failure is likely to be visible only on the client side. The spec does not discuss the operational symptom; treat this as a reasonable expectation, not a documented one.)* If you operate an OIDC provider fronting MCP servers, publishing this field is a compatibility requirement even though your own spec does not ask for it.

Separately, clients **MUST** use the `S256` code challenge method "when technically capable" (OAuth 2.1 §4.1.1) — note that this is a conditional MUST, not an unconditional one.

**VERSION ATTRIBUTION, CHECKED.** This requirement is **not** new in `2026-07-28`. All three sentences appear verbatim in `2025-11-25`'s single-file `docs/specification/2025-11-25/basic/authorization.mdx` (lines 605-609); `2026-07-28` relocated them unchanged into the standalone `security-considerations` page. They are **absent** from `2025-06-18` — grep for `code_challenge_methods_supported` returns nothing there. So the discovery rule dates from `2025-11-25`. Recorded explicitly because reading only the current revision would credit it to `2026-07-28`, which is the defect class this pack has hit before.
