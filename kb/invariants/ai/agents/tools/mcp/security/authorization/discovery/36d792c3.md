# MCP told clients to probe multiple OAuth discovery endpoints in 2025-11-25 but only told them to check the document belongs to the issuer in 2026-07-28

Revision `2026-07-28` splits MCP authorization into four pages, one of which — Authorization Server Discovery — carries a normative rule that its predecessor did not have.

**THE RULE.** After retrieving an authorization-server metadata document, MCP clients **MUST** validate it as required by RFC 8414 Section 3.3 or OpenID Connect Discovery Section 4.3: the `issuer` value inside the document **MUST** be identical to the issuer identifier used to construct the well-known URL. If they differ, the client **MUST NOT** use the metadata. The spec supplies its own worked example — a document fetched from `https://attacker.example/.well-known/oauth-authorization-server` that contains `"issuer": "https://honest.example"` **MUST** be rejected.

**THE VERSION SPLIT, AND IT IS THE POINT.** The two halves of this mechanism did not ship together:

- The **probing** half dates from `2025-11-25`. That revision already required clients to attempt multiple well-known endpoints in a fixed priority order — three for issuer URLs with a path component (`oauth-authorization-server` with path insertion, then `openid-configuration` with path insertion, then `openid-configuration` path-appended), two for issuer URLs without one. Verbatim in that revision's `basic/authorization.mdx`.
- The **validation** half is new in `2026-07-28`. It is absent from revision `2025-11-25` entirely, and that revision cites RFC 8414 Section 3.1 (the metadata *request*) and Section 5 (compatibility notes) but never Section 3.3 (*validation*). The 2026-07-28 page adds the Section 3.3 citation.

*Verification method, stated so it is checkable — and note the scope, because a narrower sweep would not support the claim.* All 41 files of revision `2025-11-25` were enumerated **on the revision date rather than on a `docs/` prefix**, which pulls in the separate top-level `schema/2025-11-25/` tree alongside `docs/specification/` and `docs/docs/`; all 41 were fetched, checked for 404-bodies (none), and swept **unanchored**. Three results, each over the whole revision rather than over the one page:

1. Zero hits for the validation rule in any phrasing tried.
2. A phrasing-independent grep for `issuer` returns only the probing rules, code samples, and one **non-normative tutorial** line advising "Pin to a single issuer/tenant unless explicitly multi‑tenant. Reject tokens from other realms" — which is about rejecting *tokens*, not about validating the discovery document.
3. Every RFC 8414 citation in the revision is Section 3.1, Section 5, or unsectioned (two bare citations in the tutorial file). **No reference to Section 3.3 exists anywhere in revision 2025-11-25.**

**WHY THE GAP WAS REAL RATHER THAN OBVIOUS.** The issuer identifier a client builds the well-known URL from comes from `authorization_servers` in the MCP server's own Protected Resource Metadata. When the MCP server is untrusted, the host being probed is attacker-influenced — so "the document came back from the URL I built" is not evidence of anything without the identity check. *(That framing is pack analysis; the spec states the requirement and the rejection example, not this rationale.)* And 2025-11-25 was not a revision short on validation rules — it carries MUST-validate obligations for CIMD documents (`client_id` matching the URL, redirect URIs, JSON structure) and for access-token audience binding. The omission was specific to the authorization-server metadata document.

**DO NOT CONFLATE THIS WITH THE RFC 9207 DEFENCE** in `bdb36fce`. That one validates `iss` in the *authorization response* and fails open when the server neither advertises nor sends the parameter. This one validates `issuer` in the *discovery document* and fails closed — a mismatch is a MUST NOT. Two mix-up defences, two protocol layers, opposite failure modes; a client can implement either without the other.

**ALSO ON THIS PAGE, AND NOT NEW:** servers **MUST** implement one of the two discovery mechanisms (the `resource_metadata` parameter in a `WWW-Authenticate` header on `401`, or the RFC 9728 well-known URI) while clients **MUST** support *both*, preferring the parsed header when present and otherwise falling back to the well-known URIs in the listed order. That asymmetry — one obligation for servers, both for clients — is verbatim in `2025-11-25` and was checked rather than assumed.
