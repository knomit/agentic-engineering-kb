# MCP has two places where a client dereferences a URI the server chose — and bans the obvious implementation of both

`59a75c06` records that in MCP the SSRF victim is the *client*, via OAuth discovery. The ordinary data plane carries two more client-side dereference paths, and the spec writes MUST-level restrictions against the naive implementation of each. Both surfaces are reached by simply listing a server's tools.

**VINTAGE, since it decides what you must support.** `icons` dates from revision **`2025-11-25`** and persists in `2026-07-28`. The JSON Schema `$ref` restrictions are **new in `2026-07-28`** — no earlier revision contains the dereference ban. (Checked directly against the `basic/index` source of `2025-06-18`, `2025-11-25` and `2026-07-28`; an earlier draft of this fact wrongly presented both as `2026-07-28` additions.)

**1. JSON Schema `$ref`.** Tool schemas are JSON Schema (2020-12 by default when no `$schema` is given; implementations MUST support at least 2020-12 and MUST handle unsupported dialects gracefully with an error naming the dialect). 2020-12 permits `$ref` to point at an absolute URI, so a tool schema can name a network location — and the spec shuts that down: "Implementations **MUST NOT** automatically dereference `$ref` values that resolve to a network URI." An opt-in fetching mode is permitted but "**MUST** be disabled by default and **SHOULD** enforce an allowlist of hosts or at minimum reject loopback, link-local, and private network addresses, apply timeouts and size limits, and log dereferenced URIs" — a compact SSRF checklist inside a protocol spec.

   **The subtler half is the failure-mode rule**, which is where a validator quietly becomes permissive: "Schemas that fail to validate due to an unresolved external `$ref` **SHOULD** be rejected rather than silently treated as permissive." The default behaviour of many validators when a `$ref` will not resolve is to skip that subschema — which turns a constraint the server declared into no constraint at all. Refusing to fetch and then not refusing the schema is the bug this sentence exists to prevent.

   Related, and a genuine denial-of-service surface rather than a theoretical one: composition keywords (`anyOf`, `oneOf`, `allOf`, `if`/`then`/`else`) and `$defs` "can be expensive to validate", so implementations "**SHOULD** apply reasonable bounds, such as a maximum schema depth, a cap on the total number of subschemas, or a per-validation time budget, to prevent a malicious schema from acting as a Denial-of-Service vector against the validator." Note who the victim is — the party *validating* the schema, i.e. the client, before any tool is called.

**2. `icons`.** Servers may attach `Icon` objects (`src` URI — HTTP(S) or `data:` — plus optional `mimeType`, `sizes`, `theme`) to `Implementation`, `Tool`, `Prompt` and `Resource`. Consumers "**MUST** take appropriate security precautions" and must "treat icon metadata and icon bytes as untrusted inputs". The specific requirements read like a list of things people have shipped wrong:

   - URIs MUST be HTTPS or `data:`; clients "**MUST** reject icon URIs that use unsafe schemes and redirects, such as `javascript:`, `file:`, `ftp:`, `ws:`, or local app URI schemes", and must disallow scheme changes and cross-origin redirects.
   - "Fetch icons without credentials. Do not send cookies, `Authorization` headers, or client credentials." Verify the icon URI is same-origin as the server, to avoid "exposing data or tracking information to third-parties" — i.e. an icon URL is a beacon unless you stop it being one.
   - The payload "**MAY** contain executable content (e.g., SVG with embedded JavaScript…)". Clients that render icons MUST support `image/png` and `image/jpeg`, and only SHOULD support `image/svg+xml` and `image/webp` — the two safe formats are the mandatory ones and the risky one is optional, which is a deliberate ordering.
   - "Treat the MIME type information as advisory. Detect content type via magic bytes; reject on mismatch or unknown types", maintain a strict allowlist of image types, and bound size, dimensions and frame count against resource exhaustion.

**THE GENERALISATION WORTH CARRYING OUT OF MCP.** Every field in a tool listing that holds a URI is an outbound request your client makes on the server's instruction, before the user has approved anything and often before the model has seen the tool. Enumerate those fields when integrating any tool protocol; in the current revision they are `$ref` and `icons.src`, and the count has gone up once already. That framing is this pack's; the spec states the rules per-field without naming the class.
