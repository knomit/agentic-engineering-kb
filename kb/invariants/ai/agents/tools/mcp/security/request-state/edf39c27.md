# MCP's MRTR requestState is spec-declared attacker-controlled input — and the spec says its own replay defences do not give you single-use

MRTR removed the server's ability to hold per-request state, so that state now travels **through the client** as an opaque `requestState` string the server encodes and the client echoes back on retry. The 2026-07-28 spec is blunt about the consequence: if a client request carries `requestState`, servers **MUST treat it as attacker-controlled input**.

The concrete obligations:

- If `requestState` influences **authorization, resource access, or business logic**, servers MUST protect its integrity (e.g. HMAC or AEAD) and MUST reject state that fails verification. There is exactly one carve-out and it is narrow: integrity protection MAY be omitted only when tampering can cause nothing worse than request failure.
- To bound replay, servers SHOULD bind three things *inside* the integrity-protected payload and verify each on receipt: (1) the **authenticated principal**, rejecting state presented by a different principal; (2) a **short expiry (TTL)**; (3) an **identifier for the originating request** — the spec suggests the method name plus a digest of its salient parameters — rejecting state presented on a request that does not match.

The part worth planning against is the limit the spec names on its own advice: those three measures "bound the replay window and prevent cross-user and cross-request reuse, but do not by themselves guarantee single-use." Anything that must be consumed at most once — one-time redemptions are the spec's example — MUST enforce that invariant server-side. **So MRTR hands you no single-use primitive.** If your operation needs one, you are re-introducing server-side state, which is precisely what the revision deleted; budget for that store rather than assuming the stateless design covers you.

The client half of the contract is equally strict: clients MUST NOT inspect, parse, modify or make assumptions about `requestState`, MUST echo the exact value when retrying, and MUST NOT include one if the server did not send one. Scope is per-request — `inputRequests` and `requestState` affect only the retry of that original request and MUST NOT be attached to any other request the client has in flight in parallel.

Read this next to the session-security fact for earlier revisions: the vulnerability class was not eliminated by deleting sessions, it was **relocated onto a value the client holds and can rewrite**. Under sessions the correlation token sat behind the transport; now integrity, expiry and principal-binding are all application obligations that the transport no longer discharges for you.
