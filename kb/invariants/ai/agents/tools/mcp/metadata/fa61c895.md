# MCP's `_meta` namespace is reserved by the SECOND label, not by any label — `com.mcp.tools/` is reserved and `com.example.mcp/` is not

With the `initialize` handshake gone in revision `2026-07-28`, `_meta` is the channel every request now rides on, and its naming rules are narrow enough to fail a plausible-looking implementation.

**THE RESERVATION RULE, which is the easy one to get wrong.** A key name is an optional **prefix** plus a **name**. The prefix is dot-separated labels ending in a slash, reverse-DNS by convention. Reservation keys on **the second label only**: "Any prefix where the second label is `modelcontextprotocol` or `mcp` is **reserved** for MCP use." The spec's own examples make the boundary concrete — `io.modelcontextprotocol/`, `dev.mcp/`, `org.modelcontextprotocol.api/` and `com.mcp.tools/` are **all reserved**, "However, `com.example.mcp/` is NOT reserved, as the second label is `example`." So a vendor cannot vend under `com.mcp.*` but can freely use `com.example.mcp/`. Name segment: "Unless empty, MUST begin and end with an alphanumeric character", hyphens/underscores/dots allowed in between.

On reserved keys generally, implementations "**MUST NOT** make assumptions about values at these keys." Reserved set: `progressToken`, `io.modelcontextprotocol/protocolVersion`, `/clientInfo`, `/clientCapabilities`, `/logLevel`, `/subscriptionId`, and — **as an explicit exception to the prefix rule** — the bare OpenTelemetry keys `traceparent`, `tracestate`, `baggage`, which when present MUST follow W3C Trace Context and W3C Baggage formats. A validator that enforces the prefix grammar uniformly will reject conformant trace propagation.

**REQUIRED VS OPTIONAL, AND THE ERROR EACH PRODUCES.** Only two per-request fields are `Required: Yes` — `io.modelcontextprotocol/protocolVersion` (string, e.g. `"2026-07-28"`) and `io.modelcontextprotocol/clientCapabilities`. `clientInfo` and `logLevel` are **not** required, though clients "**SHOULD** include `io.modelcontextprotocol/clientInfo` on every request unless specifically configured not to do so." Two distinct failures follow, and they are different codes:

- Missing a required field — "the server **MUST** reject it with JSON-RPC error code `-32602` (Invalid params). On HTTP, the response status **MUST** be `400 Bad Request`."
- Needing a capability the client did not declare — "A server **MUST NOT** rely on capabilities the client has not declared", and must return `MissingRequiredClientCapabilityError` (`-32021`) "whose `data.requiredCapabilities` lists the missing capabilities", also HTTP `400`. The machine-readable list is the point: a client can repair the call from the error.

Server side, `io.modelcontextprotocol/serverInfo` is `Required: No` but SHOULD be on every result. Both info fields "are self-reported by the sender and are not verified by the protocol… Implementations **SHOULD NOT** use them to change the behavior of the client or server, and **SHOULD NOT** rely on them for security decisions" — the same warning `995c167b` records for `server/discover`, restated here for the ordinary request path.

On `subscriptions/listen` streams the server "**MUST** include `io.modelcontextprotocol/subscriptionId` in `_meta`" so notifications can be correlated to their originating subscription.
