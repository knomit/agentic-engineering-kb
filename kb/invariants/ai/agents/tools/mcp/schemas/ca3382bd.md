# MCP outputSchema: declaring one is a binding contract, and structuredContent is not LLM structured output

Spec-level rules for MCP tool results that are easy to get wrong:

- A tool definition carries `name` (unique id), optional `title` (human display), `description`, `inputSchema` (JSON Schema for parameters), optional `outputSchema`, and optional `annotations`. Revision 2025-11-25 adds optional `icons` metadata for tools, resources, resource templates and prompts, and adds explicit guidance on tool naming (SEP-986).
- If a tool declares an `outputSchema`, servers MUST return structured results conforming to it and clients SHOULD validate against it. Declaring the schema is therefore a commitment, not documentation — do not add one speculatively.
- Structured results go in a `structuredContent` field. For backwards compatibility a tool returning structured content SHOULD ALSO return the serialized JSON in a TextContent block — both, not either.
- `structuredContent` is server-produced result data. It is unrelated to LLM "structured outputs" (schema-constrained model generation) despite the naming collision, and conflating the two leads to expecting the model to enforce a server-side contract it has no part in.
- As of revision 2025-11-25, JSON Schema 2020-12 is the default dialect for MCP schema definitions (SEP-1613). Schemas written against an older draft's semantics — the usual trip hazards being `$ref` resolution, `items` vs `prefixItems` for tuples, and how `unevaluatedProperties` behaves — may validate differently than you expect. Declare `$schema` explicitly rather than relying on the default if you care.

Also worth knowing operationally: `tools/list` is paginated via a cursor, and a server that declared the `listChanged` capability SHOULD emit `notifications/tools/list_changed` when its tool set changes. A client that lists once at startup and caches forever will silently miss tools — and, worse, keep offering removed ones.
