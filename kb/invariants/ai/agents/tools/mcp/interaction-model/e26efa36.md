# MCP servers can no longer call back into the client — MRTR inverts elicitation and sampling into a retry

Under revisions through `2025-11-25`, a server that needed something mid-request sent a **server-initiated request** back down the open connection — `roots/list`, `sampling/createMessage`, `elicitation/create`. That whole direction of travel is gone in `2026-07-28`, replaced by **Multi Round-Trip Requests (MRTR)** (SEP-2322). The spec is explicit that this is a breaking change: servers **MUST** now send server-to-client requests using the MRTR pattern, and "the previous pattern of server-initiated requests is no longer supported."

The new shape inverts control:

1. The server returns an interim result of `resultType: "input_required"` — an `InputRequiredResult` whose `inputRequests` field carries what it needs, as a map from server-assigned keys to `ElicitRequest` / `CreateMessageRequest` / `ListRootsRequest` objects.
2. The client gathers that information and **retries the original request**, supplying `inputResponses` keyed identically.
3. The server correlates the retry using an opaque `requestState` token it encoded itself.

**Where MRTR is allowed at all.** Servers MAY return an `InputRequiredResult` on exactly three client requests — `prompts/get`, `resources/read` and `tools/call` — and **MUST NOT** send one on any other request. So there is no general mid-request callback: if your design needs input during some other operation, restructure it as a tool call.

**The retry contract, which is where implementations will get it wrong:**

- The JSON-RPC `id` **MUST differ** between the initial request and the retry — they are independent requests, not a continuation. Anything correlating by request id breaks.
- Servers MUST include at least one of `inputRequests` or `requestState` in every `InputRequiredResult`. If `inputRequests` is absent, the client MAY retry immediately; if present, it MUST construct the inputs first.
- Servers MUST NOT send an `inputRequests` entry the client has not declared support for in its capabilities — e.g. no `elicitation/create` to a client that never declared `elicitation`.
- Servers MUST NOT assume the client will fulfil the requests or retry at all, and MAY return `InputRequiredResult` repeatedly across attempts to keep prompting until they have what they need.
- If the client omits information the server still needs, the server SHOULD respond with a **new `InputRequiredResult` re-requesting it rather than returning an error** — the loop, not the error channel, is the recovery path. Unexpected extra fields in `InputResponses` SHOULD be ignored.

Two hard consequences:

- **Every result now carries a required `resultType` field** — `"complete"` for ordinary results, `"input_required"` for MRTR interim results. Clients MUST treat a result from an earlier-protocol server that omits the field as `"complete"`. A client that ignores `resultType` will hand the model an interim placeholder as though it were a finished tool result, which is a silent wrong-answer failure, not a crash.
- **`notifications/elicitation/complete` and the `elicitationId` field, both introduced only in `2025-11-25`, were removed.** They existed so a server could signal the outcome of an out-of-band interaction; under MRTR the client learns the outcome by retrying, so a server-initiated completion signal has nowhere to live. A server needing to correlate an elicitation across retries encodes its own identifier in `requestState`. Note the lifespan here — that mechanism was born and removed inside eight months; treat interaction-model features in MCP as unstable relative to the tool-calling core.

The design reason is the same one behind the rest of the revision: server-initiated requests require a persistent connection the server can address the client over. Once sessions and long-lived streams were removed, callbacks had no substrate, so the protocol converted them into ordinary retries of a self-contained request. The spec states the goal directly — handling these server-requests "without requiring a shared storage layer across server instances or requiring stateful load balancing."

**Migration trap:** Roots and Sampling are *also* deprecated in this revision (see the deprecation fact), so porting them onto MRTR may be wasted work — the suggested migrations bypass MCP entirely rather than re-expressing the callback.

The security obligations attached to `requestState` are substantial and are recorded separately; the short version is that the spec requires servers to treat it as attacker-controlled input.
