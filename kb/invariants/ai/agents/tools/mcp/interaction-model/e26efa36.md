# MCP servers can no longer call back into the client — MRTR inverts elicitation and sampling into a retry

Under revisions through `2025-11-25`, a server that needed something mid-request sent a **server-initiated request** back down the open connection — `roots/list`, `sampling/createMessage`, `elicitation/create`. That whole direction of travel is gone in `2026-07-28`, replaced by **Multi Round-Trip Requests (MRTR)** (SEP-2322).

The new shape inverts control:

1. The server returns an interim result of `resultType: "input_required"` — an `InputRequiredResult` whose `inputRequests` field carries what it needs.
2. The client gathers that information and **retries the original request**, supplying `inputResponses`.
3. The server correlates the retry using an opaque `requestState` token it encoded itself.

Two hard consequences:

- **Every result now carries a required `resultType` field** — `"complete"` for ordinary results, `"input_required"` for MRTR interim results. Clients MUST treat a result from an earlier-protocol server that omits the field as `"complete"`. A client that ignores `resultType` will hand the model an interim placeholder as though it were a finished tool result, which is a silent wrong-answer failure, not a crash.
- **`notifications/elicitation/complete` and the `elicitationId` field, both introduced only in `2025-11-25`, were removed.** They existed so a server could signal the outcome of an out-of-band interaction; under MRTR the client learns the outcome by retrying, so a server-initiated completion signal has nowhere to live. A server needing to correlate an elicitation across retries encodes its own identifier in `requestState`. Note the lifespan here — that mechanism was born and removed inside eight months; treat interaction-model features in MCP as unstable relative to the tool-calling core.

The design reason is the same one behind the rest of the revision: server-initiated requests require a persistent connection the server can address the client over. Once sessions and long-lived streams were removed, callbacks had no substrate, so the protocol converted them into ordinary retries of a self-contained request.

**Migration trap:** Roots and Sampling are *also* deprecated in this revision (see the deprecation fact), so porting them onto MRTR may be wasted work — the suggested migrations bypass MCP entirely rather than re-expressing the callback.
