# MCP server/discover: servers MUST implement it, clients need not call it, and nothing in its response is verified

The `server/discover` RPC in MCP 2026-07-28, read from the spec page itself rather than from the changelog summaries most of this pack's MCP facts rest on.

**The obligation is asymmetric, and both halves matter.** Servers **MUST** implement it. Clients need not call it — a client may fire any RPC directly and handle `UnsupportedProtocolVersionError` if the version is unsupported. So you cannot write a client that assumes discovery has happened, and you cannot write a server that skips it because 'our client never calls it'.

`DiscoverResult` returns `supportedVersions`, `capabilities`, an optional `instructions` string, and `_meta['io.modelcontextprotocol/serverInfo']` (name and version, which servers SHOULD include). It is a cacheable result carrying `ttlMs` and `cacheScope`.

**Nothing in that response is authenticated, and the spec says so about the part people most want to trust.** On `serverInfo`: it 'is self-reported by the server and is not verified by the protocol', is intended for display, logging and debugging, and clients **SHOULD NOT** use it to change their behaviour or **rely on it for security decisions. The concrete anti-pattern: gating tool permissions, allow-lists, or trust tiers on a server's reported name or version. A malicious server reports whatever name unlocks your most permissive policy. Bind trust to the connection's identity — the URL you configured, the OAuth audience, the pinned certificate — never to a string the peer chose.

The `instructions` field deserves the same treatment for a different reason: it is natural-language guidance 'for LLMs on how to use this server effectively', which means it is server-controlled text heading straight into your model's context. It is an untrusted input on the prompt-injection path, and it arrives before any tool has been called.

**The one case where calling it is close to mandatory is stdio.** Over Streamable HTTP a client can drive fallback off per-request HTTP status codes; on stdio there is no status code to key on. A client that wants to support both modern (per-request `_meta`) and legacy (`initialize` handshake) servers **SHOULD** send `server/discover` first and use the outcome to pick a mode. Otherwise discovery is a convenience: one round trip that replaces probing with separate `tools/list`, `prompts/list` and `resources/list` calls when you just want to display what a server offers.
