# Three implementation rules an idempotent tool must satisfy: ACID token-plus-mutation, stored parameters, bounded retention

The implementation constraints Amazon's Builders' Library places on an idempotent operation. Each is easy to omit and each failure is silent.

1. RECORDING THE TOKEN AND PERFORMING THE MUTATIONS MUST BE ONE ATOMIC (ACID) OPERATION. All-or-nothing. If they can diverge you get one of two corrupt states: the token is recorded but the resource was never created (every retry now returns success for a thing that does not exist), or the resource was created but the token was not recorded (the next retry creates a second one, which is the exact failure idempotency was meant to prevent). A tool that writes its dedupe key to one store and its effect to another, without a transaction spanning both, does not have idempotency — it has a race.

2. STORE THE ORIGINAL PARAMETERS ALONGSIDE THE TOKEN, AND VALIDATE THEM ON REPLAY. If a known token arrives with a different parameter combination, Amazon returns a validation error naming the parameter mismatch rather than serving the cached response. The reasoning: different parameters mean the caller probably intended a different outcome, so this is likely not the same request, and guessing is unsafe. For agent tools this catches a real and common bug — a harness that reuses one idempotency key across a model's revised retry, where the model corrected an argument between attempts. Silently returning the first result would discard the correction and report success.

3. RETENTION MUST BE BOUNDED, AND THE BOUND IS A DESIGN DECISION. Keeping tokens forever is impractical and actively harmful: a future request identifier could collide with one used long ago, producing a bogus cache hit. Amazon's stated rule for EC2 instances is the lifetime of the resource plus an interval after which any late-arriving request would either have arrived already or no longer be valid. Requirements vary per service and per resource type, so this is a value to choose deliberately rather than inherit.

The article is also candid that this contract is not free — it pushes real complexity into the service, and they explicitly say it is not right for every solution. Reserve it for tools with side effects that genuinely need an 'at most once' guarantee (payments, provisioning, sending, irreversible writes); read-only and naturally-idempotent tools do not need any of this.
