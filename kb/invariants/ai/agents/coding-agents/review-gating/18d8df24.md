# An agent's approval never counts as a human's, and the human who directed the agent is counted as one of the required reviewers — risk-tiered gating only works if approval binds to an identity and to one commit

Once most changes are agent-written and an automated reviewer passes them, "did a human approve this?" becomes the only remaining gate, and it is trivially satisfiable by the agents themselves unless the rules are written to prevent it. The Claude Code team's published scheme closes that in four specific ways, and all four are needed:

1. **Approval is identity-typed.** "An agent's approval never counts as a person's, either."
2. **The operator is not an independent reviewer.** On an agent-written PR, "the person directing the agent counts as one of the required reviewers" — so a two-person requirement is satisfied by the director plus ONE other, not by the director alone, and a one-person requirement is already spent.
3. **Approval binds to one artifact.** Approvals cover one specific commit, so a later push re-opens the gate rather than inheriting the earlier sign-off.
4. **Some paths are never automatable.** Owner-listed sensitive paths and any CI workflow file always require a person, and the lighter tiers apply only to authors on a trusted list.

The tiering itself: Low risk (docs, copy, internal-only features, additive changes behind a flag) needs no human approval once the automated and security checks pass; Medium (ordinary product changes, plus sensitive areas such as caching, the auto-updater and system prompts) needs one person; High needs two, and some paths always do. A classifier assigns the tier from the CHANGE rather than from who wrote it, and a second classifier can demand a person regardless of tier.

What this does NOT mean: the tiering is not a claim that low-risk changes are unreviewed. They still pass required CI (lint, types, tests across platforms, build, packaging), an AI code review and a separate security review, and both security findings and bug findings block merge until resolved; the merge queue re-runs checks against the latest main. What is removed at the low tier is the human, not the gate. Note also what the scheme deliberately leaves with people: whether to build the thing at all, risky code, architecture, reading the evidence behind a finding, and owning the outcome — and that post-merge containment (flags, internal use first, a `latest` channel before `stable`, fix forward or flag off or revert) is doing part of the work that the removed human reviewer used to do.
