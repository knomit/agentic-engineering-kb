# Claude Code mods: a hook gets 10 seconds of its OWN time per dispatch with host-call waits excluded, only host-held state survives a reload, and an undeclared state key fails validation rather than defaulting

A mod is a JavaScript or TypeScript module that runs inside a Claude Code session, declared by a plugin folder whose `hooks/hooks.json` names exactly one module. The module exports `register(on, options)` and calls `on(event, matcher?, hook)`; hooks form a middleware chain where each hook receives `($, e, next)` and may observe (`await next(e)`, then inspect the result), rewrite (`return next({ ...e, command: safer })`), or answer outright (`return { deny: "..." }` without calling `next`). Events cover tool calls, the submitted prompt, turn start and finish, session start and end, slash commands, and `ui.render`. It requires Claude Code 2.1.287 or later.

Four parts of the contract are load-bearing and each has an attractive wrong reading.

THE TIME BUDGET. "A hook gets 10 seconds of its own time per dispatch, but time spent waiting inside a `$` call doesn't count." Both halves matter together. It is not a 10-second wall clock on the dispatch, so a hook may legitimately sit for much longer while a host call it awaited is outstanding; and it is not a per-session or per-turn allowance, so a hook that burns 10 seconds of its own compute is over budget even on its first dispatch.

STATE. Module-level variables do not survive a reload, because every save re-runs `register` and `session.start`. `$.state` holds named values in the host for the whole session and does survive reloads. Anything a mod needs across reloads therefore lives in `$.state`, not in a closure.

STATE DECLARATION. A state key must be declared in the types contract: the manifest needs `"types": "./types/index.d.ts"` and that file must declare `interface PluginState { ... }`. Skipping it does not yield an undefined value at runtime — `claude plugin validate` fails, naming the key and saying the manifest's types contract must declare it. Type declarations are regenerated into `.claude-plugin/types/` on each load and are the authority for the installed version, so the generated types rather than any document are what a mod should be written against.

SUBAGENT TURNS. Subagent turns are dispatched to the same hooks and carry `e.agentId`. A hook that counts turns, accumulates context, or draws per-session UI without testing `e.agentId` silently folds subagent activity into main-loop state, and the symptom is inflated counters rather than an error.

TWO FURTHER SPECIFICS. `$.process.run` takes its arguments as an argv array, so nothing in a path is interpreted as shell code. In a render hook, a `$.state.get` subscribes that drawing, so a later `$.state.set` redraws it and no explicit invalidate call is needed; component props sit on `e.props`, with only `e.component`, `e.surface`, `e.requestId` and `e.viewport` at the top level of `e`.

TRUST POSITION. A mod runs with the same access Claude Code has, and is written by its publisher rather than by Anthropic, so installing one is a decision about the publisher and not only about the code's function.

SCOPE. Taken from the vendor's own published getting-started guide for this API at the version named above. The guide itself warns that the API can change between releases, which is why it directs readers to the generated type declarations; a limit quoted here should be re-read against the types shipped with the installed version before a design depends on it.
