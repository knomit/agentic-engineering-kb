# An agent session outlives its environment: reusing the environment ID does not restore files on replacement compute, and deleting the session neither stops the compute nor emits a webhook

In OpenAI's Agents API a session and the compute it runs on have independent lifetimes, and for a `self_hosted` environment your application owns the compute and the files. Three documented consequences are each the opposite of the intuitive reading.

THE ENVIRONMENT ID IS AN IDENTITY, NOT A VOLUME. "Reusing the environment ID does not restore files in replacement compute." The ID is how the session names an environment it expects to be connected to; it carries nothing. If work must outlive the compute, it goes to provider storage or a snapshot, and reattaching the same ID to a fresh machine gives you an empty machine under a familiar name — which is worse than an error, because the session proceeds.

DELETING THE SESSION DOES NOT STOP THE ENVIRONMENT. It also emits no deletion webhook. Provider compute must be stopped separately, so a cleanup path that deletes sessions and considers itself done leaks running machines silently, with no event anywhere to count them by.

A DISCONNECT MID-TURN CAN FAIL A TOOL EVEN IF THE TURN COMPLETES, and reconnection does not restart a command that was killed. So a completed turn is not evidence that every tool call inside it ran.

CONNECTION TIMING. Startup is requested, not assumed: a webhook receives `agent.session.action_required` with `required_action.type: "environment_connection"` (the same request appears on the session stream as `agent.session.requires_action`), and the connection events — `agent.session.environment.connected`, `.disconnected`, `.pending`, `.failed` — only report state and do not request compute. "The API waits up to five minutes for an input-time connection." A connection that arrives later still works, but "A late connection does not replay input that timed out", so the input is lost rather than queued. Initial input can also fail asynchronously and leave the session in `failed`.

WHAT THIS PAGE DOES NOT ESTABLISH. It gives no idle timeout and no maximum lifetime for an environment, and it does not say which files or processes survive a normal turn boundary while compute keeps running — `idle_timeout` appears as a session error code described only as inactivity-based. Do not infer a retention guarantee from its absence; treat anything that must survive as something you persist yourself.

SCOPE. One vendor's documented contract, for self-hosted environments in particular; the hosted-environment boundary is described elsewhere and not here.
