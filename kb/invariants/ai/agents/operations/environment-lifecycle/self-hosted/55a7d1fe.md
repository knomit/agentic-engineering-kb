# A self-hosted agent environment is one executor per session, outbound-only, with an in-sandbox key whose every other permission is None — and sharing one environment shares its credentials

Running your own compute for OpenAI's Agents API means running `codex exec-server` inside the environment, with `/workspace` created and the Codex CLI installed, and allowing outbound connections to exactly two hosts: `https://api.openai.com` for environment registration and `wss://codex-cloud-environments.chatgpt.com` for commands and results. Every connection is outbound — the executor registers with an environment ID and a restricted key, then holds a WebSocket and reconnects if it drops. There are no inbound endpoints to implement, and the remote URL is used "unchanged, including when reconnecting".

The allocation rule is one to one, and it is the constraint that shapes the deployment: "Each session has its own environment ID and needs its own executor", and "Leave the executor running while the agent works." An executor is therefore not a pool — you cannot serve many sessions from one long-lived process — and the scaling unit is a process per concurrent session, not a shared worker fleet. The agent also "needs both a connected environment and user input to start work", so a connected executor alone starts nothing.

Two keys live in two different places. The application's `OPENAI_API_KEY`, which needs `api.agents.read`, `api.agents.write` and `api.responses.write` (plus `api.vaults.read` and `api.vaults.write` for vault management), stays OUTSIDE the sandbox. The environment key is passed in as `CODEX_API_KEY`, must belong to the same organization, project and user or service account as the session, and is scoped to connecting environments and nothing else: "Set every other permission to **None**." That scoping is what makes it survivable that agent-generated code inside the environment can read the key. It must not go into source code, container images or logs, and it is rotated or revoked like any other credential.

What moves from the provider to you, relative to the hosted option: provisioning and supplying the compute; preparing the files and dependencies the agent needs; configuring the outbound allowlist; the whole key lifecycle; keeping the executor alive; passing `session.environment.id` and `session.environment.remote_url` through; and, where a webhook provisions environments, owning provisioning and cleanup policy explicitly. API environment templates apply only to OpenAI-hosted environments, so reuse is something you maintain yourself out of the environment image, `workspace_directory` and `capability_directories`.

The isolation rule is the one most likely to be traded away for cost: "Agents that share an environment can access the same files, credentials, and other resources", so environments are isolated by user or by workload. Reusing one environment across users is a cross-user data path, not an optimization, and the one-executor-per-session rule above means there is no supported way to share one anyway.
