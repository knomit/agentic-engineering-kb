# Load balancing across model instances buys zero extra throughput when the quota is scoped above the instance

Microsoft states it flatly for Azure Foundry standard deployments: "Standard quotas are subscription level, not instance level. Load balancing against standard instances in the same subscription doesn't achieve additional throughput."

This is the failure mode that makes it worth writing down: the natural response to hitting a rate limit is to deploy N instances and round-robin across them. If the quota is enforced above the instance boundary, you have built a load balancer, added a component, added latency, and gained nothing — and the symptom is that HTTP 429s continue at exactly the previous rate while your dashboard shows traffic nicely spread. The architecture looks correct and the constraint is simply somewhere else.

The corollaries Microsoft draws. To actually add standard quota you must cross the scope boundary the quota is attached to — for Azure that means deploying instances across multiple subscriptions, which is the stated reason a central team offering AI-as-a-service ends up multi-subscription. But they also say don't do that first: "Don't implement a unified gateway solely to increase quota" — prefer Global Standard or Data Zone deployments, which route to datacentres with available capacity and are themselves a gateway implementation. Provisioned throughput units and priority-processing features are also called out as NOT a substitute: priority processing reduces latency within a deployment but "doesn't increase overall quota."

The generalisable rule for any provider: before building capacity-scaling infrastructure, establish which entity the limit is actually attached to — key, deployment, instance, project, subscription, or account. Replicating anything below that level scales nothing.
