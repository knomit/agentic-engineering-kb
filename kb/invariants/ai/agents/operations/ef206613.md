# A model provider's capacity state is unobservable from the client — its scope, its level, and its health are all hidden, which rules out a whole class of standard routing designs

Two pieces of Microsoft's multi-backend guidance look like separate operational tips. Together they establish a single constraint that explains why the ordinary distributed-systems playbook mis-transfers to model endpoints: THE PROVIDER'S CAPACITY STATE IS NOT OBSERVABLE FROM THE CLIENT SIDE — not where the limit is enforced, not how much is left, and not whether the backend is healthy.

THREE THINGS YOU CANNOT SEE:

1. WHERE THE LIMIT IS ATTACHED. "Standard quotas are subscription level, not instance level. Load balancing against standard instances in the same subscription doesn't achieve additional throughput." The endpoint you address is not the entity the limit binds to, and nothing in the request or response tells you which entity it is.

2. HOW MUCH IS LEFT. Forecasting throttling from your own token accounting "is fraught with edge cases" and Microsoft's recommendation is not to try. The reasons are structural, not fixable with better bookkeeping: token counts are approximate before the response exists, capacity is shared with consumers you cannot enumerate, and the provider's accounting is the only authority.

3. WHETHER THE BACKEND IS HEALTHY. "Many AI services don't provide a dedicated health check endpoint... You can send synthetic transactions through, but doing so consumes model capacity." Cheap health probing — assumed free everywhere else — costs real money here and consumes the very resource you are protecting.

WHAT THIS RULES OUT. Predictive or capacity-aware routing (you cannot know the level). Synthetic health probing as a standing practice (you pay for every probe). Fanning out across instances to gain throughput (you may be replicating below the boundary the limit binds to). Each of these is standard practice against ordinary backends and each is either unbuildable or useless here.

WHAT IS LEFT, and it is the whole design. The response to a real request you have already paid for is the ONLY authoritative capacity signal, so the router must be reactive: assume the backend is available, and treat 429, 500 and 503 as the signal to circuit-break that instance or model for a period. For 429, honour the `Retry-After` value rather than choosing your own backoff — that is the provider telling you when capacity returns — and "don't continuously hit an endpoint that returns 429 Too Many Requests." The gateway should retry the failed request against another backend in the pool before returning an error to the client, and should report itself unhealthy when no backend remains.

BEFORE BUILDING ANY OF IT, establish which entity the limit is actually attached to — key, deployment, instance, project, subscription, or account. Replicating anything below that level scales nothing. To genuinely add standard quota you must cross that boundary, which on Azure means multiple subscriptions and is the stated reason a central team offering AI-as-a-service ends up multi-subscription.

WHAT THIS DOES NOT MEAN. It is NOT an argument for building a gateway: "Don't implement a unified gateway solely to increase quota" — prefer Global Standard or Data Zone deployments, which route to datacentres with available capacity and are themselves a gateway implementation, before writing routing infrastructure of your own. Provisioned throughput units and priority-processing features are explicitly NOT substitutes for capacity: priority processing reduces latency within a deployment but "doesn't increase overall quota." And the reactive design carries its own known blind spot rather than being cost-free — because the observed request stream is the only health signal, a LOW-TRAFFIC route has no health information at all until it fails a real user's request, which is the price paid for not probing. Note this sits against the general four-tier health-check taxonomy elsewhere in this pack, which assumes you can cheaply ask a dependency how it is; that assumption is what fails here, and only for model endpoints.
