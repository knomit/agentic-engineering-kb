# OWASP's Agent Control Standard is a wire spec for authorizing an agent action BEFORE it happens — v0.1.0, nineteen lifecycle hooks, five dispositions, and an ACS-Core signature requirement its own reference implementation does not yet meet

The Agent Control Standard, from the OWASP GenAI Security Project, is a wire specification rather than a control catalogue or a maturity model: it defines a JSON-RPC hook exchange between an Observed Agent and a Guardian Agent that decides whether an action is allowed before it happens. That is the distinction that makes it worth knowing — most AI security artefacts tell you what to require, and this one specifies the message on the wire at the moment of the decision.

SHAPE. Nineteen native lifecycle hooks, of which `toolCallRequest` is one. Five dispositions a Guardian may return: allow, deny, modify, ask, defer. Hook requests validate against schemas in the repository, 44 of them, each under the `v0.1.0` namespace. Requirements are organised in three pillars: Instrument (the hooks and dispositions), Trace (OpenTelemetry spans and OCSF events for every hook and decision), and Inspect (an agent bill of materials, serialized as CycloneDX, SPDX or SWID).

CONFORMANCE. "ACS-Core, the Instrument pillar plus the wire format and the audit chain, is the mandatory baseline." The other pillars and features are conformance profiles declared independently, so a deployment can claim ACS without the trace or inventory pillars — read a conformance claim for which profiles it names, not as a single badge. A chain may delegate to a second, agent-layer LLM when the deterministic layer cannot resolve a request, and a deterministic-only deployment is fully conformant; where that delegation exists, the LLM never reads the policy source.

THE GAP TO WATCH. "ACS-Core requires a baseline HMAC-SHA256 signature on every envelope", and the README states that the reference implementation does not implement it. The envelope signature is what makes the audit chain evidence rather than a log, so an integration built by following the reference code inherits an unsigned chain while believing itself to be on the mandatory baseline. Check for the signature in your own implementation rather than assuming the reference supplied it.

MATURITY. "Specification v0.1.0 ships today" is the README's own framing, with no explicit release date given there; "The next specification release, v0.2.0, targets March 2027", and "A v1.0 date has not been set." Treat hook names, disposition semantics and schema namespaces as pre-1.0 surfaces that will move. Building against it now is a bet on the shape — pre-action authorization over a typed wire — not on the identifiers.

SCOPE. Read from the project's own README, which is a specification document and not a measurement; nothing here establishes adoption, interoperability between independent implementations, or that any shipping agent runtime speaks it.
