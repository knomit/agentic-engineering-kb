# Context trimming must never separate a tool_use from its tool_result — plus the Strands conversation-manager defaults

The invariant first, because every hand-rolled context-trimming implementation violates it eventually: a tool-use message and its corresponding tool-result message must never be separated. The Strands Agents SDK enforces this in both of its conversation managers, calling it dangling message cleanup (sliding window) and tool pair preservation (summarizing).

Evicting a tool_use without its tool_result, or the reverse, produces a message list that most provider APIs reject outright; where it is accepted, it reliably confuses the model about what it has already done. Any naive 'drop the oldest N messages' or 'keep the last N tokens' scheme breaks this on the first eviction that lands mid-pair. If you write your own compaction, this is the first thing to test, and the failure is easy to miss in development because short conversations never trigger an eviction at all.

STRANDS DEFAULTS, useful as a reference and as a checklist of decisions a compaction layer has to make:

SlidingWindowConversationManager
  window_size = 40 messages
  should_truncate_results = True — truncate oversized tool results rather than drop messages
  per_turn = False — manage after the loop completes; True runs before every model call, an int runs every N calls
  pin_first = 0 — leading messages protected from eviction
  proactive_compression = None — enable with a ratio, e.g. {"compression_threshold": 0.7}

SummarizingConversationManager
  summary_ratio = 0.3 — fraction of oldest messages summarized per reduction (accepted range 0.1–0.8)
  preserve_recent_messages = 10 — floor on recent messages always kept verbatim
  summarization_system_prompt / summarization_agent — optional overrides, so summarization can run on a cheaper model than the main loop
  pin_first, proactive_compression — as above

Two further design decisions worth copying. On context-window overflow the sliding-window manager trims oldest-first until the request fits, but truncates TOOL RESULTS before dropping messages — preserving conversation structure while shedding the bulk, which is where the tokens actually are. That truncation is content-aware: text keeps a head and tail with markers, images and binary become typed placeholders, and status/error fields survive intact so the model can still see that a call failed and why.

And pin_first: the pin metadata is written during the FIRST context reduction and then remains set permanently, so those messages survive every subsequent reduction. This is the simplest available mechanism for keeping a system prompt or initial task statement alive across an arbitrarily long run — goal drift after compaction is a common long-horizon agent failure, and an unpinned objective is one summarization away from being paraphrased into uselessness.
