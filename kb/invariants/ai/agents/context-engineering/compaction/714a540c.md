# Context trimming must never separate a tool_use from its tool_result — plus the Strands conversation-manager defaults

The invariant first, because every hand-rolled context-trimming implementation violates it eventually: a tool-use message and its corresponding tool-result message must never be separated. The Strands Agents SDK enforces this in both of its conversation managers, and the page's own names for the two mechanisms are "Dangling Message Cleanup" (sliding window — "Removes incomplete message sequences to maintain valid conversation state") and "Tool Pair Preservation" (summarizing — "Ensures tool use and result message pairs aren't broken during summarization").

Evicting a tool_use without its tool_result, or the reverse, produces a message list that most provider APIs reject outright; where it is accepted, it reliably confuses the model about what it has already done. Any naive 'drop the oldest N messages' or 'keep the last N tokens' scheme breaks this on the first eviction that lands mid-pair. If you write your own compaction, this is the first thing to test, and the failure is easy to miss in development because short conversations never trigger an eviction at all.

STRANDS DEFAULTS — useful as a checklist of decisions a compaction layer has to make. **Read the scope note below before quoting any of these numbers.**

SlidingWindowConversationManager
  window_size — NO default is stated for either binding. The docs page shows 20 in a Python example and 40 in a TypeScript one and calls neither a default, so treat both as example values and read your own SDK rather than carrying either number across
  should_truncate_results = True — truncate oversized tool results rather than drop messages
  per_turn = False — manage after the loop completes rather than before every model call
  proactive_compression — not enabled by default

SummarizingConversationManager
  summary_ratio = 0.3 — fraction of oldest messages summarized per reduction, clamped to 0.1–0.8
  preserve_recent_messages = 10 — floor on recent messages always kept verbatim
  summarization_system_prompt / summarization_agent — optional overrides, so summarization can run on a cheaper model than the main loop
  proactive_compression — not enabled by default

One design decision worth copying regardless of the framework: on context-window overflow the sliding-window manager trims oldest-first until the request fits, but truncates TOOL RESULTS before dropping messages — preserving conversation structure while shedding the bulk, which is where the tokens actually are.

**SCOPE — WHAT THE CITED PAGE DOES AND DOES NOT SUPPORT.** The tool-pair invariant, both mechanism names quoted above, and the values listed for `should_truncate_results`, `per_turn`, `summary_ratio` (with its 0.1–0.8 clamp) and `preserve_recent_messages` are all stated on the conversation-management docs page as defaults. Three things are not. The page states no `window_size` default at all; it does not mention `pin_first`; and it carries no `compression_threshold` example for proactive compression. Any figure for those has to come from the Strands API-reference pages (`strands.agent.conversation_manager.conversation_manager`, `strands.agent.agent`), which are not among this fact's refs — so do not treat a number for them as documented here. The page also prints snake_case and camelCase spellings side by side (`should_truncate_results` / `shouldTruncateResults`), so a parameter name taken from this fact may not exist in the binding you are using. The content-aware truncation behaviour — text keeping a head and a tail with markers, images and binary becoming typed placeholders, status and error fields surviving intact — rests on one earlier read of the same host and is not backed by a quoted clause.

The surviving general point, independent of Strands: pinning the initial task statement so it survives every reduction is the simplest defence against goal drift on long runs, since an unpinned objective is one summarization away from being paraphrased into uselessness. Treat that as a design recommendation from this pack, not as a documented Strands feature.
