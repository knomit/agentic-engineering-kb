# A coding harness's sandbox covers only the harness's own shell tool — Codex leaves MCP-server tools outside it entirely

Codex's sandbox policy, in its own engineering account of the agent loop, "applies only to the Codex-provided shell tool"; "other tools, such as those provided from MCP servers, are not sandboxed by Codex".

The operational consequence: selecting a sandbox mode constrains the shell commands the harness itself runs and nothing else. Every MCP server configured into the session keeps whatever filesystem, network and credential reach its own process was started with, so the session's real blast radius is the union of the sandbox and each server process's own privileges. Audit those processes separately; a harness advertised as sandboxed does not extend that property to the tool surface MCP adds to it.

What this does NOT mean: it is not a claim that MCP calls are unapproved. Approval policy and sandboxing are separate mechanisms in this harness, and a tool can require approval while running unsandboxed. Nor is it a claim that the sandbox is weak — only that its scope is one tool, not the session.
