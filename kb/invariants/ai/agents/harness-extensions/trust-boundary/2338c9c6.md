# A harness extension is not sandboxed and inherits the user's permissions, so installing one is a code-execution grant — there is no intermediate level of trust to grant it

Claude Code mods are TypeScript or JavaScript functions that run inside the harness and can respond to prompts, tool calls and interface renders. A published account of the system states the trust position plainly: "mods aren't sandboxed." And what that buys the mod: "once it loads, a mod can read and write your files, see every prompt you send, and spend your usage."

THE OPERATIONAL CONSEQUENCE. Decide on an extension the way you decide on a dependency you will execute, not the way you decide on a configuration setting: read the code before installing a third-party one, which is what the source advises. There is no per-mod permission dialog to fall back on, so the install is the entire security decision.

WHAT THIS DOES NOT MEAN. It does not mean the harness's own permission and sandbox machinery is absent — it means the extension sits on the trusted side of it, alongside the harness, rather than being subject to it like the model's tool calls are. So a mod written to enforce a policy is enforcing it from inside the blast radius, and a mod that misbehaves is indistinguishable from the user misbehaving.

Nor does the absence of a sandbox make a mod more dangerous than any other code the user runs locally; the point is that it is exactly as dangerous, while being installed through a surface that feels like a settings toggle.
