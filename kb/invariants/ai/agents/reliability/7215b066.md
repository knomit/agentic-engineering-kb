# Agent systems assume independence in three different places and it is false in all three — replicas, clients, and successive calls within one operation

Independence is the assumption that makes reliability arithmetic work, and it is almost never stated out loud. These three facts locate it in three different places in an agent system. It is false in all three, for three different reasons, and each has its own remedy — so "assume correlation" is not one lesson but a three-item checklist.

**LOCUS 1 — ACROSS REPLICAS. The correlation lives in shared software and shared limits.** The arithmetic that justifies redundancy (one server failing at 0.01% means two failing at 0.000001%) holds ONLY when the failures are independent, and a single underlying cause routinely makes them dependent. Amazon calls this the Lemmings problem: every replica runs the same software with the same limits and the same failure modes, and load balancers distribute load evenly — which is exactly what makes the failure correlated. When an input class or load level pushes one replica past a limit, the even distribution pushes all of them past it at roughly the same moment.

For agents the shared limits are concrete: the same context-window ceiling, the same tokens-per-minute quota against the same provider, the same prompt with the same failure triggers, the same tool timeout, the same max-steps cap. **Running twenty copies of an agent gives twenty times the throughput and roughly ZERO additional protection** against a prompt that makes the model loop, an input length that overflows the window, or a provider-side rate limit — every copy hits it on the same input at the same time. Remedy: shuffle sharding (no two servers see the same exact workload) and jitter on limits and behaviours. **Diversity — different model, different provider, different prompt, different limit — is what buys independence; replica count is not.**

**LOCUS 2 — ACROSS CLIENTS. The correlation lives in behaviour, and needs no shared infrastructure at all.** This is the asymmetry that makes it easy to miss. Amazon's illustration: the author's home ISP went down, he tethered to a different provider's cellular network, and that network then slowed too — because every neighbour working from home had the same fallback and executed it simultaneously. A completely independent backup was taken down by the correlated behaviour of the clients failing over to it.

The agent version is a fallback model provider, a secondary API key, or a cheaper backup model. The failover trigger is a primary-side outage or rate limit, which is fleet-wide by nature, so **the fallback receives the entire load of the primary, instantly, from every client at once.** A fallback provisioned for "some traffic sometimes" fails at exactly the moment it is needed, and now both paths are down. Remedies: size and rate-limit-negotiate the fallback for FULL primary load rather than average spillover — or accept explicitly that it is best-effort and will shed — and stagger the failover decision itself, because a threshold every client evaluates against the same signal fires on every client at the same instant. Note the two providers can share nothing whatsoever and the correlation still exists.

**LOCUS 3 — ACROSS SUCCESSIVE CALLS INSIDE ONE OPERATION.** This is the one with no fleet dimension at all, and the one agent evals systematically miss. In single-process code, if a call to a collaborator succeeded it is reasonable to assume the next call to the same collaborator will also work — they share fate. **Across a network they do not:** the remote side can fail independently between two calls in the same logical operation.

The cost is a test-matrix multiplier, and it is per CALL SITE, not per program: single-machine Pac-Man needs 10 test scenarios; distributed, with four calls to a remote board service each having five outcomes (POST_FAILED, RETRYABLE, FATAL, UNKNOWN, SUCCESS), it needs 200. Agent evals overwhelmingly test the happy path plus a handful of hand-written error strings and then assert on the final answer. What goes untested is **the state the agent is left in when a tool succeeds and then the NEXT call to the same service returns UNKNOWN or FATAL mid-task** — where agents produce confidently wrong output, because they hold partial state, have no signal that it is partial, and carry a strong prior toward continuing. Remedy: fault injection at EVERY tool call site rather than only the first, paired with trajectory assertions rather than output-only scoring.

**WHY ALL THREE STAY HIDDEN:** distributed bugs are latent. They can sit in production for months before the combination of conditions that triggers them occurs, so **absence of incidents is not evidence of coverage** — and each of these three specifically requires a coincidence (simultaneous limit crossing, simultaneous failover, a mid-operation failure after a success) that ordinary testing does not generate.

**WHAT THIS DOES NOT MEAN.** Redundancy is still worth having — the point is that the availability number computed from independent-failure math is an **upper bound you will not reach, not a prediction**. Nor is it an argument against having a fallback provider: it is an argument for sizing it honestly or declaring it best-effort. And locus 3 is not a claim that every call site needs all five outcomes hand-tested in every eval; it is that the multiplier is real, per call site, and that the specific untested case worth covering first is failure AFTER an earlier success in the same operation.

This is a different axis from the separate finding that a control at the wrong GRANULARITY turns a partial failure into a total one, and from the finding that a stress-triggered MODE is both untested and fleet-simultaneous. Those concern where a control sits and whether a branch exists; this concerns whether the failures you are counting on to be independent actually are. Locus 2 in particular has no mode and no granularity error — the design can be entirely correct and still fail, because the correlation is in the clients.
