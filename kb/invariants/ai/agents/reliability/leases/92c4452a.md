# Check the lease before every side-effecting action, and never heartbeat it from a background thread

If an agent orchestrator or worker holds a lease to do work — the standard way to elect a coordinator, and the mechanism Amazon uses most — these are the implementation rules that separate a correct lease from one that merely looks correct. Amazon's stated experience is that leases are conceptually simple but that hardening against these issues is 'often the biggest challenge'.

1. USE ELAPSED LOCAL DURATION, NEVER WALL-CLOCK TIME. Leases depend on time, but only on locally measured duration, never on clocks agreed between machines. Amazon's blanket rule is that distributed systems use time only for human consumption. This sidesteps leap seconds, clock drift under sustained high CPU, and the general impossibility of synchronising cluster clocks well enough to order operations. Caveat that bites: verify your duration source is monotonic — if the library can observe time jumping backwards, the lease's core assumption is broken.

2. CHECK REMAINING LEASE TIME BEFORE ANY OPERATION WITH SIDE EFFECTS BEYOND THE LEADER ITSELF. Not at the top of the loop — immediately before each externally visible action. For an agent this means before each tool call that writes, sends, or spends, not once per turn.

3. ASSUME THE LEASE EXPIRED EARLIER THAN YOUR CODE THINKS. Slow networking, timeouts, retries, and garbage-collection pauses all elapse between the check and the act. A GC pause between checking the lock and doing the work is the canonical way this goes wrong, and it is invisible in testing.

4. DO NOT HEARTBEAT THE LEASE FROM A BACKGROUND THREAD. This is the counterintuitive one, and it fails in both directions. Correctness: the heartbeat thread happily renews while the work thread runs past an expiry it cannot be interrupted at. Availability: the work thread dies or stalls while the heartbeat thread keeps holding the lease, so nobody else can take over and nothing progresses.

5. PREFER A BATTLE-TESTED CLIENT OVER YOUR OWN. Amazon's stated preference is the DynamoDB or ZooKeeper lease clients, and to avoid custom implementations. For anything where at-most-one actually matters, they model and formally verify with TLA+ — the stated reason being that these bugs are subtle, rare, and hard to observe, which is exactly the class that testing does not catch.

Operationally: keep an audit trail of leadership changes so you can answer who held the lease at a given time, and track how much work a leader CAN do against how much it is doing now, so you see the scaling ceiling before you hit it.
