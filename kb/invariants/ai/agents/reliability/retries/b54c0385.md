# Retries multiply across layers: 3 retries at each of 5 layers is 243x load on the bottom dependency

Amazon's Builders' Library states the arithmetic plainly: in a stack where a customer call fans through five service layers and each layer independently retries three times, a failing database at the bottom sees a 243x load increase (3 to the power of 5). The retries compound multiplicatively — three tries, then nine, then twenty-seven — which makes recovery unlikely because the amplified load outlasts the original fault.

This is the single most transferable pre-LLM lesson for agent stacks, because agent systems nest retries by default and usually without anyone deciding to: the model retries a failed tool call, the SDK/HTTP client retries the request, the MCP server retries its own upstream, and an orchestrator retries the whole subtask. Four independent layers at three attempts each is 81x.

Amazon's rule: for low-cost control-plane and data-plane operations, retry at a SINGLE point in the stack. The tradeoff they name explicitly is that retrying only at the top layer wastes the work already done by lower layers, so it is less efficient — they accept that inefficiency to avoid amplification. Note this does NOT mean 'never retry more than once'; it means only one layer should own the retry policy, and every other layer should fail through.

OpenAI states the same rule for LLM-provider stacks and names the layers that collide there: "One layer should control retries across the application, SDK, and gateway so they do not multiply", under a shared retry budget, with a valid `Retry-After` respected and otherwise bounded exponential backoff with jitter and a limited attempt count. So the rule is not an artefact of pre-LLM service topology — the same three-layer collision exists in a plain model-API client, before any agent loop is added on top.

Also note: retries are 'selfish' — a client retrying is spending the server's resources to raise its own success probability. Where failures are rare and transient that trade is good. Where failures are caused by overload it is actively harmful and can keep load high long after the original issue is resolved.
