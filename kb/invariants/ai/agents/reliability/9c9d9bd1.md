# Every fixed queue parameter is a bet on job duration, and an agent turn has the worst possible distribution for it — heavy-tailed AND fleet-correlated

Queue systems are configured with fixed numbers — visibility timeout, in-flight cap, max time-in-queue, backpressure threshold. Every one of those numbers is an implicit bet about how long a job takes. Classical request processing makes that bet safe because durations cluster tightly. AN AGENT TURN DOES NOT, and it fails the bet in BOTH of the two ways that matter, which is why queue parameters carried over from a conventional service misbehave here specifically.

FAILURE ONE — THE DISTRIBUTION IS HEAVY-TAILED. A turn may take one tool call or forty, decided by the model at runtime. So any fixed visibility timeout WILL be exceeded by the tail. When it is, the queue hands the same message to a second consumer while the first is still working; the second also runs long, so a third picks it up. Amazon names this a fork bomb, and it is a positive feedback loop rather than a bounded annoyance: processing latency RISES under overload, so the condition that triggers duplication is the same condition duplication makes worse.

FAILURE TWO — THE TAIL IS CORRELATED ACROSS THE FLEET. A slow model endpoint shifts the WHOLE duration distribution at once, on every worker simultaneously. This is what makes it different from ordinary tail latency: you do not get a few unlucky messages duplicating, you get the entire fleet crossing its timeout together, at exactly the moment there is no spare capacity.

THE TWO STATED FIXES for the visibility-timeout case, and they are alternatives rather than a pair: HEARTBEAT the message, periodically extending the lease while genuinely still working (the same mechanism as a leader-election lease); or have the processor STOP work when the message expires, so a doomed run does not race its own replacement. Note the heartbeat option inherits the lease rules recorded separately in this pack — in particular, do not run the heartbeat on a background thread that can outlive or predecease the work.

THE OTHER PARAMETERS THE SAME DISTRIBUTION BREAKS, each with its own symptom:
- IN-FLIGHT CAPS. The cap is on messages delivered-but-not-yet-deleted, NOT on queue depth (which is effectively unbounded). Long turns hold their slots, duplicate delivery inflates the count further, and under load that cap silently becomes your real throughput limit. A handler that dequeues without deleting — an uncaught exception is the classic cause — holds its slot for the full visibility timeout.
- SQS FIFO's ~20k POLLING WINDOW. If message groups accumulate more than ~20,000 unprocessed messages between them, groups with FRESH messages beyond that window are not polled at all. So per-entity message groups do NOT give isolation under backlog: a few stuck or hot entities silently halt work for every other entity. If one tenant, repo or conversation can produce tens of thousands of messages, you need separate or sharded queues, not message groups on a shared FIFO queue.
- MAX TIME-IN-QUEUE. Bounding DEPTH does not bound STALENESS; depth says nothing about age. Record time-on-queue at every dequeue, bound it explicitly, and discard what exceeds it. And assume there are queues you have not found — OS socket buffers, framework executor queues, load-balancer surge queues — since overload testing finds them far more reliably than reading the code does.
- BACKPRESSURE THRESHOLDS. Scaling inbound admission inversely to backlog depth only works if the depth you can MEASURE is the workload you are throttling; on a shared queue you throttle innocent workloads too, and SQS exposes total depth but not per-attribute counts. Queue topology, decided earlier, determines whether fair backpressure is available at all.

WHAT TO MEASURE INSTEAD OF GUESSING THE PARAMETERS: the AGE of messages at dequeue, and specifically first-attempt age, because producer error rate merely mirrors the queue service's own availability, consumer error rate makes things look better than they are (retries usually succeed), and dead-letter volume is a good measure that arrives far too late to act on. Categorise first-attempt latency separately from retry latency — for an agent platform that is the difference between 'the run queue is backing up' and 'one customer's webhook is flaky'. Track the fraction of polls returning EMPTY as a cheap saturation signal: empty polls are headroom, and if nearly every poll returns a message a small spike converts directly into sustained backlog. For in-memory queues, stamp your own enqueue time BEFORE enqueueing, or time-in-queue is unmeasurable after the fact.

THE PREREQUISITE NOBODY GETS TO SKIP: because duplicate parallel delivery is not preventable in general, an agent task handler that has side effects MUST be idempotent. That is a consequence of this distribution, not an optional hardening step.

WHAT THIS DOES NOT MEAN. Not an argument against queueing agent work — but do make the async-vs-sync choice knowing the recovery arithmetic: a one-hour outage needs DOUBLE steady-state capacity for a further hour just to return to normal, and a spike queueing 10x what the fleet is scaled for takes 10x as long to drain (a 30-minute spike noticed 30 minutes late produced a 300-minute drain in Amazon's worked example). Choose async when losing the request is worse than serving it very late; choose sync when a stale answer is worthless, which is most interactive agent work. Nor does 'asynchronous' mean latency stops mattering — even async systems are expected to hit subsecond latency in practice, and the durability-for-latency trade is easy to accept without noticing you also accepted an unbounded recovery time. Scope note: the ~20k figure and the in-flight/depth distinction are SQS-specific limits; the heavy-tailed-and-correlated property of agent turns is the general claim, and you should re-derive the specific numbers for whatever broker you use.
