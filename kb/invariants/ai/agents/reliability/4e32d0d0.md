# A mode is a branch that only executes under stress — so it is simultaneously your least-tested code and the code most certain to run fleet-wide at once

Six of these facts describe different mechanisms — caches, fallbacks, health checks, control-plane config, constant work — and share a structure none of them names on its own. **Every one of them is a MODE: a branch whose condition is "the system is under stress". That gives it two properties simultaneously, and it is the conjunction that kills.**

**PROPERTY ONE — A MODE IS THE LEAST-TESTED CODE YOU HAVE**, because the condition that selects it is the condition you rarely reproduce. The 2001 amazon.com outage is the documented case: the cache-miss-falls-back-to-database branch shipped, worked for months, and Amazon's own assessment is that **even simulating a cache failure would not have caught it**, because the bug required simultaneous failures across MULTIPLE machines to trigger. The code was correct in isolation and wrong in aggregate, and no single-machine test expresses that.

**PROPERTY TWO — THE TRIGGER IS FLEET-CORRELATED BY CONSTRUCTION.** A mode selected by "stress" fires on every replica at once, because stress is what load balancers distribute evenly. The caches in 2001 all failed at around the same time precisely because every web server ran the same cache process; every server then fell back simultaneously and delivered the database exactly the load the cache existed to prevent. The same correlation is why dependency health checks must not drive fast automation: they fail in a correlated way, so a provider-side blip fails the check on every worker at once and drains the fleet during the incident you most need capacity for.

**THE TWO PROPERTIES COMPOSE INTO THE CHARACTERISTIC FAILURE:** untested code executes, everywhere, at the worst moment, at full scale. That is why a fallback can be **worse than having none** — without it, losing the caches in 2001 would have degraded one feature (shipping speeds not displayed); with it, the result was a total site outage plus every fulfillment center worldwide.

**THE MODES TO GO LOOKING FOR, each with its stated symptom:**

- **A cache is a mode, not an optimisation.** It has two transitions and both fire under stress: cold/empty (any deploy, restart, eviction wave or key-schema change puts the whole system into its slow mode at once) and overwhelmed (traffic the cache was absorbing lands directly on a backing source never scaled for it). Caches look anti-fragile — they improve more as hit rates climb — and most actually AMPLIFY fragility when over-stressed.
- **A health check on a dependency is a mode.** It converts a SOFT dependency (the service can still do useful work without it) into a HARD one: when the dependency goes down your service goes down too, manufacturing a cascading failure with larger scope than the original fault.
- **A fallback path is a mode**, and its reasoning is often self-refuting on inspection — the 2001 fallback could only ever work while it was rarely used, because the cache existed precisely because the database could not take the load.
- **Fetching configuration at startup is a mode** you discover only during recovery. Surviving a control-plane outage on warm in-memory cache is easy and is NOT static stability; static stability means a worker that boots cold DURING the outage, or one autoscaling adds during it, also comes up working. Otherwise a control-plane blip does not degrade the fleet, it prevents every new agent process from starting — precisely when the fleet is restarting.

**THE DESIGN RESPONSE IS TO DELETE THE MODE, NOT TO HANDLE IT BETTER.** Constant work names this as an explicit property: no modes, the same operations run in all conditions, and any variation makes the system do LESS work under stress rather than more. The two concrete mechanisms are *pad to the maximum always* (Route 53 health checkers send a fixed-size result set sized to the maximum supported — 10,000 results when 10 checks are configured, 9,990 of them dummies) and *reload everything unconditionally* (Hyperplane nodes fetch and process the whole config from S3 every few seconds even when byte-identical). The payoff is the AZ-failure case: when tens of thousands of health checks fail simultaneously, the system does exactly what it was already doing — there is no "Availability Zone unreachable" mode to enter. Where deleting the mode is not available, the fallback rule is to **prefer paths that carry production traffic continuously over paths that activate only on failure**, since a path exercised continuously is no longer a mode.

**WHAT THIS DOES NOT MEAN — carried from the sources, because each blocks a specific misreading.**

- **Not "do not cache."** It means size and test the backing service for the cache being ABSENT, treat cold-start as a load case you have measured rather than a transient, and never let a cache be the reason a capacity number looks affordable. Amazon states a genuinely anti-fragile cache is possible but is its own body of work, not a property you get by adding one.
- **Not "do not health-check dependencies."** The prescription is placement: restrict FAST-ACTING load-balancer checks to liveness and local checks only (resources not shared with peers, unlikely to fail fleet-wide at once), and hand dependency checks and anomaly detection to slow, rate-limited central monitoring that escalates to humans. The stated principle is to stop sending traffic to ONE bad server while continuing to send traffic when the WHOLE fleet looks sick. Fail-open is the mitigation that lets you keep deep checks, but Amazon is sceptical of it — they have no general proof it triggers correctly for every kind of overload, partial or gray failure, and a dependency that is merely SLOW or failing at a low rate makes servers flap without ever crossing the fail-open threshold. Test that partial-failure case specifically if you rely on it.
- **Constant work does not fit everywhere.** Its own author excludes fleets where elastic scaling saves real money — a site needing 100 web servers at peak and 50 off-peak should scale — and adds that the daily scaling exercise itself has value because it shakes out problems. Note also that O(1) here means a CONSTANT number of operations regardless of input size, not a small number (both examples do many thousands per tick; O(C) is the honest notation), and that constant work is bounded rather than infinite: sizing comes from a cellular design where the sustainable units per cell are measured and a new cell added as the limit approaches.
- **Static stability has a real cost, not an imaginary one.** It means running on STALE configuration, so any control action that must take effect promptly — revoking a tool, disabling a tenant, killing a runaway model version — cannot use the same path and needs its own fast channel with its own failure mode.
- **This is a different axis from granularity.** The separate finding that a control at the wrong GRANULARITY turns a partial failure into a total one is about where a control is placed; this is about whether a branch exists at all. They compose rather than substitute, and the granularity finding's own caveat still holds — an imprecise control is usually still better than none.

**AGENT-SPECIFIC INSTANCES**, since the labels change but the structure does not: prompt/prefix caches, embedding and retrieval caches, tool-result caches and model-response caches all have both cache transitions, and the second one — a cache-miss storm arriving at a rate-limited model or vector store — converts a latency problem into an outage. A fallback model provider is the 2001 pattern exactly: the fallback receives the entire load of the primary, instantly, from every client, because the trigger is fleet-wide. Optional tools (web search, a code interpreter, one MCP server among several, a memory store, an observability sink) must not sit in a worker's readiness probe, or every optional capability becomes a hard dependency for the whole agent — let them degrade by returning a tool error the model can route around, which is a failure it can handle, unlike being removed from the pool, which it cannot. And the configuration to make statically stable is the system prompt, the tool and skill catalogue, model routing and fallback policy, per-tenant limits, and credentials scope.
