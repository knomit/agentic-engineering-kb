# Bounding a queue's DEPTH does not bound how stale its work is — you must also bound time-in-queue and discard what exceeds it

A bounded queue still hands the worker requests nobody is waiting for any more, because depth says nothing about age. Amazon's practice is to record time-on-queue as a service metric at every dequeue and to place an explicit upper bound on it, throwing away work that exceeds the bound so the worker can spend itself on newer requests that still have a chance of being useful. Where the protocol permits, they go further and use a LIFO queue rather than FIFO — under overload the newest request is the one most likely to still have a waiting client. (HTTP/1.1 pipelining on one connection cannot do LIFO; HTTP/2 generally can.)

The part that generalises hardest: queues you did not know about. Amazon's stated stance is to ASSUME there are queues you have not found — OS socket buffers hold pent-up requests per connection, web framework executors have a queue in front of the thread pool, and load balancers have surge queues. Their guidance on that last one is specific: a load-balancer surge queue causes brownout because the server receives a request with no idea how long it waited, so a spillover configuration that fast-fails excess requests is the safer default than one that queues them. This learning was built into the next generation of the product — the Classic Load Balancer used a surge queue, the Application Load Balancer rejects excess traffic instead.

Every one of these has an agent analogue: the task queue in front of a subagent pool, an MCP server's request buffer, a batching layer in front of a model endpoint. The invariant to hold is that any queue without a maximum AGE will, under overload, deliver work whose requester is already gone — and overload testing finds these queues far more reliably than reading the code does.
