# SQS FIFO polls only the newest ~20k unprocessed messages, so a backlog in a few message groups starves every other group

A spec-level limit that is easy to get wrong when using FIFO queues to serialise per-entity agent work. SQS FIFO guarantees in-order consumption WITHIN a message group while allowing different groups to proceed in any order — which is exactly why people reach for it: one message group per conversation, per user, or per repository gives you per-entity serialisation with cross-entity parallelism.

The limit that breaks the guarantee you thought you bought: SQS FIFO only polls the most recent ~20,000 unprocessed messages. If a subset of message groups accumulates more than 20k unprocessed messages between them, groups with FRESH messages sitting beyond that window are starved out entirely — they are not slow, they are not polled at all. A small number of stuck or hot entities can therefore silently halt work for every other entity on the queue.

The practical consequence for an agent platform: per-entity message groups do NOT give you isolation under backlog. If one tenant, repository, or conversation can produce tens of thousands of queued messages, you need a separate queue or a sharded queue pool for isolation, not message groups on a shared FIFO queue.

Related in-flight limit on standard queues, same failure shape: the cap is on messages delivered-but-not-yet-deleted, not on queue depth, and any handler path that dequeues without deleting (an uncaught exception is the usual cause) holds its slot for the full visibility timeout.
