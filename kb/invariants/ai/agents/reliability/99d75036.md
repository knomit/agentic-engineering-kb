# Load shedding is never a local decision — it couples to your metrics, your autoscaler and your router, and all three couplings point the wrong way

Load shedding is usually designed as a property of one service: past a threshold, reject cheaply. Four separate findings show it is actually a property of the SYSTEM, because shedding couples to three adjacent components — and in all three cases the coupling is a positive feedback loop pointing away from recovery. Each source sees only its own coupling; the checklist below is the union.

ThE COMMON CAUSE, worth stating once: REJECTION IS FAST. A shed request completes in milliseconds against multi-second real work. Every one of the three failures below is downstream of that single fact.

COUPLING 1 — TO YOUR METRICS. Every shed request enters the latency histogram as a very fast sample. A service shedding 60% of its traffic can show excellent median latency while the requests it actually served are terrible. Errors are fast in general — access-denied, throttling and validation responses all return quickly — so ANY spike in rejections makes latency look deceptively good. The name for this is metric pollution, and the consequence is that your system looks fastest at its worst moment. FIX: log a SEPARATE timer for successful responses and dashboard/alarm on that, not on a generic Time metric covering all outcomes. Keep rejection count and rejection RATE as first-class metrics rather than letting rejections hide inside a p50.

COUPLING 2 — TO YOUR AUTOSCALER. If the service sheds on the same utilisation signal the autoscaler scales on (CPU, in-flight concurrency, queue depth), the shedder wins: it rejects enough work to hold the metric below the scaling threshold, so the scaler never fires. The system stabilises in a permanently degraded state, rejecting traffic and refusing to grow. The second-order version bites even when the thresholds differ: teams infer headroom from system metrics when sizing for the loss of an availability zone, and shedding makes those metrics understate how close the fleet is to its rejection point — so the fleet looks like it has redundancy it does not have. FIX: separate the signals (shed on request age or queue latency, scale on offered throughput INCLUDING rejected requests), or set the shed threshold strictly above the scale-out threshold so scaling always fires first. And note the stated consequence: with shedding in play you must LOAD-TEST TO BREAKAGE to know real capacity, because inferring headroom from CPU stops working.

COUPLING 3 — TO YOUR ROUTER, and this one inverts the standard advice. Behind a least-outstanding-requests balancer, a shedding server's in-flight count drops fastest, so the balancer concludes it is the HEALTHIEST node and steers more traffic into it. The overloaded server gets hammered precisely because it fails efficiently. DOCUMENTED INSTANCE: one server in amazon.com's remote catalog service filled its disk, mishandled the error, and began returning EMPTY responses very fast; the balancer noticed only that it was faster than its peers and steered a large share of all site traffic into it, taking the whole site down. Note the trigger need not be a deliberate shed or even an error status — ANY degraded-but-fast path does it, including a success-coded empty result. FIX: slow shed responses to match the latency of successful ones so the in-flight signal stays honest. CHECK FIRST which algorithm your router uses: round-robin and connection-count balancers do NOT have this inversion; least-outstanding-requests and latency-aware ones do.

AND WHEN YOU DO SHED, THE ORDERING IS COUNTER-INTUITIVE: prioritise requests that FINISH work over requests that START it. Given start() and end() APIs, prioritise end() — admitting work that then cannot complete is the definition of a brownout. Given a paginated API, prioritise page N over page 1, because a client failing at page N-1 has wasted N-2 calls plus retries. The unifying rule: shedding a request that would have COMPLETED a chain destroys all the work already spent on it; shedding one that would have STARTED a chain destroys nothing.

THE AGENT-SPECIFIC SHARPENING: cheap-rejection paths are everywhere in an agent stack — a tool server returning 429, an orchestrator refusing to spawn a subagent past a concurrency cap, a router rejecting before the model, a guardrail refusing a prompt. So coupling 1 is near-universal here. For coupling 3, the agent version of the fast-empty-response is a worker returning truncated, refused, or zero-token completions quickly: it looks like the best endpoint to a latency-aware router, and nothing in the routing layer inspects whether the completion was USEFUL. For the ordering rule, a subagent's final write-back, a session's commit/finalise call, and later pages of a search tool should all outrank fresh task submissions.

A SECOND METRICS AXIS worth adopting at the same time: where latency depends heavily on input or response SIZE, emit bucketed metrics (SmallRequestLatency / LargeRequestLatency) rather than one blended timer — agent turns vary by orders of magnitude in context length and tool-result size, so a blended metric mixes distributions with nothing to do with each other. Pair it with bounding request and response sizes in the first place, to avoid complex brownout modes.

WHAT THIS DOES NOT MEAN. Not an argument against load shedding — it is genuine capacity protection and all four sources keep it. Not an argument to stop measuring rejected requests either: the rule is to stop MIXING them into the same distribution as served requests. A persistently non-zero false-positive rate (rejecting while capacity was actually available) should be treated as evidence the service is tuned too sensitively or has a load-balancing imbalance, not as normal operation. And prioritisation has its own limit: in a large architecture where many services each apply local prioritisation heuristics, conflicting heuristics can hurt system-wide availability — push prioritisation as early as possible, ideally at the service receiving the original request, rather than deciding independently at every layer.
