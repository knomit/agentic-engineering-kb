# When a pinned backend fails mid-conversation, return the error — rerouting to an instance with no history hides the failure instead of handling it

Stateful model APIs — Microsoft names the Assistants API, and the same applies to any server-side conversation or response state — require the gateway to pin a client to one backend for the duration of the interaction, typically by storing instance data in a cookie. The non-obvious part is what to do when that pinned backend becomes unavailable partway through.

Microsoft's recommendation: "consider returning an API response like a 429 to a pinned client instead of redirecting it to a different back-end instance. Doing so allows the client to explicitly handle sudden unavailability rather than hiding it and being routed to a model instance that has no history."

The reasoning generalises past this one API. Rerouting a stateless request to a healthy peer is a fix; rerouting a STATEFUL request to a peer is a silent semantic change, because the new backend answers the same call from a different — usually empty — conversation state. The client gets a 200 and a coherent-looking response computed without the history, which is strictly worse than an error: the failure is now indistinguishable from success and will be discovered, if at all, as inexplicable model behaviour further downstream. An agent is especially exposed here because it will accept that response and keep going.

This is the same rule as the general argument against fallback in distributed systems — a fallback path that is not exercised continuously is a mode you have not tested — applied to conversation state, and it is the reason session affinity cannot be treated as a pure performance optimisation. Note the tension worth holding: session affinity is REQUIRED for stateful APIs, and it is also what converts a small per-request defect into a large per-user one when the pinned backend is subtly wrong rather than down. Pinning concentrates both correctness and failure onto the same client.
