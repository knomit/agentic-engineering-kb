# Health-checking a dependency converts it from a soft dependency into a hard one

Stated directly in Amazon's Builders' Library, and it is the sharpest single sentence on health check design: if a service only sometimes calls a dependency, that is a SOFT dependency — the service can still do useful work without it. The moment you add a health check that tests that dependency, and there is no fail-open protection, you have made it a HARD dependency. When it goes down, your service goes down too, and you have manufactured a cascading failure with a larger scope of impact than the original fault.

The same argument applies below the service level. A service usually serves several APIs with different dependencies; failing the whole server's health check because ONE code path is unhealthy widens the blast radius unnecessarily. Their examples: a control plane (occasional CRUD) and a data plane (high-throughput, business-critical) in one service — the data plane should keep serving when the control plane cannot reach its dependencies. And a read API that caches locally can keep serving cached reads while its database is down, unless a health check takes it out of service first.

The agent translation is immediate and commonly gotten wrong. An agent typically has many optional tools — web search, a code interpreter, one MCP server among several, a memory store, an observability sink. Putting any of those into the worker's readiness probe converts every optional capability into a hard dependency for the entire agent. The agent that could have answered from context, or used the other four tools, is instead removed from the pool. Health check only what the agent cannot do ANY useful work without, and let the rest degrade by returning a tool error to the model — which is a failure the model can route around, unlike being taken out of service, which it cannot.

The article also uses this as a lens on service granularity: 'which dependencies do I health check, and does failing them increase my scope of impact' is a more useful question for deciding how micro to make a service than the usual ones.

Fail-open (the load balancer allows traffic to everything when ALL servers report unhealthy — supported by AWS Network Load Balancer, Application Load Balancer, and Route 53) is the mitigation that lets you keep deep checks. Amazon's own caveat: they are sceptical of it because they have no general proof it triggers correctly for every kind of overload, partial failure, or gray failure, and a dependency that is merely SLOW or failing at a low rate makes servers flap in and out of service without ever crossing the fail-open threshold. Test that partial-failure case specifically if you rely on it.
