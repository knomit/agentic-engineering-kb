# A failover edge is a policy decision wearing a routing decision's clothes — and it is the least-reviewed path in the system because it only runs during an incident

Three independently-sourced rules about routing model traffic turn out to be the same rule. In each, the act of sending a request somewhere else silently changes a property that has nothing to do with traffic — and in each, the change is made by code that executes only when something is already going wrong.

THE THREE INSTANCES, and what each failover silently breaks:

1. JURISDICTION. Failing over across a geopolitical boundary breaks a residency guarantee, and Microsoft is categorical rather than cautionary: a unified gateway spanning geopolitical regions "would violate the data residency requirements." Note the guarantee is narrower than people assume in the first place — for Azure Global and Data Zone deployments, "data stored at rest remains in the designated Azure geography," but that data "might be transmitted and processed for inferencing in any hosting location." So residency covers storage; the prompt itself — which for an agent carries retrieved documents, tool outputs and conversation history — crosses at inference time.

2. CONVERSATION STATE. Failing a pinned, stateful request over to a peer is a silent semantic change, because the new backend answers from a different and usually empty state. Microsoft's recommendation is to return an error instead: "consider returning an API response like a 429 to a pinned client instead of redirecting it to a different back-end instance," so the client "can explicitly handle sudden unavailability rather than hiding it and being routed to a model instance that has no history." The client otherwise gets a 200 and a coherent-looking answer computed without the history — worse than an error, because the failure is now indistinguishable from success. An agent is especially exposed: it accepts the response and keeps going.

3. COMPLIANCE POSTURE. "Routing to a fallback under load is where a compliance boundary silently gets crossed" — any fallback model must satisfy the SAME data-handling, residency and safety requirements as the primary, and the gateway itself sits where it can see raw prompts and raw completions, so regulatory scope covers it too.

THE COMMON STRUCTURE, and why it is dangerous. A failover edge is written as though its only output is "which backend," but it also outputs which jurisdiction, which conversation state, and which compliance posture. Those outputs are invisible in the routing config and are never exercised in normal operation — the path runs during an incident, at speed, when nobody is reviewing routing decisions. That is the worst possible combination: consequential, silent, and untested.

THE PRESCRIPTION. Every failover or fallback edge should carry an explicit predicate over the properties it must PRESERVE, not merely the health it is reacting to — same geopolitical boundary, same model and version, equivalent data-handling and safety terms, and state-affinity respected or the request failed outright. Where preservation is impossible, the correct behaviour is to return the error rather than to serve a silently different thing. And because an unexercised fallback is a mode you have not tested, prefer paths that carry production traffic continuously over paths that activate only on failure.

WHAT THIS DOES NOT MEAN, carried from the sources because each blocks a distinct misreading. It is NOT an argument for more failover machinery — whether to have a gateway at all is a separate decision with its own stated vetoes, and managed Global/Data Zone deployments are already a gateway implementation, so the component may be redundant before it is built. It does not make session affinity optional or purely a performance choice: pinning is REQUIRED for stateful APIs, and it simultaneously concentrates both correctness and failure onto the same client, which is a tension to hold rather than resolve. Enforcement must be blocking, not advisory — clients must be BLOCKED from reaching endpoints outside their own region rather than merely configured to prefer their own, and the gateway must not make a cross-boundary call on the client's behalf even when the client asked correctly. Deterministic limits, not model-based detection, are what establish any of these boundaries: a probabilistic classifier on the path of an irreversible action is not a control. And the audit record needs the policy VERSION applied alongside the outcome — without it you cannot reconstruct what the rules were when the failover fired, which is exactly the moment you will need to.
