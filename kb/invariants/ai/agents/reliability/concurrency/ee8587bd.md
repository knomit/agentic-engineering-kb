# Timeouts do not bound concurrency — the timeout-to-normal-latency ratio is your concurrency multiplier

By Little's Law, concurrency = arrival rate x latency. So a dependency that slows down raises the number of in-flight requests even when the request rate is flat, and the ceiling on that increase is set by the timeout, not by the timeout being 'reasonable'.

Amazon's worked number: if a remote call normally takes 10ms and the timeout is set to 100ms or 1s, a pathologically slow dependency produces a 10x or 100x increase in concurrency before any request times out. That is enough to exhaust thread pools, connection pools, file descriptors, or memory on the calling server.

The consequence for agent builders: tuning tool-call timeouts is NOT a concurrency control, and treating it as one is the mistake. An agent harness that fans out to a slow MCP server or a slow retrieval backend can exhaust a shared worker pool while every individual call is still 'within timeout'. You need an explicit concurrency limit (see the bulkhead pattern) in addition to the timeout.

What this does NOT mean: timeouts are still necessary — Amazon sets them on other grounds, chiefly aligning a downstream timeout with the caller's own timeout so no work is done after the caller has stopped waiting. The claim is only that timeouts are the wrong tool for bounding concurrency.
