# Redundancy only compounds probabilities if failures are independent — identical replicas running identical software are not

The arithmetic that justifies redundancy: if one server fails with probability 0.01% on a given day, two servers both failing is 0.000001%. Amazon's Builders' Library is explicit that this compounding holds ONLY when the failures are independent, and that a single underlying cause routinely makes them dependent — at which point the redundancy buys far less than the arithmetic promised.

The cause most relevant to agent fleets is the one the article calls the Lemmings problem: every replica runs the same software, with the same limits and the same failure modes, and load balancers do a good job of distributing load evenly — which is exactly what makes the failure correlated. When an input class or a load level pushes one replica past a limit, the evenly-distributed load pushes all of them past it at roughly the same moment. The historical example is running out of file descriptors; the limit changes over time but the shape does not.

For agent systems the shared limits are obvious once named: the same context-window ceiling, the same token-per-minute quota against the same model provider, the same prompt with the same failure triggers, the same tool timeout, the same max-steps cap. Running twenty copies of an agent gives you twenty times the throughput and roughly ZERO additional protection against a prompt that makes the model loop, an input length that overflows the window, or a provider-side rate limit — because every copy hits it on the same input at the same time.

The article's stated countermeasures are shuffle sharding (ensure no two servers see the same exact workload, so a workload-triggered failure cannot take the whole fleet) and jitter on limits and behaviours. The corollary for agents: diversity — different model, different provider, different prompt, different limit — is what buys independence, and plain replica count is not.

What this does NOT mean: redundancy is still worth having. The point is that the availability number you compute from independent-failure math is an upper bound you will not reach, not a prediction.
