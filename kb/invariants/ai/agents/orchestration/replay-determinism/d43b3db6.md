# An orchestration runtime that resumes by replaying cached agent results has to put the clock and the RNG out of the script's reach — Claude Code makes Date.now(), Math.random() and a no-argument new Date() throw, and the first changed prompt invalidates every agent after it

A resumable fan-out resumes by REPLAYING the run in the order its agents started, returning each completed agent's saved result instead of re-running it. That is only sound if the script computes the same agent prompts on the second pass, so Claude Code's dynamic-workflow runtime takes the two ordinary sources of per-run variation out of the script's reach: "Claude Code makes Date.now(), Math.random(), and a no-argument new Date() throw inside the script, so that a relaunched run repeats the same agent() calls." A timestamp the orchestration needs is passed in through the `args` global instead. Note the scope — the constraint is on the ORCHESTRATION, not on the work: the agents themselves remain as nondeterministic as any model call.

THE CACHE-INVALIDATION RULE IS POSITIONAL, AND IT IS THE EXPENSIVE HALF. Replay walks agents in start order, and "the first agent whose prompt differs from the previous run, because you edited the script or an earlier agent returned something different, runs again, and so does every agent after it, even ones that completed". A failed agent behaves identically: it runs again "and so does every agent that started after it, even ones that completed", and stopping a single agent by itself COUNTS as failing it. The documentation's own example: a script that starts A, B, C and D where B fails returns A from cache and runs B, C and D again. Reordering has the same effect by the same rule — editing the script to start A, C, B, D makes the second agent to start C where the previous run started B, so A returns from cache and C, B and D all run. Only one case is exempt: an agent still running when you stopped the WHOLE run starts over, and stopping the whole run counts no agent as failed.

OPERATIONAL CONSEQUENCE: in a long fan-out, position is cost. A failure or an edit near the START of the agent order discards every cached result after it, so the cheapest place for fragile or likely-to-change work is late in the order, and an edit to an early stage of a saved script should be expected to rerun the entire run rather than the stage you changed. A script whose first agent's prompt depends on something volatile has no usable cache at all.

WHAT THIS DOES NOT MEAN. It does not mean a replayed run is side-effect-free or that resume is idempotent per agent. Agents write files and run commands; the runtime caches their RESULTS, not their effects, so an agent that runs again runs its writes again. Nor does it mean resume always works: when the runtime cannot find a run's saved results at all, a relaunch fails with a `nothing to resume` error rather than silently starting the run over.
