# An agent scheduler's safety reduces to two rules — only the orchestrator mutates scheduling state, and claimed plus running are checked before any launch — and Symphony needs no database because the tracker and the filesystem are the state

Symphony's spec states the scheduling invariants as rules rather than as implementation advice, and they are the transferable part of it.

**Single writer.** Only the orchestrator mutates scheduling state; every worker outcome flows back to it rather than being written by the worker. This is what makes the next rule checkable at all.

**Claim before launch.** Both the `claimed` and the `running` checks are REQUIRED before any worker is launched — the spec's stated purpose being to prevent duplicate dispatch. The claim lifecycle is explicit: Unclaimed, Claimed, Running, RetryQueued, Released.

**Reconcile before dispatch, every tick.** Reconciliation runs ahead of dispatch on every pass of the loop, which makes the scheduler level-triggered rather than edge-triggered and therefore self-healing by construction ([[b844c2b5]]) — a crashed worker is noticed because the next tick compares the world against the desired state, not because a failure event was delivered.

**Dependencies gate dispatch.** A Todo issue with ANY non-terminal blocker is not dispatched. Note the quantifier: any blocker not in a terminal state holds the issue, so a half-closed dependency chain stalls work rather than racing it.

**Recovery carries no database.** Restart recovery "needs no persistent database; it relies on tracker state and the filesystem". The consequence worth drawing: the durable state of the system is the tracker plus the per-issue workspaces, so the orchestrator is free to be a crash-only process, and anything it would have wanted to remember has to be representable in one of those two places. Config reloads follow the same spirit — they apply to future work without a restart, and an invalid reload keeps the last good config rather than failing the process.

What this does NOT give you: exactly-once execution. Claim checks prevent duplicate dispatch by one orchestrator; they are not a distributed lock, and the spec's non-goals rule out being a distributed job scheduler. Two orchestrators against one tracker is outside what these rules cover — see [[ded300bb]] for why that guarantee is the one you should assume you do not have.
