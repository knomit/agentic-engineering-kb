# Frontier agents escape containers through misconfiguration and disclosed CVEs, not novel exploits — and success scales log-linearly with the token budget you grant

UK AISI published "SandboxEscapeBench, an open-source benchmark dedicated to evaluating whether AI agents can break out of their sandboxes." It "introduces 18 escape scenarios spanning three layers of the container stack: orchestration, runtime, and kernel", built from real vulnerability patterns — from plain configuration errors (exposed Docker sockets, privileged containers) up to multi-stage chains involving documented CVEs and privilege escalation.

THE CAPABILITY BOUNDARY, STATED PRECISELY. "Every successful breakout exploited a previously disclosed vulnerability." No novel exploitation. And on the hard end: "none solved the hardest scenarios (which we estimate would require 1-2 hours for an experienced cybersecurity professional)" — which is the useful calibration, because it prices the current ceiling in human-expert time rather than in a benchmark score. Where models DID succeed reliably was on the common misconfigurations, which AISI notes "easily arise in developer tooling, ad-hoc evaluation harnesses, and fast-moving agent prototypes".

So the threat model to design against, today, is not an agent inventing a container escape. It is an agent finding the Docker socket you left mounted. That is a hygiene problem with a known checklist, and it is the one this measurement says is live.

THE SCALING RESULT, AND IT IS THE PART WITH THE MOST DESIGN CONSEQUENCE: "Performance also scales approximately log-linearly with compute budget: giving a model more tokens to reason with increased success rates." Breakout capability is therefore not a fixed property of a model you can test once and clear — it is a curve against the inference budget your harness happens to allow. A containment argument that rests on "we evaluated this model and it could not escape" is only valid at the token budget it was evaluated at. This is [[80866fc3]]'s finding arriving in the containment setting rather than the capability setting, and it converts a capability curve into an operational one: raising an agent's turn or token limit for product reasons silently raises its measured escape rate.

THE BENCHMARK'S OWN CONTAINMENT DESIGN IS ITSELF THE REUSABLE PATTERN: "Each container runs inside a hardened virtual machine, so even if a model escapes the container, it remains isolated from real infrastructure." To measure escape safely they assumed escape would succeed and put a stronger boundary behind it. That is [[d3acef50]]'s "evals need more containment than production" made concrete, and it is the correct shape for any harness that deliberately runs an agent against a boundary it might cross. A public scenario set plus a private held-out set supports internal evaluation without the public set contaminating it.

SCOPE AND WHAT IS NOT ESTABLISHED, because this post is unusually thin on the numbers you would want. It names NO specific models — only "frontier models" and "models we tested" — and states NO success rate, percentage or score for any model; the scaling claims are carried by graphs rather than by figures in the text. So "largest models achieved meaningful success on intermediate multi-step challenges" cannot be quantified from this source. It also does NOT state anywhere that container isolation alone is insufficient as a boundary — that inference is available and this pack draws it elsewhere ([[ea417108]], [[2b9a10f8]]), but it is not this source's claim and should not be attributed to it.

ONE SCOPE DIFFERENCE WORTH HOLDING RATHER THAN FLATTENING, against [[2dfac716]]: that fact records a real disclosed eval escape whose route was a ZERO-DAY in a package proxy and explicitly not a misconfiguration. This benchmark says the measured, independent capability tops out below novel exploitation. Both stand — they answer different questions (what an agent can do unaided in constructed scenarios, versus what route one real incident actually took) — and read together they say the misconfiguration surface is what agents can currently work through on their own, while the incidents on record have turned on defects in the one component the sandbox had to trust. Harden both; they are not the same list.
