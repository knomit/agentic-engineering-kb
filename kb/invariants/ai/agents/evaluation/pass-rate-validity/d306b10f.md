# An agent pass rate is a capability claim only after the failures are partitioned — AISI found refusal, resignation and scaffold non-compliance inside its own results at rates of 10-30%, each of which reads as incapability and is not

An average pass rate records how often agents fail, not why, and the UK AI Security Institute measured the size of that gap inside its own pre-deployment results: 6,390 samples from ReAct agents built on nine anonymised models across 71 private capture-the-flag tasks, each attempt terminated on a correct flag, a context-window overflow, or a total of 2.5 million tokens, whichever came first. Reading the transcripts turned up four distinct failure classes that a pass rate scores identically to incapability.

HARD REFUSAL AND PROVIDER-SIDE POLICY BLOCKING. One agent refused to comply with the task instruction in 10% of its attempts; a different one triggered the provider's policy violation detector in 30% of its attempts. Note that these are two separate mechanisms — the model declining, and the serving platform intervening — and only the first is a property of the model.

SOFT REFUSAL, OR RESIGNATION. Several agents ceased engaging with hard tasks without any explicit refusal, concluding the task was unsolvable or asking the user for help; for those agents roughly 30% of messages contained text to the effect of 'The task can't be solved with the information provided'. Resignation is a perseverance property and it varies by model, so two models with equal pass rates can differ in how much of the task they actually attempted.

SCAFFOLD NON-COMPLIANCE. The scaffold instructed the model to call a tool every turn. Compliance was mixed, and two agents had tool call rates under 50% — meaning more than half their turns did no work the harness could act on. A pass rate cannot distinguish a model that cannot solve the task from one that was not driving the harness.

UNDER-ELICITATION VIA AN IGNORED SETTING. Two reasoning models had reasoning set to 'high' and still used proportionally few reasoning tokens, while two models from a different developer used roughly as many reasoning tokens as output tokens. A reasoning-effort setting is a request the model may not spend against, so a configured setting is not evidence that the capability was elicited; measure the token counts.

THE OPERATIONAL CONSEQUENCE. Do not compare two models by pass rate, or report one as a capability measurement, without also reporting refusal rate, resignation rate and scaffold-compliance rate — a 10-30% effect on any of them is large enough to reorder a leaderboard. AISI's own recommendations from this are to take an adversarial position toward your own results and seek positive evidence that the experiment measures what was intended; to verify by multiple methods rather than one (it used transcript metadata AND transcript content); and to publish the integrity-check results alongside the eval results, and to expect them from others.

WHAT THIS DOES NOT MEAN: none of these classes makes the pass rate wrong as a measure of end-to-end task completion under that harness, which is a real thing to know. They make it wrong as a measure of what the model CAN do. The direction of the bias is also asymmetric — every class listed here pushes the measured rate DOWN, so a partitioned re-analysis raises the capability estimate rather than lowering it, and a defender who treats an unpartitioned pass rate as a safe upper bound has it backwards.
