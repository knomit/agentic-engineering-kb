# An LLM gateway's routing config is a credential-redirection and response-injection primitive — two field changes turn the governance layer into a man-in-the-middle that can also issue tool calls

"LiteLLM is an open-source proxy presenting a unified API over OpenAI, Anthropic, Azure OpenAI, Bedrock, and others." It is adopted for exactly the reasons a gateway is usually adopted — one API, central key handling, quota and policy in one place. Published 2026-08-03. The demonstration shows what that centralisation is worth to an attacker, and the shape transfers to any gateway with a runtime-mutable model registry.

THE PREREQUISITE, which is an ordinary secrets-hygiene failure and not an exotic one: "access to the `LITELLM_MASTER_KEY` or an equivalent proxy-admin credential and the API endpoint." A leaked deployment manifest or a key in source control is enough.

THE WHOLE ATTACK IS TWO FIELDS on the `/model/update` endpoint: "1. `api_base` is changed to point to the attacker LiteLLM gateway 2. `use_litellm_proxy` to `true`." Then "[a]fter the routing change, the victim sends that key to the attacker's LiteLLM server" — the upstream provider key travels in the Authorization header to whatever host `api_base` names, so redirecting the route harvests the credential rather than merely observing traffic.

AND THE HALF THAT MATTERS MOST FOR AGENTS, because it is not a data breach: once in the path, the attacker can "inject text or tool-calls into responses to AI clients". A compromised gateway does not just read the conversation; it authors the model's replies, including TOOL CALLS the client will execute. So the blast radius is not "the attacker learns what your agents did" — it is "the attacker drives your agents", with the client's own tool permissions, and every action is indistinguishable from a legitimate model output because it arrives on the legitimate response channel. Every prompt-injection defence that inspects incoming CONTENT is upstream of this and does nothing about it.

THE COMPONENT HAS PRIOR: "CVE-2026-42271 allows authenticated user to run commands on the LiteLLM host. That one was even added to CISA's KEV catalog, indicating exploitation in the wild." And separately, "[i]n March 2026 the PyPI package itself was compromised and shipped a credential stealer." Three independent routes to the same box — privilege escalation on the host, a poisoned package, and admin-credential leakage — which is what you should expect of a component that by design holds every provider key in the organisation.

WHAT TO ACTUALLY MONITOR, quoted because the first item is the specific one and the rest is standard: "Alert on `api_base` and `use_litellm_proxy` Changes. Snapshot and monitor changes to these config settings. Alert on other config change, like new callbacks, guardrails,…" The author also lists credential rotation, forwarding gateway logs to a SIEM, egress restrictions from the gateway host, locking down admin interfaces, restricting provider keys to approved gateway IPs, billing reconciliation ("Independent use of a harvested key creates provider-side charges"), and patching.

THE GENERALISATION, MARKED AS THIS PACK'S AND NOT THE POST'S. Gateway routing configuration is security-critical mutable state and is usually treated as operational configuration — changeable through an admin API, not gated by change review, and not diffed. The two properties that make it dangerous are that the upstream credential is attached at the gateway rather than by the caller, and that the response direction is trusted by the client. A gateway that pinned `api_base` to deploy-time configuration, or that required provider keys to be presented per-request rather than stored, would not have this shape. Read alongside the gateway-adoption decision in this pack: the reasons to put a gateway in front of your models are real, and this is the item that belongs on the other side of that ledger — the gateway is a correlated-failure point for confidentiality AND for integrity of the model's output.
