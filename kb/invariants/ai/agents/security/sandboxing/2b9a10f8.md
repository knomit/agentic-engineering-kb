# Filesystem isolation and network isolation are only useful together — either one alone leaves the exfiltration path open

Anthropic's stated design rule for Claude Code sandboxing, verbatim: "It is worth noting that effective sandboxing requires _both_ filesystem and network isolation." Neither is sufficient alone, and this is the part teams get wrong because filesystem isolation is the one that feels like 'the sandbox'.

The reason is the lethal trifecta reduced to one boundary. Filesystem isolation alone stops the agent writing outside its working directory but leaves it able to read secrets it legitimately has access to and POST them anywhere — the exfiltration leg is untouched. Network isolation alone stops the exfiltration but leaves a prompt-injected agent free to destroy or tamper with files locally. Anthropic states the pair's purpose directly: "This way, a compromised Claude Code can't steal your SSH keys, or phone home to an attacker's server."

The implementation shape is worth copying: filesystem access is confined to the current working directory, and "Network isolation, by only allowing internet access through a unix domain socket connected to a proxy server running outside the sandbox." Enforcement is at the OS level — "OS level primitives such as Linux bubblewrap and MacOS seatbelt". Putting the enforcement in a separate proxy process rather than in the agent's own logic is what makes it a boundary rather than a suggestion — the agent cannot reason its way past a socket it does not control.

THE NUMBERS, with their frames attached:
- BEFORE: "Our telemetry showed users approved roughly 93% of permission prompts." That is the definition of approval fatigue, and it means the prompt that actually mattered was approved along with the other nineteen.
- AFTER: "In our internal usage, we've found that sandboxing safely reduces permission prompts by 84%." Note the frame — Anthropic's own internal usage, not a customer population.

Read those together, because the pair is the actual argument. The case for sandboxing is not that it blocks more than prompting does — it is that it ASKS LESS, so the residual asks get read. A permission system with a 93% approval rate is not a control, it is a logging mechanism with a confirmation dialog attached. Cutting prompt volume by 84% is what restores meaning to the ones that remain.

The corollary for anyone designing an approval flow: measure your approval RATE, not your prompt count. A high approval rate is evidence the prompts are mostly unnecessary and should be replaced by an enforced boundary, not evidence that users are engaged.
