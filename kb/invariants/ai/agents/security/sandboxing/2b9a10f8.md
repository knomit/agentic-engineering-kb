# Filesystem isolation and network isolation are only useful together — either one alone leaves the exfiltration path open

Anthropic's stated design rule for Claude Code sandboxing: effective sandboxing requires BOTH filesystem isolation and network isolation. Neither is sufficient alone, and this is the part teams get wrong because filesystem isolation is the one that feels like 'the sandbox'.

The reason is the lethal trifecta reduced to one boundary. Filesystem isolation alone stops the agent writing outside its working directory but leaves it able to read secrets it legitimately has access to and POST them anywhere — the exfiltration leg is untouched. Network isolation alone stops the exfiltration but leaves a prompt-injected agent free to destroy or tamper with files locally. The two named threats the pair defeats together are a prompt-injected agent stealing SSH keys and exfiltrating sensitive files to an attacker-controlled server.

The implementation shape is worth copying: filesystem access is confined to the current working directory, and network access is routed through a Unix domain socket to an external proxy that enforces domain restrictions and asks the user to confirm connections to new destinations. Putting the enforcement in a separate proxy process rather than in the agent's own logic is what makes it a boundary rather than a suggestion — the agent cannot reason its way past a socket it does not control.

The reported operational payoff, which is the argument for doing this rather than relying on prompts: sandboxing reduced permission prompts by 84% in internal usage. That number matters for security rather than just convenience — approval fatigue is what makes users click through the prompt that actually mattered, so cutting prompt volume by that much raises the attention paid to the ones that remain.
