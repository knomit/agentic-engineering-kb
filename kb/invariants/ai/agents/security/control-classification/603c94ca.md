# Three axes decide whether an agent control is a boundary, and a permission is only proven by a call that was denied

OWASP's GenAI Red Teaming Manual v1.0 classifies every control in an agent system on three independent axes before anyone relies on it: preventive or detective, advisory or enforced, and fail-open or fail-closed. The combination decides what the control is worth, and the control's name tells you nothing about it: a detective, advisory, fail-open control is telemetry, and a system whose authorization rests on one of those has no authorization at all.

Two consequences the manual states directly. A prompt instruction, a model refusal or a safety classifier is "defense-in-depth, not an enforced trust boundary by itself", so a permission claim is verified by a denied-call test against runtime policy enforcement — never by reading the tool description that says the agent may not do it. And "Never use system/developer prompts, model context, tool output, or agent memory as a secret store": all four are reachable by the model, and therefore by anything that can influence the model.

The CI consequence follows from the same axes. Gates "should block deterministic control failures", for which the manual names authorization bypass and cross-tenant retrieval. A deterministic control failure is a reproducible pass or fail, so it can gate a build; a probabilistic behavioural score cannot, and a gate wired to one ends up either blocking good builds or switched off.

This does not mean prompt-layer controls are worthless — the manual keeps them explicitly as defense in depth. The claim is about which layer carries the boundary, not about removing the others. Nor does "enforced" alone suffice: an enforced control that fails open under load is a boundary only while the load is low, which is why the third axis is scored separately from the second.
