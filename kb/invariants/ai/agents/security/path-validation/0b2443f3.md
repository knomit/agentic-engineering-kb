# Resolve symlinks BEFORE validating a path, and defer all project config execution until after the trust prompt

Two specific ordering bugs Anthropic names from containing Claude across products. Both are ordering errors, not missing controls, which is why they survive a design review — the control exists and runs in the wrong order.

1. SYMLINK RESOLUTION MUST PRECEDE PATH VALIDATION. If you check that a path is inside the workspace and then open it, a symlink inside the workspace pointing outside it defeats the check. The validation must operate on the fully resolved real path. Stated as a flat rule because there is no version of this that is safe the other way round.

2. PROJECT CONFIGURATION MUST NOT BE PARSED BEFORE THE TRUST BOUNDARY IS ESTABLISHED. Anthropic found that project configuration was being parsed before the user accepted the trust prompt for that project — so opening an untrusted repository executed its configuration and hooks regardless of what the user then clicked. The trust prompt was real; it just came second. The fix is to defer ALL config parsing and hook execution until after the user has accepted.

The second one generalises to any agent harness with per-project config files: repository-level instruction files, hook definitions, MCP server declarations, and dev-container specs are attacker-controlled content in any repo you did not write. Anything your harness does with them before the user consents is done on the attacker's behalf.

Related framing from the same source, worth holding alongside these: the three layers Anthropic defends are the model (prompts, classifiers, training), the environment (sandboxes, VMs, egress controls), and external content (tool permissions, connectors) — and their stated reason for layering is that 'probabilistic defence has a non-zero miss rate'. Both bugs above are environment-layer, and neither was catchable at the model layer.
