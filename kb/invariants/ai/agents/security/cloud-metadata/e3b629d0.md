# An agent pod that can reach the instance metadata endpoint can authenticate to the cluster API as the node itself

From a single code-execution foothold in a production pod, the July 2026 intrusion escalated to cluster-level access without exploiting any further vulnerability — purely by using credentials that were reachable by design.

The chain, which works on any default EKS-style setup:
1. Read the EC2 node role credentials from the instance metadata service at 169.254.169.254. A pod can reach this unless you explicitly stop it.
2. Build a presigned sts:GetCallerIdentity URL and wrap it as a 'k8s-aws-v1.' bearer token. This is the documented AWS-IAM-to-Kubernetes authentication mechanism, used exactly as intended.
3. Authenticate to the cluster API as the NODE identity — which has far more permission than the pod.
4. List pods, find the CSI storage-driver pods, and use the TokenRequest API to mint fresh service-account tokens for them. The CSI driver's ClusterRole permitted cluster-wide pod creation.
5. Create a privileged pod with a hostPath mount of the host filesystem — no admission policy forbade it — reaching root on the node, then replicate into a self-respawning fleet across 11 nodes.

Every step after the foothold is a legitimate, documented API used with legitimately reachable credentials. There is no exploit to detect.

The control that breaks the chain at step 1 is the one Hugging Face shipped: block pod-level access to the instance metadata service entirely, and move workloads to workload identity so there is no node-role credential to steal. If you run agent code execution on Kubernetes, treat IMDS reachability from the agent's pod as a sandbox escape that has already happened — the agent does not need a bug, it needs a curl.

Second, separable control: an admission policy that forbids privileged and hostPath pods, and a review of which ClusterRoles grant cluster-wide pod creation. A storage driver having that right is the kind of grant nobody re-reads after install.
