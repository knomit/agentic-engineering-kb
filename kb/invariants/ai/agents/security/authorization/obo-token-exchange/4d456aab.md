# Propagating the user's identity through an agent means the gateway re-mints the token on every request so its audience becomes the downstream service's own client ID — and the exchange silently does not happen unless the custom parameter requested_token_use:on_behalf_of is set

The principle that an agent should act as its user rather than as itself is well covered. This is the mechanics of doing it through a gateway, from one vendor's implementation walkthrough (AWS, Bedrock AgentCore Gateway to a ServiceNow REST API via Microsoft Entra ID), and the parts worth holding are the ones that are easy to get wrong rather than the console clicks.

THE DEFAULT IS THE FAILURE. "Without identity propagation, API calls arrive at downstream services as the application itself," and the stated consequence is threefold: "This breaks audit trails, bypasses user-level access controls, and violates the principle of least privilege." Nothing fails loudly — the calls succeed, attributed to the wrong principal.

WHY A TOKEN EXCHANGE IS STRUCTURALLY NECESSARY, AND NOT MERELY TIDIER. The token the agent holds is scoped to the agent: "it presents a JWT with an `audience` claim matching the agent’s client ID." The downstream service will not take that token: "ServiceNow, however, expects a token with an `audience` claim matching its own API connector client ID." So the audience must change while the subject must not, which is exactly what the exchange does — the identity provider "validates that the calling user consented to the delegation," then "issues a new token for the ServiceNow API with the original user’s claims intact." Forwarding the inbound token instead is the passthrough defect recorded at [[ba5db3ec]]. This is also why the setup needs "[t]wo Entra application registrations: one representing the AI agent, and one representing the ServiceNow API connector" — the second registration exists to be the new audience.

THE ONE PARAMETER THAT DECIDES WHETHER ANY OF THIS HAPPENS. The gateway "sends the inbound token to the Entra token endpoint along with the agent application’s client credentials, the target scope" and the custom key-value pair "`requested_token_use:on_behalf_of`". The post is emphatic: "This parameter is critical." "Without it, Entra doesn’t perform the OBO exchange and the call to ServiceNow fails with an authentication error." Note the walkthrough prints it two ways, with and without a space after the colon ("requested_token_use: on_behalf_of" in prose, "requested_token_use:on_behalf_of" in the configuration step), so the literal form has to be checked against the console rather than copied from the prose.

WHAT THE DOWNSTREAM SERVICE ACTUALLY KEYS ON. The exchanged token carries the user through one claim: "ServiceNow receives a valid token whose `preferred_username` claim maps to an existing ServiceNow user," and the mapping is configured explicitly — "if your Entra tenant places the user’s email in the `preferred_username` claim, map that to the **Email** field." That makes claim-to-local-user mapping the load-bearing join, and it is correspondingly the first troubleshooting check the post gives. The requested scope is a single exposed scope, "a scope named `user_impersonation` using the default Application ID URI," and "[t]his scope is what the OBO flow requests when exchanging tokens"; least privilege is applied on the resource side instead — "[l]imit the auth scope to the Table API, or whichever ServiceNow APIs your agent needs to access."

REPLAY PROTECTION IS OPT-IN AND IT IS A CLAIM RENAME. "Entra uses an internal claim named `uti` on tokens it issues, which is equivalent to JTI," and the recommendation is to "[c]onsider mapping this `uti` claim to a `jti` claim to provide additional replay protection and denylisting." So an exchange configured the obvious way has NO replay protection or denylist capability until that mapping is made, and the check must be cleared outright "if your Entra tenant doesn’t include it in tokens." Treat the presence of a replayable token identifier as a configuration you own, not a property the flow gives you.

TWO OPERATIONAL CONSTRAINTS. First, cost and liveness: "AgentCore Gateway performs the exchange on each request" — per-request, not per-session, with no caching or refresh behaviour documented. Second, and the one that will bite a team mid-project: the gateway must be created with "MCP version **2025-11-25**", "[t]his version is required for native OBO support," and "[y]ou can’t turn on native OBO for gateways created with earlier MCP versions." An identity capability is therefore gated by a protocol-version choice made when the gateway object was created and is not retrofittable — an existing gateway has to be replaced. (That version is this product's selectable MCP revision, not a statement about the protocol's current revision; do not read it as the live MCP spec version.)

SCOPE AND STRENGTH. The pattern is presented as general — "[t]he pattern can be applied to other REST APIs protected by OAuth" — and the vendor notes it removes earlier glue: "native OBO support in AgentCore Gateway removes the need for custom AWS Lambda interceptors to perform token exchanges." But this is a vendor how-to, not a specification: the literal OAuth grant_type value is never given (only "the OBO grant type"), and no token lifetimes, expiry values, rate limits, caching behaviour or error codes beyond "an authentication error" are stated. Build from it, then verify those against the identity provider's and the gateway's own reference documentation.
