# Downstream services must re-authorize every agent call — trusting the orchestrator is the failure mode

The load-bearing rule in Microsoft's agent least-privilege guidance is that downstream systems must re-check authorization on every call. Implicitly trusting the orchestrator — letting a service accept "the agent framework already validated this" — is named as a critical failure mode, because it collapses every tool the agent can reach into a single trust boundary and makes the orchestrator's prompt the actual access-control policy.

The corollary they state directly: do not rely on prompts instead of hard authorization boundaries. An instruction telling the agent not to delete things is not a permission; it is a suggestion that survives exactly until a prompt injection or a confused-deputy path disagrees with it.

The rest of the prescription, in the order it constrains a design:

- Give each agent a DEDICATED identity — not a reused service account and not a shared secret. Shared secrets across agents erase accountability, so an audit log cannot answer which agent did it.
- Scope RBAC roles to "discrete tasks, not teams or org charts" (their examples: read-only knowledge retrieval; summarize labeled documents; create a draft ticket). Team-shaped roles are how agents acquire permissions nobody intended.
- Separate read from write with different roles or different tools, and gate delete, export, and privilege changes behind step-up approval.
- Scope on three axes, not one: resource boundary (tenant/subscription), data boundary (collection/label/sensitivity), operation boundary (read/write/export).
- Prefer time-limited just-in-time elevation that auto-drops to baseline at workflow end, over standing grants. Temporary access without an expiry mechanism is a standing grant with extra steps.
- Log agent identity, role used, effective scope, resource, action, on-behalf-of user, timestamp, and correlation ID — a trace missing on-behalf-of cannot reconstruct a confused-deputy incident.

The named anti-pattern to avoid at the start: granting broad Owner/Admin during a pilot and intending to refactor permissions later.
