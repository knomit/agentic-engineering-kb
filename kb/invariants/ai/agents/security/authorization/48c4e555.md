# Downstream services must re-authorize every agent call — trusting the orchestrator is the failure mode

The load-bearing rule in Microsoft's agent least-privilege guidance is that downstream systems must re-check authorization on every call: "Downstream tools and services must re-check claims, roles, and scope on each call rather than trusting the orchestrator implicitly." Implicitly trusting the orchestrator is named as a critical failure mode, because it collapses every tool the agent can reach into a single trust boundary and makes the orchestrator's prompt the actual access-control policy.

The corollary they state directly: "Relying on prompts or 'the agent will only do X' narratives instead of hard authorization boundaries invites prompt injection." An instruction telling the agent not to delete things is not a permission; it is a suggestion that survives exactly until a prompt injection or a confused-deputy path disagrees with it.

The rest of the prescription, in the order it constrains a design:

- Give each agent a DEDICATED identity — "a dedicated agent identity (not a shared secret or reused service account)" with a documented purpose statement. Shared secrets across agents erase accountability, so an audit log cannot answer which agent did it.
- Design RBAC "around discrete tasks, not teams or org charts" (their examples: read-only knowledge retrieval; summarize labeled documents; create a draft ticket). Team-shaped roles are how agents acquire permissions nobody intended.
- Separate read from write with different roles or different tools — explicitly when a workflow spans both evidence gathering and remediation — and "gate high-impact actions like delete, export, or privilege changes behind step-up approvals". Note the "like": delete, export and privilege change are EXAMPLES of high-impact actions, not the closed set, so a design that gates exactly those three has applied the examples rather than the rule.
- Scope on three axes, not one: "by resource boundary (tenant/subscription/workspace/site), by data boundary (collection, label, sensitivity), and by operation boundary (read/write/export/admin)."
- Keep the baseline role minimal and prefer time-limited entitlements — temporary role activation, short-lived tokens — that auto-drop at workflow end, over standing grants. Temporary access without an expiry mechanism is a standing grant with extra steps.
- Make sure "logs capture the agent identity, role used, effective scope, resource accessed, action taken," and the “on behalf of” user "(if applicable), timestamps, and correlation IDs". The on-behalf-of field is qualified as applicable rather than always required — but where an agent CAN act for a user, a trace missing it cannot reconstruct a confused-deputy incident.

The named anti-pattern to avoid at the start: "Granting broad Owner/Admin roles to unblock a pilot, then never coming back to refactor permissions."
