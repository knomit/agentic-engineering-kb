# One agent's write to another agent's config file is a code-execution grant — the second agent is reconfigured rather than compromised, so none of its own permission checks fire

Johann Rehberger's cross-agent privilege escalation write-up (September 2025). The mechanism: "An indirect prompt injection hijacks Copilot and makes it write to Claude's MCP config to add a malicious server; it can also update the custom agent instructions for Claude to take specific agents (e.g. `CLAUDE.md`)". When the second agent is next used it "will run arbitrary code".

The paths the post names as writable or creatable by an agent, ten of them: `.vscode/settings.json`, `.vscode/mcp.json`, `.vscode/tasks.json`, `.vscode/copilot-instructions.md`, `.mcp.json`, `~/.mcp.json`, `.gemini/settings.json`, `.claude/settings.local.json`, `CLAUDE.md`, `AGENTS.md`. Two of those are worth separating out from the rest. `.vscode/tasks.json` is a task definition, so a write there is a command the editor will run rather than a setting that loosens a check. And `~/.mcp.json` is at the HOME level, not in the repository — a write to it escapes the shared checkout entirely and follows the user into every other project. Products named: GitHub Copilot, Claude Code, AWS Kiro, with VS Code as the host and Gemini present through its settings path.

THE ROOT CONDITION HAS TWO PARTS AND NEEDS BOTH: "Many developers use multiple coding agents on the same codebase" AND "Many agents write to files without the user's permission." A single agent writing its own dotfiles is not this bug; a shared checkout with one permissive writer is.

WHY IT DEFEATS THE OBVIOUS DEFENCE. Agent B is not exploited. It loads attacker-authored configuration as its own trusted configuration, through its normal startup path, so hardening B — tighter tool allowlists, a stricter approval mode, a better injection classifier — changes nothing: those mechanisms are configured by the file that was just rewritten. The security property that matters is agent A's injection resistance, and on a shared tree the weakest agent in the toolchain sets the bound for every other one, across vendors, with no trust relationship declared anywhere between them.

SO: treat any write to a dot file or dot directory as privileged, not as a routine edit, and audit which agents can perform one unprompted. The published recommendations are five, and the post ranks one of them: "Isolate your agent's configuration to make it less accessible to others"; do not automatically overwrite or create files but propose changes first, and at minimum require user approval for writes to dot files and folders — which the post calls the most practical approach currently available; "Beware that if you use multiple agents on the same data/code or infrastructure they might interfere with each other"; "Indirect prompt injection can exploit such behavior - so be careful with untrusted data!"; and "Consider least privilege execution for agents." Note what is missing from that list: nothing there detects a config file that was already modified, so a tool that reads its configuration at startup without integrity-checking it has no way to notice.

Provenance: an independent security researcher's demonstration with named products, disclosed to MSRC, with no CVE cited and no vendor confirmation quoted; the path list is what the post enumerates, not an exhaustive inventory of any product's writable paths. The post also records that vendors have added mitigations against overwriting configuration without permission, while agents can still write or create other files and folders — so the live form of this grant is the CREATION of a file the second agent will read, not necessarily the overwrite of one that already exists, and a check that guards a known list of existing config paths does not cover it. The related shape where an allowlist accelerates an attack because the agent can influence its own execution environment is [[92dc0441]], and the CI version — editing a non-workflow script an existing workflow already runs — is [[ab8f0a7e]].

The same grant exists outside the filesystem wherever an agent reads persistent instructions from a shared store. CVE-2026-65669 is the worked case: SQL Copilot's `AGENTS.md` and `CONSTITUTION.md` are database extended properties, so an ordinary schema-level write became a write into another user's agent context, and because the agent ran with the reading user's privileges a `db_owner` reached sysadmin. See [[4ac8983f]]. When auditing for this, the question is not "do we have config files" but "who can write the store the agent reads instructions from, and whose privileges does the agent then act under".
