# Sealing client-held state authenticates the issuer, not the holder — reasoning-trace envelopes replayed across sessions, users and models because identity was never in the associated data

Frontier providers keep reasoning-trace APIs stateless by handing the trace to the client and making the client hand it back: "Rather than incurring overheads of storing reasoning states, providers leverage client-side storage." The blob is an AEAD envelope "containing a header, which, depending on providers, can specify the model name, block type, version, and key ID along with a nonce, an authentication tag, and the ciphertext". Evaluated against "major API vendors including OpenAI, Google, and Anthropic".

THE DEFECT IS A CATEGORY ERROR ABOUT WHAT A SEAL PROVES, AND IT IS THE TRANSFERABLE PART. The MAC attests two things — this provider issued this blob, and it has not been altered. It does not attest whose blob it is or where in a conversation it belongs, because none of that was put in the associated data. The paper reports that "providers appear to be using a single global key to encrypt and authenticate every reasoning block", and measures three resulting compatibility forms it names "In- and cross-session compatibility... Cross-user compatibility... Cross-model compatibility." One exception was found: for "Claude: the thinking traces of any model can be replayed by any other, except Fable 5's thoughts."

GENERALISE PAST REASONING TRACES — THIS SHAPE IS EVERYWHERE IN AGENT PLUMBING (marked as this pack's inference; the paper is about reasoning traces only). Any design that hands a client an opaque sealed value to hand back has it: session-resumption handles, tool-call continuation tokens, cached-context references, agent checkpoints, resumable-task identifiers. If the seal is the only check, the value is a BEARER TOKEN and you have accidentally built one. The test to apply: name the fields inside the associated data. Whatever is not in there is not something you can enforce on. Note that the header above carries the MODEL and the KEY ID and nothing about the principal — which is exactly why cross-user replay works and cross-model replay does too.

THE PROPOSED FIXES, in the authors' own terms, ordered by how much of the class each removes:
- ARCHITECTURAL, and the only one that removes it: "A robust mitigation would involve retaining reasoning traces entirely on the server side", the client holding only an opaque random identifier.
- CONTEXTUAL BINDING: "Embedding these specific markers within the Authenticated Encryption with Associated Data (AEAD) payload would enable the API to reject signatures replayed in other sessions or by unauthorized users", and "statefully hashing the precise prompt and preceding conversation history into the Message Authentication Code (MAC) would invalidate the signature if an adversary attempts to inject the trace into a fabricated context".
- INFRASTRUCTURE: "API gateways could be engineered to enforce strict cross-model isolation, automatically rejecting AEAD envelopes generated by a model version different from the one currently being queried."
- REVOCATION: "Model providers could introduce mechanisms to actively track and revoke specific trace signatures."
- BEHAVIOURAL, and it is last for a reason: "Providers would benefit from implementing targeted refusal training, fine-tuning their models to explicitly recognize and reject adversarial prompts designed to transcribe or surface hidden reasoning".

WHY THE ORDERING MATTERS (pack analysis, not the paper's ranking): the paper states the structural limit itself — "whatever model is queried must, by necessity, decrypt and process the contents of prior reasoning tokens." Refusal training therefore sits downstream of a decryption that has already happened, which makes it a mitigation of the last resort rather than a boundary. This is the same substitution [[1d01a338]] documents from the practitioner side: a confidentiality control implemented as model willingness to refuse.

SCOPE AND STATUS. Past-turn injection is narrower than current-turn: "Past-turn injection is available only against models that do not omit previous reasoning blocks (e.g., Sonnet 5, Opus 4.8, Fable 5, and the GPT-5.6 series)." The paper states "As of August 2026, the results presented in Figure 1 are no longer reproducible with attacks described in Section 2.4 and Appendix C because of mitigations implemented by providers following our disclosure" — note the scope of that sentence is Figure 1 and two named sections, NOT a claim that the architecture changed. The full tested model roster is deliberately not reproduced here; only the identifiers confirmed verbatim against the paper are named.
