# Check a config WRITE path for symlinks and refuse outright, and scope the check to the components the user did not choose: the shared project location checks the directories too, the personal one checks only the file

An agent that saves a file into a well-known config directory can be made to write outside that directory if any component of the path is a symlink. Claude Code's workflow-save path shows both the control and the reason its strictness differs by location.

The control: "Claude Code checks the save location for symlinks before writing, and shows an error instead of writing through one." What it checks depends on the destination. "Project location: Claude Code refuses if `.claude`, `.claude/workflows`, or the target file is a symlink. Personal location: Claude Code refuses only if the target file itself is a symlink, so a `~/.claude` directory managed by a dotfiles tool still works."

That asymmetry is the design lesson, and it is not laxness. The project location lives in a repository that other people write to, so a symlinked `.claude` directory could have arrived with a clone and redirect the write somewhere the user never chose; every directory component is therefore untrusted. The personal location is the user's own home directory, where a symlinked `~/.claude` is a legitimate and common arrangement — dotfiles managers create exactly that — so refusing it would break a normal setup to defend against the user's own configuration. Scope the path check to the components an adversary could have supplied, not to every component.

The failure this prevents is documented as the prior behaviour: "Before v2.1.216, Claude Code followed the link, which could place the file outside the location you chose." So the bug class is real and was shipped — a save that silently honours a symlink writes attacker-chosen content to an attacker-chosen path under the user's own credentials.

HOW THIS SITS WITH THE READ-PATH RULE in [[0b2443f3]]: that rule says a path must be fully resolved BEFORE it is validated, because a symlink inside the workspace pointing outside defeats a validate-then-open check. This is the write-side counterpart and it goes further: the destination is refused rather than resolved and accepted. On a read you must know the real path before deciding; on a write into a directory that is itself part of the security boundary, the presence of a link is the answer, and the user resolves it rather than the tool.
