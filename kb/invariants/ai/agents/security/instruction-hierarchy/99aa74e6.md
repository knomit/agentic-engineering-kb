# Never interpolate untrusted text into a developer/system message — it promotes the attacker into the trusted tier of the instruction hierarchy

OpenAI's agent safety guidance carries a rule that is easy to violate by accident in ordinary templating code: do not put untrusted variables into developer messages. Pass untrusted input through user messages instead.

**WHY IT MATTERS MORE THAN IT LOOKS.** Models are trained on an instruction hierarchy that grants developer/system content more authority than user content, and more still than tool results and retrieved documents — OpenAI names Instruction Hierarchy as the research line behind this. String-interpolating a retrieved document, an email body, a support-ticket subject, or a tool result into a developer message hands the attacker the highest-trust slot in that hierarchy. The model's trained defence against injection keys on *where the text sits*, so the defence is what you disable. This is a direct analogue of parameterised SQL: the injection is not the content, it is putting untrusted content where the interpreter expects trusted structure.

The practical failure mode is mundane — a prompt template that assembles system instructions and retrieved context in one f-string, which reads as good prompt engineering and quietly removes the hierarchy the model was trained to respect.

**THE COMPANION RULES FROM THE SAME GUIDANCE.** Constrain the model's output with structured outputs rather than free text, to remove the freeform channel an attacker would otherwise steer; where an agent reaches MCP tools, enable tool approvals so a person confirms each operation; and pick a model tier for instruction-following and jailbreak resistance rather than only for capability. OpenAI's own framing is that these are layers and none is sufficient — the guidance closes by saying that even with these mitigations agents will not be perfect.
