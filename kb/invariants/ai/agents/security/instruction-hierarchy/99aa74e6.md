# Never interpolate untrusted text into a developer/system message — it promotes the attacker into the trusted tier of the instruction hierarchy

OpenAI's agent safety guidance carries a rule that is easy to violate by accident in ordinary templating code, and it gives the reason in one sentence: **"Because developer messages take precedence over user and assistant messages, injecting untrusted input directly into developer messages gives attackers the highest degree of control."** The prescription: "Pass untrusted inputs through user messages to limit their influence."

**NOTE THE SOURCE'S OWN HEDGE — "to limit their influence", not to remove it.** Moving untrusted text from the developer message to the user message demotes the attacker from the highest-precedence tier to a lower one. It does not make the content safe, and it is not a substitute for the sink-side controls this pack records elsewhere. This fact is filed as an invariant because the *don't* is absolute — there is no case where interpolating attacker-reachable text into a developer message is the right call — not because the alternative is sufficient on its own.

**WHY IT MATTERS MORE THAN IT LOOKS.** The precedence ordering is a trained behaviour, so the model's defence against injection keys partly on *where the text sits*. String-interpolating a retrieved document, an email body, a support-ticket subject, or a tool result into a developer message is therefore not merely untidy — it is the step that disables the defence. This is a direct analogue of parameterised SQL: the injection is not the content, it is putting untrusted content where the interpreter expects trusted structure. (That analogy is this pack's framing, not OpenAI's.)

The practical failure mode is mundane — a prompt template that assembles system instructions and retrieved context in one f-string, which reads as good prompt engineering and quietly collapses the hierarchy.

**THE COMPANION RULES FROM THE SAME PAGE, quoted.**
- Structured outputs: "By defining structured outputs between nodes (e.g., enums, fixed schemas, required field names), you eliminate freeform channels that attackers can exploit to smuggle instructions or data."
- Tool approvals: "When using MCP tools, always enable tool approvals so end users can review and confirm every operation, including reads and writes." Note the scope — *including reads*, not just writes.
- Model choice, on GPT-5 / GPT-5-mini: "These models are more disciplined about following developer instructions and exhibit stronger robustness against jailbreaks and indirect prompt injections." **This leg is version-tied and those models have since been superseded** — the transferable claim is that robustness to indirect injection varies by model tier and is worth treating as a selection criterion, not that any named model is the right choice today.

OpenAI's own framing is that these are layers and none is sufficient; the guidance closes by saying that even with these mitigations agents will not be perfect.
