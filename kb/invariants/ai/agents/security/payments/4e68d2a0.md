# A wallet approval authorizes an amount, not a cart — the agent's payment tool must re-verify the order and the approval's freshness itself

LangChain's Restock walkthrough — a sample Slack office-supply agent on Managed Deep Agents that pays through Stripe's Link wallet over the Machine Payments Protocol (MPP), with the merchant returning an HTTP 402 challenge the client retries with a credential — names a hole that a human-in-the-loop payment design does not close by itself.

**THE HOLE.** "The token doesn't enforce cart details on its own". The human approves an exact amount in the wallet, and the wallet's consent is to that amount: it does not bind what is in the cart, where it ships, or which merchant is charged. An approval collected for one order can therefore be spent on a different order that happens to cost the same. The remedy has to live in the agent's own payment tool, and it is two checks rather than one: "the tool also checks the order against what the user reviewed and confirms the approval is still fresh". Contents AND recency — a stale approval whose amount still matches is the second half of the same hole, and a design that checks only the contents has closed half of it.

**THE APPROVAL MUST BE OUT OF BAND OF THE MODEL.** The run is paused by an interrupt until the human approves or rejects in the chat surface, and the design states the property plainly: "Nothing the model writes into a tool call can approve it." An approval the model can emit as a tool argument is not an approval, it is a token the model can produce — under prompt injection, or under ordinary confusion about what it has already been told. This is the same property [[f1cbb540]] states for permission classifiers, applied to money.

**ORDERING: READ THE REAL CHARGE BEFORE YOU ASK THE HUMAN.** The agent requests the order unpaid first and reads the actual amount off the merchant's 402 challenge, because "Tax and shipping aren't known from a product listing" and optional fees reduce what is left for the retailer. A human shown a listing price is approving the wrong number. The user then picks an upfront amount up to the budget; the merchant captures that amount and refunds the remainder. So the approved amount is a ceiling and the budget is a ceiling on the ceiling — neither is the price.

**WHAT THIS DOES NOT MEAN.** It is not an argument against wallet-level approval. The wallet approval and the in-agent verification cover different things: the wallet consents to a charge, the agent's tool is the only component that knows what the human was looking at when they consented. You need both. Nor does it mean "a human approved it" discharges the design — that sentence is exactly the compression this fact exists to block.

**SCOPE.** A published build walkthrough of one sample agent, written by the vendor of the hosting product it uses, which it also promotes. The authors report a single live hosted order reaching `order_placed` with the expected refund — a stated design with one confirming run, not a measured reliability result. Stated constraints are narrow: MPP-enabled merchant APIs only (the post calls browser checkout for other sites fragile), US delivery, USD, one office per deployment, and payment only from the requester's own wallet.
