# Goose subagents: the turn limit resolves through five levels and defaults to 1000, so the 5-minute timeout is the binding constraint — and a failed or timed-out subagent returns nothing at all

Concrete limits from Goose's subagent implementation, useful both as defaults to know and as a reference point for what any subagent contract should specify.

- Max turns: the limit is not one setting but a precedence chain, and the docs state it as "Subagent turn limits use the first configured value below:" — (1) "The `delegate` tool's `max_turns` argument.", (2) "The child recipe's `settings.max_turns`.", (3) "`GOOSE_SUBAGENT_MAX_TURNS` in the environment or configuration file.", (4) "`GOOSE_MAX_TURNS` in the environment or configuration file.", (5) "The default of 1000." The Default Settings table gives the Max Turns default as "`GOOSE_MAX_TURNS`, otherwise 1000". Note the consequence of level 4: a parent-level `GOOSE_MAX_TURNS` silently becomes the subagent's limit when no subagent-specific value is set, so one variable governs both unless you separate them.
- Timeout: "5 minutes" by default; a longer one is requested in the prompt rather than configured. WITH A 1000-TURN CEILING THE TIMEOUT IS THE LIMIT THAT ACTUALLY FIRES — size subagent tasks against five minutes of wall clock, not against a turn budget, because a task will almost always run out of time before it runs out of turns.
- Context: subagents INHERIT the parent session's context and extensions by default — the table's Extensions default is "Inherited from parent", and the prose states "By default, subagents inherit all extensions from your main session, but you can restrict access for security, focus or performance.". Restricting tool access is opt-in, and is recommended for security, focus, or performance — so the safe-by-default assumption does not hold; a subagent sees what its parent sees unless you narrow it.
- Recursion is blocked: "Subagent spawning: Cannot create additional subagents to prevent infinite recursion." A subagent also cannot enable or disable extensions, or manage scheduled tasks.

The failure semantics are the part that bites, and the source is explicit: "If a subagent fails or times out (5-minute default), you will receive no output from that subagent. For parallel execution, if any subagent fails, you get results only from the successful ones." Not partial work, not a summary of how far it got. So a parallel fan-out silently returns an incomplete result set rather than an error, and the parent has to notice the gap itself. Design the parent's prompt to verify it received a result per dispatched task, and prefer subagent tasks small enough to finish inside the 5-minute envelope over ones that will half-finish and vanish.

Tool calls made by a subagent surface as expandable sections in the parent conversation, and the return mode is configurable between full detail and summary-only.

The source page carries no publication date (site copyright 2026), so there is no way to tell from it when any of these defaults last changed — treat every number here as needing a re-read against the live page before it is relied on, and expect the turn default in particular to move.
