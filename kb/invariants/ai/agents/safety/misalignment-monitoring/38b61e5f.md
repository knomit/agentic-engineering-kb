# OpenAI's misalignment safety check halts a run only on three specific request shapes, never reverses what already happened, and request_paused: true does not mean execution stopped

OpenAI's misalignment monitoring is a platform-side safety check that reviews a request's reasoning and actions asynchronously and can stop the conversation. Its coverage is conditional, and all three conditions have to be stated together or the guarantee is misread:

- **Responses API requests using persisted reasoning, WebSockets, or OpenAI compaction** — monitored, and the platform can block further execution.
- **Responses API requests using none of those three** — monitored, but NOT stopped automatically. A configured webhook can receive alerts; configuring one does not enable stopping.
- **Chat Completions API** — not covered by this monitoring at all.

That narrows the product-level statement that on the API "the task will stop" ([[8a0b760f]]): automatic stopping is a property of three specific request shapes, not of the API as a surface, so a team that reaches for the plain Responses API without persisted reasoning, WebSockets or compaction is choosing alerting without interception — and may not know it has.

What a stop is and is not. A blocked request returns HTTP 403 with error type `invalid_request_error` and code `misalignment_policy_violation`; match on the code rather than the message. The error can also arrive mid-stream, after output has already begun. A stopped request **does not undo earlier actions**, and the API provides no general way to resume a stopped conversation. On an alert, `request_paused: true` confirms only that the safety block was registered — not that execution stopped, and not that anything was reversed. So the tool-call side effects an agent had already committed when the check fired are still committed, and reconciling them is the application's job.

The alert surface. The webhook event is `safety.alert.created` and its payload carries only `data.id`, so details require a retrieval call; reading alerts needs the `api.safety.alerts.read` permission, and an unknown id returns 404 with code `safety_alert_not_found`. The retrieved alert's fields include `error_type`, `reason`, `request_id`, `response_id` and `request_paused`. `reason` may be `null`, including for Zero Data Retention requests, so an alert can arrive with no stated cause. Alert delivery and retrieval do not provide a complete audit history — they are not the system of record.

What the vendor tells the developer to do when it fires: stop dispatching further actions for that conversation, do NOT automatically retry the blocked workflow, preserve the request and response IDs and tool-call records, and surface the error to the responsible operator to compare the agent's actions against the intended work and review changes already made.

WHAT A FLAG DOES NOT ESTABLISH. The vendor states that a flag does not show the user violated a policy or that the agent acted against instructions, and that the check can both miss issues and flag legitimate activity. It is explicit that this is not a complete safeguard and that human approval should be kept for consequential actions — so a team must not retire an approval gate on the grounds that the platform now watches for misalignment.
