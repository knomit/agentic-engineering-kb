# Logging is the only control that addresses all ten agentic threat classes — and there is a stated rule for when it is a frontline control rather than a forensic one

In OWASP's crosswalk of AIUC-1 against the Top 10 for Agentic Applications, one requirement — **log AI system processes, actions and model outputs** — is the only one **mapped to all ten threats: Primary for four, Secondary for six.** No other control comes close to that coverage.

The valuable part is not that logging is broadly useful (a model already knows that) but the **stated rule for when detection is a frontline control instead of an audit trail**, which is a real design decision with a real answer:

> A detective control is **Primary** when the threat is **persistent, cross-session, or multi-agent** in nature *and* the threat is **operationally invisible without that specific detection mechanism**. It is **Secondary** when preventive controls serve as the frontline mitigation and detection provides the forensic and audit layer.

Where logging is **Primary** — the threat leaves no other trace:
- **ASI06 Memory and Context Poisoning** — the crosswalk's own gloss: memory poisoning is invisible without logging. The agent behaves incorrectly long after the attack, and nothing at request time looks wrong.
- **ASI07 Insecure Inter-Agent Communication**
- **ASI08 Cascading Failures**
- **ASI10 Rogue Agents**

Where it is **Secondary** — input validation, access control, sandboxing and human approval are on the front line, and logs are for afterwards: ASI01 goal hijack, ASI02 tool misuse, ASI03 privilege abuse, ASI04 supply chain, ASI05 code execution, ASI09 trust exploitation.

**What this changes in practice.** The four Primary threats share a property: they are **stateful across time**. A per-request security control cannot see them, because no individual request is anomalous — the attack is the *sequence*. That is why detection is not a fallback for these and why "we have input filtering and sandboxing" does not cover them. Conversely, for the six Secondary threats, reaching for more logging instead of a preventive control is treating a symptom.

**The coverage gap to check in your own system:** the same crosswalk flags that a requirement to log *model* activity does **not** necessarily extend to **agent-level or application-level activity**, leaving tool interactions unlogged. Since tool calls are where an agent touches the world, model-output logging alone leaves the four Primary threats above still invisible. Log the tool I/O, not just the completions.

The crosswalk also states its own limit plainly, and it applies to any control-mapping exercise: it "identifies relevance, not sufficiency." A Primary mapping means the requirement addresses the threat's core risk — **not** that the requirement as written provides complete mitigation. Evaluate implementation depth, testing coverage and operational maturity separately.
