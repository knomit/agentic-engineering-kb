# Logging is the only control that addresses all ten agentic threat classes — and there is a stated rule for when it is a frontline control rather than a forensic one

In OWASP's crosswalk of AIUC-1 against the Top 10 for Agentic Applications, one requirement — **E015, "Log model activity"** — is the only one **mapped to all ten threats: Primary for four, Secondary for six.** No other control comes close to that coverage. The document states it outright: "E015 is mapped to all 10 Agentic Top 10 threats (4 Primary, 6 Secondary)".

**The four Primary mappings are the ones that carry the guidance**, and they were read off the table rather than taken from the summary: **ASI06** (Memory and Context Poisoning), **ASI07** (Insecure Inter-Agent Communication), **ASI08** (Cascading Failures) and **ASI10** (Rogue Agents). The remaining six — ASI01, ASI02, ASI03, ASI04, ASI05, ASI09 — are Secondary.

The valuable part is not that logging is broadly useful (a model already knows that) but the **stated rule for when it is a frontline control rather than a forensic one**: logging is Primary "where it serves as the core detection or traceability mechanism for threats that are persistent, cross-session, or multi-agent in nature", and Secondary "where preventive controls (input validation, access control, sandboxing, human approval) are the primary mitigations and logging provides the forensic and audit layer".

That gives a usable test, and the four Primary entries confirm it holds — every one of them is persistent, cross-session or multi-agent. **Persistent, cross-session, or multi-agent** is the condition under which you cannot prevent the thing and detection is the actual control — memory poisoning is the canonical case, because the harm is deposited in one session and realised in another, so there is no single call at which a preventive check could fire. For everything else, logging is the audit layer and the real control is elsewhere; if your design leans on logs for a threat that a preventive control could have stopped at the boundary, you have chosen forensics over prevention by accident.

**AN INTERNAL CONTRADICTION IN THE SOURCE, AND IT POINTS THE WRONG WAY FOR LOGGING** (found by re-counting rather than re-reading). The same document asserts, in its Part A commentary, that "**B006 is the most broadly mapped requirement in this crosswalk**". Counted from its own mapping tables that is false: B006 (prevent unauthorized AI agent actions) maps to **8 of 10** threats and D003 (restrict unsafe tool calls) to **8 of 10**, while E015 maps to **10 of 10**. The document never reconciles the two statements.

The consequence is practical rather than pedantic: a reader who takes the Part A sentence at face value concludes that scope enforcement is the broadest control and that logging is a supporting one, which is the opposite of what the tables show and the opposite of what an agentic threat model needs. **A logging requirement is not a footnote to the security requirements here — by this crosswalk's own arithmetic it has strictly wider coverage than either of them.** `2d060289` records the B006/D003 side of the same count.

**VERIFICATION (2026-08-15, 18th run, and a method correction made the same day).** Re-read against the primary PDF (download id 54627, 55 pages, dated 2026-05-25 — unchanged since this fact was written). Both quotations confirmed verbatim.

*A first pass claimed the 4/6 split had been "independently re-derived" when it had not: the `grep`-based count used to check it returned only nine of the ten rows and was quietly wrong.* The cause is worth knowing, because it is a silent undercount that looks like a clean result: **`pdftotext` emits a form-feed character at each page break and prepends it to the first token of the next page**, so `ASI07` — the first row after a page boundary inside this very table — appears as `\fASI07` and does not match a `^`-anchored pattern. One item goes missing per page boundary, always the same way. The split has since been verified by reading the table region directly, and it is correct as the document states. Unanchored `grep -o` is immune and recovers all ten, which is why the frequency-counting technique used elsewhere in this pack is unaffected.
