# Bind the agent's tool set per request from the signed-in user's own permissions, so "the agent can only access data the user could already see" — and note this is orchestrator-side filtering, not authorization

Snyk ships one LangGraph agent behind a Slack app, a web app and direct API access. Its access-control decision is made at request construction rather than inside the agent: "We attach tools at request time based on the permissions the signed-in user actually has", with the stated consequence that "the agent can only access data the user could already see". Most tools run as separate microservices that scale independently; context management, guardrails and model fallbacks are attached as middleware at defined lifecycle points; session history lives in PostgreSQL keyed by session through the checkpointer.

WHY THE PER-REQUEST PART IS THE LOAD-BEARING PART: a static tool set plus a service account makes the agent's reachable surface the union of every user's, and the only thing standing between a given user and someone else's data is the model's own behaviour. Deriving the tool set from the caller's identity on each request makes the reachable surface equal to that caller's surface by construction, so a prompt injection or a confused agent cannot reach past it — there is no tool bound in that request that could.

WHAT THIS DOES NOT MEAN, and it is the misreading that matters: per-request tool binding is a reduction of what the agent can attempt, not a grant of authority to what it attempts. The downstream service still has to re-authorize the call on its own, because trusting the orchestrator's filtering is itself the documented failure mode ([[48c4e555]]). Read the two together: the orchestrator narrows the surface, the service enforces the boundary, and neither substitutes for the other.

THE ROLLOUT DETAIL THAT MAKES IT CHEAP: Snyk moved the same runtime through three surfaces — internal support tool, customer support portal, then a panel in the core product — changing the surface and not the runtime, with a shared factory returning the compiled graph and each team supplying configuration, so most new workflows are configuration rather than new architecture. That is a vendor-channel case study of the practice working at one company, not a measured comparison against the alternative.
