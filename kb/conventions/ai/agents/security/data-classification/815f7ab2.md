# A key to a model running WITHOUT production safeguards is a higher sensitivity class than the same key with them on — METR's four tiers, and the transcript viewer that leaked across them

METR handles nonpublic model access and confidential partner information, and publishes the classification scheme it works to. Four categories of company data, least to most sensitive:
1. PUBLISHED — data exposed publicly, e.g. published transcripts or evaluation results.
2. GENERIC MODEL ACCESS — data: unpublished evaluation results involving only public models and information, or outputs such as agent transcripts from public models. Credentials: API keys granting access to public models.
3. SENSITIVE MODEL ACCESS — data: evaluation results and outputs from private models or including hidden chain-of-thought. Credentials: "API keys granting access to hidden CoT, non-public models, or models without production safeguards."
4. HIGHLY SENSITIVE INFORMATION — sensitive IP or business information: architectures and training processes, release dates, internal incidents.

TWO CLASSIFICATION DECISIONS WORTH COPYING. A credential is classified by what it unlocks, so the same model reached with cyber safeguards reduced sits a whole tier above the same model reached normally — the credential that makes accurate capability testing possible is the one that most needs a barrier around it. And hidden chain-of-thought is treated as sensitive DATA in its own right rather than as a byproduct of a run, which is the same asset [[a7863d24]] and [[33aed84c]] treat as a theft target. METR's stated design goal is to keep categories 3 and 4 behind information barriers "while minimizing friction for researchers working with less-sensitive data (categories 1 and 2)" — the tiering exists to buy speed at the bottom, not only safety at the top.

HOW THE BOUNDARY WAS CROSSED ANYWAY, May 2026. METR "inadvertently exposed a read-only SQL query mechanism via our public transcript viewer. The queries were scoped to public data by default, but a bug could be exploited to access unpublished evaluation data. This dataset was supposed to contain only data from non-sensitive models, i.e. category 2 above. However, some sensitive model data (i.e. category 3 above) was accidentally included in this database." Two independent failures had to line up: a query-scoping bug, and a store whose classification was maintained by convention rather than enforced by a mechanism. A classification that nothing checks drifts by accumulation. An independent security researcher found and responsibly disclosed the vulnerability; METR took the API offline and paid a bounty, and reports that attackers probing the endpoint during a concurrent campaign showed no indication of having discovered the exploit or accessed non-public data.

THE ARCHITECTURAL REMEDY, stated as an invariant: METR "now maintain[s] an isolated public production environment for public-facing applications that is architecturally separated from our internal infrastructure, so that a misconfiguration in a public service cannot expose internal data."

CONTEXT ON THE ATTACKER SIDE, because it is a datapoint on agentic offence against an AI organisation: in the same May campaign METR observed attackers "systematically probing our publicly accessible infrastructure, with heavy use of agents to automate vulnerability discovery, including by credential stuffing authentication providers, attempting OAuth token grants, scanning newly deployed services, and attempting to phish staff."

SCOPE: METR states the described measures were accurate as of 2026-07-30 and are subject to change, and that this post covers external actors attacking METR's systems, not AI agents hacking during METR's evaluations — on which it reports an initial scan with no evidence of agents hacking third parties, and a fuller update promised.
