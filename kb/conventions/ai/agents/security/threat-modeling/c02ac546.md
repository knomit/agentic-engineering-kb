# A threat taxonomy is a checklist; walking a layered architecture against it is a generator — MAESTRO applied to one real system produced 13 threats the taxonomy did not contain

OWASP's multi-agent threat modelling guide is not another taxonomy — it deliberately reuses the ASI T1–T15 list and instead demonstrates a *method*: MAESTRO (Multi-Agent Environment, Security, Threat, Risk and Outcome, originally from the Cloud Security Alliance), which walks a system layer by layer. Three properties of the result are worth more than the framework's name.

**THE LAYERS.** Seven, plus a cross-layer category: (1) Foundation Model — model integrity, alignment, poisoning; (2) Data Operations — vector store integrity, prompt management, retrieval attacks; (3) Agent Frameworks — execution logic, workflow control, autonomy boundaries; (4) Deployment Infrastructure — container runtime, orchestration, networking; (5) Evaluation and Observability — monitoring, logging, human-in-the-loop interfaces; (6) Security and Compliance, drawn as a *vertical* cutting all layers — access control and policy enforcement; (7) Agent Ecosystem — interaction with humans, external tools and other agents; and (8) Cross-Layer — emergent behaviour from multi-agent interaction.

**THE POINT THAT CHANGES HOW YOU RUN THE EXERCISE.** Applying the walk to a concrete system (the guide works ElizaOS, a blockchain agent framework) generated **T26–T38 — thirteen threats that are not in the ASI taxonomy at all**, because they are properties of that system rather than of agents in general: wallet key compromise, selective log manipulation, manipulation of a proof-of-sampling verification mechanism, cross-chain bridge attacks, emergent collusion between trading agents producing a flash crash. The generalisable lesson is about your own output: **if your threat model produced only the entries already on the published list, you performed a mapping exercise, not a threat model.** The taxonomy tells you what everyone has; the layer walk against your actual architecture is what finds what only you have.

**TWO STRUCTURAL CONSEQUENCES FOR HOW YOU ASSIGN OWNERSHIP.**

*The same taxonomy entry recurs at several layers, with different mechanisms and different mitigations.* Privilege Compromise (T3) appears both at Deployment Infrastructure and at the Security and Compliance vertical. Rogue Agents (T13) appears at Deployment Infrastructure, at Agent Ecosystem, and again cross-layer. Misaligned and deceptive behaviour (T7) appears at the Foundation Model layer and at Agent Ecosystem. A tracker that gives each threat one owner and one mitigation will close it at the layer where it was easiest to see and leave the other instances open.

*Cross-layer is a separate category precisely because a per-layer review cannot reach it.* The threats seated there — Intent Breaking, Agent Communication Poisoning, Rogue Agents, Human Trust Manipulation — arise from interaction between layers rather than inside any one of them. A review that walks layers and stops has structurally excluded the class of failure that multi-agent systems are distinctively prone to. Budget an explicit cross-layer pass; it will not fall out of the per-layer work.

**WHERE THIS SITS RELATIVE TO OTHER FRAMEWORKS.** The guide maps MAESTRO onto MITRE ATLAS rather than competing with it, and positions itself as a companion to the ASI taxonomy. Its stated scope is multi-agent systems, where the guide's own framing is that decentralised architecture, uneven autonomy and uneven trust between agents are what make perimeter-based models inadequate.
