# Logging mechanics that buy headroom at high request rates — rotate every minute, pre-compress, and carry skip counts in sampled entries

Concrete techniques Amazon uses to keep per-request logging affordable at high per-host throughput, several of which are non-obvious:

- **Rotate log files every MINUTE, not every hour.** Counter-intuitive but stated plainly: with per-minute rotation the shipping agent reads the file from PAGE CACHE rather than from disk, and the CPU and IO cost of compressing and shipping is spread evenly across the hour instead of spiking at the top of it.
- **Write logs already compressed.** If the shipping agent compresses before sending, system CPU and disk spike periodically. Streaming compressed logs to disk amortises that and halves disk IO. The caveat they attach: use a compression algorithm that tolerates TRUNCATED files, because the application can crash mid-write.
- **Write to tmpfs / ramdisk.** Keep logs in memory until shipped. Explicitly noted to work best with per-minute rotation, not hourly.
- **Offload serialisation and flushing to a separate thread.** Easy, commonly done.
- **Sample, but carry the skip count.** Write every Nth entry and include in each written entry HOW MANY were skipped, so downstream aggregation can still estimate true volume in its metrics. Reservoir sampling gives more representative samples; other schemes prioritise errors and slow requests over fast successes. The cost is explicit: with sampling you lose the ability to troubleshoot a specific customer's specific failure, and some compliance regimes forbid it outright.
- **In-memory aggregation** is the last resort at hundreds of thousands of TPS per machine — and they warn not to reach for it prematurely, because it costs a lot of observability.

Two capacity rules that go with these, and they are test requirements rather than settings:

- Load-test at maximum sustained load, or overload, FOR HOURS, and prove the shipping agents keep up with log production — otherwise disks fill during exactly the incident you needed the logs for. Put logs on a partition other than root so excessive logging cannot break the system.
- Decide in advance what happens when the disk DOES fill: stop accepting requests, or keep serving with no logging? Amazon calls operating without logging risky and tests that near-full-disk servers are detected. Measure per-server IO and CPU consumed by the logging agents specifically.

For agent platforms the arithmetic differs in a way that makes this easier, and worth stating: request rates are far lower than a 20M-TPS datastore, but each entry is far larger (prompts, tool arguments, tool results, reasoning traces). The binding constraint is usually bytes per entry, not entries per second — so truncation and field-level opt-in buy more headroom than sampling does, and sampling costs you the one trace the customer is asking about.
