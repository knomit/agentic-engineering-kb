# Measure an async agent queue by the AGE of first-attempt messages — producer errors, consumer errors and DLQ rate each mislead you in a different direction

Amazon's stated problem: for a queue-backed system, none of the obvious availability signals work.

- PRODUCER-side error rate just mirrors the availability of the queue service itself. If you enqueue to SQS, your producer availability IS SQS's availability — it tells you nothing about whether work is getting done.
- CONSUMER-side error rate makes the system look WORSE than it is, because failures get retried and usually succeed.
- DEAD-LETTER QUEUE volume is a genuinely good availability measure but arrives far too late to act on. Alarm on it, but never rely on it for detection.

What they use instead: the AGE of messages in the queue, computed at dequeue from the enqueue timestamp the queue service provides. And the refinement that makes it usable — AWS IoT emits `AgeOfFirstAttempt`, which is now-minus-enqueue-time but ONLY for the first delivery attempt of a message. This strips out the noise of retrying and re-enqueueing, so the metric moves when the SYSTEM is behind rather than when individual consumers are choosing to be slow. A second metric, `AgeOfFirstSubscriberFirstAttempt`, stabilises fan-out: publishing to a million subscribers is legitimately slower than to one, so they time the first attempt to the FIRST subscriber and track the rest separately.

The generalisable rule Amazon says is used across the company: categorise the latency of first attempts separately from the latency of retry attempts. For an agent platform this is the difference between 'the run queue is backing up' and 'one customer's webhook is flaky and everything is being retried'.

A second, cheap saturation signal from the same article: track the fraction of poll attempts that return EMPTY. If nearly every poll comes back with a message, you have exactly enough polling capacity or too little, and no buffer left to absorb a burst — a small spike will convert directly into sustained backlog. Empty polls are headroom.

Finally, propagate a request/trace id inside the queued message itself. Once work bounces across hosts and sits in queues, that id is the only thing that reassembles the story; Amazon pairs it with X-Ray, and moves to a workflow service (Step Functions) once the flow is more than a trivial queue.
