# Dataset, request, task — each reporting unit hides defects visible at the one below it, and for agents the only honest denominator is the task

Anthropic's August-September 2025 incidents produced two separately-recorded blind spots that are the same blind spot at two altitudes. Put together they give a rule about which denominator to report in.

THE LADDER, from most aggregated to least:

DATASET LEVEL — an eval suite scores aggregate accuracy over a fixed set. Anthropic: "the evaluations we ran simply didn't capture the degradation users were reporting." A defect affecting a minority of requests, or only requests of a certain shape, does not move an aggregate score, because most requests are fine. The eval passes and the deployment is broken.

REQUEST LEVEL — a dashboard reports errors per request. This is finer, and still understates harm whenever requests are not independent. Under sticky routing, misrouted traffic peaked at 16% of Sonnet 4 requests while "approximately 30% of Claude Code users who made requests during this period had at least one message routed to the wrong server type." Session affinity removed the independence that makes a low per-request rate feel safe.

TASK / SESSION LEVEL — the unit the user actually experiences. An agent issues many model calls per user task, so it sits at the worst end of this curve: the gap between per-request rate and per-task rate widens with the number of calls, and a per-request rate that reads as acceptable background noise is a materially higher per-task failure rate.

THE RULE: report at the unit of user-visible harm, which for an agent is the completed task, and treat coarser units as screening tools rather than evidence of health. Concretely — keep the eval suite, but do not let a green aggregate close an investigation; add per-session or per-task defect rate alongside per-request error rate; and when quality is reported as degraded while your metrics disagree, look at per-request outcome DISTRIBUTIONS and the tails rather than the mean, and correlate against your provider's deployment timeline rather than only your own change log.

WHY THIS IS EASY TO GET WRONG. Each level up is the more natural thing to build: eval suites come with the model, per-request metrics come with the HTTP layer, and per-task attribution has to be constructed deliberately because the task boundary is an application concept the infrastructure does not know about. So the honest denominator is the only one nobody hands you.

WHAT THIS DOES NOT MEAN, carried from both sources. It is NOT the claim that evals are useless — it is that a benchmark run samples the MODEL, not your deployment, so it is the wrong instrument for a serving-layer fault specifically. It is a different failure axis from harness-induced eval noise such as CPU and RAM allocation or trial isolation: there the serving stack is constant and the harness moves the score; here the harness is constant and the serving stack moved underneath it. Do not conflate the two when diagnosing. The sticky-routing amplification is also NOT the same mechanism as ordinary correlated failure — the correlating factor is a routing decision that is deliberately cached, not a shared dependency — so the remedy is a reporting-unit change, not dependency isolation. And note this is about which denominator to use, not about whether you have enough traffic to populate it; low-volume workloads face the separate problem that at very low incidence rates no denominator gives them detection power at all.
