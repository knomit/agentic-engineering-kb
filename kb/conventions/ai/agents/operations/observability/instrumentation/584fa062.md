# Log first, aggregate later: write every timer and counter into one structured entry per unit of work, and compute metrics downstream

Amazon's stated inversion of the usual approach: measurements are NOT aggregated in-process and periodically flushed to a metrics system. Every timer and counter for every unit of work is written to a structured log file, and aggregate metrics are computed afterwards by a separate system reading those logs. The payoff is that a single instrumentation effort yields both ends of the range — fleet-level aggregate metrics for dashboards and alarms, AND request-level detail for troubleshooting — rather than two parallel instrumentation stacks that disagree.

The discipline that makes it work:

- **Exactly one request-log entry per unit of work.** One entry per inbound request or per message pulled from a queue. Never combine units of work, so a failed request is one entry containing its inputs, its caller, and all timings.
- **And no MORE than one.** In a non-blocking or staged pipeline it feels natural to log per stage. Amazon explicitly rejects this: thread a single 'metrics object' handle through the stages and serialise it once when all stages complete. Multiple entries per unit of work make log analysis harder and multiply the already-expensive logging overhead. Their warning is that this must be planned UP FRONT for a non-blocking service, because it is very difficult to refactor in later.
- **The stated exception, which is the agent case:** a long-running, multi-minute or multi-hour workflow-like task SHOULD emit periodic entries, so you can tell whether progress is being made and where it slowed down. An agent run is exactly this shape — one entry at the end tells you it took 11 minutes and nothing about where.

So for an agent platform the unit of work is the agent RUN, carrying a metrics object accumulated across every model call, tool call, and subagent — serialised once at completion, with periodic progress entries in between. Not one entry per tool call scattered across the log.

Amazon also keeps the two log types in SEPARATE files: the structured per-unit-of-work request log (an audit log and trace of what happened) and the unstructured application/debug log (Log4j-style error and warn lines). The reason given is that homogeneous entry formats make log analysis much easier. They also state the cost position honestly — logging this much detail per request is expensive, and they do it anyway, because without it you cannot answer customers about availability blips and latency spikes. DynamoDB serves over 20 million requests per second of internal traffic and still logs every request.
