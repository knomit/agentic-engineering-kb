# Break tool and dependency metrics out per call, per resource, per status code and per retry count — aggregated dependency timing hides the actual cause

Amazon's rule for instrumenting calls to dependencies, and the specific diagnoses it produced.

**Log availability and latency of every dependency, from the caller's side.** Without it you are reduced to eyeballing the dependency's own graphs next to yours and guessing whether a spike over there caused a failure over here. Note that many client frameworks plumb this automatically but some — they name the AWS SDK — require manual instrumentation, so verify rather than assume.

**When you call the same dependency several times in one unit of work, measure each call separately** and make clear which resource each one touched. Their DynamoDB example breaks timing out per TABLE, per ERROR CODE, and even per NUMBER OF RETRIES. Two real findings they credit to that breakdown, both of which would have been invisible in an aggregate:
- slowness caused by retries from conditional-check failures;
- client-perceived latency increases that turned out to be throttling-retries and result-set PAGINATION rather than packet loss or network latency.

**Add a counter per error REASON**, starting with one metric per failure exception class, so you can see trends in why things fail without mining the application log for it.

**Categorise errors by cause, or the metric is noise.** The minimum split is client's-fault versus server's-fault. Beyond that, separate DELIBERATE errors from bugs — their example is a DynamoDB conditional write failing its precondition, which is expected and occasional, versus an 'invalid request' error, which is most likely a bug to fix. Lumping them together makes the metric useless for alarming.

For agents this is the difference between 'tool calls are failing' and an actionable signal. The dimensions that matter: per TOOL, per resource the tool touched, per status/error class, per retry attempt, and — the agent-specific one — split model-refusals and schema-validation failures of model-generated arguments away from genuine remote failures, because the first two are prompt or schema bugs and the third is an outage. Also record the request ID a failing dependency returned so its owner can find their own log entry; timeouts make this tricky because no ID may have come back yet, but log it whenever one did.
