# Agent telemetry inverts three assumptions classical logging advice is built on — the unit is a run not a request, the constraint is bytes not entries, and the content is adversarial and read back by models

Amazon's observability practice is written for services handling many short, cheap, trusted requests. Every one of these facts carries an agent-specific delta, and the deltas move in the same direction: **three of the assumptions the classical advice rests on are inverted for agents, and each inversion changes which technique is correct.**

**INVERSION 1 — THE UNIT OF WORK IS A RUN, NOT A REQUEST, AND IT IS LONG.** The classical rule is exactly one structured log entry per unit of work, and explicitly *no more than one*: thread a single 'metrics object' through the stages and serialise it once when all stages complete, because multiple entries per unit make analysis harder and multiply already-expensive logging overhead. Amazon warns this must be planned UP FRONT for a non-blocking service because it is very difficult to refactor in later.

But Amazon also states the exception, and the agent case lands squarely in it: a long-running, multi-minute or multi-hour workflow-like task SHOULD emit periodic entries so you can tell whether progress is being made and where it slowed. So for an agent platform the unit is the **agent RUN** — a metrics object accumulated across every model call, tool call and subagent, serialised once at completion, **with periodic progress entries in between**. Not one entry per tool call scattered through the log. One entry at the end tells you the run took 11 minutes and nothing about where.

**INVERSION 2 — THE BINDING CONSTRAINT IS BYTES PER ENTRY, NOT ENTRIES PER SECOND.** The high-throughput techniques are built for a 20-million-TPS datastore: per-minute rotation (so the shipping agent reads from page cache rather than disk, spreading compression cost evenly instead of spiking hourly), pre-compressed writes (halving disk IO — with a compression algorithm that tolerates TRUNCATED files, since the application can crash mid-write), tmpfs, and sampling every Nth entry while carrying the skip count so downstream aggregation can still estimate true volume.

Agent request rates are far lower, but each entry is far larger — prompts, tool arguments, tool results, reasoning traces. **So truncation and field-level opt-in buy more headroom than sampling does, and sampling costs you the one trace the customer is asking about.** That is the practical inversion: reach for the size lever, not the count lever. The stated cost of sampling is explicit — you lose the ability to troubleshoot a specific customer's specific failure, and some compliance regimes forbid it outright.

**INVERSION 3 — THE CONTENT IS ATTACKER-INFLUENCED, AND IT IS READ BACK BY MODELS.** The classical ordering rule still holds and is counter-intuitive: record request details BEFORE validation, authentication and throttling, or the requests you most need to explain — the rejected ones — have no log entry. But logging attacker-controlled input has two named failure modes that must be handled at the same moment: **disk fill and cost** (a 1 MB caller string lands in the entry; truncate before logging) and **log injection** (filter ASCII control characters and any escape sequences meaningful to your log format, because a caller can pass a string that is itself a well-formed log entry — a forged entry corrupts the audit trail and every metric computed from it).

Agents have far more untrusted-content surface than a typical API, and it is longer and more adversarial: user prompts, tool results fetched from the web, file contents, subagent outputs, and model-generated arguments all reach the trace. Anything in an agent trace has already passed through a channel a prompt-injection attacker may control. **And the agent-specific escalation: traces are increasingly read back BY MODELS during debugging, which makes an injected entry an instruction-delivery channel, not merely an audit-integrity problem.** Pair this with opt-IN rather than opt-out field logging, so a sensitive parameter added later is not logged by default.

**WHAT SURVIVES UNCHANGED, and is worth keeping because it addresses failures agents have in abundance:**

- **Emit 1 for success and 0 for failure**, so the metric's *average* is availability directly, with no ratio arithmetic and no dependence on error count and total count arriving at the same aggregation interval. And emit the ZEROS deliberately, so a process that stops emitting anything is distinguishable from one that is fine — a worker that stopped polling, a background evaluator that crashed, a scheduled agent that never fired all look exactly like 'nothing to report' otherwise. Every standby, follower or idle-by-design component should be emitting its zeros.
- **Break dependency metrics out per call, per resource, per error class and per retry count.** Aggregated timing hid two real diagnoses: slowness from retries on conditional-check failures, and latency increases that turned out to be throttling-retries and result-set PAGINATION rather than network latency. The agent-specific dimension to add: **split model refusals and schema-validation failures of model-generated arguments away from genuine remote failures**, because the first two are prompt or schema bugs and the third is an outage. Categorise errors by cause at minimum client-fault vs server-fault, and separate DELIBERATE errors (a conditional write failing its precondition — expected) from bugs (an 'invalid request' — probably yours), or the metric is useless for alarming.
- **Keep the structured per-unit-of-work request log in a SEPARATE file from the unstructured application/debug log**, because homogeneous entry formats make analysis much easier.

**THE FAN-IN CONSTRAINT THAT BOUNDS ALL OF IT.** Workers pushing traces, token metering and run state back to a collector is exactly the 100:1 client-to-service shape where the obvious direction becomes fragile: in steady state the calls arrive uncorrelated and load is smooth, but any small environmental change makes clients act in a CORRELATED way and past the breaking point goodput does not degrade, it **drops to zero**. The named triggers include recovery from an outage where every client reconnects at once — and 'everyone restarted and re-pushed' is a routine agent-fleet event. Interpose a hyperscale store, or invert the direction, rather than assuming the collector scales with the fleet.

**WHAT THIS DOES NOT MEAN.** Not an argument to log less: Amazon states the cost position honestly — logging this much detail per request is expensive and they do it anyway, because without it you cannot answer customers about availability blips and latency spikes, and DynamoDB logs every one of 20M+ requests per second. Not an argument that sampling is never right, only that for agents it trades away the wrong thing first. The capacity rules still bind and are TEST requirements rather than settings: load-test at maximum sustained load or overload FOR HOURS and prove the shipping agents keep up, or disks fill during exactly the incident you needed the logs for; put logs on a partition other than root; and decide in advance what happens when the disk fills — stop accepting requests, or keep serving with no logging — because operating without logging is itself risky. In-memory aggregation remains a last resort, not a default, because it costs a lot of observability. Finally, this concerns HOW to instrument; the separate question of which DENOMINATOR to report defect rates in — dataset, request, or task — is recorded elsewhere and is not the same rule.
