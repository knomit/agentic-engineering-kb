# A model swap breaks four things — one loudly and three silently — and the silent three are cost, defaults and inverted prompt behaviour

Changing a model string is routinely treated as a config change. Across these sources it breaks four distinct things, and only ONE of them announces itself — which is why migrations look clean in staging and show up later in the bill and the p95. Run all four checks.

BREAKAGE 1 — HARD 400s (the loud one, and the only one you will notice immediately). Two long-standing techniques became errors rather than degraded behaviour:
- TRAILING ASSISTANT PREFILL (a partial assistant message on the LAST turn for the model to continue) is unsupported from Claude 4.6 models and Claude Mythos Preview onward and returns 400. Assistant messages ELSEWHERE in the conversation are unaffected — it is specifically the trailing prefill. Replacements by use case: structured outputs (or a tool with an enum field) for forcing JSON/classification shape; a plain system instruction for preamble suppression, with post-processing for the occasional leak; and for continuations, move the interrupted text into a USER message.
- `thinking: {type: "enabled", budget_tokens: N}` is deprecated on Opus 4.6 and Sonnet 4.6 and returns 400 on Claude 4.7 and later. Replacement is `thinking: {type: "adaptive"}` with `output_config.effort`, using `max_tokens` as the hard ceiling. There is no direct token-budget equivalent — you steer depth with effort, not a number.

BREAKAGE 2 — SILENTLY CHANGED DEFAULTS. Omitting a parameter does not mean the same thing across models. Omitting `thinking` leaves it OFF on Opus 4.6–4.8 and Sonnet 4.6, but ON by default on Opus 5 and Sonnet 5. On Opus 5 it can only be disabled at effort high or lower; on Fable 5 / Mythos 5 it is always on regardless of the parameter. So an unchanged request body produces different behaviour and different cost. Never assume an omitted parameter carries across a migration — enumerate the defaults for the new model explicitly.

BREAKAGE 3 — SILENTLY CHANGED COST, NON-MONOTONICALLY. Enabling tools injects a tool-use system prompt billed as input tokens on EVERY request, and its size depends on the tool_choice mode: `auto`/`none` use the cheaper prompt, `any`/`tool` the larger one — on Opus 5, 286 vs 406 tokens; on Sonnet 5, 354 vs 474. So reaching for forced tool use as a reliability fix is a standing ~120-token-per-request tax. And the overhead moves unpredictably across versions: Opus 4.7 sat at 675/804 while both its predecessor (Opus 4.5, 496/588) and successors (Opus 4.8, 290/410; Opus 5, 286/406) are far lower. Do not carry a cost estimate across an upgrade. The only way to pay zero is to pass no `tools` at all with tool_choice `none` — passing tools and setting `none` does not get you back to zero. NOTE these figures exclude the tool definitions and every tool_use/tool_result block, which dominate in an agentic loop; check them against live docs rather than a cached value.

BREAKAGE 4 — INVERTED PROMPT BEHAVIOUR (the most expensive, because its failure signature is invisible). Scaffolding written to stop a WEAKER model under-using tools pushes current models the other way. 'CRITICAL: You MUST use this tool when…' now overtriggers where plain 'Use this tool when…' is correct; 'If in doubt, use [tool]' overtriggers; 'Default to using [tool]' should become conditional; and appended self-verification instructions cause OVER-verification on Opus 5 because it already verifies its own work — the instruction there is to REMOVE the line, not soften it. Why this survives: an under-triggering model gives a visibly lazy answer so you notice, while an over-triggering one gives the RIGHT answer after four unnecessary tool calls, degrading as cost and p95 latency rather than as an error. Nobody files a bug and the prompt is never revisited.

ONE THING THAT DOES NOT RELIABLY CHANGE, and must be re-tested per tier rather than assumed fixed: when a required tool parameter is missing from the user's request, a model may ASK or may INVENT a plausible value, and this varies by tier — Opus is much more likely to ask; Sonnet might ask, especially if prompted to think first, or might infer. The documented example invented both the missing required argument AND an optional one the user never mentioned. Strict tool use does not help: schema conformance says nothing about whether values were GROUNDED, and a hallucinated location is perfectly schema-valid. If a wrong value is costly, defend elsewhere — validate arguments against something real before executing, require confirmation for consequential calls, or make an unspecified parameter representable (explicit null, or an ask-the-user branch) rather than silently defaultable.

WHAT THIS DOES NOT MEAN. Not an argument against upgrading — this pack separately records that upgrading the model beat doubling the token budget on the older one. The claim is that the migration has a checklist and three quarters of it is silent. For the PROMPT side specifically, the corrective direction is covered separately and at length: on upgrade the first experiment is DELETION rather than addition, because scaffolding a model no longer needs consumes attention and constrains the output distribution — with the countervailing note that models now OVER-delegate to subagents without being prompted, so on some axes the new-model tuning problem is damping behaviour rather than removing scaffolding. Source-strength caveats carry: the ~80%-prompt-reduction figure and the per-model-prompt practice come from a conference-talk summary rather than published documentation, and its named exemplars (Fable, Opus 4.8) have been succeeded by Opus 5; the token-overhead and API-breakage figures are from vendor documentation and have changed with every model release, so re-read them rather than quoting these.
