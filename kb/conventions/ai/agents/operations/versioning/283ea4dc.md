# Have workers report their running version in the health check so the fleet can detect zombies

A small, concrete convention from Amazon's Builders' Library. Servers can drop off the network or power down for a long stretch and then come back — 'zombies'. A returning zombie may be running significantly outdated code, incompatible with the current database schema or configuration, and it will happily rejoin the pool and start serving.

The stated fix: have each server answer its health check WITH its currently running software version. A central monitoring agent compares versions across the fleet, spots anything unexpectedly out of date, and keeps it out of service. Anomaly detection covers the same ground from a different angle — 'old code' is listed as one of the things a fleet-wide comparison catches that a server can never detect about itself.

For agent systems the version that matters is not just the binary. The things that drift and that a returning or long-lived worker can be stale on: the system prompt / context-file revision, the tool and MCP schema set, the model version pin, guardrail and policy rules, and the skill or plugin bundle. These are typically fetched at process start and cached for the life of the worker, which is precisely the zombie condition — a worker running yesterday's tool definitions against today's backends will produce plausible, well-formed, wrong calls rather than crashing. Report a hash or revision of each in the health response and compare across the fleet.

This pairs with the dependency-health-check tier: 'stale config or metadata' is named there as a failure a server cannot self-assess, because when a server has not seen an update for a while it genuinely cannot tell whether ITS update mechanism broke or the central publisher stopped publishing to everyone. Only a cross-fleet comparison distinguishes the two.
