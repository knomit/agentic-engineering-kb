# Any tool that can act on every agent at once is a correlated-failure source — give it velocity controls and make it respect the fault boundary

Amazon's stated rule, from the correlated-failures article: any action by an operator, or any tool that can act on multiple servers at the same time, introduces a correlated failure mode — because if anything goes wrong it goes wrong everywhere simultaneously. Their example of the bad old practice is running a command across the whole fleet in parallel to grep a log line or adjust an OS parameter.

Two requirements are placed on such tooling, and the second is the one usually missed:

1. Velocity controls and feedback loops, so a bad action reaches only a small percentage of the fleet before it is stopped.
2. The tool must respect the SAME fault boundary the system is architected around — for Amazon, never operating on servers in more than one Availability Zone at a time. The reasoning is that the service is already designed and practised to survive the loss of one such boundary, so confining the blast radius of tooling to that boundary means an operational mistake degrades into a failure mode the team has already rehearsed. Their automated patching system has both properties.

The agent-system translation, where the equivalent fleet-wide levers are numerous and unusually easy to pull: system-prompt updates, tool-definition and MCP-server changes, model-version pins, temperature and sampling config, guardrail rules, skill or context-file deployments. Each of these is typically a single config value read by every agent instance, which makes 'change it everywhere at once' the default rather than an unusual action. Roll them out with the same velocity controls you would apply to a binary deploy, and align the increments with whatever isolation boundary the system already has — tenant cell, region, or agent pool — so that a bad prompt or tool description lands inside a boundary the system can already lose.

The non-obvious part: this is an argument for coupling deployment granularity to an EXISTING, exercised fault boundary rather than inventing a new one for rollouts. A rollout boundary nobody has ever failed over is untested.
