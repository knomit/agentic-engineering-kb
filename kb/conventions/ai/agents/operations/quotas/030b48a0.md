# For requests whose cost is unknown until they finish, admit at the cheapest price and debit the true cost afterwards — letting the balance go negative

Rate limiting assumes you can price a request before admitting it. Often you cannot: Amazon's example is a query returning a single 1KB row versus one returning 1MB of rows. Pagination bounds the worst case but the spread between cheapest and most expensive page is still wide enough to make a single pre-admission threshold either too strict or useless.

Amazon's technique: treat every request as the cheapest possible request at admission time, then once the call completes, go back and debit the caller's quota by the true observed cost — pushing the balance negative if necessary, and letting it refill over time before the caller is admitted again. Services also assign lower quotas to APIs that are simply more expensive, and some count an oversized response as multiple requests.

This is close to an exact fit for agent workloads, where the pre-admission uncertainty is larger than in any of Amazon's examples: you cannot know before running a turn how many tokens it will consume, how many tool calls it will make, or how many subagents it will spawn. Metering a turn as one unit up front and reconciling against actual token and tool consumption afterwards — with a negative balance throttling the tenant's next request — gives you enforcement that tracks real cost without needing a prediction.

The operational consequence to design for: enforcement lags consumption by one request, so a single very expensive request always gets through. Size the maximum negative balance you are willing to carry against the most expensive single request the API can produce, and bound that request independently (max steps, max tokens, max fan-out) rather than relying on the quota to contain it.
