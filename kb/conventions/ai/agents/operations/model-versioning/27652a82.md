# Pin the prompt, config and model version together as one tested combination — and know that a retired model returns errors, not a fallback

Pin a specific dated model version rather than a floating alias, and treat an upgrade as an evaluated decision. Prompts do not migrate for free — re-tuning across a version bump is genuine work.

The operational pattern: keep a shadow pipeline running the newest version against the same traffic, compare it on your evals, and promote deliberately. This turns an upgrade into a measured change instead of an unannounced regression appearing in production.

THE PINNING RULE IS STRONGER THAN 'PIN THE MODEL' (Microsoft's Azure architecture guidance, which corroborates the above and sharpens it). A prompt and a set of hyperparameters are authored FOR a specific model version. What must be pinned is the COMBINATION — prompt version, configuration, and model version travel together, and only combinations you have tested may reach production. The explicit warning: A/B testing, load balancing, and blue-green deployment MUST NOT mix components, because each of those mechanisms will otherwise happily pair prompt v1 with model v1.1 and expose users to a combination nobody evaluated. If you upgrade model1 to model1.1 and that requires prompt1 to become prompt2, your architecture has to guarantee prompt1 only ever meets model1.

Two implementation shapes for that guarantee: deploy the prompt and config INSIDE each orchestrator deployment so a router selecting a deployment implicitly selects a matched set; or, behind a gateway, have the orchestrator set an HTTP header naming the model and version and let the gateway route on it. The External Configuration Store pattern works for prompts and hyperparameters when the orchestration logic itself is unchanged — it does not help when the update also changes orchestration code.

DEPRECATED AND RETIRED ARE DIFFERENT, and the difference is an outage. For hosted model-as-a-service deployments: a DEPRECATED model cannot be newly deployed, but existing deployments keep working. A RETIRED model's existing deployments RETURN HTTP ERRORS. There is no graceful degradation and no automatic substitution — if you have not migrated by the retirement date, your application stops. Self-hosted and managed-compute deployments are exempt because you control the lifecycle, which is one of the real arguments for those hosting modes.

TURN OFF AUTOMATIC UPGRADES EXPLICITLY. Platform features that silently move production to a new version remove the evaluation gate this whole practice exists to create. On Azure OpenAI that means setting deployments to 'No Auto Upgrade'; on the Foundry Models API it means setting a specific version and supplying no upgrade policy, accepting that upgrades then become manual.

Observability requirement that makes the rest debuggable: log enough metadata to correlate any observed behaviour with the exact prompt, configuration, model version, and retrieval path that produced it. Without that correlation you cannot attribute a regression to the thing that changed.

Also plan for the change to be broader than the model call. Microsoft enumerates six surfaces a model update can touch: the model, its hyperparameters, the prompt, the orchestration logic, the grounding data and retrieval strategy, and the HARDWARE (managed-compute models run only on specific compute SKUs, and those SKUs are themselves retired on their own schedule). A fine-tuned model must be re-fine-tuned against the new base version before use.

Related skew detection worth wiring up at the same time: monitor input and output lengths and format-compliance rates (does the JSON still parse?), cluster embeddings to catch semantic drift, and include production's real typos and fragments in the hold-out set rather than clean synthetic inputs. Run the pipeline more than once on the same input to expose nondeterministic failures — a single passing run proves less than it appears to.
