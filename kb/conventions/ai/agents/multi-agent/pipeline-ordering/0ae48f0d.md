# A sequencing constraint stated in the agent's instructions gets skipped — put the gate in the pipeline so the next stage cannot start until the review passes

LangChain's design agent produces film in three stages — storyboard, then animatic timed to audio, then production — with a review between acts. The ordering was first expressed as instructions: "We first described this order in the skill's instructions", and the agent sometimes skipped reviews. The fix was to move the constraint out of language: "Now the pipeline enforces it in code, so assembly waits until every act passes review,".

The reason the engineering is worth it is a cost asymmetry between the stages, stated in the same account: "A storyboard frame takes about 50 milliseconds to render, compared to 8 to 40 seconds for a single" second of finished film. A defect that escapes review into production is therefore paid for at orders of magnitude the render cost of catching it a stage earlier, which is also why exploration happens in storyboards rather than in rendered footage.

The operational rule: an instruction is a preference the model weighs against everything else in context; a code gate is a precondition it cannot weigh at all. When an ordering or review constraint matters, express it as a precondition on the next stage and keep instructions for the parts that genuinely cannot be expressed that way.

What this does NOT mean: not "emphasise it harder in the prompt", and not that the agent was disobedient — skipping a review it had been told about is the ordinary outcome of a constraint that competes for attention. The same account draws the boundary of what code can gate: measurable defects, such as default capitalization, are caught by automated checks, while subjective calls, such as whether an idea is any good, stay with designer feedback captured as skill guidance.
