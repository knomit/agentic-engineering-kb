# Shape tools around workflows, not around your API's CRUD surface

Mechanically wrapping an existing API one endpoint per tool is the common failure. Anthropic's guidance: more tools do not lead to better outcomes. Rather than exposing `list_users`, `list_events`, and `create_event`, ship one `schedule_event` tool that performs the whole intent internally.

Two costs are being avoided. First, context — every tool definition is resident tokens, and the intermediate results of a three-call chain land in the window too. Second, selection accuracy — tools with overlapping surfaces are where the model picks wrong, and a CRUD decomposition maximises overlap by construction.

The test to apply: if completing one user intent reliably requires the model to chain three of your tools in a fixed order, that chain should have been one tool. Consolidation is not always right — it costs flexibility when the sub-steps genuinely recombine — but the default of one-tool-per-endpoint is a mapping of your implementation onto the model, not a design.
