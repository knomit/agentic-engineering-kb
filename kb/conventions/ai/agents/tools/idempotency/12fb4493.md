# Idempotency keys for agent tools must be caller-supplied, not derived from hashing the arguments

Amazon's Builders' Library rejects the obvious implementation and gives the reason. The tempting approach is to synthesise an idempotency token by hashing the request parameters, treating any identical request from the same caller as a duplicate. It does not work, because identical arguments do not imply duplicate intent — and the service cannot tell the difference.

Their worked contrast: two identical CreateTable calls arriving close together are almost certainly a retry of one request. Two identical RunInstances calls are not — the caller may genuinely want two identical EC2 instances. Same shape, opposite correct behaviour. No amount of inspecting the payload distinguishes them, because the distinguishing information is the caller's INTENT, which only the caller has.

Amazon's approach is therefore a unique caller-provided client request identifier in the API contract (in the EC2 API it is the `ClientToken` field). Two requests from the same caller bearing the same token are duplicates by definition; two bearing different tokens are two requests, however identical their parameters. Secondary benefits they name: the token appears in CloudTrail so intent is auditable, and resources labelled with the token let a caller identify which of its requests created which resource (visible in the DescribeInstances response).

This matters acutely for agent tools, where the parameter-hash approach is the intuitive one and the failure mode is silent. A model asked to file three similar tickets, send two reminders, or provision two identical workers will emit tool calls with identical arguments — legitimately. Deduplicating on an argument hash silently drops the second one, and the agent sees a success response, believes both happened, and reports completion. Conversely, without any token, the harness retrying after a timeout duplicates the effect. The tool schema needs an explicit idempotency-key parameter, and the HARNESS should populate it per intended call — generated once when the model emits the call and reused across every retry of that call. This is what the AWS SDK and CLI do: they know which operations are idempotent, generate a ClientToken when the caller omits one, and reuse it on retries, so 'at most once' holds without the caller writing any retry logic.

Do not let the model generate the key itself. A model asked for a unique id will often produce the same one across a retry AND across two genuinely distinct calls, which reintroduces exactly the ambiguity the token exists to remove.
