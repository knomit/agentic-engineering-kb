# MCP client registration: CIMD client IDs are portable across authorization servers, pre-registered and DCR credentials are not

Revision `2026-07-28` gives MCP clients three registration mechanisms and a stated priority order, with Dynamic Client Registration demoted to a compatibility fallback:

1. **Pre-registered** client information, if the client already has it for that server.
2. **Client ID Metadata Documents (CIMD)**, if the authorization server advertises `client_id_metadata_document_supported: true` in its OAuth Authorization Server metadata.
3. **DCR** (RFC 7591), if the AS advertises a `registration_endpoint`.
4. Prompt the user to enter client details.

CIMD makes the `client_id` an HTTPS URL resolving to a JSON metadata document the client hosts itself. The URL MUST use the `https` scheme and contain a path component; the document MUST carry at least `client_id`, `client_name` and `redirect_uris`; and the `client_id` inside it MUST match the document URL exactly. Authorization servers MUST re-validate that match, MUST validate the redirect URIs presented in an authorization request against the document, MUST validate the document is well-formed JSON with the required fields, and SHOULD cache it respecting HTTP cache headers.

**The property that should decide the choice is portability, and it is easy to miss.** A CIMD client ID is portable across authorization servers, because it is a self-hosted URL the AS resolves on demand — no re-registration when the AS changes. Pre-registered and persisted-DCR credentials are not portable, and the spec makes that a hard rule: clients holding either MUST associate them with the issuing authorization server keyed by its `issuer` identifier, MUST NOT reuse them with a different authorization server, and MUST re-register when protected-resource metadata points at a new one. On a mismatch, surface an error rather than silently attempting the old credentials. That means an AS migration is a silent-breakage event for every client except the CIMD ones.

**THE MULTI-AS CASE IS SIMULTANEOUS, NOT JUST SEQUENTIAL — AND THAT IS WHERE THE PORTABILITY PROPERTY EARNS ITS KEEP.** The 2026-07-28 Authorization Server Discovery page notes that a Protected Resource Metadata document "can define multiple authorization servers", and that when `authorization_servers` lists several, **each is an independent OAuth 2.0 authorization server**. Client identifiers are unique to the AS that issued them (RFC 6749 §2.2), so clients **MUST** maintain separate registration state — client credentials and tokens — per authorization server, and **MUST NOT** assume credentials valid for one will be accepted by another. Reading the binding rule above as only an *AS-migration* concern therefore understates it: one MCP server can put a client in front of two live authorization servers at once, and a client that caches "the" `client_id` per server rather than per issuer breaks the moment it switches between them.

**AND MCP STATES NO CRITERIA FOR CHOOSING BETWEEN THEM.** The spec puts the selection responsibility squarely on the MCP client and then delegates it outward: the specific use of `authorization_servers` is "beyond the scope of this specification", with implementers pointed at RFC 9728 §7.6. So an MCP client facing a two-entry `authorization_servers` list has a normative obligation to pick one and no MCP-level guidance on which — a decision that is security-relevant (it determines who issues your tokens) and that every client will therefore answer differently. Treat "we take the first entry" as the undocumented default it is, and see `36d792c3` for the separate obligation to verify that whichever AS you select actually owns the metadata document you fetched.

**Gotcha if you stay on DCR:** clients MUST specify `application_type`. Omitting it defaults to `"web"` under OIDC, which conflicts with native-style redirect URIs such as `http://127.0.0.1:3000/callback`. The failure is environment-dependent and therefore easy to miss in testing — non-OIDC authorization servers safely ignore the parameter, so a desktop or CLI client that omits it works everywhere until it meets an OIDC-compliant server and gets its registration rejected. Use `"native"` for desktop, mobile, CLI and localhost-hosted apps; `"web"` only for remote browser-based apps.

DCR's deprecation also shifts the confused-deputy surface already recorded in this pack: a static client ID shared across users is one of that attack's preconditions, and CIMD does not by itself remove it — the client ID is still static per client, it is merely self-published rather than server-issued.
