# A Desktop Extension's manifest is both the secrets boundary and the install gate — declared sensitive config goes to the OS keychain, a required value blocks activation, and only Node gets a host-provided runtime

Claude Desktop Extensions package a local MCP server together with its dependencies as a zip archive whose only required member is manifest.json. The file extension changed from .dxt to .mcpb (MCP Bundle) on 2025-09-11, with existing .dxt bundles stated to keep working, and the specification and toolchain are deliberately versioned 0.1. The specification, packaging tools, reference implementation and TypeScript schemas are published as open source.

Three manifest mechanics decide how a bundled server should be written.

CONFIGURATION IS DECLARED, NOT SHIPPED. A `user_config` entry marked `"sensitive": true` is held in the operating system's secret vault, and `${user_config.<key>}` is substituted into the server's `args` or `env` at launch; `${__dirname}` resolves to the extension's unpacked directory. The operational consequence is the reason to use it: a server that reads its API key from a config file inside its own bundle has put that key in a distributable zip, whereas declaring the key moves it to the keychain and out of the artifact.

A REQUIRED VALUE IS AN ACTIVATION GATE, NOT A DEFAULT. For a `user_config` entry with `"required": true`, the host "will not enable the extension until the user has supplied that value". Treat a required config key as a hard install-time dependency; there is no run-with-missing-value path to fall back on.

RUNTIME SUPPORT IS ASYMMETRIC. Node.js ships with Claude Desktop, so a Node extension needs no externally installed runtime; Python extensions are expected to vendor their packages into the bundle (the documented layout puts them in `lib/`). Platform-specific command and environment overrides live under `server.mcp_config.platforms.<win32|darwin>`.

DISTRIBUTION IS NOT PURELY DEVELOPER-CONTROLLED, which matters when planning to ship one. Enterprise administrators are given Group Policy (Windows) and MDM (macOS) controls that can pre-install approved extensions, blocklist specific extensions OR PUBLISHERS, disable the built-in extension directory entirely, and deploy private directories. A publisher-level blocklist means an organisation can exclude everything you ship, not just one bundle.

What this does NOT establish: the `tools` and `prompts` arrays in the manifest are author-written declarations shown to the user before install. The source describes them as helping "users understand capabilities upfront" and says nothing about whether the host enforces them against what the server exposes at runtime, so do not read the declaration as a capability restriction.
