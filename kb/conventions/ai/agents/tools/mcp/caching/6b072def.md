# MCP now requires cache metadata on list results, and asks servers to order tools deterministically to protect the LLM's prompt cache

Revision `2026-07-28` adds a cache contract to MCP's read paths, and one of the two parts is aimed at the LLM's prompt cache rather than at HTTP caching — which is the non-obvious half.

**Required cache metadata (SEP-2549).** `tools/list`, `prompts/list`, `resources/list`, `resources/read` and `resources/templates/list` now return a `CacheableResult` carrying two required fields:

- `ttlMs` — a freshness hint in milliseconds, letting clients cache the response instead of polling.
- `cacheScope` — `"public"` or `"private"`, controlling whether a **shared intermediary** may cache the response. Getting this wrong is a cross-tenant disclosure: a per-user resource listing marked `"public"` can be served by a gateway to a different user.

These complement, and do not replace, the existing `listChanged` notifications — `ttlMs` bounds staleness when you are not subscribed; `listChanged` tells you about a change you would otherwise wait out.

**Deterministic tool ordering.** Servers **SHOULD** return tools from `tools/list` in a deterministic order, and the spec's stated reason is twofold: client-side caching, and improving **LLM prompt cache hit rates**.

That second reason is the one worth internalising. Prompt caching keys on an exact token prefix, and tool definitions sit near the front of that prefix. A server that returns its tools in map-iteration order — genuinely nondeterministic in Go, Python before insertion-ordered dicts were relied upon, or anything backed by a set — reshuffles the prefix between calls and invalidates the cache on every request, for every client connected to it. The symptom is a cost and latency regression with no corresponding change in behaviour or accuracy, appearing on the *client's* bill, attributable to a *server* that looks entirely healthy. Nothing errors; the tools are all present and correct, merely in a different order.

This is now a spec-level SHOULD rather than folklore, so it is a legitimate thing to raise against an MCP server implementation.
