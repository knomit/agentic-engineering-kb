# "One Task, One Session": reset at the task boundary so an injected instruction cannot outlive the task that picked it up

OWASP's secure MCP server development guide lists session reset as a prompt-injection control in its own right, under the name "One Task, One Session": reset sessions when the agent changes task or context, so that hidden instructions do not persist.

What it buys and what it does not: it bounds the *lifetime* of an injection to a single task. It does nothing about an injection acting inside the task it arrived in, and it is not a substitute for the three controls the same guide lists beside it — preferring structured, schema-validated JSON tool calls over freeform model-generated commands; a human-in-the-loop pause requiring explicit confirmation for high-risk actions such as deleting data, sending money, or changing systems, with "MCP elicitations" named as the mechanism; and an LLM-as-a-Judge check running in a separate context session, evaluating high-risk calls against a policy prompt.

The design consequence worth planning for: this makes cross-task continuity a cost rather than a free convenience. Any memory, cache, or accumulated context carried across a task boundary for performance is also the carrier this control exists to cut, so it has to be re-derived or re-validated rather than inherited. Decide per artifact which side of the boundary it lives on.

Note the altitude, because it determines whether you can implement this at all: the guide places the control on the server, not the client. A server that keeps one long-lived session per connected user — which is what the simplest implementation does — has no task boundary to reset at. The boundary has to be made visible to the server before the control can exist.
