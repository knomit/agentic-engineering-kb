# An approved third-party MCP server is a lockfile problem, not a review problem — pin the version, re-validate on a schedule, and name who holds the kill-switch

OWASP's governance workflow for third-party MCP servers has five steps — Submission, Scanning, Review & Sign-off, Deployment & Monitoring, Periodic Re-validation — and five named roles: Submitter (Developer), Security Reviewer, Domain Owner, Approver, Operator (SRE). Two rules in it are load-bearing: "Security and domain owners must both sign off before a server is enabled", and the Operator role owns the kill-switch.

The reason to carry the shape rather than invent one is that the approval moment is not where the risk lives. A server that passes scanning and sign-off can change afterwards — that is the rug-pull mechanism, and in one documented case the change arrived on the fourth tool call of a server that had behaved normally until then. So the steps that do the work against a server which changes after approval are the last one (Periodic Re-validation) and the pairing of it with the connection-side rules the same document states: **Verify Origin Before Connecting**, **Use Registry-Only Discovery**, **Pin Versions**, **Staged Rollout**, and **Record Human Approvals**. Pinned versions plus scheduled re-validation turn a silent substitution into a diff; an unpinned server approved once is trusted indefinitely on the strength of a review of code it no longer runs.

Two roles exist because two different judgements are needed and neither subsumes the other: the Security Reviewer decides whether the server is safe to run, the Domain Owner whether this data and these actions belong in its hands. A single approver collapses them, and the one that gets dropped in practice is the second.

The transport rule that goes with this: STDIO for local servers, Streamable HTTP with "TLS/mTLS or OAuth 2.1" for remote ones, plus a WAF, rate limiters and regular credential rotation. On registration the document advises against the convenient path — "Dynamic Client Registration is not advised for most use cases" — and names three alternatives: Access Token, Software Statements, Signed Request Bodies.

WHAT THIS DOES NOT MEAN. A kill-switch owner is not an incident process. The document assigns the switch to the Operator and says nothing about what triggers it, who may pull it without consultation, or what happens to in-flight agent sessions when it is pulled — decide those yourself, because an unexercised switch with no stated trigger is a name on an org chart.
