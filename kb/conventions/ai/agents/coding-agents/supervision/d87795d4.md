# Execution drift and direction drift need different check cadences — conflating them is why supervision feels expensive

A useful split when supervising a running coding agent, because the two failure modes have different detection costs and different correct responses. Eugene Yan's framing, quoted: execution drift is 'is the model doing the task right? This is local and tactical, like ignoring an error, reporting a bad metric, or diverging from the spec.' Direction drift is 'is the model doing the right task? These are bigger picture and strategic, and occur when the model misinterprets the original intent.'

The cadence rule is explicit: 'Check for execution drift often and direction drift occasionally.'

EXECUTION DRIFT is the agent doing the right task badly — ignoring errors it should have investigated, optimising a metric that is not the one you care about, quietly working around a failing step. It is cheap to spot from the recent turns, and it accumulates fast, so check it FREQUENTLY.

DIRECTION DRIFT is the agent doing the wrong task well. It is invisible in the recent turns, because locally every step looks correct; you only see it by comparing current work against the original intent. So check it PERIODICALLY, and check it with FRESH CONTEXT — the recommended mechanic is 'a secondary session with fresh context to read the original spec and the recent turns of the primary session'. A reviewer inside the primary session has already absorbed the drift and will rate it as on-track.

BOUNDARY CAVEAT worth knowing, because it cuts against the obvious reading: the source files 'diverging from the spec' under EXECUTION drift, not direction drift. The distinction is not spec-vs-no-spec. It is whether the model has misunderstood the INTENT (direction) or is executing an understood task badly, including drifting off a spec it understood correctly (execution). If you draw the line at 'does it match the spec document' you will classify most direction drift as execution drift and check it on the wrong cadence.

This is the same clean-context principle that applies to reviewer agents generally, applied to the supervision loop rather than to code review.

The supporting practice: cheap deterministic checks run first and without model involvement — the concrete example is post-edit hooks running 'ruff format' and 'ruff check --fix' on files the model just updated, described as the lowest rung of the verification ladder. They cost no tokens and remove a whole class of execution drift before anyone looks at it. Reserve model and human attention for what a hook cannot decide.
