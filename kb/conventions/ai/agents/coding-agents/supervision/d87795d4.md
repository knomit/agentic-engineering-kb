# Execution drift and direction drift need different check cadences — conflating them is why supervision feels expensive

A useful split when supervising a running coding agent, because the two failure modes have different detection costs and different correct responses.

EXECUTION DRIFT is the agent doing the right task badly: ignoring errors it should have investigated, optimising a metric that is not the one you care about, quietly working around a failing step. It is cheap to spot from the recent turns, and it accumulates fast — so check it FREQUENTLY.

DIRECTION DRIFT is the agent doing the wrong task well. It is invisible in the recent turns, because locally every step looks correct; you only see it by comparing the current work against the original specification. So check it PERIODICALLY, and check it with FRESH CONTEXT — the recommended mechanic is a second session acting as a pair programmer, which reads the primary session's spec and its recent turns and reports whether they still describe the same task. A reviewer inside the primary session has already absorbed the drift and will rate it as on-track.

This is the same clean-context principle that applies to reviewer agents generally, applied to the supervision loop rather than to code review.

The supporting practice: cheap deterministic checks should run first and without model involvement — post-edit hooks running a formatter and a linter with autofix cost no tokens and remove a whole class of execution drift before anyone looks at it. Reserve model and human attention for what a hook cannot decide.
