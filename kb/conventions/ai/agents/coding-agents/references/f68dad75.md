# Specify a change with the most executable artifact you have, not a description of it — Anthropic's own rule is that a HTML mockup beats both a written description and a screenshot of the same design

Claude Code's context-engineering guidance treats the @-mentioned reference — a spec, a mockup, a rubric, code from another codebase, a test suite — as a first-class part of the context, and ranks the FORM of that reference, not just its presence. Its stated rule: "For example, a HTML mockup of a design will generally produce better results than a description of the design or a screenshot." Code-based references are described as generally higher fidelity than prose or image ones.

Note the ordering carries two separate comparisons, and the second is the surprising one. Beating a written description is expected. Beating a SCREENSHOT is not, on a vision-capable model: a picture is a lossy projection of the structure the agent has to reproduce, whereas the markup is the structure — nesting, naming, spacing and state are all recoverable from it and only inferable from pixels.

Operational consequence when you are preparing work for a coding agent: spend your effort converting the intent into something executable or structural rather than into a better paragraph. A rough HTML page, a failing test, a rubric a verifier agent can score against, or a pointer at an existing implementation to imitate are all stronger inputs than a careful description of any of them — and the same artifact then doubles as the check the agent can run, which is the other half of getting it to stop at the right place (see [[519ec939]]).

WHAT THIS DOES NOT MEAN. It is not a claim that screenshots are useless, and it is not a measurement: the source says a HTML mockup will "generally" produce better results, with no benchmark attached. It also does not mean the reference should be polished — a throwaway mockup qualifies. The claim is about which representation of the intent you hand over, not about how much work goes into it.
