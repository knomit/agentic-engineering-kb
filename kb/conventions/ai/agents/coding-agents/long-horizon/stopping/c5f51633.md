# On long autonomous runs the model stops to REPORT rather than to ask, in three recognizable forms — the remedy is a standing rule that distinguishes blocked from unblocked, with the stop before destructive actions deliberately kept

A long autonomous run can halt without being blocked, and the vendor names three forms it takes: a summary that states the next step without taking it, an offer to continue, and a list of choices none of which actually block the work. All three read like a request for input and none of them is one. Recognising the signature matters because the natural operator response — replying "continue" — works but converts an autonomous run into a supervised one, turn by turn.

THE REMEDY IS A STANDING RULE WITH BOTH HALVES NAMED. The guidance is to put in CLAUDE.md, or the equivalent standing-instruction file, a rule in two parts: keep going when a step does not need the operator's input, putting status notes in the same message as the next action; and stop only when the work genuinely cannot continue without the operator, OR before anything destructive. The source names the destructive set explicitly — deleting data, force-pushing, and changing anything outside the repository — and keeps permission prompts on for destructive commands.

BOTH HALVES OR NEITHER. This is the compound condition that must not be compressed. A rule that says only "keep going" buys autonomy by removing the stop that matters; a rule that says only "stop and ask" reproduces the problem. The stop being removed is the one before a status report, and the stop being kept is the one before an irreversible action — "let it run unattended" is the false slogan this rule has to survive.

AND THE PAIR-PROGRAMMING SETTING IS THE OPPOSITE, not a weaker version of the same thing. Where the operator is present and reading, the guidance is to ask instead for a one-line plan before starting and a short recap at the end. The amount of reporting is set by whether anyone is watching, so the standing rule belongs to the mode of work rather than to the project.

TWO SUPPORTING SPECIFICS. Specify the summary format rather than parsing whatever arrives — the example given is three fixed headings for what is blocked on the operator, what changed, and what was found. And on long runs keep the task checklist in a file and update it as the work proceeds, reading the FILE rather than the scrollback, because the conversation gets summarised as context fills and a checklist held only in the transcript does not survive that.

SCOPE. Vendor guidance for its own model and coding harness at launch, from reported testing rather than measurement; the three stopping forms are the vendor's own characterisation of the behaviour, with no frequency attached.
