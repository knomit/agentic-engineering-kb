# Give a coding agent a check it can run, or you become the verification loop

An agent stops when the work looks done. Absent a check it can execute itself, "looks done" is the only available signal and every mistake waits for a human to notice it. The source states the rule as a single instruction — "Give Claude something it can run that comes back pass or fail" — and names a test file, a build's exit code, a linter and a browser screenshot as the forms. Supplying something that returns pass/fail — a test suite, a build exit code, a linter, a script diffing against a fixture, a screenshot compared to a design — closes the loop: the agent works, runs the check, reads the result, iterates.

This is the difference between a session you must watch and one you can walk away from, and it is why the concrete-verification version of a prompt beats the vague one: "write validateEmail; example cases: user@example.com true, invalid false, user@.com false; run the tests after implementing" versus "implement email validation".

Escalating strength of gate, trading setup effort for attention:
1. Ask for the check and iteration in the same prompt — works today, on any task.
2. A session-level goal condition, which "sets a condition that a separate model checks against the conversation after every turn".
3. A deterministic stop hook, where "the turn doesn't end until the typecheck passes or the block limit is reached".
4. A reviewer with no shared history — "/code-review reviews the diff in a fresh subagent that never saw your conversation" — so the agent that did the work is not the one grading it.

THE BLOCK LIMIT IS A GATE WITH TWO CONDITIONS, AND BOTH MATTER. The cap fires only on an unbroken run of blocks: "If the hook blocks eight stops in a row" "with no tool call between them, Claude Code overrides the next block and ends the turn." A single tool call between blocks resets the count, so an agent that keeps attempting a fix is not approaching the cap — which is what makes the hook a usable gate rather than an infinite loop, and also means the cap is NOT a bound on how long a stubborn hook can hold a turn. The cap itself is configurable: "To raise the cap, set CLAUDE_CODE_STOP_HOOK_BLOCK_CAP". Treat eight as the default rather than as the limit.

Also require evidence rather than assertion: "Whichever option you use, ask Claude for evidence: the command it ran and its output, or the screenshot." Reviewing evidence is faster than re-running the verification yourself, and it is the only thing that works for a session you were not watching.
