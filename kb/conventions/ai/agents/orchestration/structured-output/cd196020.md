# Prove a structured-output schema is satisfiable before spawning the agent that must satisfy it, and cap the retry loop — an unsatisfiable schema otherwise burns a full agent run per attempt

An agent asked to return JSON against a schema can be set an impossible task by the schema itself, and the cheapest place to catch that is before the agent starts.

Claude Code's dynamic workflows do exactly this on an `agent()` call carrying a `schema`: "Claude Code checks the schema before starting the subagent: when it can prove the schema contradicts itself, the call fails with an error naming the contradiction, and the subagent never starts. One contradiction it can prove is a `required` key that `additionalProperties: false` rules out."

Two design choices in that sentence are the transferable part. The check is a satisfiability proof, not a lint: it fires only when the contradiction is provable, so it never rejects a schema that is merely awkward. And the error names the contradiction rather than reporting a generic validation failure, which is what makes it actionable — the author learns which pair of constraints collide.

The second half is the bounded retry. "If the subagent's output still fails validation after five attempts, the call fails with an error that includes the last validation failure. To change the attempt count, set `MAX_STRUCTURED_OUTPUT_RETRIES`." Carrying the last validation failure into the terminal error matters because the alternative — a bare "failed after 5 attempts" — tells the author nothing about which field never came out right.

The operational consequence: in any fan-out where many agents share one output schema, a schema defect multiplies by the number of agents and by the retry count before anything surfaces. A pre-start satisfiability check converts that from N times five wasted agent runs into one immediate error, and the retry cap converts an unsatisfiable-in-practice schema from an unbounded loop into a bounded, diagnosable failure.
