# In a monorepo, a saved workflow is written to the nearest existing config directory but loaded from every one on the path, with the nearest definition winning and the project copy beating the personal one

A per-repository config directory in a monorepo has to answer two different questions — where does a new file go, and which of several same-named files runs — and Claude Code's workflow directories answer them differently, which is the shape worth copying.

Write resolution picks one directory, and picks an existing one: "Saving to the project location writes to the closest `.claude/workflows/` directory that already exists between your working directory and the repository root, or to the repository root if none exists yet." So saving does not create a new config directory next to wherever you happen to be standing; it attaches the file to the nearest directory someone already established, and falls back to the repository root. That keeps a monorepo from accumulating a `.claude/` in every package as a side effect of people saving things.

Read resolution is the union, with a precedence rule: "Project workflows also load from every `.claude/workflows/` along that path, and when more than one defines the same name Claude Code runs the one closest to the working directory." A package can therefore override a repository-wide workflow of the same name simply by defining it, and the override is scoped to work done inside that package.

Across the two locations rather than within one: "If a project workflow and a personal workflow share a name, the project one runs." The shared, committed definition wins over the individual's private one, so a teammate's personal file cannot shadow what the repository specifies.

The operational consequences: a name clash is resolved silently by distance, so two packages defining the same workflow name is a supported arrangement rather than an error — and debugging "the wrong version ran" means asking which directory you were standing in, not which file you edited last. Note also that saving and loading are asymmetric: a file loaded from a directory further up the path is not where your next save will land.
