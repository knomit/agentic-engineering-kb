# Record an agent's side effect only on the destination's own confirmation, and give the ambiguous case a third state instead of guessing

The run record moves through three states, not two: `posting` before the send, then `posted` with the message ID on success, or `maybe posted` when the result is unclear. "the post counts as sent only if Slack returns `"ok": true` and a message ts", and the ledger and the bookmarks are updated only after that confirmation. "If the result is unclear, it marks the run "maybe posted" and changes nothing else."

The third state exists because the two ways of collapsing it are both lossy, in opposite directions: recording a post that never landed drops those items permanently (the bookmark moved past them), while re-posting whenever unsure duplicates the output for readers. Neither is recoverable by the next run on its own.

What makes the retry safe is a separate dedupe read before sending: check whether this run's dated title is already among recent messages at the destination. Confirmation decides whether to record; the dedupe check decides whether to send.

Operational consequence: for any agent side effect, write the intent before acting, record completion only from the destination's own acknowledgement, and make the pre-send check idempotent on a key the destination carries — not on local state, which is exactly what you cannot trust after an ambiguous call.
