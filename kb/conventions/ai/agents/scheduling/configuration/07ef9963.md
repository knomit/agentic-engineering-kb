# Keep an unattended agent's rules in a store it cannot write, re-read them fresh every run, and stop rather than fall back to defaults when the read fails

The reference design splits memory in two by write permission, not by content type. The read-only side: "**preferences** (yours, read-only to the agent): which channels and repos to read, what to leave out, the length cap, the destination, and when to stop." The read-write side: "**state** (the agent's, read-write): the bookmarks, a ledger of what it reported, one record per run, changes it proposes to your preferences, and notes on how each source behaves."

Three rules hang off that split:
- "Have the agent read the file fresh every run." A copy baked into the system prompt keeps applying rules the file no longer contains, and the symptom is a retired topic reappearing rather than an error.
- "If it can't read the file, it should stop and say so instead of running on defaults." A default-configured unattended run is a different agent doing a similar-looking job.
- Changes the agent wants made to its own rules live in `state`, as "changes it proposes to your preferences" — on the side it may write, not the side that bounds it. So it can accumulate proposals across runs without being able to enact one. Pack analysis: that only becomes a learning loop if someone moves a proposal into the preferences file, and the source does not describe who does that or when.

A fourth, operational: creating the store does not seed its contents. "`ant apply deployment.md` creates the preferences store, but not the file in it. Before the first run, write your preferences.md there with the repo's `scripts/seed-preferences.sh`." If the file does not exist before the first run, the first run is the default-configured one.

Operational consequence: the write boundary is the enforcement. A prompt instruction not to change its own rules is not the same control, because the text that reaches an unattended agent includes other people's messages.
