# An unattended run cannot approve a tool call, so pre-authorisation is forced — pay for it with a read-only credential, not with a prompt rule

MCP tools ask for approval by default and nobody is present on a schedule, so the toolset has to be pre-authorised — "the GitHub toolset is set to `always_allow`" — which widens the trust surface by construction. The design pays for that with capability limits rather than instructions: the GitHub token is read-only, the preferences store is read-only to the agent, secrets stay outside the sandbox (the shell sees a placeholder such as `$SLACK_BOT_TOKEN` and the platform substitutes the real token for allowed hosts), and the environment reaches only allowlisted hosts.

What that buys and what it does not, stated precisely: a planted instruction arriving in someone else's message can still distort the agent's output text, and can persist through notes the agent writes into its own state store; it cannot write to GitHub and cannot edit the rules. The residual is a corrupted report, not a corrupted system.

The named exception is the destination credential: one Slack token both reads and posts, so least privilege there is channel scope — invite the bot only where it is needed — not token scope.

Operational consequence: for every tool an unattended agent is pre-authorised to call, ask what the worst write is, and if the answer is anything, split the credential. "Instruct the agent not to" is not a control on an input channel other people can write to.
