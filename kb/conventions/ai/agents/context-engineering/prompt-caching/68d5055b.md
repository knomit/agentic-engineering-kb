# Narrowing an agent's tool set by deleting definitions destroys the cached prefix — mask callability instead, and append instructions rather than editing them

Prompt caching keys on an exact token prefix, and a persistent agent's tool definitions and standing instructions sit at the front of it. The three edits a long-running agent most naturally wants to make mid-session — drop the tools it no longer needs, reorder them, rewrite the system prompt to add a correction — each rewrite that prefix and re-bill every token after the edit point at full price. Nothing errors and no behaviour changes; the only symptom is cost and latency, which is why this is usually found in a bill rather than in a trace.

OpenAI's GPT-6 caching guidance names the cache-preserving substitute for each move, and the substitutes are the operational content:

- **To narrow what the agent may call, keep every tool definition, schema and ordering in place and restrict callability instead.** Use `allowed_tools` to make only the relevant subset callable, or `tool_choice: "none"` when no tool should fire this turn. Removing the definition is what breaks reuse; leaving it present but uncallable does not.
- **To change instructions, append a NEW developer message at the end of the context** that overrides the older one, rather than editing the earlier instruction in place.
- **Reasoning effort is adjustable without breaking cache** on GPT-6 models: append a `configuration_update` and leave request-level reasoning effort unchanged. Raising effort for a hard step and lowering it for a routine follow-up no longer costs the prefix.
- **Eligible shared prefixes are reused within a 30-minute window**, with discounts stated as up to 90% on cached input tokens.
- **A miss is diagnosable, not mysterious.** The API returns `prompt_cache_diagnostics` carrying a `reason` (for example `"tools_changed"`) plus `comparison_reusable_tokens` and `cache_missed_tokens`, so the cause and the size of the loss are both readable from the response.

Two further controls in the same guidance change where the prefix boundary sits rather than how to avoid moving it:

- **Explicit cache breakpoints** let you choose which prompt prefixes are reused, which turns prefix layout into a design decision: put stable context above a breakpoint and frequently changing content at the end. One operator reports this is what made it economically viable to FORK a conversation for background tasks while reusing nearly all of the shared context — so breakpoints are what makes a branch-per-subtask architecture affordable, not merely a cost tweak on a linear conversation.
- **Prewarming** prepares known context before a request arrives — shared instructions, tool definitions or reference material at application startup, before the user's first question — moving that processing out of the user's wait time. It reduces latency; it is not an additional discount.

**What this does not mean.** It is not an argument for loading every tool definition upfront. Deferring definitions so they never enter the prefix is a different move from deleting definitions already in it: the first leaves the prefix stable, the second rewrites it. The rule is about mutating a prefix, not about its size — the volume question is decided separately, on the deferral break-even.

**Scope.** The named mechanisms (`allowed_tools`, `configuration_update`, the 30-minute window, the 90% figure) are OpenAI GPT-6 API specifics and do not transfer verbatim to other vendors; the prefix-mutation principle does, and its server-side counterpart is deterministic tool ordering. The hit-rate and cost figures in the source are the vendor's and its customers' own reported numbers, not independent measurement — one customer reports a few percentage points of hit rate translating to roughly 20% lower cost, which is a plausible nonlinearity but a single testimonial. A second customer figure is easier to misread: a reported reduction of more than 50% in the share of prompt tokens requiring fresh processing is a RELATIVE improvement against that customer's own previous baseline, across billions of requests — it is not a cache hit rate and it is not a 50% cost reduction.
