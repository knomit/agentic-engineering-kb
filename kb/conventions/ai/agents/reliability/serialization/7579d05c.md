# Version the serializer independently of the build and store that version with the data — and a serializer that preserves unknown attributes removes the need for a two-phase deployment

Four practices Amazon states for data that crosses a version boundary, in descending order of how much coordination each one saves you:

- **Design serializers to tolerate and PRESERVE unknown attributes.** Where a serializer retains attributes it does not understand when writing the data back, a host on the new version can add fields without a host on the old version wiping them out on its next update — and then "a two-phase deployment isn't necessary". This is the one practice that removes a deployment phase rather than making it safer.
- **Assign each serializer change a distinct version, independent of source-code or build versioning, and store that version with the serialized data or in its metadata.** Older serializer versions keep working in the new software. Emitting a metric for the version of data written and read gives operators the signal they need when something does fail. The same applies to RPC and API versions.
- **Avoid custom serialization formats.** The first iteration looks trivial and may be faster; the later iterations hit problems that JSON, Protocol Buffers, Cap'n Proto and FlatBuffers have already solved, including escaping, backwards compatibility, and distinguishing a field that was explicitly set from one that took a default.
- **Do not serialize data structures you do not control.** Reflecting over a standard-library collection means a runtime upgrade can change the underlying implementation and break deserialization; the same risk applies to classes from libraries shared across teams.

The source hedges these itself: the guidelines are not applicable to all applications and scenarios.

Pack analysis, not stated by the source: the attribute-preservation rule is the one to reach for first when the serialized thing is agent state — a memory file, a checkpoint, a task record, a run ledger — because those are written by whatever version happens to be running and read by whatever version runs next, with no deployment coordinating them.
