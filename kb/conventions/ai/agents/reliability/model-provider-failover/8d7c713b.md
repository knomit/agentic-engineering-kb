# Most error classes must never trigger a model-provider failover — the switch is only for transient faults, and for throttling only when waiting would breach the deadline

"Provider failover means retrying a request through another approved provider when the primary cannot serve it" — so it is a retry, and the question is which errors are retryable through a DIFFERENT provider. OpenAI publishes the classification, and most classes are on the do-not-switch side.

Switch: transient failures, connection resets and timeouts.

Switch only conditionally: sustained throttling or slow responses, and only if waiting would breach the deadline. Distinguish temporary throttling from a quota or billing problem first, because they look alike at the HTTP layer and only one is transient.

Do not switch, ever: malformed requests, 401/403 errors, safety refusals, and exhausted quota, credits or spend limits — "Do not automatically switch routes" for these. And "Unclassified errors should not trigger failover." An error you have not classified defaults to no switch, not to a switch.

Try a cheaper remedy first: for a model-specific capacity problem, "Try another approved model" that meets the quality, feature and latency requirements before moving provider at all.

Two structural rules the classification depends on. Retries must be controlled in one place — "One layer should control retries across the application, SDK, and gateway so they do not multiply" — under a shared retry budget, with valid `Retry-After` respected and otherwise bounded exponential backoff with jitter. And both a request deadline and a workflow deadline must be enforced, with a retry attempted only if it can finish inside both.

The foreseeable misreading: this is NOT "classify the HTTP status and act". The source says to build provider-specific error mappings from error DETAILS rather than from status alone, because the same status means different things across providers. A 429 that is temporary throttling on one provider and an exhausted spend limit on another lands in two different branches of this classification.

A second trap: "Quota alone does not guarantee completion before the deadline." A provider-wide quota dashboard can show headroom while a specific model, project or region is throttling, so capacity has to be tracked per model, per account or project, and per region.
