# Scale the inbound throttle inversely to backlog depth — but only works if the backlog you can measure is the one you are throttling

Amazon's backpressure implementation is deliberately unclever: periodically measure the queue depth for a workload and scale that workload's inbound admission limit inversely proportional to it. As the backlog grows, the producer side starts rejecting that workload's new work more aggressively. The justification is that a day-long backlog is trivially easy to accumulate, and even when it is perfectly isolated from other tenants it is expensive and slow to churn through — so refusing the work up front beats accepting work you will complete far too late to matter.

The precondition that decides whether you can do this at all: the workload must be on its own queue, or on a queue whose depth you can attribute. Amazon flags the concrete blocker — SQS exposes an API for the number of messages in a queue but NOT for the number of messages carrying a particular attribute. On a queue shared by several workloads you can still read total depth, but throttling on it applies backpressure to innocent workloads that merely share the queue. (They note Amazon MQ offers finer-grained backlog visibility.) So the ability to apply backpressure fairly is a consequence of your queue topology, decided earlier — not a feature you can add later.

And the counter-case, which Amazon states rather than hiding: backpressure is not right everywhere. Their amazon.com order processing deliberately keeps ACCEPTING orders while a backlog builds, rather than refusing new ones — backed by heavy prioritisation behind the scenes so the most urgent are handled first. The condition that separates the two: if a rejected request is simply lost business or a lost intent, prefer to accept and prioritise; if a rejected request will be retried by its caller anyway, prefer backpressure, because accepting it only converts one queued item into several.
