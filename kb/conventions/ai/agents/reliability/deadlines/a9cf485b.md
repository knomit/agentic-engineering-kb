# Propagate a remaining-time deadline through every hop of an agent call chain so the last hop can refuse work nobody is waiting for

Amazon's practice: clients attach a timeout hint to each request, and in multi-hop service architectures the REMAINING time is propagated transitively at every hop, so a service at the end of the chain knows how long it has for its answer to still be useful. A server that has spent half a request's budget and can see the client's deadline has passed abandons it immediately rather than finishing and replying into the void — from the server's side that late reply counts as a success, while the client recorded an error, which is also how success-rate metrics on the two sides drift apart.

This maps directly onto agent call chains: user → orchestrator → subagent → tool server → downstream API. Without deadline propagation the tool server has no way to know the orchestrator already gave up, so under load the deepest, most expensive layer is the one doing the most wasted work.

Implementation constraints Amazon names, both of which bite: (1) an ABSOLUTE deadline requires servers to agree on the current time, which distributed systems are notoriously bad at without a real time-sync service; (2) a DURATION avoids consensus but requires a monotonic clock (one that does not jump backwards on NTP sync) and, harder, requires knowing when to start the stopwatch — under heavy overload requests can sit in TCP buffers so long that the client has already timed out before the server ever reads them. Amazon's verdict is that enforcing client deadlines server-side is still better than the alternative despite this, because the alternative is unbounded piles of doomed work.

Check the deadline at dequeue points, not just at entry.
