# Don't predict model throttling from your own token accounting — react to 429/500/503 and honour Retry-After, because LLM endpoints have no free health check

Microsoft's guidance for routing across multiple model backends makes two connected points that invert normal load-balancer design.

FIRST, DO NOT PREDICT. Tracking prior consumption to forecast when a deployment will start throttling "is possible in the gateway, but this approach is fraught with edge cases. In most cases, it's best not to try to predict throttling events, but to use HTTP response codes to drive future routing decisions." The edge cases are structural: token accounting is approximate before the response exists, capacity is shared with consumers you cannot see, and the provider's own accounting is the only authority. Build the router reactive.

SECOND, THERE IS NO HEALTH ENDPOINT, AND PROBING COSTS REAL MONEY. "Many AI services don't provide a dedicated health check endpoint to preemptively determine whether instances are available... You can send synthetic transactions through, but doing so consumes model capacity." This is the specific way LLM backends differ from ordinary services, where a cheap health endpoint is assumed and active probing is close to free. Microsoft's recommendation follows: assume the backend is available, and treat 429, 500 and 503 as the signal to circuit-break that instance or model for a period.

For 429 specifically, honour the `Retry-After` value from the response rather than choosing your own backoff — that is the provider telling you when capacity returns, and "don't continuously hit an endpoint that returns 429 Too Many Requests." The gateway should retry the failed request against another backend in the pool before returning an error to the client, and its own health check should report unhealthy when no backend remains.

Note where this sits against the general health-check advice already in this pack: the four-tier health-check taxonomy assumes you can cheaply ask a dependency how it is. For model endpoints you cannot, so the observed request stream is your only health signal — which means a low-traffic route has no health information at all until it fails a real user's request.
