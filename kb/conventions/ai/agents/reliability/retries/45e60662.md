# Alarm on retry RATE, because retries silently turn into a fallback mode nobody tested

A specific operational practice from Amazon's Builders' Library, and the reasoning behind it is the non-obvious part.

Retries are insurance against transient, uncorrelated problems — spurious packet loss, a single machine failing. That is what they are designed and sized for. The hazard is that a service can run for months without needing many retries, and then the retry path activates in bulk during a scenario nobody has tested. At that point retries have stopped being insurance and become a fallback mode: a rarely-exercised code path carrying real load at the worst possible moment, with all the latent-bug and load-amplification risks that implies.

Amazon's countermeasure is to maintain metrics on OVERALL RETRY RATE and alarm when retries become frequent. Note what is being monitored: not the error rate, and not the success rate after retries. A system retrying heavily can look perfectly healthy on end-to-end success metrics while sitting one step from collapse — the retries are absorbing the failures and hiding them, right up until the amplified load tips the dependency over. Retry rate is the leading indicator that success rate conceals.

The alternative they offer for making the redundant path continuously exercised is PROACTIVE RETRY, also called hedging or parallel requests: always issue the redundant request rather than issuing it only on failure. Systems doing quorum reads and writes get this for free — requiring two of three responses means the third request is always in flight. The property that makes this work is the CONSTANT WORK pattern: because the redundant requests are issued unconditionally, load does not increase at the moment the redundancy becomes necessary. A conditional retry does the opposite, adding load exactly when the system is least able to absorb it.

For agent systems both halves apply directly. Retry rate on model API calls and on tool invocations belongs on the dashboard next to latency and cost, because an agent harness that retries transparently will show a healthy task-completion rate while quietly multiplying load against a provider that is already rate-limiting it — and provider rate limits are correlated across your whole fleet, so this escalates rather than settles. Hedging is worth considering for latency-critical single model calls where the extra spend is acceptable; it is a poor fit for anything with side effects unless the call is idempotent.
