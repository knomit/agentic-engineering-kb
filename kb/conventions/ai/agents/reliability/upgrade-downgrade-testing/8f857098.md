# A test environment with one host per service cannot detect a rollback bug, because it makes every deployment atomic — version coexistence is the thing under test

Two first-hand failures, both of which let a rollback bug reach production after a green test run, and both of which are properties of the test HARNESS rather than of the tests:

- services in the test environment ran one server each, so every deployment there was atomic and two versions of the software could never run at the same time;
- the test environment had several servers but deployed to all of them at once, to make testing faster, which removed the coexistence window just as effectively.

The corrections: multiple servers across different Availability Zones behind each service, as in production, and the same deployment configuration in test as in production. Where microservices coordinate, the same deployment ORDER across them in test and production.

The test itself — what the source calls upgrade-downgrade testing — has three stages against simulated production traffic that exercises every API continuously, each stage lasting long enough for all APIs, backend workflows and batch jobs to run at least once: deploy to about half the fleet so the versions coexist; complete the deployment; then roll back until every host runs the old version. No errors or unexpected behaviour across all three is the pass condition.

Operational consequence: a rollback test's validity depends on a property of the environment that nothing in the test output reports. Before trusting a green upgrade-downgrade run, check that the environment could have exhibited the failure — more than one host per service, and a partial rollout.

The stated reason to test rather than reason: explicit rollback testing "eliminates the need to rely on manual analysis, which can be error-prone".
