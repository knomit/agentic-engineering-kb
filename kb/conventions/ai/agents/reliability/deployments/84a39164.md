# Two-phase deploy makes each phase rollback-safe but never the pair — so verify every host finished Prepare, let a bake period of days pass, and backfill before removing the old read path

The technique: split a protocol change into Prepare, where every host learns to READ the new form while continuing to write the old one, and Activate, where hosts start WRITING the new form. Each phase is individually rollback-safe — rolling back Prepare is harmless because nothing is written in the new form yet, and rolling back Activate is harmless because the Prepare-era code can read both.

Three precautions carry the actual risk, and all three are easy to drop:

1. **Prepare must reach every host, not a healthy quorum.** Deployment tools will call a rollout successful once a minimum number of hosts report healthy (AWS CodeDeploy's `minimumHealthyHosts`). A host that missed Prepare fails to read data during and after Activate. The source describes explicitly verifying success on every single server at the end of each phase, and coordinating phase order across microservices when several are involved.
2. **The two phases cannot both be rolled back.** After Activate, the pre-Prepare version cannot read what is now being written. The mitigation is time: a bake period between the phases, "usually a few days", spent making sure no rollback to the earlier version will be needed.
3. **The old read path outlives the old write path.** Removing the ability to read the old form is safe only after every existing object has been rewritten in the new one — backfilling, which may need its own tooling running concurrently with live reads and writes.

This does NOT mean two-phase deployment makes a change reversible. It makes each step reversible one at a time, and converts the irreversibility into a window you choose the length of.

For serialization changes specifically there is an ordering rule worth keeping: readers go before writers when rolling forward, writers before readers when rolling backward.
