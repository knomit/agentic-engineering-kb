# An agent-improvement loop hands code a document, not a patch — traces and eval results become ranked harness recommendations that a developer approves as a diff, and the output contract is checked by a script the agent must run

OpenAI's agent-improvement-loop cookbook wires traces, human and model feedback and eval results into harness changes, and the design decision worth copying is what crosses the boundary into code: a document. The loop writes `codex_handoff.md` carrying the diagnosis, ranked recommendations, supporting evidence and implementation guidance, and a coding agent implements from that. The degree of automation is left to the developer, and the named default is the reviewed form: "A common starting point is a reviewed loop, where the system proposes the change set and a developer approves the diff before merge." So the approval binds to a diff, while the analysis stays a proposal — the loop never has commit authority of its own.

Three supporting decisions make that handoff legible.

The harness is an explicit versioned object, not ambient settings: dataclasses `ModelSettings` and `AgentConfig`, with the run's configuration named (`v001`). A recommendation can then be attributed to a config rather than to drift, and the loop's own rules protect that attribution — "Do not modify the runtime config during the run." and "Do not modify dataroom inputs."

The output contract is enforced by scripts the agent is required to run, not by a judge: `check_evidence_coverage.py` and `validate_output_contract.py`, which write `evidence_coverage.json` and `output_contract_validation.json` as their own artifacts. Each run must produce six named files, and one of the failure modes the cookbook calls out is exactly the one a final-answer grader would pass — a polished answer with incomplete citations, risk files or evidence artifacts. A deterministic validator catches that; a reader scoring the prose does not. The agent also works under a filesystem contract (read only `data/`, write only `outputs/`) and a stated honesty rule, "Never fabricate missing numbers."

Traces are exported locally rather than relied on as a hosted service: the notebook installs a local JSONL trace processor via `set_trace_processors` because hosted trace ingestion "may be unavailable in some environments". If the loop's input is traces, the trace path is a dependency of the loop and not of the product.

The sample size is small and stated as such: the default is five traced runs, and the cookbook says to "budget about 20 minutes for a full run". Five traces is enough to rank candidate harness changes for a human to read; it is not a pass-rate measurement, and treating a ranked recommendation from five traces as an A/B result is the foreseeable misreading. See [[0d7dd3d1]] on why the ranking has to be produced inside the product harness at all.
