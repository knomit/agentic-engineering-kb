# Grade traces before you build datasets, and design online evaluators reference-free from the start

Two mechanics from vendor eval docs that change the order you build things in.

Start with trace grading, not datasets. A trace is the end-to-end record of one run — model calls, tool calls, guardrails, handoffs. Grading traces answers the questions that actually block an early agent (did it pick the right tool, did the handoff fire, did it comply with policy) and it needs no reference outputs and no curated dataset, so you get signal on day one. Datasets and repeatable eval runs come after you know what you are asserting on; building them first means curating examples against criteria you have not discovered yet.

The constraint that bites later: reference-based evaluators only work offline. Offline evaluation runs against a dataset with known ground truth — benchmarking, regression, backtesting. Online evaluation runs against live production traces, where by definition there is no reference output, so ONLY reference-free evaluators work there. This means your carefully built offline suite does not port to production monitoring. If you want online quality signal, you have to design reference-free evaluators (safety checks, structural validity, self-consistency, policy adherence) deliberately and early, rather than discovering at launch that every grader you own needs an answer key you will never have.

On getting started at all: LangSmith's stated floor is 5–10 human-labelled examples as ground truth — small enough that "we do not have an eval set yet" is not a real reason to have no evals. Evaluator families to reach for, in rough order of cost: code/heuristic (deterministic rule-based checks), LLM-as-judge (reference-free or reference-based), pairwise comparison between two versions, and human review via annotation queues.

WHAT SIZES AN ONLINE SUITE IS ITS COST PER TRACE, NOT ITS DESIGN. Because an online evaluator's bill scales with traffic rather than with a fixed dataset, a reference-free suite that is affordable in principle still has to be sized deliberately. The levers, from the same vendor's later write-up: sample a percentage of traffic rather than scoring everything; filter to a subset worth scoring, such as traces carrying negative user feedback; prefer code checks, which cost almost nothing; or use a cheaper judge. And the loop closes the other way — anything an online evaluator flags becomes an offline dataset example, so production failures accumulate into the regression suite instead of being handled once each.

The judge-price datapoint, as reported: "Jev from TypeSafe AI matched human labels on every pass/fail decision and cost $0.34 in total," "compared with $28.17 for Claude Sonnet 4.6."

Scope, which those figures need: one experiment, written up by the tooling vendor, on one pass/fail labelling task, against named model versions. The ratio is not a general property of judge models and will not outlive either version. What transfers is the SPREAD — the price of a binary label can differ by roughly two orders of magnitude between judges that agreed on the label — which makes judge selection a cost decision on high-volume online eval, not only an accuracy one. It does NOT establish that a small judge matches a frontier judge in general. It establishes that on one task it did, and therefore that this is worth measuring before paying the difference.

One portability test stated plainly, which is the operational form of the reference-free constraint above: an existing offline evaluator can be reused online if and only if it does not need a reference output.
