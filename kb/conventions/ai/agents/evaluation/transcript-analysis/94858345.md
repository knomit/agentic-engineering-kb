# Transcript analysis has a published seven-stage method, and its two load-bearing choices are scanning per MESSAGE rather than per transcript, and validating each scanner against ground truth before believing its rate

The UK AI Security Institute, with Meridian Labs, publishes both a tool (Inspect Scout, open-source, built on Inspect) and a seven-stage method for turning agent evaluation transcripts into structured data: (1) define the purpose of the analysis, as either a primary question ("can this agent solve this challenge?") or a secondary one ("can I trust the results of this evaluation?"); (2) collate the transcripts into a structured database, filtering or pre-processing — removing personal data, imputing missing values — at this stage; (3) manually inspect at least a few samples to learn the transcript structure and format, choosing samples by a filter such as transcript length or pass/fail; (4) refine the research question until it names a CONCRETE SIGNAL locatable inside a transcript, because that is what becomes a scanner; (5) design the scanner, which includes choosing the level to analyse at — user messages, reasoning traces, or tool calls; (6) validate the scanner's first run against a ground truth on a subset of its results; (7) use the results, either as immediately actionable flags or as structured data for downstream analysis.

The unit of work is the **scanner**: a function taking a specific input from a transcript and returning a legible result. Pre-configured families include refusal scanners (a model declining in compliance with its safety specification rather than failing from incapability), evaluation-awareness scanners (evidence the model knows it is being evaluated, which may lead it to sandbag), and command-error scanners (the model calling tools that are unavailable — a signal to make the flagged tool available and re-elicit).

TWO CHOICES INSIDE THIS METHOD ARE NOT OBVIOUS AND ARE WHERE ITS RELIABILITY COMES FROM.

GRANULARITY. AISI's own case study scanned whole transcripts first and changed: "We initially scanned transcripts in their entirety but found message-level scanning produced more reliable results." Its implementation passes a system prompt plus ONE Assistant message to a judge model, for each Assistant message in the transcript. So the default granularity for an LLM-driven scanner is the message, not the transcript — a whole-transcript prompt is the configuration that was measured and abandoned.

VALIDATION, AND THE ANNOTATOR COUNT DEPENDS ON THE SIGNAL'S TYPE. An objective signal ("did the agent generate valid code?") is checkable by a single human annotator; a subjective one ("was this output harmful?") needs MULTIPLE annotators to account for disagreements and biases. A scanner whose rate has not been spot-checked against ground truth on a subset is an unvalidated instrument, and the case study names its own spot-checking as rudimentary.

COST, so a reader can budget: scanning 10 failed attempts from each of 9 models — 90 transcripts, each terminated at a 2.5-million-token budget — cost approximately £30 per scanner, or £300 for the full set. Scanner cost scales with the number of Assistant messages, not the number of transcripts, which is the direct consequence of the message-level choice above.

WHAT THIS DOES NOT MEAN: the stages are not a substitute for reading transcripts. Stage 3's manual pass is what tells you which signals exist to operationalise, and AISI's own stated limitation is that its manual review lacked a tighter protocol, not that manual review was unnecessary. LLM assistance is offered at stage 3 at two levels — querying a model about one transcript, or querying the database for statistical patterns not visible in individual transcripts — as partial automation of that reading, not as a replacement for it.
