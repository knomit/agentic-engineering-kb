# Phrase an agent's boundary as an instruction, never as a claim about its environment — a false environment claim is what let the model doubt its own briefing

After its July 2026 incidents Anthropic asked every organisation that tests pre-release models with reduced cyber safeguards to commit to a set of practices. They apply in full wherever a partner runs cyber-related evaluations "using their own harnesses, sandboxes, or agents", and explicitly do not apply to customers using safeguarded models.

THE ONE-LINE RULE THAT MATTERS MOST, because it costs nothing and the incident turned on it: "Boundaries should be phrased as instructions (e.g. 'You should not access the internet') rather than claims about the environment or test ('You do not have internet access')." A claim about the environment can be false, and in these incidents it was. Anthropic's own alignment analysis: Claude "was explicitly told that it had no internet access, despite the internet being available, which may have led it to question whether the systems it saw were real." An instruction remains true whatever the network configuration actually does, survives a misconfiguration without becoming a lie, and does not hand the agent evidence that its briefing is unreliable. Every prompt should state what is in and out of scope: targets, permitted actions, and network boundaries.

This sharpens rather than contradicts [[127fd5f9]]. That fact's claim — the prompt is not the containment boundary — still holds; this is about what the prompt should say GIVEN that something else enforces the boundary.

THE REST OF THE SPEC:
- DEFAULT ISOLATION. Run inside a hardened sandbox with no internet. The only outside connection permitted is to the model's own API, and "the API keys should be kept outside the environment." The configuration "should be verified before every evaluation begins." Where an evaluation genuinely requires internet access, Anthropic says it will work with the evaluator to determine whether runs taking out-of-scope actions can be reliably detected and halted.
- PRE-ENGAGEMENT VALIDATION, and this is the unusual one: have the model being tested probe its own sandbox — first a static analysis of the configuration, then task the model to actually try to escape, instructed to stop and report if it succeeds, under close human supervision, without internet access and ideally inside a second sandbox. Because evaluations run "hundreds or even thousands of runs", do this at length before any of them begin.
- SOLVABILITY PRE-CHECK. "Confirm any evaluation challenge is actually solvable in principle. When an evaluation target is offline or a task can't be completed, agents will often look for other ways to complete a challenge, increasing the chance that they take actions outside the intended scope of the evaluation." Anthropic's footnote keeps the layers apart rather than collapsing them: an aligned model should stop or report that the task cannot be completed as specified, they are training that behaviour directly, "but a defense-in-depth approach means not relying on alignment alone."
- REAL-TIME MONITORING over the model's thinking, actions and network activity, by a model- or rule-based monitor "that has been provided with the scope of the exercise", flagging to a human and ending the exercise on violation. The monitor needs the scope declaration as an input — which is the missing piece [[193d5de2]] identified, that harnesses score task success and none asserts the agent stayed in scope.

WHY EVALUATIONS SPECIFICALLY, and this argument transfers to any high-volume adversarial workload: "Cyber evaluations are unusually likely to produce the behaviors seen in these incidents. They create selection pressure towards persistence and creativity in probing their surroundings and working around obstacles, and they are run many thousands of times." The task selects for boundary-probing and the volume multiplies it — on top of, not instead of, [[d3acef50]]'s point that these runs also have production safeguards deliberately switched off.
