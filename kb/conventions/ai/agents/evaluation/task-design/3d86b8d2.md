# Admit an eval case only if you can say why it is hard before adding it, and do not let user traffic set the distribution

The admission test for a hard case is articulable difficulty: "Pick hard cases because a human judged them hard: a useful test is to be able to say why a task is hard before you include it."

The counterpart caution covers the easy end of the distribution: "users sometimes try what they expect to work, so a task distribution drawn strictly from user traffic may skew easy." Production traffic is therefore a pool to sample from, not the sampling frame. The build-eval workflow draws in a stated order — production transcripts, then bug reports and tickets, then five to ten hand-written cases, then synthetic cases generated from the codebase — and shows the inputs for review before proceeding.

Operational consequence: two admission gates, an articulable reason the case is hard and a distribution you chose rather than inherited.

Pack analysis, not stated by the source: the reason the human-judgement test earns its place is that "the current model fails this" is a criterion that moves with the model, so a set assembled from today's failures silently re-scopes itself at every model upgrade. This is not an argument against adversarial sampling; it is an argument against letting current failure be the whole reason a case is in the set.
