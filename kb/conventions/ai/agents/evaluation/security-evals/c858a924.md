# Run security-relevant agent evals both with and without defenses — the gap is the number that matters

From a survey of seven cybersecurity agent benchmarks — Cybench, CVE-Bench, CyberGym, ExploitGym, ExploitBench, Multi-Host Bench (MHBench) and SCONE-Bench — measure capability twice: once against a bare target and once with realistic protections (ASLR, sandboxing) enabled.

The single-number version of why: on ExploitGym, Claude Mythos "led the evaluation by exploiting 157 out of 898 instances" with defenses disabled, and enabling security protections cut that to **45**. Reporting either number alone misleads — the first overstates real-world risk, the second hides the raw capability that a defense regression would expose.

The same discipline applies outside security. Any agent eval run against a permissive environment measures something different from the same eval run against the guardrails you actually ship. Report both, and treat the ratio as the value your defenses are providing.

Two further measurement rules from the same survey, both about not fooling yourself:

- Use **deterministic graders keyed on outcomes** — a sanitizer crash, a captured flag — rather than validating the method the agent used. The survey's stated reason: "Because exploitation is open-ended, most benchmarks evaluate outcomes instead of the method used." Outcome graders survive an agent that finds a better route; method graders do not.
- **Control for contamination by separating post-training-cutoff tasks.** Public exploits and their writeups leak into training data, so a benchmark built from known CVEs measures recall as much as capability. SCONE-Bench's zero-day evaluation limited tasks to contracts exploited after the models' knowledge cutoffs, taking best-of-eight attempts.

**CALIBRATION FIGURE — CORRECTED 2026-07-30, AND THE CORRECTION CHANGES WHAT IT LICENSES.** An earlier revision of this fact reported "94% agreement between independent auditors" and concluded that *human* transcript review is reproducible enough to be worth doing. That is wrong. The source says the ExploitGym creators used **GPT-5.5 and Opus 4.6 as transcript auditors**, and "these auditors achieved a 94% agreement rate across 313 production tasks."

So the 94% is **inter-model agreement between two LLM judges**, not inter-rater reliability between humans. What it actually supports is narrower and more useful: an LLM-as-judge panel checking whether an agent targeted the real vulnerability or took an unrelated shortcut is consistent enough across two different frontier models to be worth automating. It says nothing about human reviewers, and it is not independent evidence that the judgement is *correct* — two LLM auditors can agree and both be wrong, particularly if they share failure modes on the same transcripts. Use it to justify automating reward-hacking detection at scale; do not use it to skip human spot-checks, and do not cite it as a human-reliability number.

The underlying finding stands: reward-hacking risk in these benchmarks is real, and solves need auditing rather than trusting the score.
