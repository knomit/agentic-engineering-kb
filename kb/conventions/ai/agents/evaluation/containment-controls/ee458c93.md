# The answer to 'no eval harness catches out-of-scope behaviour' turned out to be monitors inside the training and eval loop, plus gating internal work on containment

Four eval-containment failures were disclosed in three weeks in mid-2026, and the sharpest finding across them was that no eval harness detected any of them — harnesses score task success and none asserted that the agent stayed in scope. This fact records the control set the operator converged on afterwards, because it is the first published answer to that gap and it is concrete enough to copy.

On declaring that it could not rule out Critical cyber capability for an upcoming model, OpenAI listed the internal controls it applied:

- **Monitoring moved inside the eval and training loop, not just production.** 'Universal monitoring for risky actions and misalignment across all agentic applications' of the model, explicitly *including training and evaluation*. The monitors 'evaluate the model's Chain of Thought and trigger a security response to review and interrupt high risk activity.' Two properties are load-bearing: the monitor reads the reasoning trace rather than only the tool calls, and it can INTERRUPT rather than merely log for later review.
- **Capability gating applied to internal development, not only release.** They paused internal activities involving the model that did not yet meet the strengthened control requirements. The gate blocks your own researchers, which is the part that costs something — OpenAI describes accepting 'the cost of research velocity'.
- Isolated testing environments, restricted network and tool access, sandboxed execution, enhanced model-weight protection and encryption, additional detection capability.
- Recommended security controls supplied to third-party testing partners, which is where two of the four disclosed failures happened.

The companion operational guidance for teams running cyber-capable agents names four practices: run workflows in controlled environments with no access to production systems or the open internet; **regularly test sandbox boundaries** rather than establishing them once; review tool calls that need elevated permissions before they execute (an 'auto-review' mode that can block destructive actions, recommended over full-access mode); and define scope explicitly via scoped permission profiles that enumerate authorised systems and actions.

**What generalises past the frontier-lab setting.** The pattern is that runtime safety machinery was moved from the deployment path into the development path — the environments that had deliberately disabled production safeguards in order to measure raw capability. If you disable classifiers, guardrails or permission checks to make an eval meaningful, that run needs compensating detection, and 'the harness reports a score at the end' is not detection. A trajectory-level monitor that can halt a run is the control that was missing.

Read this as a documented remediation from one operator responding to its own incident, not as a validated standard: no effectiveness figures are published, chain-of-thought monitoring depends on the trace being faithful to the behaviour, and 'universal' is the operator's own characterisation.
