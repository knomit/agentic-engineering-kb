# In a generate-and-check attack search the VERIFIER decides the yield: a yes/no gate ends runs on trivial successes, and over iterations the attacker drifts to whatever the rubric still accepts

Screwtape is Redwood Research's pipeline for finding attacks that evade action-only monitors (monitors that see tool calls but not reasoning). An attacker agent edits a real agent transcript to insert an attack, an LLM verifier judges the edit, and the monitor scores whatever the verifier accepts; an attack counts as successful when the monitor's score falls below "a threshold set to a fixed false positive rate on honest transcripts". The loop repeats until success or an iteration cap.

Two properties of the VERIFIER, not of the attacker, decided what the search produced.

1. A simple yes/no verifier was abandoned because "Runs stopped early on trivial “successes”". A coarse gate accepts the first thing that technically satisfies it, so the search terminates before reaching anything worth measuring. The replacement was "a detailed rubric with dimensions inspired by security engineering frameworks", with the judge additionally required to reason explicitly about consequences.

2. Even with the rubric, "the attacker tends to drift toward borderline cases" that are not severe enough, which is why the team set conservative severity thresholds up front rather than filtering afterwards.

Operational consequence: in any generate-and-check loop where an LLM is the check, the gate's coarseness sets the floor on output quality and the gate's boundary sets the direction of drift. Write severity and consequence into the rubric before the run; a binary accept/reject gate on an optimising loop is a specification, not a formality.

What this does NOT mean: the rubric did not make the verifier reliable. The authors report that "Verifier mistakes concentrate towards the end of the funnel" and that "the pipeline still requires human review of the resulting attacks", so a rubric buys a better search, not an unsupervised one.
