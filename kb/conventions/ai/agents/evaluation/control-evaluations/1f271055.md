# A simulated control evaluation replays a real transcript with the attack's tool calls never executed and a simulator LLM faking the outputs — and it predicts the safety number to 3.6 points where a purpose-built arena errs by 10.1

A control evaluation asks whether the monitors you run over an agent would catch that agent deliberately attempting harm. The usual way to get one is a purpose-built arena (Redwood names BashArena and LinuxArena) where the attack really executes — which is why its answer is about the arena and only indirectly about your deployment. Redwood's **simulated control evaluation (SCE)** removes the execution instead of the realism.

**THE METHOD, and every component matters.** Start from transcripts of an agent doing real work in a real codebase. The attacking model continues that task toward a harmful objective, but **its tool calls are never executed**: a simulator LLM writes plausible tool outputs from the transcript and the codebase, and an LLM judge estimates whether the attack would have succeeded. The whole point of starting from a real transcript rather than a synthetic scenario is that the environment is then your environment, at the cost that nothing in it is real.

This is not the same thing as editing an attack into a recorded transcript, and the difference is operational: a pre-edited transcript cannot test an *interactive* protocol — resampling, dynamic permissioning — because the protocol's responses would change what the attacker does next, and the attack written into the transcript may not be one the evaluated model could actually produce. An SCE keeps the attacker in the loop.

**THE FIDELITY MEASUREMENTS, with their conditions. State the audit budget whenever you quote the headline.** At a 5% audit budget, "the pooled safety-prediction RMSE is 3.6 percentage points for simulation, versus 10.1 for BashArena" — safety being defined as the probability of detecting an attack before an undetected success. Sample efficiency: "simulation beats the full BashArena safety prediction with only 4.6% as many task-pair draws as deployment." Decomposition: "SCEs explain 95% of the variation in expected safety between side-task categories and 78% between environments." Behaviour: "the estimated KL divergence is more than an order of magnitude below the BashArena comparison", measured by embedding behaviour summaries and clustering them into shared groups, following Mehri et al. (arXiv 2605.07847). The run-to-run frame for all of it: "the gap between simulated and real was often about as small as the gap between two independent real runs".

**THE APPARATUS IS PART OF THE RESULT.** "Our primary simulator is gpt-6-astra, with gpt-5.6-sol as a fallback when Astra refuses or fails to return a valid tool response", and "we use a gpt-5.6-sol attack success judge which estimates the probability that the attack succeeded". A simulator that *refuses* is a load-bearing failure mode of this design, not an edge case — budget a fallback.

**WHAT IS NOT ESTABLISHED, stated by the authors.** Fidelity can be checked only where real execution is possible, so carrying SCEs over to a real deployment "involves some extrapolation"; the validation ran the same control evals on real and simulated LinuxArena because deployment ground truth does not exist. The real-transcript runs used Redwood's own sessions, which contained no attacks, so they cannot validate the attack-success or safety predictions. The simulator sees only the transcript and the repository, so live state outside them (a CI runner's IAM role, say) is guessed. Untrusted simulators are unsolved: "we do not currently know how to obtain reliable SCEs with an untrusted simulator." The clearest gap is long-horizon, multi-agent attacks, for which no simulators have been built. The authors' own summary carries its hedges: "SCEs are faithful where we can check, and we think they can make control evaluations substantially more representative of deployment."

**THE FORESEEABLE MISREADING, AND IT IS TWO.** (1) A 3.6-point RMSE is an error in predicting a *safety number under a stated audit budget*. It is not evidence that any particular simulated attack would have worked in production, and the judge's probability is not an execution. (2) An SCE is not a capability evaluation: "We also don't expect SCEs to reveal the limits of a model's dangerous capabilities" — the attacker never executes anything, so nothing here measures what it could achieve if it did. Use an SCE to price your *monitoring*, and something else to price the model.
