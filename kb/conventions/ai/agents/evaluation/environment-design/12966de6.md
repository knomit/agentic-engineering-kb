# Verify computer-use agents against database state, not screen output — and build the world you train against, because live sites cannot be re-run

Microsoft Research's stated reason for building synthetic training worlds rather than using real sites is an evaluation-methodology argument, and it is the part worth keeping. In their words: "Pages get redesigned, listings and dates roll forward, and hosts throttle or block automated traffic, so a benchmark that is pinned to them drifts, and no two runs face the same site." And the reason this bites training harder than evaluation: "An occasional evaluation can absorb that; training cannot, since it runs the same task thousands of times and needs the same world each time." Live sites also give an agent nowhere safe to practise login-gated, write-heavy workflows — exactly the workflows that matter commercially and that you cannot rehearse against someone's production account.

Two design choices generalise to anyone evaluating an agent that acts on a UI:

- **Ground the verification in database state, not in the interface**, and the mechanics are more specific than the slogan. "Every task carries its own answer key, a value or a state change minted from the real database by a SQL query at generation, true by construction and re-checked after the agent finishes." The two assertion types are graded differently: "A _read_ is graded on semantic equivalence to the stored value ($288 for $287.62 passes); a _write_ on a real before/after database diff, so claiming a ticket was closed fails unless the row flipped." Note what each choice buys — semantic equivalence on reads stops the eval failing an agent over formatting, and a before/after diff on writes makes narrated success unscoreable. This is the computer-use analogue of the trajectory-vs-output-scoring rule: an agent can narrate success, or land on a page that looks right, without the write having happened. The assertion belongs where the state actually changed, and the reward is then, in their phrase, "a grounded, verifiable reward rather than one inferred from pixels."
- **Treat a failed run as possible evidence against the environment.** Their pipeline runs analyser and fixer agents over failures and loops them back 'to improve the world itself, not just the model', repairing generated apps until they 'pass machine-checkable claims' about routes, state and behaviour. Pair this with the standing rule that an environment failure rate above ~5% is a harness problem rather than a model problem — same principle, applied as a build loop.

*** CORRECTED 2026-08-21: THIS FACT PREVIOUSLY TOLD THE READER THE LIVE-WEB TRANSFER WAS "described qualitatively rather than quantified". THAT WAS FALSE, AND IT UNDERSOLD THE EVIDENCE. *** The post reports it directly: "The frozen model clears base on both, WebVoyager 66.5% to 71.5% and Online-Mind2Web 40.5% to 43.4%." So transfer to two INDEPENDENT public live-web benchmarks is measured, not asserted — which is a materially stronger evidential position than the fact credited, because those benchmarks are not the domains the model trained on.
AND THE SIZE OF THE TRANSFER IS THE ACTUALLY USEFUL NUMBER, so read the deltas rather than the levels (arithmetic is this pack's, from the figures above): in-domain the training is worth **+30.6 points**; on the live-web benchmarks it is worth **+5.0** (WebVoyager) and **+2.9** (Online-Mind2Web). Transfer is real and it is roughly a sixth to a tenth of the in-domain gain. For anyone deciding whether to build synthetic environments, that ratio is the decision input: expect most of the measured improvement to stay inside the worlds you built, and size the investment against the smaller number.

Read the method with more confidence than the headline scores. This is a research-blog announcement from the team that built the system, the largest gains are measured on the same synthetic domains the model trained on, and no independent replication exists. The methodological claims (database-grounded verification with distinct read/write assertion types, environment repair loops, capability-isolating worlds for specific UI interactions such as date pickers and nested filters) are the durable part; treat the percentages as the authors' own.
