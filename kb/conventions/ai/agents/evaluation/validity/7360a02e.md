# Sweep model capability and effort across your eval and read the slope as a verdict on the eval, not on the model

"More capable models and higher effort levels typically should perform better on an evaluation." When they do not, the first suspects are ambiguous tasks and a miscalibrated grader, not a capability plateau: an eval whose score is insensitive to the quantity it is meant to measure cannot register an improvement either, so a flat sweep predicts a useless hillclimb.

Two range checks belong beside the slope check. The strongest model at the highest effort should land "well below 100% on the evaluation", and a baseline already at about 95% or higher is saturated — the build-eval workflow warns the user at that threshold. Variance is a third, separate check with named sources: ambiguous task design, an inconsistent grader (re-run the grader on the same output to detect it), configuration drift, and leftover environment state.

Operational consequence: before trusting a score as a measure of the system, establish all four properties — it moves with capability, it moves with effort, it has headroom, and it is stable across reruns. Any one of them failing is an eval defect to fix before optimising against the eval.

This does NOT mean a monotone curve validates an eval. It removes one way for the eval to be broken, and says nothing about whether the tasks mirror production.
