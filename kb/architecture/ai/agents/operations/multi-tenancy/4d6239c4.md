# Load shedding alone is unfair in a multi-tenant system — an aggregate spike is almost always one tenant, so shed per tenant

Amazon's argument: tenant workloads are uncorrelated, each having its own use case and request rate. Therefore when total load on a multi-tenant service rises abruptly, the overwhelmingly likely cause is one tenant, not all of them. Plain load shedding responds by failing some fraction of requests across every tenant — so the well-behaved tenants absorb the cost of one tenant's spike, and none of them get the single-tenant experience that is the entire promise of the platform.

The correction is to keep load shedding for genuine capacity protection but enforce rate-based quotas at per-tenant or per-workload granularity, so the unplanned portion of one tenant's traffic is what gets rejected and everyone else keeps predictable performance.

The two rejections are semantically different and must be distinguishable by the client: HTTP 429 means the client exceeded its quota, HTTP 503 means the server is out of capacity. A client should back off differently in each case. Beware that this is not reliable in the wild — 429 only entered the HTTP spec in RFC 6585 (2012), and AWS services predating it (SQS launched 2004) still return 503 for rate-exceeded for backward compatibility. Do not build client logic that assumes a rate limit always arrives as 429.

Amazon also notes the paradox to plan around: quotas simultaneously raise availability (by containing one tenant's blast radius) and lower it (a throttled tenant sees errors on requests the service had ample capacity to serve). That is why the quota has to come with visibility — per-tenant consumption metrics the tenant can see and alarm on — rather than being a silent backstop.

For an agent platform, the tenant dimension is usually customer or workspace, and the natural quota units are agent runs, tool calls, or tokens per second rather than HTTP requests.
