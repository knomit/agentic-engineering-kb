# Put agent cost and policy enforcement in a gateway, and reserve deterministic limits for consequential actions

LangChain's argument for a gateway as the enforcement point for agent policy. Most of the framing is standard enterprise governance; four specifics are worth keeping.

1. DETERMINISTIC LIMITS BEAT DETECTION FOR CONSEQUENTIAL ACTIONS. Their rule: "Consequential actions should rely on deterministic limits or human approval rather than relying on content detection alone." Guardrails split into pattern-based (SSNs, card numbers, API keys — regex, reliable) and model-based (names, locations, political affiliation, jailbreak attempts — probabilistic, not reliable). Do not put a probabilistic classifier on the path of an irreversible action and call it a control. This is the same conclusion reached independently about second-agent tool-call reviewers shipping fail-open — model-based checks reduce friction, they do not establish a boundary.

2. ACCOUNT FOR CACHED, BATCH, AND REASONING TOKENS SEPARATELY. Provider pricing now differentiates these tiers, so a single tokens-consumed number no longer tracks spend, and the effective price of an unchanged workload moves when a provider changes tier pricing. A cost model that sums tokens is wrong by construction.

3. DECIDE FAIL-OPEN VS FAIL-CLOSED PER WORKLOAD RISK, EXPLICITLY. The gateway needs timeouts, load balancing, and a stated failure posture chosen per workload rather than one global default — and any fallback model must satisfy the SAME data-handling, residency, and safety requirements as the primary. Routing to a fallback under load is where a compliance boundary silently gets crossed.

4. ROUTING WITHOUT TRACING IS NOT GOVERNANCE. A standalone router cannot explain why a call happened, what the agent did next, or whether it passed policy. Audit records need the policy VERSION applied alongside the outcome, tools used, and users involved — without the version you cannot reconstruct what the rules were at the time.

Layer spend limits at organisation, business-unit, team, API-key, and user level with daily/weekly/monthly windows and defaults, so teams inherit sane limits rather than configuring their own.

Source caveat: vendor content from a company selling the observability and gateway tooling it recommends; confidence is set accordingly. The deterministic-boundary point is the part corroborated elsewhere.
