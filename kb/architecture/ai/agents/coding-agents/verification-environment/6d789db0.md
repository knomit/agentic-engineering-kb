# Raising code throughput moves the bottleneck to verification, so the harness investment that pays is making the running application and its telemetry readable by the agent

Once agents produced code faster than people could inspect it, the constraint in this repository stopped being code generation and became human QA capacity. The team's response was to make the consequences of a change observable to the agent rather than only to a person.

Three concrete pieces. The application boots per git worktree, so a change under review runs in isolation alongside others. The Chrome DevTools Protocol is wired into the agent runtime, so the agent can drive the UI to reproduce a bug and then confirm its own fix. Each worktree gets an ephemeral logs, metrics and traces stack queried with LogQL and PromQL, which turns a performance requirement into something the agent can assert on — the post's example target is to "ensure service startup completes in under 800ms".

With that in place the reported envelope is a single run working on one task for "upwards of six hours", and a single prompt carrying a bug through reproduction, a recorded video, implementation, validation, PR, feedback and merge. The post caveats the whole arrangement: it "should not be assumed to generalize without similar investment—at least, not yet."

The transferable claim: when verification is the bottleneck, spend on the agent's ability to observe the system it just changed. Prompt changes do not move a verification constraint, and an agent that cannot read the telemetry of its own change can only report that the code compiles.
