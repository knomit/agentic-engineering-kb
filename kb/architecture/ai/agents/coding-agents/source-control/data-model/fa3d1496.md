# Immutable, content-addressed objects plus a single-row compare-and-swap for refs is what makes a high-rate commit path cacheable and lock-free

The mechanism behind Scion's throughput is a data model in which almost everything is immutable and exactly one thing is mutable.

- A commit is a diff, not a snapshot: "a changeset stores a list of the files that changed relative to its first parent," with content-addressed pointers to blobs. Writing one therefore costs the size of the change, not the size of the tree.
- The one mutable thing is the ref, and it is isolated: "moving one is a compare-and-swap on a single Spanner row that happens separately from creating changesets." Creating history and publishing history are different operations with different contention.
- The fetch protocol asks per object rather than negotiating a whole history: "it operates exclusively on trees and blobs the client wants", requested recursively from a root tree, and transfers are resumable rather than one multi-gigabyte response.
- Immutability is what makes the caching tiers possible: "Every request is for a specific object that never changes", so any cache at any tier can answer any request. A per-node daemon talks to regional caches which talk to authoritative servers, all tiers sharing the same RPCs, with tiering strictly enforced so that a regional cache failure cannot stampede upstream.
- Derived data (blame, path history, commit-graph skip lists) is computed from changesets by one generic recursive mechanism, eagerly or lazily per type, and is never exposed to the client — so it can be changed without changing clients.

Operational consequence, and the part that transfers beyond source control: separate the append of immutable content from the compare-and-swap that makes it visible, and keep every client-facing read addressed by immutable identity. That combination is what buys an unbounded read-caching tier and a write path with no global lock; a design that lets clients request mutable, named state instead gets neither.

What this does NOT mean: the content-addressed-blob idea is git's too. The change is where the work sits — server-side, with the client negotiating per object rather than reconciling whole histories — and that only pays when clients are reliably online.
