# Virtualize the agent into session, harness and sandbox — an append-only event log is what lets a crashed harness resume instead of dying

Anthropic's Managed Agents architecture separates three things that agent harnesses normally fuse. In the article's own words, they "virtualized the components of an agent: a session (the append-only log of everything that happened), a harness (the loop that calls Claude and routes Claude's tool calls to the relevant infrastructure), and a sandbox." (The informal shorthand *brain / hands / session* maps onto harness-plus-model / sandbox / session, but **session, harness and sandbox are the source's terms** — an earlier revision of this fact presented the shorthand as though it were Anthropic's own.)

Their description of the prior coupled design uses the pets-vs-cattle analogy: "a pet is a named, hand-tended individual you can't afford to lose, while cattle are interchangeable." Losing a container meant losing the entire session.

What each separation buys:

- **Resilience.** Because the session is a durable event log rather than in-process state: "When one fails, a new one can be rebooted with `wake(sessionId)`, use `getSession(id)` to get back the event log, and resume from the last event." A failed sandbox is simply replaced through normal provisioning. In the coupled design engineers could not even tell a harness bug from a network fault from a container crash.
- **Latency.** Stateless harnesses no longer block on container provisioning when a sandbox is not immediately needed. "Using this architecture, our p50 TTFT dropped roughly 60% and p95 dropped over 90%."
- **Security.** "In the coupled design, any untrusted code that Claude generated was run in the same container as credentials." Decoupled, credentials are bundled with resources or held in vaults outside the sandbox, so tokens are not reachable from the execution environment at all.
- **Scale.** A single container becomes a bottleneck as soon as one harness needs multiple sandboxes. Each is instead exposed uniformly: "It called the container the way it called any other tool: `execute(name, input) → string`."
- **Placement.** A decoupled harness works regardless of where the sandboxes live — customer VPCs, custom infrastructure — because it no longer assumes resources are adjacent to the container.

The stated interface surface is `execute(name, input)`, `provision({resources})`, `wake(sessionId)`, `getSession(id)`, `emitEvent(id, event)`, and `getEvents()`, the last allowing the harness to interrogate context across positional slices of the log.

The design deliberately assumes nothing about the number of harnesses or sandboxes, their physical location, or the harness implementation. What it does assume is that the agent will need durable state, computation, and room to scale — so if your agent is short-lived and single-sandbox, this buys you very little for real added complexity.

Verified against the source 2026-07-31; published 2026-04-08, no update notice, every quoted claim re-confirmed.

*** INDEPENDENTLY CORROBORATED BY A SECOND VENDOR (added 2026-08-14). *** OpenAI's Agents SDK release of 2026-04-15 — a week after Anthropic's post, and a separate product line — arrives at the same separation and gives the same three reasons, under the heading "Separating harness from compute for security, durability, and scale":
- SECURITY, with the threat model stated as a design premise rather than a mitigation: "Agent systems should be designed assuming prompt-injection and exfiltration attempts. Separating harness and compute helps keep credentials out of environments where model-generated code executes." This is the same credentials-not-in-the-sandbox conclusion Anthropic reached.
- DURABILITY, with the same causal chain — externalized state is what buys resumability: "When the agent's state is externalized, losing a sandbox container does not mean losing the run", with built-in snapshotting and rehydration restoring state "in a fresh container and continue from the last checkpoint if the original environment fails or expires."
- SCALE, including routing subagents to isolated environments and parallelizing across containers.
OpenAI adds a portability primitive Anthropic's account does not have: a **Manifest** abstraction describing the agent's workspace — mounted local files, output directories, data from S3/GCS/Azure Blob/R2 — so the same workspace definition moves across sandbox providers (Blaxel, Cloudflare, Daytona, E2B, Modal, Runloop, Vercel are named as built-in). The stated benefit is aimed at the model as much as the developer: "a predictable workspace: where to find inputs, where to write outputs, and how to keep work organized across a long-running task."
WHAT THE CORROBORATION IS AND IS NOT: two vendors independently choosing this decomposition is real evidence the pattern is load-bearing rather than one team's taste. Neither is a controlled comparison, and both are describing their own products — the p50/p95 TTFT numbers remain Anthropic's alone and are NOT corroborated. The boundary condition above still stands unchanged: short-lived single-sandbox agents pay the complexity and get little back.
