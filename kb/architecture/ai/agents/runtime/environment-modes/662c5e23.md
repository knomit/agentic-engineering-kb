# Choosing an agent's environment mode subtracts tool capability, not just compute: with no environment the built-in Bash and apply-patch tools, workspace files and executor MCPs all disappear while remote MCP tools keep working

OpenAI's Agents API splits an agent into three named parts: the harness, which is the OpenAI-hosted Codex instance that runs the model and tool loop and maintains the session; an optional environment, where commands run and files live; and the application server, which submits tasks, receives events and handles function tools. The environment is selected by `environment.type` and the choice is a capability decision, not only a hosting decision.

WITH `type: none` the harness still runs the loop, but a specific set of tools is gone: "Without an environment, the built-in Bash and apply-patch tools, workspace files, and executor MCPs are unavailable." What survives is remote MCP tools, which the harness calls directly, and function tools, which your code receives, runs and returns results for. So an agent design that assumes a filesystem or a shell silently loses its means of acting, while an agent built only on remote MCP and function tools runs unchanged — which is the condition that decides whether no-environment is viable for a given product.

WITH `type: openai_hosted` OpenAI creates and manages a sandbox for the session and the harness runs commands in it directly. The application still submits tasks, receives events and handles function tools.

WITH `type: self_hosted` your code starts the environment and connects an executor to the session; the executor runs the commands and tools the harness requests. The documentation assigns provisioning, reconnection, shutdown and the preservation of any files you need to keep to the operator, and states one ordering constraint on teardown: "Before stopping compute, coordinate incoming work and confirm that no execution is pending."

THE FAILURE SHAPE TO PLAN FOR is on the application side rather than the harness side, and it is open-ended rather than an error: "Function tools need a handler that receives calls and returns results. If that handler is unavailable, the agent can remain waiting for a result." Failures in your event or lifecycle handlers can likewise interrupt progress updates or environment management. No timeout, retry or abort behaviour is documented for any of these, so a deployment that relies on the platform to time out a stalled function tool has no stated guarantee to rely on; the deadline has to be yours. Progress and results arrive over two channels that can be used together: streaming for detailed events during the run, and webhooks for session state changes without holding a stream open.
