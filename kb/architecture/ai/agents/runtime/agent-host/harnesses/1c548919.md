# Harness matrix for VS Code's Agent Host at the 2026-11-04 docs: Cloud is an execution target rather than a harness, Local is reclassified as legacy, and an administrator setting can prohibit Local, Claude and Codex outright

What VS Code's Agent Host can run, read from the harness documentation dated 2026-11-04. A dated reference: this page changed materially within six weeks, so re-check a row before depending on it.

THE ROWS, in the comparison table's own words (header: "Harness | What runs | What this means for your work").

- Copilot: "Run tasks using the Copilot SDK, which provides the shared agent experience across GitHub Copilot products." Auth: "Copilot harness sessions use the same GitHub authentication context as chat in VS Code," "including your GitHub Enterprise account when configured." The tool limitation stands: "Copilot harness sessions don't have access to every built-in or extension-provided tool."
- Claude: "The Anthropic Claude Agent SDK is integrated into VS Code." "Sessions use Claude project configuration and provider workflows in your current workspace or an isolated worktree." Copilot-routed models are offered: "The Anthropic Claude and OpenAI Codex integrations also offer Copilot-routed models, subject to their requirements."
- Codex: "OpenAI Codex runs through the OpenAI Codex extension or the experimental Agent Host integration." The extension-free path sits behind `chat.agentHost.codexAgent.enabled` and is labelled experimental. Access is either a "GitHub Copilot subscription" — which "requires Copilot Pro+" — or a "ChatGPT account".
- Local: "Run tasks within VS Code's built-in agent harness", which "works in VS Code's extension host" rather than in the Agent Host. Its session is window-bound: "The session is tied to the editor window: closing that window stops the agent's ongoing work."
- Cloud: NOT a harness. "The Copilot harness runs in a managed cloud environment" and "Cloud is an execution target, not a separate harness." "The cloud environment has its own workspace and tools." Cloud sessions are experimental: "Cloud sessions is experimental and might change or be removed."

THE TWO ADMINISTRATIVE CONSTRAINTS, which are the load-bearing additions and change the architecture decision rather than the feature list.

First, enterprise policy can remove three of the four: "Claude and Codex harnesses are disabled when Copilot enterprise-managed settings apply". A design that assumes a particular harness is available does not survive a managed Copilot tenancy.

Second, Local is on the way out and is now gated by version-numbered settings: "Starting with version 1.142, administrators can set vscode.temporaryDefaultToLocalHarness to true", and "Starting with version 1.143, vscode.temporaryAllowLocalHarness: false prohibits Local, Claude, and Codex". The page's own framing: "The Local harness remains a legacy editor harness option while you adapt integrations that depend on it." The word is legacy, and both setting names carry `temporary` in them.

TOOL REACH, stated more narrowly than before. The page no longer claims that Local has full access to built-in tools, extension tools, MCP servers and configured models. What it does state is a scope rule that applies by surface rather than by harness: "Tools from extensions are available only in chats in an editor window where the extension is running", and, for a session running without a client attached, "Tools provided by a client still require that client." So extension-provided tooling is tied to a live editor window, whichever harness is selected.

NOT PRESENT, and the absences are the useful part for anyone planning an integration. The page lists no Gemini, Antigravity, Hermes or OpenClaw harness, and documents no mechanism or extension API for registering a third-party or custom harness with the Agent Host. The nearest statements are architectural rather than procedural: "different agent runtimes plug into one host-facing interface and present common session concepts to clients", and "Agent adapters run inside the Agent Host process." Neither says how an adapter is added. A non-first-party harness therefore reaches AHP only through an ACP-bridging host.

NOT READ. The per-harness requirements content sits behind tabs ("Copilot Claude Codex Local"), and the Claude tab's body did not come back in the extracted text, so the Claude authentication paths — an API key versus a Claude Code OAuth token — and any claim that the Claude SDK loads in-process or is enabled by default are unverified at this reading rather than removed from the product. The customization-file baseline (AGENTS.md, CLAUDE.md, GEMINI.md, copilot-instructions.md, `.mcp.json` conversion) comes from a separate migration tracker and was not re-read this time; whether the Claude adapter honours a workspace `.mcp.json` remains untested from documentation alone.

CONSEQUENCE. Choose the harness by tool reach and by what your administrator can switch off, not by model. The combination that bites is a session needing extension-provided tools, which requires a live editor window, with an enterprise-managed Copilot tenancy that disables the non-Copilot adapters and a version where Local can be prohibited.
