# Let the agent write code to compute with, then throw the code away and pass only a strict expected format — the guardrails go on the format, which is the thing that reaches the back end

An agent that writes code to do arithmetic or data work gets a capability and hands you a problem: whatever that code produced is now an arbitrary artifact flowing toward a system of record. Arca's pattern separates the two. The agent's code runs in a sandbox for the computation; then, in its CTO's words, the system "translates the code it [the agent] wrote into a strict format that we expect, throw away the code", and "you install guardrails on that format before it reaches your back end."

WHY THE DISCARD IS THE POINT. Validating generated code is open-ended — you are reasoning about a program. Validating a fixed schema is closed — you are checking fields against a contract you wrote. Discarding the code means nothing downstream can re-execute it, re-interpret it, or inherit a behaviour the validator did not model, so the sandbox boundary and the validation boundary coincide instead of being two places where something can leak through.

THE OPERATIONAL RULE. Define the strict format first, as a narrow schema the back end already accepts; let code generation be a means of filling it, never a means of talking to the back end; put every guardrail on the format rather than on the code or on the model's intent.

WHAT THIS DOES NOT MEAN. Discarding the code does not make the sandbox optional — the code still executes somewhere, with whatever reach that environment has, and this pattern says nothing about containing that. It also does not mean the format is safe by construction: a schema wide enough to carry an arbitrary payload field reintroduces exactly what was discarded. The source gives no schema example, no validation detail and no measurements.
