# A monitor that can execute code checks the agent's claims instead of believing them — at about 10x the model invocations and 14x the output tokens of a single API call

On the SLEIGHT-Bench attack set, the Claude monitor was run two ways: as a passive reader of the transcript, and as a coding agent (Claude Code) able to execute code. The structural difference is what the monitor can do with a claim the agent made, and the authors state it concretely: "if an agent copies a large file but subtly alters part of it, a coding agent monitor can write a script to compare the two, while a regular monitor would have to take the output at face value."

THAT IS A MATCHED REMEDY FOR A SPECIFIC FAMILY OF BLIND SPOTS, not a general uplift. Counting lines in long output, tracking what a file holds after reassignment, finding a needle in an opaque blob, and checking whether a command behaves as claimed in a non-default environment are all things a passive reader must INFER and an executing monitor can simply MEASURE. Those are exactly the lowest-scoring categories in the post's blind-spot table, which is headed "Catch rate at 1% FPR": "Counting" 13%, "File/object reuse" 15%, "Model priors" 13%, "Needle in haystack" 38%. Read those four as published catch rates by attack class and NOT as the passive configuration's rates specifically — the table names no monitor and no configuration, and the prose names Opus 4.6 only as "the main monitor we work with" without tying the table to it. The threshold is stated in the body: "We calibrate our monitors to a 1% false positive rate," "meaning they would only incorrectly flag 1 in 100 benign transcripts." For scale on that same monitor, "On Opus 4.6, the main monitor we work with, 50% of attacks are never caught on any of the 10 trials."

**THE COST, stated by the authors, and the reason this is an architecture decision rather than a default:** "The Claude Code monitor on average takes ~10x more model invocations and generates ~14x more output tokens than the API call." The two multipliers are different and they constrain different things — invocations drive latency and rate limits, output tokens drive spend. Do not collapse them into a single "10x more expensive"; a system that is rate-limited and one that is budget-limited hit different walls.

**WHERE TO PUT IT**, offered as a possibility rather than a recommendation, and the modality is the authors' own: "While this cost might be high, it may be worth it in high-stakes applications", "it may also be mitigated, for example by using these expensive classifiers only as a second stage" "in a multi-stage classification system." Three hedges in one sentence — might, may, for example — so this is a suggested mitigation and not a published design. A cheap passive monitor triages the whole stream; the executing monitor adjudicates what the cheap one flags, or covers a narrow high-stakes path outright. This is the same staging this corpus records for permission classifiers, arriving on the monitoring side of the same problem.

ALSO MEASURED, AND CHEAPER THAN EITHER: across every model tested as a monitor, "the general trend shows that more compute means better detection", and enabling extended thinking — on top of always letting the monitor write out reasoning before scoring — "improves performance for most models." Extended thinking is the first knob to turn; the agentic scaffold is the expensive one.

**NOT ESTABLISHED, AND THE ABSENCE IS ITSELF BOUNDED.** In the post's prose and tables there is no catch-rate comparison between the Claude Code monitor and the passive one: no per-category number, no headline number, no table row, and the Claude Code paragraph carries no numbers at all. So the SIZE of the uplift bought by that 10x/14x is not stated in the text — only its direction and its price. The bound on that absence is Figure 3, captioned "Catch rate by attack class and monitor configuration for the Opus 4.6 monitor (ControlArena prompt, 1% FPR threshold)": "monitor configuration" could include the agentic one, and a figure's values live in an image that text extraction does not return. So treat the comparison as NOT READ rather than as absent, the cost figures as firm, and the benefit as directional. The post also does not say which Claude model ran the agentic monitor — only "For Claude models, we also test running the monitor as a coding agent using Claude Code," "rather than just having it read the transcript passively."
