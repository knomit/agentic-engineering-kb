# An agent driving lab hardware compiles its exploration into a deterministic script — because the device's control loop outruns model inference — and it misreads physical failures as software bugs

Anthropic's Model Hardware Standard is a research-preview specification for AI agents to operate physical instruments — microscopes, liquid handlers, robotic arms — through a standardised driver built on read/write primitives ("get temperature", "set temperature"), with devices discoverable in a standard format so agents and devices find each other without a bespoke translator. It is model-agnostic and "any agent harness can access it using standard protocols, such as the Model Context Protocol." Two things in it are engineering content rather than announcement.

THE CONTROL-LOOP PATTERN AND ITS BOUNDARY CONDITION. Agents get three control mechanisms: MCP, a command line interface, and code files. "When the agent needs to execute long-running tasks or operate devices faster than its online reasoning would allow, it can chain together driver commands from one or more devices in code files. This allows the devices to carry out operations themselves, without the agent needing to reason at every step." The worked example is the shape to copy: Anthropic observed Claude adjust a laser, observe the result through a camera to assess how the adjustment moved the beam, and repeat — then package what it learned into code files, "writing a deterministic script that let it align the laser without having to reason at each step, so the whole process could run as a single command." The agent's deliverable is a program, not an action sequence, and the explore-then-compile split is forced by a hard constraint rather than by cost: the device's control loop is faster than model inference, so per-step reasoning is infeasible, not merely wasteful. That is the condition to test for before reaching for this pattern.

THE FAILURE MODE, with a worked example. "As a large language model, Claude learns about the physical world through text and images, meaning its spatial and physical reasoning have limitations that still require expert oversight. When working with protein samples, for example, Genentech researchers had to guide Claude to recognize that errors caused by foaming in samples were physical failures, not software bugs, that could only be mitigated through the appropriate physical corrections." An agent whose entire error vocabulary comes from software will classify a physical fault as a software fault and keep debugging the code. Anything driving hardware needs the physical failure modes written down where the agent can read them, in the same place it reads the interface.

WHERE THE UNWRITTEN KNOWLEDGE GOES. The driver carries tags letting a user state, in natural language, machine characteristics "that may not be discernable from code alone (for example, the weight of a robot arm, which is important for knowing how to manipulate it safely)" — information that previously lived in paper manuals or as tacit knowledge, and which the user can supply directly or by being interviewed by an agent. From those tags the driver generates a reference file covering what a device can measure, what can be adjusted, "and what safety limits will be enforced." So safety limits appear in the discovery document the agent reads, not only in a layer beneath it.

MODALITY AND LIMITS. This is a research preview shared with selected partners ahead of open-sourcing, with safety evaluations described as still to be built with launch partners and a physical safety roadmap still in development; MHS does not yet work with hardware lacking a programming interface. The one quantitative partner result stated is QuEra's agent-developed controller recovering a laser's frequency lock "99.3% of the time without human intervention", reported in a linked partner write-up this fact does not cover.
