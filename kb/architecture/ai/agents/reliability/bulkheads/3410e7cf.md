# Bulkhead each dependency separately — a single global concurrency limit still lets one slow tool kill unrelated capability

A single service-wide concurrency limit prevents outright overload but does not preserve partial function: when one dependency slows, it consumes the whole shared allowance and the service starts rejecting work that never needed that dependency. Amazon's fix is a separate concurrency bulkhead per dependency (or per API), so a slow dependency degrades only the codepaths that use it.

Implementation, from Amazon's practice:
- In a threaded server, the naive form is one thread pool per API group. Amazon largely avoids this because thread-pool sizes cannot be reconfigured at runtime.
- The form they prefer, and the one that also works in non-blocking servers, is a plain counter per dependency: increment on entry, decrement on completion, reject when above the limit. The limit is then a runtime-reconfigurable value rather than a startup-time pool size.
- Where the isolation matters enough, split the APIs into separate services outright. AWS Lambda's per-function-concurrency reservation is this idea productised; Amazon API Gateway and Application Load Balancer let you keep one client-facing endpoint while routing to separate backends.

For agent builders the mapping is direct: an agent with N tools has N dependencies with independent failure modes. Bulkhead per tool (or per tool-group), not once around the agent loop, or a single slow search backend takes down file edits and everything else with it. The same applies to a cache-plus-database tool: limit the concurrency of the database calls specifically, so cache hits keep being served when the database is slow.

Note that Amazon's internal example is exactly this shape — Lambda's worker manager caps how many threads may be concurrently waiting on the placement service, so the slow cold-start path cannot starve the warm-invoke path that shares its pool.
