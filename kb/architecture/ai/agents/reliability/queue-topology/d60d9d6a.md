# Shape an agent backlog with MORE queues, not smarter ordering — sideline excess, sideline old, delay, and shard

Once a backlog exists in a single shared queue it is too late to prioritise within it: the ordering is fixed and the expensive work is already interleaved. Amazon's answer is topological — move messages between queues rather than trying to reorder one. The pattern family, cheapest to most involved:

- **A queue per workload/tenant.** Simple and effective, but the consumer must poll every queue, so the cost does not scale. Amazon uses it for a handful of tenants, not hundreds; AWS IoT explicitly does not do this per-device.
- **Shuffle-shard the queues themselves.** AWS Lambda provisions a FIXED number of queues and hashes each customer to a small subset, then enqueues into whichever of that subset currently holds the fewest messages. One customer's surge backs up their mapped queues, and other workloads are automatically routed away from those. This gets isolation without per-tenant polling cost — the shuffle-sharding idea applied to queues rather than to workers.
- **Sideline EXCESS traffic.** On dequeue, if the tenant is over their rate, re-enqueue that message to a spillover queue and delete it from the primary. Work continues on the spillover when resources free up. This approximates a priority queue and can be done on the producer side too, so one heavy workload never crowds the hot-path queue.
- **Sideline OLD traffic.** On dequeue, check message age and move anything stale to a backlog queue worked only once the live queue is caught up. Draining a spike into a side queue as fast as you can dequeue-and-re-enqueue frees consumers for fresh messages — this is how you approximate LIFO on a FIFO substrate, and customers consistently ask for exactly this behaviour: fresh data first, backlog when there is room.
- **Delay queues.** To back a workload off, re-enqueue with a delivery delay of several minutes so the system works on fresher data meanwhile.
- **Drop old messages outright (message TTL).** Valid only where a later full reconciliation exists — Amazon's example is a system doing fast deltas plus a periodic full sync ('anti-entropy sweeper'), where anything enqueued before the last sweep is redundant and can be discarded cheaply.

The framing that generalises: real-time systems are usually built on FIFO-ish queues but WANT LIFO-ish behaviour under backlog. You get it by moving messages between queues, not by finding a cleverer ordering inside one.

Also stated, and easy to skip: protect at every layer. Synchronous systems can rely on front-door admission control because they build no backlog; asynchronous ones cannot, because some workload always evades the front door and the consequence accumulates rather than being dropped. Every component needs its own protection.
