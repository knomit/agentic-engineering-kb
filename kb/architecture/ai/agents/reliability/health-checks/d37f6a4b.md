# Split health checks by blast radius: fast automation gets only local checks, dependency checks go to a rate-limited central actor

Amazon's Builders' Library gives a four-tier taxonomy and, more usefully, a rule for which tier is allowed to drive which automation.

The tiers:
- LIVENESS — is the process up and accepting connections. TCP accept, a 200 on a basic HTTP request, EC2 status checks. Requires no application code.
- LOCAL — can this application actually function, testing only resources NOT shared with peers: disk readable/writable, critical child processes alive and answering correctly, support/monitoring daemons present. These are unlikely to fail fleet-wide at once.
- DEPENDENCY — can this server talk to its adjacent systems: stale config or metadata, expired credentials, unreachable peers, deadlocks and connection-pool bugs. Thorough, but produces false positives whenever the DEPENDENCY itself is having trouble.
- ANOMALY DETECTION — compare each server against its peers across the fleet. Catches what a server cannot know about itself: clock skew, outdated code, and unanticipated modes such as returning 400 where it should return 500, or responding FASTER than peers (a sign it is returning false responses).

The rule that makes this actionable: the tension is between catching single-server failures and a false positive that fires across the whole fleet at once. Because dependency checks fail in a correlated way, Amazon teams restrict their FAST-ACTING load balancer health checks to liveness and local checks only, and hand dependency checks and anomaly detection to external/centralised monitoring that reacts slowly, with thresholding and rate limits, and escalates to humans. Stated principle: automation should stop sending traffic to one bad server, but keep sending traffic when the entire fleet looks sick.

For agent fleets this maps directly. Local checks: can the worker write its scratch directory, is its sandbox process alive, is the tool subprocess responding. Dependency checks — model provider reachable, MCP server responding, vector store queryable, API key valid — must NOT be wired into whatever removes workers from the pool, because a provider-side blip fails them on every worker simultaneously and drains the entire fleet during the exact incident you most need capacity for.

Preconditions for the anomaly-detection tier to work, which are easy to violate: servers must be doing approximately the same thing (explicit routing of different traffic to different workers breaks outlier detection), fleets must be homogeneous (collate metrics by instance type otherwise), and the errors must be reported by something other than the sick server — use load balancer access logs or client-side instrumentation, since a server broken enough to matter often cannot self-report.
