# The constant work pattern: process the full configuration every cycle, padded to maximum size, so nothing about the system changes when everything fails at once

Colm MacCarthaigh's pattern, and the reason Amazon's most reliability-critical systems are its dumbest. A constant work design has three defining properties: (1) it does not scale up or slow down with load or stress; (2) it has NO MODES — the same operations run in all conditions; (3) any variation it does have makes it do LESS work under stress, not more (anti-fragility).

The reason this matters is timing: the moments when a system is handling a load surge, a reconfiguration, or a failure are exactly the moments when getting slower is most dangerous, because slower means longer queues, which means client retries, which feeds itself. Correct timeouts and retries do not eliminate this — slowness during failure response is downtime regardless.

Two mechanisms make it concrete, both worth stealing:

**Pad to the maximum, always.** Route 53's health checkers send the aggregators a fixed-size result set sized to the maximum they could ever support — if 10 health checks are configured but the checker supports 10,000, it sends 10,000 results and 9,990 of them are dummies. Network load and aggregator work therefore do not grow as customers add configuration. Likewise AWS Hyperplane's Network Load Balancer configuration file is written at its full final size from the moment a Region is activated, with empty slots waiting to be filled. The variance is not managed, it is removed.

**Reload everything unconditionally.** Hyperplane nodes fetch the whole configuration file from S3 every few seconds and process and load it — even when it is byte-identical to last time. The system permanently behaves as though the maximum number of changes just arrived, so one change and a hundred changes cost the same. Route 53's DNS servers do the same at query time: having found one healthy answer they check ALL the other candidate answers anyway, so lookup cost cannot change when statuses do.

The payoff is the AZ-failure case: when tens of thousands of health checks fail simultaneously, the health checkers and aggregators do exactly what they were already doing. There is no 'Availability Zone unreachable' mode to enter, no burst of millions of DNS record updates to grind through. The system in fact does slightly LESS work, because some of the redundant checkers were themselves in the failed zone.

Where it does NOT fit, stated by the author: fleets where elastic scaling saves real money — a website needing 100 web servers at peak and 50 off-peak should scale rather than pin at 100. He adds a second argument for scaling there that is easy to miss: the daily scaling exercise itself shakes out problems, so the dynamism has value.

Two notes on interpretation. O(1) here means a CONSTANT number of operations regardless of input size, not a small number — both examples do many thousands of operations per tick; O(C) would be the honest notation. And constant work is bounded, not infinite: sizing comes from a cellular design where the sustainable number of units per cell is measured and a new cell is added as the limit approaches.
