# Once agent workers outnumber the service they poll by 100:1, invert the direction — let the small fleet set the pace, or put a hyperscale store between them

Amazon's stated threshold: pay attention when clients outnumber a service by a factor of 100 or more. Below that, the obvious direction — many workers periodically calling a small control service — is the simpler architecture and has real availability advantages: each worker initiates, so the service keeps no inventory of them, answers from its datastore, and forgets. Above it, that direction is fragile for a specific reason: in steady state the calls arrive uncorrelated and the load is smooth, but any small environmental change makes the clients act in a CORRELATED way and issue concurrent requests together. Past the breaking point goodput does not degrade, it drops to zero. The three named triggers are a client-side code or config bug that raises call frequency, recovery from an outage where every client reconnects at once, and a few failures whose retries generate the load that generates more failures.

The agent version of this shape is everywhere: a fleet of agent workers polling a service for the current system prompt, tool/skill registry, model routing policy, feature flags, or per-tenant configuration; workers pushing traces, token metering, and run state back to a collector. The fan-in ratio is exactly the 100:1 case, and 'everyone restarted at once and re-fetched config' is the most common agent-fleet outage-recovery pattern there is.

The remedies, in Amazon's order of preference:

1. **Interpose a hyperscale store.** The control service periodically writes computed configuration to S3; workers poll the object and cache locally. Workers write their operational state to a bucket the control service polls. Simple, scales to the largest client fleets, keeps the control fleet small as the worker fleet grows. AWS Hyperplane (behind NLB, NAT Gateway, PrivateLink) does exactly this: a periodic task scans DynamoDB config and writes S3 files the data plane downloads.
2. **When (1) does not fit, invert the call direction** so the small fleet pushes to the large one at its own pace. An overloaded or underscaled control fleet then just goes SLOWER instead of falling over. Costs: it must maintain an inventory of all workers, handle the ones that are unreachable, and guarantee every worker is covered by exactly one control server without any control server taking too many — typically consistent hashing over a membership list built from heartbeats in a shared store (DynamoDB), which is close to leader election in complexity.
3. **Decouple the direction of DISCOVERY from the direction of CONTROL FLOW** — the version that avoids all three costs above. Each worker opens a long-lived connection to one control server (through a load balancer); the control server then drives API calls down that connection, HTTP-server-push style. Busy control servers simply reject the connection and the worker tries another; same on disconnect. No inventory, no consistent hashing, no distributed algorithm — every decision uses local state only. The price is a more sophisticated protocol between the two sides.
4. **At 1000:1 or worse, make the initial contact cheaper than a connection.** Workers send a small UDP packet and wait for the control plane to open the connection, because TCP plus TLS handshake cost alone can overload the small fleet when everyone reconnects at once. Amazon EC2 control planes use a variation of this to push configuration to Nitro.

The boundary conditions for option 1, which are the ones that force you up the ladder: it fails when the configuration is large and CONSTANTLY changing so recomputing and republishing the whole thing is impractical (Amazon's example is EC2 itself — instances, VPCs, IAM roles, EBS volumes all churning), and it fails when changes must reach the fleet in single-digit seconds (their example is telling a server to start a container). For agents: a slowly-changing skill catalogue or routing policy fits option 1 comfortably; live per-run interrupts, cancellations, or steering do not.
