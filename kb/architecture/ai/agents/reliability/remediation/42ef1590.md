# Removing a sick worker and routing around one fail in OPPOSITE directions — health checks over-remove, load balancers and queue pollers under-remove

Two families of mechanism respond to a sick worker: REMOVAL (a health check takes it out of service) and ROUTING (a load balancer or queue poller decides where work goes). They express the same intent at different layers, and the pack's evidence is that they fail in OPPOSITE directions. A fleet with only one of them has a known, predictable failure shape.

REMOVAL OVER-REMOVES, and does it hardest exactly when you need capacity.
- Health-checking a dependency converts a soft dependency into a hard one. If there is no fail-open protection, the dependency going down takes your service down too — a cascading failure with larger scope than the original fault. For agents this is acute because so many tools are optional: putting a model provider, MCP server, or vector store into a readiness probe means a provider blip drains every worker simultaneously, since dependency checks fail in a CORRELATED way across the fleet.
- Under overload a worker fails its health check by being too BUSY to answer the ping within its timeout — CPU contention, GC pauses, or no free worker threads — not by returning errors. Removing it during a surge shrinks the fleet, pushing more load onto the rest, which brown out and fail their own pings. The concrete fix is to size the worker pool LARGER than the proxy's max-connections (Amazon sizes it "anywhere from a handful of extra workers to double the configured proxy max connections") and to always admit health checks while rejecting normal requests past a threshold. The priority statement behind that is stronger than an exemption: the load balancer's ping is the single most important request the server receives, because failing it removes the server and leaves it idle, so the ping sits at the TOP of the shedding priority order, above every piece of real work — not merely outside the shedding rules.
- The reason over-removal is a FLEET event rather than a server event is a separate established mechanism: identical replicas running identical software do not fail independently, and an evenly distributing load balancer is what makes the failure simultaneous. Replica count therefore buys throughput and close to no protection against a shared limit — the same provider quota, the same context ceiling, the same tool timeout — which is exactly the class of thing a dependency check tests. Independence has to be bought with diversity, shuffle sharding or jitter; it does not come with the replica.

ROUTING UNDER-REMOVES, and actively prefers the sick node.
- A least-outstanding-requests balancer routes to whoever has fewest requests in flight. A failing server returns errors almost instantly, so its in-flight count drops and the balancer concludes it is the healthiest node. The amazon.com catalog outage is the documented instance: one server with a full disk began returning EMPTY responses very fast, the balancer noticed only that it was faster than its peers, and steered a large share of all site traffic into it. Note the trigger need not be an error status — any degraded-but-fast path, including a success-coded empty result, does this.
- A queue-polling worker has NOTHING external deciding whether it should keep working. It pulls messages as fast as it can and fails them all, out-competing healthy workers because failing is fast. Amazon notes this is HARDER to fix than the balancer case precisely because there is no routing layer to correct.

THE RULE THIS GIVES YOU: pair the two, and check which direction your specific stack errs in.
- If work arrives via a load balancer, restrict fast-acting removal to LIVENESS and LOCAL checks only (disk, child processes, support daemons — things that cannot fail fleet-wide at once), and hand dependency checks and anomaly detection to a slow, rate-limited central actor that escalates to humans. The stated principle: stop sending traffic to ONE bad server, but keep sending traffic when the WHOLE fleet looks sick.
- If work arrives from a queue, the worker must gate its own POLLING on a health check, not just its request handling. 'Should I take another job' is the decision a balancer would otherwise make for it.
- Either way, check what your router actually measures. Round-robin and connection-count balancers do not have the fast-failure inversion; least-outstanding-requests and latency-aware ones do. Where you cannot change the router, slow shed responses to match the latency of successful ones so the in-flight signal stays honest.

THE AGENT-SPECIFIC SHARPENING: agent request handling is long-lived — a single turn can occupy a worker for minutes across many model round-trips — so worker pools are small and saturation is the NORMAL state under load rather than an exceptional one. That makes the over-removal failure more likely than in a conventional service, and it is why the readiness path must be kept off any code path that calls the model. On the routing side, the agent version of the fast-empty-response is a worker returning truncated, refused, or zero-token completions quickly: it looks like the best endpoint to a latency-aware router, and nothing in the routing layer inspects whether the completion was useful.

WHAT THIS DOES NOT MEAN: not an argument to remove health checks or to distrust routing. Both are necessary; the claim is that each has a characteristic error direction, and a design that installs one without the other inherits that direction uncorrected. Scope conditions from the sources carry: fail-open (the balancer allows traffic to everything when ALL servers report unhealthy, supported by AWS NLB, ALB and Route 53) is the mitigation that lets you keep deep checks, but Amazon is sceptical of it because they have no general proof it triggers correctly for every kind of overload, partial or gray failure — and a dependency that is merely SLOW or failing at a low rate makes servers flap in and out of service without ever crossing the fail-open threshold. Test that partial-failure case specifically if you rely on it. For the queue case, verify you actually have the compensating factors rather than assuming them: visibility-timeout redelivery means messages are not lost but end-to-end LATENCY rises, so the symptom is a latency and redelivery-count problem that error-rate alarms will not catch, and the processing-error alarm must be reported by the QUEUE service rather than by the worker, since a worker broken enough to black-hole is often too broken to report itself.

A THIRD DIRECTION THE TWO-WAY FRAMING LEAVES OUT: THE HEALTH SIGNAL CAN FREEZE. The standard way to keep ping responses fast while still running deep checks is a background thread that probes dependencies and updates an isHealthy flag, with the ping handler only reading the flag. That also puts a constant, predictable load on the dependency instead of one request per ping. The failure mode is the thread exiting: the server then stops noticing failures AND stops noticing recoveries, holding whatever the flag last said. A frozen-healthy server is an under-removal failure and a frozen-unhealthy one is an over-removal failure, so this single defect can present as either direction, and neither pairing rule above detects it. Monitor the prober's own liveness, not only what it reports.

PACK ANALYSIS, FROM TWO OF THE FACTS THIS STANDS ON: ONE OBSERVATION IS READ WITH OPPOSITE SIGN BY THE TWO TIERS. Fleet anomaly detection lists a server "responding FASTER than peers" as a sickness signal, on the reasoning that it is probably returning false responses. A least-outstanding-requests or latency-aware router reads the identical observation as a health signal and sends that server more work. The same measurement is therefore evidence of sickness at the monitoring tier and evidence of health at the routing tier, and in a stack that has both, the router acts on it in milliseconds while the monitor acts on it in minutes. That is the mechanism behind the catalog outage rather than a coincidence of it, and it means the pairing rule needs an ordering as well: where a router optimises on latency, the latency-based sickness signal must be able to remove a server faster than the router can reward it.

ONE PRECONDITION THAT GENERALISES BEYOND THE QUEUE CASE. The rule that a processing-error alarm must be reported by the queue service rather than by the worker is a specific instance of a general one: fleet-level detection requires the error to be reported by something other than the server being judged — load balancer access logs or client-side instrumentation — because a server broken enough to matter often cannot self-report. Anomaly detection also assumes the servers are doing approximately the same work on homogeneous hardware; explicit routing of different traffic to different workers breaks outlier detection, so a fleet that routes by task type has to collate its comparisons accordingly.
