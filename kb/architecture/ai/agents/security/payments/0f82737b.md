# Keep the payment credential out of the model's context entirely — private sandbox file for one command, deleted after use, only a public summary returned

From the same Restock walkthrough (a Slack agent paying through Stripe's Link wallet over MPP): the model never sees card data, and the mechanism is specific enough to copy. The authorization side of the same design — what the human's approval does and does not bind — is at [[4e68d2a0]].

**THE MECHANISM.** The user's wallet session is held in a user-owned Connection and placed into the sandbox only while a command runs. "The payment tool reads the token from a private sandbox file, deletes it after use," and only a public summary of the result is returned into the model's context. On the delivery address the source says only "The delivery address stays private." and does not say what it is withheld from, so take that as the address not entering the model's context and not as a claim about what the human reviewer is shown.

**WHY A FILE RATHER THAN A TOOL ARGUMENT OR A RETURN VALUE.** Anything that passes through the model's context has been published: it is in the transcript, it is in every subsequent prompt, and it is reachable by whatever gets injected into that context later. A secret handed to a tool as an argument, or handed back as a tool result, is not scoped to the one call that needed it — it is scoped to the rest of the session. Writing it to a path the tool reads directly, and deleting it on the way out, leaves the model orchestrating a payment it is structurally unable to make itself. The general form: a credential's blast radius is the context it entered, not the call that used it.

**COMPLETION IS THE COUNTERPARTY'S TO REPORT.** "count an order as placed only when the merchant says so". The agent's belief that it submitted an order is not evidence that an order exists, and a run that reports success on its own say-so is reporting its intent. Treat the external system's confirmation as the only completion signal for any action with an outside effect — the same discipline an at-least-once delivery path needs, for the same reason.

**SCOPE.** A stated design in a vendor build walkthrough, with one live hosted order reported. Nothing here is measured: there is no evidence offered about how often the file is left behind on an error path, which is the obvious place this pattern would fail in practice.
