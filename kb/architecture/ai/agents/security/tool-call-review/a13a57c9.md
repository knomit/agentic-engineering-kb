# A second-agent reviewer for tool calls ships fail-open and biased to allow — it is a friction reducer, not a boundary

Goose's adversary mode is a shipped implementation of the pattern people reach for after learning about prompt injection: a separate reviewing agent inspects each tool call against the user's original request and recent history, and blocks ones that look dangerous. Its stated purpose is to be "a second pair of eyes — protecting you in case the main agent is compromised, manipulated by a prompt injection, or simply doing something that doesn't match what you asked for." It is contextual review rather than pattern matching.

FOUR STATED PROPERTIES DECIDE HOW MUCH YOU MAY RELY ON IT, AND ALL FOUR CUT THE SAME WAY.

**It is fail-open.** "If the reviewer fails for any reason, the tool call is allowed through (fail-open)." That is an availability-over-security choice, and it means an attacker who can make the reviewer fail — or simply a flaky model endpoint — removes the control silently.

**It is tuned toward permissiveness on purpose.** The reviewer's guidance says "Err on the side of ALLOW — only block truly dangerous things" and, again, "Err on the side of ALLOW — the adversary should catch genuinely dangerous actions, not slow down normal work." The reasoning is that a noisy guard gets disabled and then protects nothing. Its miss rate is deliberately non-zero.

**Its default scope is ONE tool.** "By default, the adversary reviews `shell` — the tool that can execute arbitrary code." Everything else is unreviewed unless configured, which matters most for exactly the MCP-server tools a user added later and never thought about.

**The blocklist is a plain-language file the user owns, not enforcement code.** The behaviours commonly cited — exfiltrating data, destruction beyond project scope, installing malware, privilege escalation, downloading and executing untrusted remote scripts — are EXAMPLE RULES, not a fixed policy. The docs are explicit: "The rules in `adversary.md` are your policy, written in plain language", users are told to "tailor rules to your environment", and "An empty file uses sensible default rules similar to the example above." So the control's coverage is whatever prose someone wrote, interpreted by a model.

THE CONSEQUENCE FOR DESIGN: treat a reviewer agent as raising the cost of an attack and catching careless behaviour, not as the thing that makes an untrusted-content path safe. If the deployment has private data, untrusted content and an exfiltration channel at once, this control does not break the trifecta — it is another model that can be talked around, guarding one tool by default, judging against user-written prose, that defaults to yes when it breaks. UK AISI's independent red-teaming of production monitors at two frontier labs found vulnerabilities in every version tested and reports that where routing rules decide what gets reviewed, the winning attack is simply to avoid review — which is the same lesson arriving from the other direction, and it makes the one-tool default the most important line above.
