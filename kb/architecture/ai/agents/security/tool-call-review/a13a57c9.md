# A second-agent reviewer for tool calls ships fail-open and biased to allow — it is a friction reducer, not a boundary

Goose's adversary mode is a shipped implementation of the pattern people reach for after learning about prompt injection: a separate reviewing agent inspects each tool call against the user's original request and recent history, and blocks ones that look like exfiltration (posting to unknown URLs, piping secrets outward), out-of-scope destruction, malware installation, obfuscated code, unnecessary privilege escalation, or downloading and running untrusted remote scripts. It is contextual review rather than pattern matching, and its threat model explicitly assumes the PRIMARY agent is already compromised.

Three stated properties decide how much you may rely on it, and all three cut the same way.

It is fail-open: if the reviewer errors for any reason, the tool call is allowed through. That is an availability-over-security choice, and it means an attacker who can make the reviewer fail — or simply a flaky model endpoint — removes the control silently.

It is tuned toward permissiveness on purpose. The reviewer's own guidance is to err on the side of ALLOW and block only clearly dangerous things, on the reasoning that a noisy guard gets disabled and then protects nothing. So its miss rate is deliberately non-zero.

Its default scope is two tools (`shell` and `computercontroller__automation_script`). Everything else is unreviewed unless configured, which matters most for exactly the MCP-server tools a user added later and never thought about.

The consequence for design: treat a reviewer agent as raising the cost of an attack and catching careless behaviour, not as the thing that makes an untrusted-content path safe. If the deployment has private data, untrusted content and an exfiltration channel at once, this control does not break the trifecta — it is another model that can be talked around, guarding a subset of calls, that defaults to yes when it breaks.
