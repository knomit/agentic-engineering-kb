# OWASP's agentic mitigations treat declared intent as a separate object to be validated — a signed intent envelope per execution cycle, and a policy gate that reads planner output as untrusted input

Most of the OWASP Top 10 for Agentic Applications 2026's per-entry mitigation lists are generic control checklists and below this pack's bar. Four named patterns are not, and they share a structure worth naming: **they check the agent's *declared intent* as an object distinct from the action it is about to take.** Ordinary guardrails ask "is this call permitted?"; these ask "does this call match the goal that was declared?" The unifying framing is this pack's; the document lists the patterns separately and never groups them.

**INTENT CAPSULE (mitigation 5 under ASI01, Agent Goal Hijack).** An emerging pattern that binds the declared goal, constraints and context to *each execution cycle* in a **signed envelope**, restricting run-time use. The signature is the point — it makes the goal that authorised a step tamper-evident at the moment the step runs, so a goal mutated mid-run by injected content does not silently become the authority for later tool calls. **Note the modality: the guide says to *evaluate use of* it and calls it emerging.** That is weaker than a recommendation, and it is recorded that way here deliberately; the document offers no implementation, no reference deployment and no measurement.

**INTENT GATE (mitigation 4 under ASI02, Tool Misuse and Exploitation).** Policy-enforcement middleware placed *before* execution that treats "LLM or planner outputs as untrusted". A PEP/PDP pair validates intent **and arguments**, enforces schemas and rate limits, issues short-lived credentials, and revokes or audits on drift. The load-bearing idea is the trust boundary: the planner is inside the system but its output is classified as untrusted input, so the gate sits between an agent's own two halves rather than at the system edge.

**SEMANTIC FIREWALLS (mitigation 7 under ASI02), the most concrete of the four.** Enforce **fully qualified tool names and version pins** to defeat tool-alias collisions and typosquatted tools; validate the *intended semantics* of a call — the guide's example is query type or category — "rather than relying on syntax alone"; and **fail closed on ambiguous resolution**, prompting the user to disambiguate rather than guessing. Name resolution as an attack surface is the same shape `78ab92f2` records for tool metadata: the agent selects on a string it did not verify.

**ADAPTIVE TOOL BUDGETING (mitigation 5 under ASI02).** Usage ceilings expressed as cost, rate or token budgets, with **automatic revocation or throttling** when exceeded — not merely alerting. A budget that only pages someone is not a containment control; the pattern's content is that the ceiling acts on its own.

**ONE MORE WORTH LIFTING, from ASI02 mitigation 2:** display a pre-execution plan or **dry-run diff** before final approval of high-impact actions. Approving a described action and approving a computed diff are different acts, and only the second shows the user what the agent actually resolved its arguments to.

**WHAT THIS SECTION DOES NOT GIVE YOU.** No incidents, no measurements, no deployment reports — these are prescriptions. Confidence is set accordingly. Two are explicitly forward-looking, and an implementer should treat "intent capsule" as a design direction rather than a shippable control.
