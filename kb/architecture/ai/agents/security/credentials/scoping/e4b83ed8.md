# Hold the human's VCS token in a proxy outside the sandbox and mint the agent a credential that can push only to its own working branch — and keep secrets out of environment variables, which every user of the environment can read

The shipped design for Claude Code's cloud sessions keeps the user's GitHub token out of the execution environment entirely: a proxy holds it, and the session gets a short-lived credential that can push only to its own working branch. The agent therefore has exactly the write capability its task needs — one branch it owns — and the compromise of a session yields a credential that cannot reach the default branch, another session's branch, or any other repository.

The second half of the pattern is the part teams get wrong. Environment variables on a shared agent environment are visible to anyone who uses that environment, so they are configuration, not a secret store. A credential placed there is as exposed as the environment's membership is wide, and no sandboxing of the VM changes that.

Two design rules follow. Hold the broad, long-lived credential in a component the agent cannot read, and hand down a derived credential scoped to the single resource the task writes and expiring with the session. And route secrets through a mechanism that attaches them to outbound requests outside the sandbox, rather than through anything the agent or its environment's other users can enumerate.

What this does NOT mean: the point is not that short-lived credentials are safe and long-lived ones are not. A short-lived credential with broad scope is still a full compromise for its lifetime; the load-bearing property here is the narrowness of what it can write, with expiry as the second line.

A second vendor documents the same architecture from the opposite direction, starting from what it concedes rather than what it provides. OpenAI's Agents API sandbox-security guidance states flatly that agent-generated code can access the files, credentials, and network available to its environment, that agent-generated code can read the environment key, and that injecting a stored secret into the environment still exposes it to agent-generated code. Its answer for hosted sandboxes is the placeholder: sandbox code uses a placeholder and a network proxy supplies the real secret for approved hosts. Its answer for the one credential that must exist inside the environment is to make that credential worth nothing on its own — the executor's environment key "only permits connecting environments. It cannot authorize any other API action" — while the application key, which carries the scopes that do things, stays outside.

Two independent implementations therefore agree on the shape: no secret of value inside the execution environment, a proxy outside it holding the real credential and attaching it per approved host, and any unavoidable in-environment key reduced to a join token. The corollary is the test to apply to a design: ask what an attacker gets from full read access to the environment, since both vendors treat that as the expected case rather than the breach.

One asymmetry worth noting rather than smoothing over: on the OpenAI side, isolation of the execution environment is stated as a recommendation to the operator (run workloads in isolated compute, use separate environments for data that must not mix) and the hosted sandbox's own isolation boundary is not described, so the strength of that half is not established from this source.

OpenAI's self-hosted environment guide states the same split as a requirement rather than a recommendation, and names both halves. The application's `OPENAI_API_KEY` is kept outside the sandbox; the key that goes inside, as `CODEX_API_KEY`, is scoped to connecting environments and nothing else — "Set every other permission to **None**" — and must belong to the same organization, project and user or service account as the session. The guide's stated reason is the one this pattern is built on: agent-generated code inside the environment can read that key, so the mitigation is its scope, not its hiding place, though it must still stay out of source code, container images and logs.
