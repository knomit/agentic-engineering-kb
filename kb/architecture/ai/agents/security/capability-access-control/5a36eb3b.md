# Post-hoc unlearning suppresses a capability; routing it into a deletable module during pretraining removes it — and the measured gap between those two is the whole argument

Anthropic's Alignment Science team reports a pretraining-time construction for capability-level access control, "Gradient-Routed Auxiliary Modules (GRAM)": small auxiliary modules are added at every MLP layer, one per specialised dataset, and gradient routing updates the auxiliary weights preferentially when the model trains on that dataset — sometimes freezing the general-purpose weights entirely. "At inference, deleting a module removes the capability."

The framing it starts from is the reason this matters to anyone building a tiered product rather than a frontier model: refusal training and classifiers are behavioural layers sitting on top of knowledge the model still has, so they are jailbreakable by construction, and the usual alternative — route the untrusted user to a smaller model — trades every capability at once instead of the one you wanted to withhold.

**The result a builder should carry away is the comparison between removal methods, not GRAM itself.** Ablating GRAM's modules, or deleting LoRA's adapters, removes the capability about as effectively as never having trained on the data. Post-hoc unlearning does not: "In contrast, MaxEnt, an unlearning method used to modify pre-existing models, recovers to near the performance of the all-data baseline indicating that MaxEnt does not truly remove capabilities but instead learns to suppress them." Filtering, LoRA and GRAM were all robust to malicious fine-tuning; MaxEnt was not. So an unlearning step applied to a finished model is a suppression layer with the same jailbreak surface as a refusal, and the only methods that survived a fine-tuning attack were the ones that decided at or before pretraining where the capability would live.

**The economics are what make it an architecture choice rather than a research curiosity.** "GRAM produces all five from one run and switches between them by deleting weights at inference. Filtering needs five training runs to produce these five configurations. GRAM and LoRA track filtering at every scale and both require only a fifth of filtering's training compute." And it composes: "Composability multiplies the payoff of a single run: four GRAM modules give sixteen possible configurations, where filtering would need sixteen different runs." Where GRAM beat LoRA was composability and partial labelling — LoRA degraded across categories once all adapters were active, and GRAM isolated better when only half the training data carried labels.

**Scope, and it is narrow in three directions that a one-line summary drops.**
- The removed capability was a thin slice of training: "We train 800M-parameter models on web text, code, and scientific papers, plus four dual use domains: virology, cybersecurity, nuclear physics, and specialist code. The dual use data is a small fraction of training: 16B general tokens against roughly 40M per risky domain, about 0.25% each." Nothing here establishes the behaviour when the capability to be withheld is a large fraction of the corpus.
- Scaling was tested to 5B parameters: "Can this actually work in production? Our scaling experiments show clear trends up to 5B parameters, but we didn't verify whether these trends continue at frontier scales or hold in a production setting." The post states the research is preliminary and has not been applied to Anthropic's production models, and names instruction-tuning a GRAM-trained model as an open problem.
- All its performance figures are in "Compute Ratio, a compute-adjusted version of loss" — relative to a baseline, not absolute capability levels — and the evaluations were loss-based only.

**What this does NOT mean.** It is not a jailbreak defence for the capabilities a shipped configuration retains; it relocates which capabilities are present, and everything still present is still reachable by the usual behavioural attacks. It is also not a runtime control: the access tier is chosen by which weights you ship, so it is a build-and-deploy artifact, not a per-request decision, and a system needing per-request capability gating still needs a permission layer in front of it. And the clean separation is conditional on the capabilities actually being separable — "Some general capabilities (like knowledge of biology), might be so closely related to dual use capabilities (like virology), that there is no way to cleanly separate them."

Pack analysis: this is the same shape as [[control-substitution]] from the other end. There, a control scoped to one workload class redirected the activity instead of reducing it; here, a control applied after training suppresses the capability instead of removing it. Both say that where in the pipeline a control sits decides whether it bounds anything, and that a control measured only on the behaviour it was pointed at will look like it worked.
