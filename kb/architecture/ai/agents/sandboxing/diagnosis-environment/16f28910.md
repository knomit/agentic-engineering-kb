# Give a diagnosing coding agent a writable worktree and mount the evidence it is diagnosing read-only — the production traces are the thing it must not be able to edit

In the Tax AI self-improvement loop, the Codex task environment is split by writability rather than by directory convenience. The post states that "A bounded Codex task environment separates the writable worktree [1] from read-only production context [5]," and that the read-only mount lets Codex investigate "without mutating the underlying evidence."

What goes in each half follows from what the agent is for. Writable: the scoped product code, the eval suites, and the docs and skills the agent may extend. Read-only: the production traces, the source documents, the agent's own earlier predictions, the finalized returns, and the tax-engine documentation. The agent's job is to explain a discrepancy between a prediction and a filed value, so the prediction and the filed value are exactly what it must not be able to rewrite.

The operational consequence: when an agent both diagnoses and fixes, decide the mount mode per path from whether that path is evidence or product. An agent that can edit the trace it is reasoning from can make a failing case pass without changing behaviour, and the resulting green eval is indistinguishable from a real fix.

WHAT THIS DOES NOT MEAN: read-only is not a security boundary against a hostile agent here — it is an evidence-integrity measure in a loop whose output is a proposed pull request that humans and a regression suite then validate. Nor does it mean the eval suite should be read-only: in this design the agent is expected to add evals, so the suites sit on the writable side, which is also why the suites alone cannot be the only check on the agent's work.
