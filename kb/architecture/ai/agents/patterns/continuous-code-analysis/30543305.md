# OpenAI's vulnerability-hunting agent builds the repo threat model once and evaluates every commit against it — then tries to trigger each finding in a sandbox before reporting it

Aardvark (announced 2025-10-30, powered by GPT-5) is an agent that watches repositories for vulnerabilities. "Use an agent to find bugs" is not the interesting part; three structural decisions are, and they transfer to any agent that must reason continuously over a codebase too large to fit in a context window.

**1. THE THREAT MODEL IS A DURABLE ARTIFACT, NOT A PER-CALL PROMPT.** The first stage analyses the *entire* repository "to produce a threat model reflecting its understanding of the project's security objectives and design". Every subsequent scan inspects **commit-level changes against the entire repository and that threat model**. When a repo is first connected it back-scans history.

   This is the general answer to repo-scale context: you cannot re-read the codebase on every commit, so you distil it once into a compact standing artifact and evaluate *deltas* against it. The expensive whole-corpus pass is amortised; the per-event pass is a diff. Note what this buys beyond cost — a diff judged against a threat model can flag a change that is locally innocuous and only dangerous given the project's security objectives, which a diff judged on its own text cannot.

**2. IT DELIBERATELY DOES NOT USE THE STANDARD SECURITY STACK.** "Aardvark does not rely on traditional program analysis techniques like fuzzing or software composition analysis." It substitutes LLM reasoning and tool use — reading code, analysing it, writing and running tests. This is a stated architectural bet worth knowing as a bet: fuzzing and SCA have known coverage guarantees and known blind spots, and replacing rather than supplementing them trades one blind-spot profile for another that is much less characterised. OpenAI reports the trade favourably; no comparison against a fuzzing baseline is published.

**3. A VALIDATION STAGE SITS BETWEEN DETECTION AND REPORTING.** "Once Aardvark has identified a potential vulnerability, it will attempt to trigger it in an isolated, sandboxed environment to confirm its exploitability", and it "describes the steps taken" to support "accurate, high-quality, and low false-positive insights".

   This is the most transferable decision here: candidate findings are executed, not just argued for, and the reproduction steps travel with the report. **A scoping note, because the source does not go as far as one might assume:** the post says validation happens and is there to reduce false positives; it does **not** state that a finding which fails to reproduce is suppressed. Whether non-reproducing candidates are dropped, downgraded or still surfaced is unstated. Read this as *reproduce-then-report*, not as a proven gate — the gate reading is an inference and is flagged here as one. Either way it is the production cousin of the adversarial-verification pattern this pack records from the other direction in `11ebefd6` (verifiers defeated by design) and `a5ade87d` (verifier gaming).

**4. THE PATCH IS GENERATED BY A DIFFERENT SYSTEM AND THEN RE-SCANNED.** Fixes come from Codex, and the patch is "Codex-generated and Aardvark-scanned" before being attached to the finding for human review. Generation and checking sit on opposite sides of a component boundary rather than in one loop.

**NUMBERS, AND WHAT THEY DO NOT COVER.** On "golden" repositories it "identified 92% of known and synthetically-introduced vulnerabilities". Ten vulnerabilities found in open-source projects received CVE identifiers. Context figures given: over 40,000 CVEs reported in 2024, and OpenAI's testing shows "around 1.2% of commits introduce bugs".

   **Read the 92% carefully.** It is vendor self-report on a vendor-chosen benchmark; the denominator mixes *known* with *synthetically-introduced* vulnerabilities, and recall against synthetic injections is the easiest case in this domain. More pointedly, it is a **recall figure only** — no precision, false-positive rate, or alert volume is published, even though reducing false positives is the stated justification for the entire validation stage. The one quantity that would let a reader judge whether the sandbox-reproduction stage works is the one not reported. Treat the architecture as the takeaway and the 92% as unverified.
