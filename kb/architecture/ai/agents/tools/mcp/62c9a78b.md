# Code execution over MCP: load tool definitions on demand instead of all upfront

Connecting an agent to many MCP servers front-loads every tool definition into the context before the request is even read — "in cases where agents are connected to thousands of tools, they'll need to process hundreds of thousands of tokens before reading a request" — and then re-pays for every intermediate result as data passes through the model between tool calls.

The alternative Anthropic describes: present MCP servers to the model as code on a filesystem and let it write code that imports what it needs.

```
./servers/google-drive/getDocument.ts
./servers/salesforce/updateRecord.ts
```

with the model writing `import * as gdrive from './servers/google-drive';`. Models navigate filesystems well, so tool discovery becomes progressive disclosure — read the definitions relevant to this task, ignore the rest. Their reported case: "This reduces the token usage from 150,000 tokens to 2,000 tokens—a time and cost saving of 98.7%."

The second, less obvious win is that filtering and transformation happen in the execution environment, so intermediate results never enter the model's context by default. That is a privacy control as much as a cost control: PII can be tokenized — the model sees `[EMAIL_1]`, `[PHONE_1]` — so that "the real email addresses, phone numbers, and names flow from Google Sheets to Salesforce, but never through the model."

The trade is that you now need a sandbox with real isolation, and the model is writing code rather than emitting structured tool calls — more expressive, and correspondingly harder to constrain. This is worth it at many-tool scale and probably not at five tools.

VERIFICATION AND VERSION PIN (checked 2026-07-30): all four claims above re-verified verbatim against the source; no update notice on the page; published **4 November 2025**. That publication date matters, because the article predates the **MCP `2026-07-28`** revision and is written against the handshake-based protocol. Two things to hold:

- The pattern is **unaffected** by the rewrite. It operates above the protocol — it is about how tool definitions reach the model's context, not about how the client talks to the server — so statelessness, `server/discover` and the MRTR change do not disturb it.
- The **baseline it argues against has partly improved**, so re-measure before assuming the full 98.7%. `2026-07-28` requires `ttlMs`/`cacheScope` cache metadata on `tools/list` and asks servers to return tools in deterministic order specifically to raise LLM prompt-cache hit rates. Cached, cache-friendly tool definitions are cheaper than the uncached front-loading this article compares against — which narrows, without closing, the gap the technique exploits.
