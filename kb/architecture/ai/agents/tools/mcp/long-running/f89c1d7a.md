# MCP durable tasks left the core protocol for an extension — and the transport stopped pretending a held connection is durable

A tool that takes minutes — a build, a deep crawl, a long query — forces a choice between blocking the connection (fragile: any disconnect loses the work, and timeouts are set by whatever proxy is in the middle) or inventing your own job-handle convention (every server does it differently, so the model has to learn each one). MCP's answer is **tasks**: track durable requests with polling and deferred result retrieval instead of holding one request-response open for the lifetime of the operation.

**Where tasks live changed in revision `2026-07-28`, and this is a migration, not a detail.** Tasks were introduced as experimental core protocol in `2025-11-25` (SEP-1686). In `2026-07-28` they were moved OUT of the core protocol into an official extension, `io.modelcontextprotocol/tasks`, and redesigned (SEP-2663):

- The blocking `tasks/result` method is **gone**, replaced by polling via `tasks/get`.
- A new `tasks/update` carries client-to-server input into a running task.
- `tasks/list` was **removed** — you cannot enumerate tasks; hold your own handles.
- Servers may now return task handles **unsolicited**, without the client opting in per request. A client that assumed "I only get a task handle if I asked for one" will mis-parse results.

The practical consequence: tasks are no longer something you get by negotiating a core revision. They are an extension, declared through the `extensions` field on client/server capabilities, released on its own schedule. Detect it as an extension; do not infer it from the protocol version.

**The transport moved the same direction, harder.** `2025-11-25` (SEP-1699) let servers drop SSE streams at will and have clients resume via GET, with event IDs encoding stream identity. `2026-07-28` removed stream resumability outright: the `Last-Event-ID` header and SSE event IDs are gone, and **a broken response stream loses the in-flight request — clients MUST re-issue it as a new request with a new request ID.**

That last rule is where this intersects the rest of your design. Re-issuing a lost request under a new ID is a retry against a server that may already have executed it, so the protocol now pushes the at-least-once problem onto you at the transport layer. Any long-running or side-effecting MCP tool needs a caller-supplied idempotency key for exactly this case; the transport will no longer deduplicate for you, and the old resumability path that used to paper over it has been deleted.
