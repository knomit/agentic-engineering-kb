# Reach a private MCP server by having it dial out, not by exposing it: a customer-run client opens one outbound HTTPS connection and long-polls for work — but a private OAuth authorization server still has to be reachable by whichever component runs the flow

An MCP server holding internal data cannot be published to the internet, and a hosted agent product cannot route into a private network. OpenAI's documented answer inverts the direction of the connection so the private side never accepts inbound traffic: "Customers run a small client inside their private environment that establishes an outbound HTTPS connection to OpenAI." The hosted tunnel service queues requests for that tunnel; the client picks them up, forwards them to the approved local MCP server, and returns responses along the same connection.

THE PIECES. A customer-run, open-source tunnel client inside the trust boundary (with health checks, readiness, logs and a local admin UI); an OpenAI-hosted tunnel endpoint and control plane that the client authenticates to, scoped to the customer's organization, workspace context and a configured tunnel identity; the private MCP server, left behind the network controls it already has. Transport is outbound HTTPS with long-polling, chosen for backpressure — "Long-polling lets the tunnel client ask only for the amount of work it can process" — and the path forwards streaming: "the tunnel can forward intermediate server-sent events." The client can be configured with "custom CA bundles, proxy settings, and MCP-side mTLS."

THE SHARP EDGE, AND IT IS THE PART A READER WILL GET WRONG. Making the MCP server reachable through the tunnel does not make its dependencies reachable. OAuth discovery for the MCP server travels through the tunnel path, but the authorization server does not automatically: "If an authorization server is private, it must still be reachable by the component performing the OAuth flow." An internal identity provider that only the private network can resolve will therefore break a setup whose MCP hop works perfectly.

WHAT THIS DOES NOT MEAN. The tunnel is "a narrow path to configured private tools, not a general-purpose network bridge" — so it is not a VPN, and it does not make arbitrary internal hosts callable. The companion REST extension (Harpoon) reaches only targets the customer registers by label, bounded by "customer-owned target registration, allowed methods, response-size limits" and further timeout, redirect and access controls; none of those limits is given as a number in the source, so do not assume a default. Ports, timeout values and OAuth scopes are not stated.
