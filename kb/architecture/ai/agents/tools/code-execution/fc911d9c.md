# Programmatic tool calling keeps intermediate tool results out of context by running model-authored code in a sandbox

Both OpenAI and Anthropic now ship the same inversion of where the agent loop runs. Instead of the model emitting one tool call, seeing the result, and deciding again, the model writes code that orchestrates many tool calls — with real loops, conditionals and intermediate processing — and that program executes in a sandbox. Only the program's final output enters the conversation; intermediate tool results never reach the model's context at all. OpenAI's runtime is a hosted V8 (JavaScript); Anthropic's is Python, with tools opting in via `allowed_callers: ["code_execution_20250825"]`.

That is the whole point, and it names the condition where it wins: a task that needs a SEQUENCE of related tool calls, or that must reduce a large tool output before anything useful can be said about it. Fetching 500 rows to compute one aggregate is the canonical case — direct calling pays for all 500 rows in context and again on every subsequent turn; the program pays for the aggregate.

Anthropic's published measurements on their implementation: a complex research task fell from 43,588 to 27,297 tokens (about 37% fewer); knowledge retrieval accuracy rose from 25.6% to 28.5%; GIA benchmark scores rose from 46.5% to 51.2%. Note the accuracy gains are modest — the dominant benefit is token and context economy, not capability.

Where it loses is equally explicit, and both vendors say direct calling remains the recommended baseline: single-tool invocations, and adaptive search where the model genuinely needs to re-evaluate after each result. Anthropic adds the case where Claude SHOULD see and reason about all intermediate results — hiding them is precisely wrong there. If the control flow cannot be written down in advance, writing it as code just produces a program that guesses. Anthropic's stated trigger for reaching for it is multi-step workflows with three or more DEPENDENT tool calls, large-dataset aggregation, wide parallel operations (their example is checking 50+ endpoints), and filtering or transforming results before the model sees them.

The constraints are sharp and worth knowing before you design around it. OpenAI's runtime is fresh and isolated per program — no Node.js, no package installation, no network, no filesystem, no console, and no persistence between programs. Client-owned functions still execute in YOUR application, so their results must be fed back to the running program explicitly rather than simply returned. MCP tools carrying a `require_approval` policy pause the program mid-execution pending authorization, so an approval gate you added for safety becomes a latency cliff inside a loop. Deferred tools are invisible to a program — the model has to load them first. With `store: false` you must replay every output item, including program and reasoning items.

The honest caveat both include: the token saving depends on the task, and is not guaranteed.
