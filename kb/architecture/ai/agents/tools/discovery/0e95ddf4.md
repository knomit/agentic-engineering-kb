# OpenAI's tool search has two modes, and the client-executed one moves the tool catalogue inside your trust boundary — only tools returned in tool_search_output are callable

Deferred tool loading on OpenAI's Responses API is marked per tool with `defer_loading: true` (for an MCP server the flag goes on the server tool definition). With namespaces the flag applies to the functions inside the namespace rather than to the namespace object, and a namespace may mix deferred and non-deferred tools. At the start of a request the model sees only the name and description of each namespace or MCP server; for an individual deferred function it still sees name and description, and what tool search defers is mainly the parameter schema. Support is gated by model: in the Responses API only models from "gpt-5.4 and later" support `tool_search`.

There are two modes and they differ in who holds the catalogue.

**Hosted.** OpenAI searches the tools you already declared and returns the loaded subset in the same response; the model can load several namespaces in one search call. Use it "if the candidate tools are already known" when the request is created.

**Client-executed.** The model emits a `tool_search_call` and stops. Your application performs the lookup and returns a `tool_search_output`, echoing the `call_id`. Use it when discovery "depends on project state, tenant state, or another system" your application controls.

Two consequences of the client-executed mode that matter more than its mechanics. First, availability is exactly what you returned: tools loaded through `tool_search_output` stay callable in later turns, and tools not listed there are not available — so a bug in your lookup presents to the model as a capability that does not exist, not as an error. Second, you are now the component that decides which tool definitions enter the model's context, which makes the catalogue a prompt-injection surface if any part of it is attacker-influenced; the guide marks returning tools that were not in the original request as an "advanced workflow" and says to validate schemas and "only expose trusted tool definitions".

Two configuration rules from the same source. In the Agents API, mixing eager and deferred functions is "supported but generally not recommended". Also in the Agents API, MCP tools are discovered automatically where the model and provider support it, so adding `tool_search` for them is unnecessary.

The cost side of this choice — the break-even point below which deferral loses money, and what it does to the prompt cache — is in [[0915b0a2]] and [[68d5055b]].
