# Pruning retrieved documents mid-search beats accumulating them — and a 20B model TRAINED to do it approaches frontier retrieval

Chroma's Context-1 is the constructive follow-up to their own context-rot finding: rather than accepting that performance degrades as retrieved documents accumulate, train the search agent to actively DISCARD irrelevant results mid-search to free capacity and reduce noise for further exploration.

The architecture is worth copying even without their model, and the shape of it is three escalating pressures rather than one limit. The harness states the first: "we bound the context window to a fixed token budget." Token usage is displayed after every turn, so the agent always knows its remaining capacity. At a soft threshold "the harness injects a response message suggesting the model start to prune chunks". Past a hard cutoff, "all tool calls except prune_chunk are rejected outright", "returning an error message directing the model to prune or conclude" — stated again as "the hard cutoff restricts the agent to pruning or concluding." That graduated soft-then-hard constraint is the transferable part: the agent is told the budget continuously rather than discovering it by hitting a wall.

A TRAP IN THE SOURCE, AND IT COSTS YOU THE NUMBERS. The page's served prose has its budget figures stripped out — it reads "bound the context window to a fixed token budget .", "When usage exceeds tokens," and "Beyond a configurable cutoff in between and tokens". So neither the budget nor the soft threshold can be read verbatim from the prose. Two numbers survive elsewhere and they do not agree: an inline example line reads "[Token usage: 14,203/32,768]", while the Results section's prose says "we give these models a token budget of 200k tokens (as opposed to 24k tokens)", attributing 24k to Context-1. Do not cite a budget figure for this harness from this page; cite the mechanism and leave the number out.

The training detail that makes it learnable: pruning removes chunks from the model's view but PRESERVES the full unpruned trajectory for reward computation. The reward credits the agent for encountering relevant documents during search regardless of whether they survive into the final output. Without this the agent is punished for discarding a document that turned out to matter, and learns to hoard. Separating what the model sees from what the reward sees is the trick.

Measured against its own base model (gpt-oss-20b): trajectory recall 0.640 → 0.739, output recall 0.361 → 0.641, prune accuracy 0.824 → 0.941, parallel tool calls per turn 1.52 → 2.56. As a 4x ensemble Chroma reports it matching or exceeding Claude Opus 4.6 on web, finance, legal, and email retrieval: "when run in a 4x parallel configuration, it does so while remaining cheaper than a single call to those models", with the abstract claiming "up to 10x faster inference speed". THE COMPARISON IS NOT BUDGET-MATCHED, and the page says so plainly — "we give these models a token budget of 200k tokens (as opposed to 24k tokens)". The frontier models were run with roughly eight times the context budget, which cuts both ways: it is not a like-for-like harness comparison, and the trained model's result is obtained from far less context than its competitors were given. Models benchmarked against include gpt-5.2, gpt-5.4, sonnet-4.5, sonnet-4.6, opus-4.5, opus-4.6, gemini-3.1-pro and kimi-k2.5.

SIZE IS NOT WHAT DOES THE WORK — read the numbers carefully, because this is easy to misread as 'a small model is enough'. The UNTRAINED base gpt-oss-20b is nowhere near frontier: on their web benchmark at Difficulty 2+ it reaches 0.58 Final Answer Found against 0.95–0.99 for frontier models. The trained Context-1 derived from it reaches 0.88, and 0.97 in the 4x ensemble configuration. So the result is about task-specific RL training for context management, not about parameter count. Do not conclude that swapping in an off-the-shelf 20B model will get you retrieval parity; it will get you 0.58.

The design position, contrasted with the alternatives they name: this is DOCUMENT-LEVEL RETENTION, not summarisation. Unlike ReSum-style lossy summarisation it never rewrites evidence, and unlike MemGPT-style external paging it does not need a memory tier — kept documents stay verbatim, discarded ones are simply gone. If evidence fidelity matters (legal, finance, anything you must cite), prefer discarding whole documents over compressing all of them.

Source caveat: Chroma sells retrieval infrastructure and this is their own model evaluated by them. The architectural pattern and the prune-vs-summarise position are the transferable parts; treat the ensemble-beats-Opus claim as vendor-reported.
