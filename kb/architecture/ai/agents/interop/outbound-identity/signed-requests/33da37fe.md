# Signed agent requests are in production, not early-stage: Cloudflare verifies RFC 9421 signatures with Ed25519 against a JSON web key set at /.well-known/http-message-signature-directory — while the agent-identity layer above the RFC is still an IETF draft

Cloudflare's own announcement (byline **July 1, 2025**) is the primary account of cryptographic request signing for agent identity actually being verified in production by a major bot-mitigation provider, and it supplies the literals that secondary guidance does not.

**WHAT IS DEPLOYED.** "Starting today, Cloudflare is ramping up verification of cryptographic signatures provided by automated crawlers and bots." The purpose: "a way for developers of bots, agents, and crawlers to clearly identify themselves by cryptographically signing requests originating from their service." Coverage is staged, and this is a compound condition to quote whole: "This is currently available for all Free and Pro plans", and it "will be released to all Business and Enterprise plans" later. So "Cloudflare verifies signatures" was not true of every zone on the announcement date.

**THE EXACT MECHANICS.** The edge "checks for the `Signature`, `Signature-Input`, and `Signature-Agent` headers." It then "checks that the incoming request presents a `keyid` parameter in your Signature-Input that points to a key we already know", and "attempts to verify the signature base against the value in Signature field using an ed25519 verification algorithm" — Ed25519, linked to RFC 9421's own section. The bot side publishes its key at a literal path: "Host a JSON web key set containing your public key under `/.well-known/http-message-signature-directory` of your website." That URL is then registered: "Register that URL with us, using our Verified Bots form." Signatures carry an expiry and "If the current time is after expiration, verification fails", which "guards against replay attacks". Two open-source implementations exist — "two open source libraries: a web-bot-auth library in rust", plus an npm package of the same name — and requests carry `tag="web-bot-auth"` in the Signature-Input.

**THE FAILURE DIRECTION, AND IT IS THE DESIGN DECISION TO NOTICE.** "If any of the above steps fail, Cloudflare falls back to existing bot identification and mitigation mechanisms." A broken, expired or unregistered signature therefore does not get you blocked — it gets you treated as an unsigned bot, which is the weaker prior regime. Cloudflare names this as temporary: "As the system matures, we would strengthen these requirements, and limit the possibilities of a soft downgrade." The consequence for a bot operator is that signing failures are *silent*: you keep working, worse, with no error to alert on, so monitor your own signature-verification rate rather than waiting for a block. The consequence for a site operator is the reverse — a fail-open verifier gives an attacker no reason not to send a malformed signature. What a *successful* verification buys: "Verified Bots and other systems at Cloudflare use a successful verification as proof of your identity, and apply rules corresponding to that identity."

**THE LAYER SPLIT, which is where a maturity judgement has to land.** The signing primitive is settled — "the IETF standardized it as part of RFC 9421" — and "HTTP Message Signatures is a primitive that is useful beyond Cloudflare." The agent-identity conventions layered on it are not: Web Bot Auth is an Internet-Draft (`draft-meunier-web-bot-auth-architecture`, linked at revision -02), "the IETF is considering forming a working group around Web Bot Auth", and "The specifications for the protocol are being built in the open, and they have already evolved following feedback." Build against the RFC and the well-known directory path with confidence; expect the directory format, the Signature-Agent conventions and the registration flow to move.

**ONE THING THIS SOURCE DOES NOT SAY.** mTLS is NOT PRESENT anywhere in the post. Guidance that pairs HTTP Message Signatures with mTLS for production bot verification is not resting on this account. Nor is the well-known path in [[0720e9d7]]'s OWASP extract (`/.well-known/agentpublic-key.json`): the deployed directory path is the one quoted above, and the two are not the same string.
