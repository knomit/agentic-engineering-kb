# A browsing agent needs an outbound identity or it gets classified as a bot — and the three available mechanisms differ sharply in maturity

Almost all agent-identity discussion is inbound — how your system authenticates an agent that arrives. OWASP's securing-agentic-applications guide covers the direction most builders hit first in production and plan for last: **how your agent identifies itself to the arbitrary third-party sites it browses**, so that bot-mitigation platforms let it work instead of blocking it. This is a functional requirement, not a compliance one; an agent that cannot establish itself as good automation simply stops being able to reach the web.

**THE THREE MECHANISMS, with the guide's own maturity assessment — which is the useful part, because they are not interchangeable today.**

*Stable network and user-agent metadata.* Serve from a documented IP range with a verbose User-Agent, optionally adding an `X-AI-Agent` header and an agent-ID/signature header, so mitigation systems can correlate requests with the cryptographic identity. OWASP rates this good but not enough — the proven approach for well-behaved bots for a decade, but not bulletproof, because IPs are shared and user-agent strings are spoofable. It is a correlation aid, not proof.

*Cryptographic request signing.* Sign every HTTP request using RFC 9421 HTTP Message Signatures and expose the verification key at a well-known path under `/.well-known/`. This is the one that actually prevents spoofing and machine-in-the-middle, since keys cannot be forged without compromise. OWASP marks it early-stage and the guide notes HTTP Message Signatures combined with mTLS is already used for production-grade bot verification — but that label does not survive the primary source: Cloudflare was verifying RFC 9421 signatures at its edge from July 2025, the same month this guide published. Build on this one now, with [[33da37fe]] for the deployed mechanics; the layer split that the "early-stage" label really describes is in the caveat below.

*Agent Name Service (ANS).* Publish an ANSName encoding protocol, capability, provider and version, and register the name plus public key in an open agent registry, giving PKI-backed lookup that prevents collisions and impersonation. Spec v1.0 is published with pilot registries and tooling emerging — so this is the intended endpoint of the design, not something to depend on yet.

**DECLARE INTENT, NOT JUST IDENTITY.** The guide's second rule is that the more an agent states what it is *for*, the easier it is for a mitigation service to allow it — advertising purpose via an `X-Agent-Intent` header with values like crawl, pay, or assist. This matters because bot-mitigation decisions are policy decisions about purpose, and an unlabelled request forces the site to guess. Alongside it: respect the site's stated policy rather than routing around it.

**THE TRUST TIER TO ANTICIPATE.** OWASP's stated expectation is that authenticated agents will carry a stable agent ID, tag each session uniquely, and accumulate a **verifiable reputation that downstream systems can query**. The design consequence is concrete and easy to get wrong now: if your agent rotates identity per session or shares one identity across unrelated tenants, it cannot accumulate reputation and cannot be distinguished from an abuser using the same fleet. Choose an identity granularity you can defend later.

**RELATED WORK NAMED**, for anyone building this: LOKA's Universal Agent Identity Layer and the open-source Agent Network Protocol, both pointing at a PKI-backed model with capability attestations, and HUMAN Security's AI verification project, an open-source implementation of HTTP Message Signatures for agent request authentication that also uses ANS.

**EXACT STRINGS — DO NOT COPY THEM FROM HERE.** The source is a PDF, and its text extraction wraps mid-token: the key path appears in the extract as `/.well-known/agentpublic-key.json`, which reads like `agent-public-key.json` with a line-break hyphen lost. That reconstruction is UNCORROBORATED and is not the path anyone deploys: a search for the literal string across the agent-identity ecosystem returns no document that uses it, and the directory path actually verified in production is `/.well-known/http-message-signature-directory` ([[33da37fe]]). Implement against that one, not against anything derived from this extract. Header names (`X-AI-Agent`, `X-Agent-Intent`) are reproduced as they appear but are subject to the same extraction risk. Verify every literal against RFC 9421 and the current ANS spec before implementing — none of these strings is load-bearing for the argument, and all of them are load-bearing for the code.

**CAVEAT ON MATURITY — NOW SETTLED PER LAYER, WHICH IS NOT THE SAME AS SETTLED PER MECHANISM.** This is guidance published July 2025, and its single "early-stage" label on cryptographic request signing collapses two layers that have very different readiness. Cloudflare's own account, bylined the same month, verifies RFC 9421 HTTP Message Signatures with Ed25519 at its edge against a key set at a well-known path, on its Free and Pro plans, with Business and Enterprise to follow — so the signing primitive is standardised and deployed, and an agent can be verified by a major bot-mitigation provider today. What remains draft is the agent-identity convention layered on the RFC: Web Bot Auth is an IETF Internet-Draft whose directory format and headers are explicitly still moving. Read the three-mechanism enumeration above as sound and the DIRECTION as sound; read "early-stage" as true of the interop conventions and false of the primitive. [[33da37fe]] carries the deployed mechanics, the exact headers and paths, and the fail-open behaviour on a bad signature.

The maturity labels on the other two mechanisms remain a July 2025 assessment with no primary check behind them.
