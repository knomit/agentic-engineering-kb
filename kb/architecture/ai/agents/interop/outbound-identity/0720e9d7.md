# A browsing agent needs an outbound identity or it gets classified as a bot — and the three available mechanisms differ sharply in maturity

Almost all agent-identity discussion is inbound — how your system authenticates an agent that arrives. OWASP's securing-agentic-applications guide covers the direction most builders hit first in production and plan for last: **how your agent identifies itself to the arbitrary third-party sites it browses**, so that bot-mitigation platforms let it work instead of blocking it. This is a functional requirement, not a compliance one; an agent that cannot establish itself as good automation simply stops being able to reach the web.

**THE THREE MECHANISMS, with the guide's own maturity assessment — which is the useful part, because they are not interchangeable today.**

*Stable network and user-agent metadata.* Serve from a documented IP range with a verbose User-Agent, optionally adding `X-AI-Agent` and an agent-ID/signature header, so mitigation systems can correlate requests with a cryptographic identity. OWASP rates this good but not enough — the proven approach for well-behaved bots for a decade, but not bulletproof, because IPs are shared and user-agent strings are spoofable. It is a correlation aid, not proof.

*Cryptographic request signing.* Sign every HTTP request using RFC 9421 HTTP Message Signatures and expose the verification key at a well-known path (`/.well-known/agent-public-key.json`). This is the one that actually prevents spoofing and machine-in-the-middle, since keys cannot be forged without compromise — but OWASP marks it early-stage. The guide notes HTTP Message Signatures combined with mTLS is already used for production-grade bot verification, so this is the mechanism to build toward now.

*Agent Name Service (ANS).* Publish an ANSName encoding protocol, capability, provider and version, and register the name plus public key in an open agent registry, giving PKI-backed lookup that prevents collisions and impersonation. Spec v1.0 is published with pilot registries and tooling emerging — so this is the intended endpoint of the design, not something to depend on yet.

**DECLARE INTENT, NOT JUST IDENTITY.** The guide's second rule is that the more an agent states what it is *for*, the easier it is for a mitigation service to allow it — advertising purpose via an `X-Agent-Intent` header with values like crawl, pay, or assist. This matters because bot-mitigation decisions are policy decisions about purpose, and an unlabelled request forces the site to guess. Alongside it: respect the site's stated policy rather than routing around it.

**THE TRUST TIER TO ANTICIPATE.** OWASP's stated expectation is that authenticated agents will carry a stable agent ID, tag each session uniquely, and accumulate a **verifiable reputation that downstream systems can query**. The design consequence is concrete and easy to get wrong now: if your agent rotates identity per session or shares one identity across unrelated tenants, it cannot accumulate reputation and cannot be distinguished from an abuser using the same fleet. Choose an identity granularity you can defend later.

**RELATED WORK NAMED**, for anyone building this: LOKA's Universal Agent Identity Layer and the open-source Agent Network Protocol, both pointing at a PKI-backed model with capability attestations, and HUMAN Security's AI verification project, an open-source implementation of HTTP Message Signatures for agent request authentication that also uses ANS.

**CAVEAT ON MATURITY.** This is guidance published July 2025 describing an emerging area, and the guide itself hedges two of the three mechanisms. Treat the direction as sound and any specific header or well-known path as liable to change — verify against RFC 9421 and the current ANS spec before implementing.
