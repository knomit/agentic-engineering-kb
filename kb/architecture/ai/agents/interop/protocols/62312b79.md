# MCP and A2A are different layers, and A2A's opacity is a deliberate bet against trace-sharing

They are not competitors. MCP standardises agent-to-tool communication — how one agent reaches APIs, data sources, and resources. A2A standardises agent-to-agent communication — how independently built, separately owned agents discover each other (via an Agent Card), delegate a Task, exchange Messages, and return Artifacts. A system can and often should speak both: A2A outward to peer agents, MCP downward to its own tools.

The design decision worth noticing is A2A's opacity principle: agents interact WITHOUT sharing internal memory, tools, or proprietary logic. That is a deliberate trade, motivated by cross-organisational trust and IP protection — you can delegate to a vendor's agent without either side exposing its internals.

That same opacity is precisely what Cognition argues destroys multi-agent reliability, since their first principle is to share full agent traces rather than individual messages. Both can hold, and the boundary is organisational: inside one trust domain, where you control every agent, withholding traces is a self-inflicted wound and A2A's isolation buys you nothing. Across trust domains, trace-sharing is not available at any price, so you accept the coordination risk and must compensate for it — narrow, verifiable task contracts and validation of returned Artifacts rather than assuming the peer inferred your intent.

VERIFIED 2026-07-26 (staleness pass): A2A has reached v1.0 and is governed by a Technical Steering Committee spanning AWS, Cisco, Google, IBM Research, Microsoft, Salesforce, SAP and ServiceNow, under Apache 2.0. The opacity principle is unchanged and still stated in the spec's own words — agents interact "without needing to share internal memory, tools, or proprietary logic." So this is no longer an early-stage proposal, and the version to build against is 1.0; check the v1.0 changelog before relying on any pre-1.0 field shapes.
