# AHP is a coordination layer over ACP's communication layer — one host, N clients, many backends — and an AHP host can bridge to any ACP agent, but VS Code's own host does not ship that bridge

Two protocols with similar names sit at different layers.

Agent Client Protocol (ACP, originated by Zed) defines how ONE client talks to ONE coding agent: initialization, authentication, prompts, streaming updates, tool calls and permission requests, as JSON-RPC over stdio. Agents that speak it include Gemini CLI (`--experimental-acp` / `--acp`), `codex-acp`, `copilot --acp`, OpenCode, Qwen Code, Kiro, OpenClaw and Hermes; the VS Code ACP Client extension lists them. Antigravity CLI (which replaced Gemini CLI on 2026-06-18) had NO ACP mode as of 2026-09-25; an open feature request asks for one.

Agent Host Protocol (AHP, Microsoft) defines how N clients share one live session: the host manages authoritative state, sequences every mutation, and synchronizes the result to every connected client. The AHP guide's own words: 'AHP is a coordination layer. ACP is a communication layer. They compose naturally.' The composition is a bridge: the host speaks AHP upstream to clients and ACP downstream to the agent, mapping ACP events onto AHP actions.

WHERE THAT BRIDGE EXISTS. The project's implementations guide and its repository README between them name five hosts, and the ACP-bridging ones are third-party rather than Microsoft's:

- VS Code's Agent Host, described on the implementations page as "The reference AHP server implementation". The page says nothing about ACP bridging or about registering a harness with it, and VS Code's own harness documentation lists only first-party adapters and documents no mechanism or extension API for registering a third-party harness.
- `AHP-ACP Gateway`: "A universal AHP WebSocket host that runs configured ACP agents, with persistent sessions", "replay and reconnect, permissions, and cancellation." This is the general-purpose bridge.
- `hydra-ahp`: "An open-source AHP host for Hydra, a multi-client ACP session daemon, exposing Hydra sessions to AHP clients".
- `ahpd`: now described as a plugin host, where "the agent, the ports and the server tools" "are all installed rather than built in, and `@ahpd/sdk` is the library to build a host of your own." The page no longer names an ACP backend for it, and the string `@ahpd/agent-acp` appears on none of the project's pages, so whether that specific backend still exists is not established from the documentation.
- `pi-ahp`: a host for one specific agent rather than a bridge — "exposing pi sessions to AHP clients over WebSocket."

The compose guide states the architectural intent on Microsoft's side too: the reference implementation targets "a standalone server (or Electron utility process)" that "manages sessions, synchronizes state, and delegates agent work to ACP-compatible backends." That is a statement of what the reference implementation TARGETS, and it does not say which bridge ships with VS Code.

Consequence: the portable, vendor-neutral part of this stack is the PROTOCOL, not Microsoft's host. Non-Microsoft harnesses (Gemini, OpenCode, Hermes, OpenClaw) reach an AHP control plane only through an ACP-capable host — the AHP-ACP Gateway and hydra-ahp are the ones the project names for that now; VS Code's Agents window can attach to such a host via `chat.remoteAgentHosts`. The direction of travel is that the bridge inventory grows while the first-party adapter list does not, so a third-party harness is a deployment decision about which host to run, not a question of waiting for Microsoft to add an adapter.

WHAT THIS DOES NOT MEAN: that AHP replaces MCP. MCP is the tool/resource layer between an agent and its servers; AHP has an MCP channel only to let a client proxy traffic to servers the host already runs (see the MCP-injection gotcha). The MCP-vs-A2A layering fact is the sibling distinction on the agent-to-agent side.
