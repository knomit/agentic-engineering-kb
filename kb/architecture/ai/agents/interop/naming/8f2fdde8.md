# ANS resolves a name to a PKI-verified endpoint and stops there — its own spec disclaims cross-protocol translation, and its identifier carries a capability and version alongside the agent

Agent Name Service v1.0 (OWASP GenAI Security Project, Agentic Security Initiative, 14 May 2025) is the DNS-inspired discovery layer that several facts in this pack cite without anyone having read it. What it actually specifies, and — more usefully — where it stops.

**THE IDENTIFIER.** `ANSName = Protocol "://" AgentID "." agentCapability "." Provider ".v" Version "." Extension`, with `Protocol ∈ {a2a, mcp, acp, ...}`. The spec's example: `"a2a://textProcessor.DocumentTranslation.AcmeCorp.v2.1.hipaa"`. Constraints: Version "MUST adhere to Semantic Versioning standards"; AgentID, agentCapability and Provider "SHOULD be registered with a governance authority (similar to ICANN)"; Extension "SHOULD be used for deployment-specific or provider-defined metadata, not for core identity".

The stated reason for encoding capability into the name at all is that ANS wants "to move beyond simple naming resolution to enable precise agentCapability discovery, which is not achievable with traditional systems like DNS."

**AN AMBIGUITY WORTH KNOWING BEFORE YOU IMPLEMENT.** The resolution entry point is `Resolve(ANSName, RequestedVersionRange)` — version arrives *twice*, once inside the name and once as a separate range argument, and step 2 of the algorithm matches the registry on "Protocol, AgentID, agentCapability, Provider" with Version conspicuously absent from the match key, deferring instead to `VersionNegotiation(Matches, RequestedVersionRange)` which may return `ERROR("Incompatible Version")`. So the version embedded in a stored ANSName is not what selects the match. The spec does not reconcile the two; treat the range argument as authoritative and the in-name version as documentation until it does. (That reading is this pack's; the document states both without comment.)

**WHAT A RESOLUTION ACTUALLY RETURNS, AND WHO SIGNED IT.** `EndpointRecord: {data, signature, Cert}`. Verification is two steps: `VerifySignature(EndpointRecord.data, EndpointRecord.signature, AgentRegistry.PublicKey)` — note the key is **the registry's**, not the agent's — followed by `VerifyCertChain(EndpointRecord.cert, TrustedCA)` walking to a trusted CA with CRL/OCSP revocation checks at each hop. The record signature attests that *the registry served this*, not that the agent authored it. Consistent with that, the guide's countermeasure against its own "Registry Poisoning" threat is procedural before it is cryptographic — "Strict RA validation during registration/renewal" — with signed responses protecting the record in transit rather than its contents at origin. A compromised Registration Authority yields correctly signed lies.

**THE BOUNDARY CONDITION, and it is the reason to read this document at all.** Section 5.5, in full force: "The registry primarily enables discovery and identity verification across protocols. An A2A agent can discover an agent advertising MCP tools, verify its identity via PKI, and potentially interact if it also understands MCP or uses a gateway. **ANS does not automatically translate A2A tasks into MCP requests.** It provides the foundational trust and location information, but deeper semantic interoperability often requires additional mechanisms or multi-protocol support within the agents themselves." A cross-protocol *registry* is routinely mistaken for cross-protocol *interoperability*; the spec disclaims the second in its own words. Its protocol adapters (`getProtocol`, `parseMetadata`, `createDiscoveryResponse`, `validateRegistration`) map registration and discovery metadata only — nothing in that interface touches a task or a tool call at runtime.

**THE OPEN PROBLEMS THE DOCUMENT NAMES ITSELF**, which are governance rather than engineering: naming collisions and squatting, requiring "a governance model, potentially similar to ICANN for DNS… to manage top-level agentCapabilities and provider identifiers"; scalability to "potentially billions of agents" via DHTs, caching layers and geographically distributed resolution points; and policies for allocation, dispute resolution and managing the CAs and RAs. None is solved in v1.0. Its MAESTRO-based threat analysis covers agent impersonation, registry poisoning, MitM and DoS — and is candid where the answer is generic: MitM mitigation notes "secure transport (e.g., mTLS) is best practice but PKI signing is the core mechanism discussed", and DoS falls back to "standard operational defenses (rate limiting, DDoS protection services)".
