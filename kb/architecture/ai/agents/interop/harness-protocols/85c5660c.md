# A harness integration protocol needs three nested units and a reverse channel — Codex's App Server exposes item, turn and thread, and a server-initiated approval request pauses the turn until the client answers

The App Server protocol is built on three nested units. An **item** is the atomic unit, with a lifecycle of `item/started`, optional `item/*/delta` events, then `item/completed`. A **turn** is one unit of agent work started by user input and containing a sequence of items. A **thread** is a durable container holding multiple turns, supporting create, resume, fork and archive with persisted event history.

Two structural rules. A single `initialize` request must precede any other method; it negotiates protocol version, feature flags and defaults. And the protocol is bidirectional: the server issues its own requests, with tool approval arriving as `item/commandExecution/requestApproval`, and the turn stays paused until the client returns allow or deny.

That reverse channel is load-bearing rather than a convenience. A request/response protocol in which only the client initiates cannot express "the agent is mid-turn and needs a decision before continuing" — the alternatives are to pre-authorise everything or to end the turn and start another, and both change the agent's behaviour rather than just its wire format. An integrator evaluating a harness protocol should check for this property first.

Process shape and transport, for anyone implementing against it: one long-lived App Server process with a stdio reader, a message processor, a thread manager and the core threads; one core session per thread; the message processor maps low-level core events into a small set of stable UI-ready notifications. Transport is JSON-RPC over stdio framed as JSONL — a "JSON-RPC lite" variant that omits the `"jsonrpc": "2.0"` header — and client bindings are generated with `codex app-server generate-ts` or `codex app-server generate-json-schema`.
