# Gate a reviewer agent's findings on a vote by separate verifiers, not on the finder's own confidence — and measure the reviewer by how authors dispose of its comments plus its harmful-suggestion rate on known-clean PRs

The topology the Claude Code team describes for its PR reviewer separates finding from publishing. Several agents hunt for bugs in parallel against the diff, the whole repo and the PR's stated intent; "Then a separate group votes on each finding, and it only gets posted if enough of them agree it's real." The finder does not decide what the author sees. Category filters then drop style, diagnostic and cleanup-only findings, and those filters were A/B tested on internal PRs (no result is published). What survives is posted as inline comments, ordered by severity and tagged **Important**, **Nit** or **Pre-existing** — the last so that inherited bugs are not attributed to the current author — and every posted finding must be fixed or resolved with a stated reason.

Two measurements make the loop steerable, and they are different instruments:
- **Disposition classes.** Each comment is classified by how the author responded: fixed, wrong, intentional, or didn't matter. "Wrong" and "didn't matter" are different defects — the first is a false positive, the second a correctly-identified irrelevance — and a single false-positive rate conflates them.
- **A negative control.** The reviewer is run on PRs known to be clean, and what is counted is how often it suggests a HARMFUL change. That catches the failure a false-positive rate does not: a reviewer that invents a plausible problem and proposes a fix that breaks working code.

Owners steer scope declaratively rather than by prompt: repo admins pick Quick, Standard or Deep (Deep where a missed bug is costly), `CLAUDE.md` carries project conventions, and `REVIEW.md` carries owner-written guidance on what matters, what failure looks like, nit caps, paths to skip, and a requirement that findings cite file and line evidence.

What this does NOT mean. The vote is a precision filter, not a correctness proof: enough verifiers agreeing that a finding is real is a threshold on agreement, and the published account gives no precision or recall figures, no number of agents and no vote threshold, so do not read "verified" as "true". Nor does the filtering replace an independent security pass — security review runs as its own step and blocks merge separately. And the stated priority order matters when the two measurements conflict: catch real bugs first, reduce review rounds second.
