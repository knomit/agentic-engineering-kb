# Dynamic workflows have the model write the orchestration program, which moves the tuning problem from topology design to default-parallelism calibration

In Anthropic's dynamic workflows a lead agent plans the task and then Claude WRITES the orchestration program: the program launches sub-agents, collects their results and manages the flow of information between phases, and Claude decides how to split the work. The reported contrast with the earlier Managed Agents shape is the whole point of the feature: there, the developer configured a coordinator and a fixed roster of sub-agents. Work is divided into discrete, verifiable units, and the developer does not wire the connections between phases. Specialist sub-agents can still optionally be passed in through the agent config, so this is a change of default, not a removal of the capability.

THE OPERATIONAL CONSEQUENCE, which is what makes this worth knowing: handing the split to the model does not remove the sizing decision, it relocates it. The reported failure runs in both directions. A simple task can trigger a large number of sub-agents, because the default agent count can be too high for it; an ambitious task under-parallelises unless it is explicitly prompted toward more parallelism. The levers named for the first direction are evals and lowering the defaults. So the knob you own is no longer the topology, it is the default parallelism plus the eval that tells you when the default is wrong for a class of task.

WHAT THIS DOES NOT MEAN: a generated orchestration program is not a self-sizing system. Nothing in the described mechanism makes the agent count fit the task, and the two named failure directions are the evidence that it does not.

The observability affordance reported alongside it: flows run in Claude Console, where a run can be graphed and the payload the lead agent passed to each sub-agent inspected at every transition. The reported limit on self-improvement is that the flow does not revise its own approach between runs; improvement comes from an external loop (evals, hill-climbing, or a research-preview memory-reorganisation feature).

SOURCE MODALITY, and it bounds the confidence here: this is a third-party write-up of a conference talk given by two Anthropic Members of Technical Staff at AI Engineer New York 2026. The write-up reports no benchmarks, no performance measurements and no cost or throughput figures, so every claim above is a description of intended design plus the presenters' practitioner experience, not a measured result. Anthropic's own documentation of the feature has not been read into this pack and is the primary account to prefer when it is.

Anthropic's own documentation states the pattern as a question about WHO HOLDS THE PLAN, and that is the axis that separates it from the neighbouring primitives. With subagents, skills and agent teams, the model decides turn by turn what to spawn next and "every result goes into a context window"; with a workflow, "the script holds the loop, the branching, and the intermediate results itself, so Claude's context holds only the final answer". Intermediate results live in script variables rather than in a context window, which is what lets one run reach a scale the documentation puts at "dozens to hundreds of agents" against "a few delegated tasks per turn" for subagents.

The second thing moving the plan into code buys, per the same source, is a repeatable QUALITY pattern rather than only more agents: the script can have independent agents adversarially review each other's findings before any are reported, or draft a plan from several angles and weigh them against each other. The orchestration itself is the artifact that is repeatable — a run's script can be saved as a command and rerun — where with subagents only the worker definition is.

Two structural constraints come with putting the plan in a script. The script body is plain JavaScript with top-level `await` and three primitives (`agent()` for one subagent, `pipeline()` for one per item, `parallel()` for a set at once), but it has "no direct filesystem or shell access from the workflow itself" — agents read, write and run commands while the script only coordinates them — and no module loading at all: a script containing `import()` fails before the run starts. Work needing a library has to sit inside an agent's task, not in the orchestration.
