# A 16-agent write fleet coordinated through git-enforced claim files in the repo, not a message bus — Opus 4.6, just under $20,000 for a 100,000-line compiler

Sixteen Opus 4.6 agents wrote one Rust-based C compiler concurrently with no orchestrator process and no inter-agent messaging. Mutual exclusion was a file in the repository: an agent claimed a unit of work by "writing a text file to current_tasks/" — the report's example is "current_tasks/parse_if_statement.txt". Each agent ran in its own Docker container with the bare repo mounted at /upstream, cloned to /workspace, and pushed back when done.

**The lock is genuinely enforced, and by git rather than by convention**: "If two agents try to claim the same task, git's synchronization forces the second agent to pick a different one." That is the load-bearing detail — a claim file works as a lock only because the push that creates it is an atomic ref update that one racer loses. Reproducing this pattern on a store without that property gives you a claim file that two agents can both believe they hold. What WAS accepted rather than prevented is downstream code merging, a separate matter: "Merge conflicts are frequent, but Claude is smart enough to figure that out."

Why the shape matters: the coordination state lives in the same artifact the work lives in, so it survives every session boundary, needs no running coordinator, and is inspectable by a human with `ls`. An orchestrator process would have had to stay up for two weeks and would have become the single point of failure for sixteen workers.

Some agents were given standing roles rather than units — "coalescing any duplicate code", "improving the performance of the compiler itself", "outputting efficient compiled code", and documentation. These are the janitorial functions a fleet with no shared context stops doing for itself.

WHERE THE FAN-OUT BROKE, and the fix, which is the most transferable part. Parallelism was trivial while there were many distinct failing tests — each agent picks a different one. It collapsed when the fleet turned to compiling the Linux kernel, because that is one giant task rather than hundreds of independent ones: "Every agent would hit the same bug, fix that bug, and then overwrite each other's changes. Having 16 agents running didn't help because each was stuck solving the same task." Sixteen workers on a monolithic failure are one worker plus fifteen wasted bills and a merge problem.

The fix was to MANUFACTURE independence with a known-good oracle: GCC compiled a random majority of the kernel's files and the fleet's own compiler only the remainder, so a working kernel exonerated that subset and a broken one could be narrowed by recompiling more files with GCC. Each agent then had its own failing file to work. Delta debugging was still needed afterwards to find pairs of files that failed together but worked independently. Generalised: before fanning out writes, check that failures localise to separate units; if they do not, the first engineering task is to build the isolation mechanism, not to add agents.

THE COST ENVELOPE, which is the part most worth carrying into a build-or-not decision: "Nearly 2,000 Claude Code sessions" over "two weeks", "2 billion input tokens" and "140 million output tokens", "a total cost just under $20,000", producing a "100,000-line compiler" that reaches "99% pass rate on most compiler test suites" and compiles Linux 6.9 on x86, ARM and RISC-V. Note the input-to-output ratio of roughly 14:1 — a write fleet's bill is dominated by re-reading context, not by generating code, so cache economics decide whether this is affordable.

SCOPE — THIS IS A MEASUREMENT OF ONE MODEL VERSION, NOT OF THE PATTERN. The report is explicit that the same project had been run across the Claude 4 series as a benchmark and that the outcome moved with the model: earlier Opus 4 models were "barely capable of producing a functional compiler"; Opus 4.5 was "the first to cross a threshold" to a functional compiler passing large test suites but "still incapable of compiling any real large projects"; Opus 4.6 produced the result described here, and the author states it "has nearly reached the limits of Opus's abilities". The cost envelope and the 99% figure therefore belong to Opus 4.6 and do not describe what sixteen agents of any other version would achieve in either direction.

WHAT THE RESULT IS NOT. The compiler is not a drop-in replacement: it has no assembler or linker of its own, its generated code is less efficient than GCC with optimisations disabled, and on 16-bit x86 it can emit correct instructions via the 66/67 opcode prefixes but produces over 60kb against Linux's 32k real-mode limit, so it calls out to GCC for that phase (x86 only; ARM and RISC-V are self-hosted). The author also reports that new features and bugfixes "frequently broke existing functionality", which was addressed by adding a continuous integration pipeline and stricter enforcement so new commits could not break existing code. A 99% suite pass rate on a 100,000-line artifact coexisted with continuous regression; a claim file gives exclusivity on a unit of work and no protection against one agent's change breaking another's finished unit. Budget for a regression-catching role, not only for feature units. The conditions under which fanning out writes pays at all are at [[kb/decisions/ai/agents/multi-agent/parallel-writes/71be00f9]].
