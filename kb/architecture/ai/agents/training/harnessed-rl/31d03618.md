# Train through the harness you deploy by proxying its model calls — and inherit four mechanical problems, of which advantage and loss normalisation must move to the ROLLOUT level because one rollout yields several samples

The problem this pattern exists to solve. "most agent RL systems require developers to reimplement the agent inside the training framework" — frameworks of that shape assume the trainer owns the ReAct-style loop, while real harnesses (mini-SWE-agent, OpenHands, OpenCode, Claude Code, Codex) manage their own context, tools and execution. The consequence the post names: "it means the agent being trained is not quite the agent that gets deployed."

The mechanism. Put an OpenAI-compatible proxy in front of the harness's model calls. Microsoft Research's Agent Lightning v1.0 splits this into an API Gateway that records prompts, responses and log probabilities; a Rollout Controller that runs agents as local processes or Kubernetes jobs; and a trainer built on verl with a sample adapter. The agent's own code is unchanged, which is the whole point — the artifact being trained is the deployed harness.

WHAT THE PROXY COSTS YOU, AND THIS IS THE PART A SUMMARY DROPS. "This brings four key challenges:" — "Retokenization and sample merging", "Advantage calculation", "Loss normalization", and "Training backend scheduling". They arise because the trainer no longer controls the loop: the harness decides how many model calls a task takes, so one rollout arrives as several samples of varying length, and the trainer has to re-tokenize and merge text it did not generate the boundaries of, then decide what unit the advantage and the loss are computed over, then fit variable workloads onto fixed GPU and parallelism settings.

The reported answer to the middle two: "Compared with sample-level handling, rollout-level advantage combined with rollout-level normalization" "achieves a higher validation reward and keeps policy entropy more stable during training". The unit of credit is the rollout — the whole task attempt — not the individual model call, because the task's reward is a property of the attempt. Getting this wrong is not a bookkeeping slip that shows up as an error; it shows up as a worse policy and as rising entropy.

Measured result: "RL training alone raised Qwen3.5-9B from 41.8% to 56.4% on SWE-bench Verified, a gain of 14.6 percentage points." "The training set holds about 6,000 samples and needs no large-scale compute." The control plane is about 3,500 lines of code.

Scheduling, reported separately: rollout and model updates share the same GPUs, and the gateway pauses new requests during an update so the harness does not observe it. This "achieved about a 2x end-to-end speedup over synchronous RL" "while using fewer GPUs than conventional asynchronous RL". The design note worth keeping: the pause is implemented in the proxy precisely so that no harness-side change is needed to tolerate it.

WHAT THIS DOES NOT MEAN. The SWE-bench gain is one model on one benchmark, reported by the framework's own authors, and it is not a comparison against in-framework RL on the same task — the post does not measure harnessed RL beating reimplemented RL, it argues that reimplemented RL trains the wrong artifact. This fact is the mechanism and the cost of the last rung of [[fa0c7945]], not independent confirmation that the rung pays.
